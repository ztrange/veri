This list is not maintained. A version is an annotated git tag, its name is the tag’s own message, and the sections under it are computed from the commits in its range — so it cannot claim a capability that did not ship, or miss one that did. Only feat: and fix: commits count: documentation, tests and refactors change this page without changing what veri can do. Choosing a version here therefore answers which capabilities changed since you last read the page, not which bytes changed: a line rewritten in the meantime by a refactor: or a test: commit stays dim, exactly like a line nobody has touched at all.

Why this exists

Ask an agent for a feature and you get the code, then tests written to agree with the code it just wrote — green on the first run, because they were derived from the implementation rather than from what the implementation was supposed to do. veri exists to take that order away from the model. Four claims, each one linked to the part of this page that shows it.

Strict TDD, not vibe coding. Work happens in steps, and every step runs Red → Green → Refactor in that order: one short-lived leaf per phase, each exiting when its phase is done. No phase can be skipped or reordered, because what the next step is comes from the committed ledger rather than from the model that would rather move on. Stage 2 is that loop, three scripts deep.

veri is built with itself. Every capability on this page was scoped, tested and landed by a veri run against this repository, 1159 issues so far — the same order, under the same blind verification, as everything described below. The figure is counted out of git when this page is built, not typed into it, so it cannot quietly go stale.

Verification is blind by construction. Whether a test is a real test is decided by a second agent, and it is handed only the phase, the spec and the path to the test. build-verify-prompt.sh has no parameter for the developer’s rationale — there is no argument to put it in, so there is nothing for it to leak through.

You can watch it, and a hang is an outcome. Every phase is narrated to the issue thread as it happens, and progress lives in a committed ledger, so a run that dies is resumed by reading the repository rather than reconstructed from a transcript. A leaf that goes quiet is not waited on indefinitely: supervise.sh watches a heartbeat and kills what stops writing, and classify-bail.sh turns the result into a labelled failure — the methodology said no, or the plumbing broke.

What veri actually is

veri solves GitHub issues under strict TDD discipline. You point it at one issue; it plans the work, then drives each step through Red → Green → Refactor, and hands you a draft pull request. The name comes from the part that makes it unusual: every test is checked by a second, independent agent that never sees the author's reasoning and must run the test itself to form an opinion.

It is not an application. It is a skill — a directory that Claude Code loads — and it is made of exactly two kinds of thing.

The division of labour

Everything in veri is either judgement or mechanism, and the two are kept in physically separate places:

LayerWhere it livesWhat it doesTested?
The conductorSKILL.md A procedure written in English that Claude follows. Decides what the plan is, what a step means, when to move on. All judgement.No — it is prose
The scriptsscripts/*.sh Small deterministic tools the conductor calls. Kill a hung process, parse a verdict, tick a checkbox. No judgement at all.Yes — make test

That line is the entire design philosophy: the model decides, the scripts enforce. Anything that must be exact and repeatable is pulled out of the fuzzy part and into a shell script with a unit test behind it. So the guarantees you can actually rely on all live in the 343 lines this page reproduces in full.

One more role, because it appears constantly:

  • A leaf is one short-lived claude -p subprocess that performs exactly one step — write the failing test, write the implementation, apply one refactor — then exits. Leaves never persist and never share memory.

The exit-code contract

Learn this before any single script, because it is the API between all of them. Unix programs return a small integer on exit; zero conventionally means success. veri assigns four specific meanings and holds to them everywhere:

CodeMeansIn practice
0 okSuccess, or PASS The leaf finished cleanly; the verifier approved; a checkbox was ticked.
1 noA clean negative The leaf ran and failed; the verifier said REJECT. A real answer — the system worked and the answer was no.
2 brokenNo answer could be obtained The leaf hung and was killed; the verdict was unparseable; the arguments were wrong. Something is broken, so there is no answer.
3 noneNothing to do No unchecked step remains; no checkbox matched. Not an error — a specific, expected, empty result.
Why this matters more than it looks

The gap between 1 and 2 is the most important distinction in veri: the difference between the methodology spoke (a blind verifier legitimately refused the work — a process failure) and the plumbing broke (no verdict at all — a system failure). veri reports, retries and blames those differently. Keeping them apart at the bottom of the stack is why that is possible at the top.

Where the TDD loop lives

Which phase it is changes only the prompt and the rubric.

Which means the five stages are not one step. They are one phase. A step is that pipeline run three times over, and the loop you are looking for is the column-to-column arrow:

Four things that only become visible once the loop is drawn:

  • Three phases, three blind verdicts, one step. Stage 1 runs once per step; stages 2 and 3 run once per phase — more, when a phase is revised. The verifier is a fresh agent every time, so nothing it approved earlier carries over. A step that was already satisfied takes one verdict, not three: the pin is an exit from Red, not a fourth phase.
  • The ledger ticks at Green, not at the end. The moment the implementation is blind-approved, the tick and the code go into one commit — so git history and the checklist cannot disagree even if the run dies during Refactor.
  • Refactor is the asymmetric one. It loops transforms inside the phase, committing each, and takes a single verdict on the settled result. Verifying each transform separately would multiply the cost of the expensive half without changing what the suite already proves — the suite is the objective gate throughout, and the verdict only asks whether the result is up to standard.
  • None of this is in a script. No file under scripts/ knows there are three phases, what order they come in, or that Refactor loops. Phase is a string the conductor passes down — verify.sh red…, green…, refactor…, pin… — which is exactly the split the division of labour promised: the model decides, the scripts enforce.

How the data moves

The last two sections say which scripts exist and in what order they repeat. This says what actually travels between them — because in veri the interesting content is not the calls, it is what crosses each boundary: a file on disk, a line of stdout, or a single exit code that chooses the next branch.

Three things in that picture are worth naming, because they are the design and not just the plumbing.

  • The supervisor never blocks on the leaf. It watches a log file’s modification time (activity, so it is alive) and an rc file’s existence (so it finished on its own). Both are ordinary files, and the leaf cooperates with neither.
  • No input of the verifier’s prompt can carry the developer’s rationale. build-verify-prompt.sh takes the phase, the spec, the test path and test id, plus --step and --fast-cmd, and each is the conductor’s words, never the leaf’s — which is exactly why the developer’s rationale cannot reach the agent judging it.
  • The verdict is parsed from stdout, not read from an exit status. claude -p exits 0 whether it approves or refuses, so the judgement lives in the text and only becomes an integer at parse-verdict.sh.

Stage 0 · prepare the target

Stage 2 · run a leaf

Launching something you do not trust

The conductor needs a developer leaf to write a failing test. That leaf is an LLM subprocess that might take five minutes, might finish in ten seconds, and might hang forever. Four scripts turn that into a bounded, observable operation.

Three of them nest inside one another, outermost first — and the outermost is the only one the conductor is ever allowed to call:

supervise.sh — the watchdogsince v0.3 · changed v0.683

The heart of veri, and the most systems-heavy script in it. The problem: you are about to start a process that will run for minutes doing real work, and you must distinguish three outcomes a plain cmd && … cannot tell apart — it finished, it failed, or it is never going to finish.

It does that with two independent clocks:

  • Heartbeat — has the leaf produced any output recently? A sliding silence window. Catches a genuine hang.
  • Hard timeout — has it run too long regardless of activity? An absolute wall-clock cap. Catches a leaf that chatters but never converges.

Everything else is machinery to run those two clocks against a live process.

#     working" from "hung". A leaf silent past the window is killed.
#   * hard timeout — a leaf that exceeds the time cap is killed even if still noisy.

# clock_gettime(CLOCK_UPTIME_RAW), else the monotonic clock (CLOCK_MONOTONIC): on macOS that is mach_absolute_time(), which does not advance while the

mtime_of is the heartbeat sensor: seconds since the log was last written to. There is no portable spelling of "ask the filesystem for a file's mtime" — GNU/coreutils is stat -c %Y, BSD/macOS is stat -f %m — so both have to be tried. The nine-line comment above the function is here because the previous version of this idea — the two attempts chained with || inside one $( … ), falling back to a bare 0 — shipped for years and then broke the instant it met a real Linux runner.

What one $( ) with || inside it can hide

On GNU coreutils, -f is not a format flag at all — it means --file-system. stat -f %m FILE reads %m as a second filename, finds only FILE, and prints a filesystem block for it — a line starting File: "…" and more — to stdout, then exits non-zero because %m itself does not exist. On BSD/macOS, where -f really is the format flag, that same command just prints the mtime and the chain never reaches its second link — which is why four years of macOS-only runs never saw this.

Chained inside one command substitution, the failed attempt's block and the fallback's digits land in the same string. The caller does $(( t - $(mtime_of "$log") )); bash's arithmetic expansion treats every bareword in that string as a variable to look up, and the first one it meets is File — unset, and fatal under this script's set -u. The supervisor dies before it can choose any of its own exit codes.

The fix tries each spelling separately, into a local variable: a plain assignment overwrites m where || inside a shared $( ) would have appended to it. GNU is tried first because BSD's stat rejects -c at option parsing and writes nothing, so the fallback direction that matters stays clean. Then a case glob, ''|*[!0-9]*), validates the result: empty, or containing any character that is not a digit, and it is rejected — whatever a third platform's stat decides to print, not just this one. An unreadable mtime now falls back to now() rather than 0: zero reads as five decades of silence and would kill the leaf on its very first poll, where "just touched" only degrades supervision to the hard timeout alone.

Found on this project's first ubuntu-latest CI run: make test had passed on macOS for years, then hung for ten minutes the first time it ran on Linux.

Stage 3 · verify the claim

The part veri is named after

A developer leaf has written a test and says it fails correctly. You cannot ask the author — it will defend its own work. So veri asks a different agent that has never seen the author's reasoning, and requires it to run the test itself.

The obvious way to build this is to instruct the verifier not to look at the developer's rationale. veri does something stronger: it makes the rationale structurally unable to arrive. Three scripts compose into one verb, and the guarantee lives in the shape of the first one's arguments.

The way to see that is to put the two prompt builders side by side. They are mirrors of one another — the same job done for the two agents — and where they differ is where the guarantee lives.

Stage 5 · or bail

Stopping in a way someone can act on

Not every run finishes. When veri gives up, the one thing that determines what a human does next is why — and that answer is too important to be improvised each time.

Three separate things can run out during a step, and veri counts each of them on its own knob. They are not three sizes of the same budget: one is about liveness — the leaf never answered at all; one is about the verdict — it answered, and the blind verifier rejected it; one is about cost — how many transforms one step's tidying is worth. shopt -u patsub_replacement 2>/dev/null || true

A shell option, disabled portably

shopt flips a named shell behaviour on or off — finer-grained switches than set -o covers. bash 5.2 added patsub_replacement and turned it ON by default: inside ${var//pattern/replacement}, an unescaped & in the replacement now expands to whatever the pattern just matched, the way sed’s & does. A value carrying a literal & is then rewritten silently — no error, no bad exit code.

shopt -u patsub_replacement turns that back off, restoring the older purely-literal meaning every ${v//a/b} below it relies on. macOS ships bash 3.2, which predates the option entirely: there shopt -u patsub_replacement fails because the name is unknown, so 2>/dev/null discards the complaint and the trailing || true makes the whole line a no-op — real work on 5.2+, harmless everywhere older.

Text & I/O

>   >>   <   <<<   2>&1   2>/dev/null

Redirection

  • > file — send stdout to the file, truncating it to empty first. That truncation happens the instant the line is parsed, before the command runs — the classic way to destroy a file you meant to read.
  • >> file — append instead.
  • < file — feed the file in as stdin.
  • <<< "$str" — a here-string: hand a variable to a command as its stdin, with no pipe and no temp file. Unlike a pipe, the command on the left of a here-string is not a separate process, so a loop reading one can set variables the rest of the script still sees afterwards.
  • 2>&1 — "make stream 2 go wherever stream 1 currently goes". The & means "this is a stream number, not a filename". Order matters: it copies the current destination of stdout, so it must come after any >.
  • 2>/dev/null — discard stderr, for a command expected to complain.

The convention veri holds to throughout: stdout is data, stderr is commentary. That is what lets a script's output be piped straight into the next one while its status messages still reach a human.

Every script.

while IFS= read -r line || [[ -n "$line" ]]

Reading lines without corrupting them

  • IFS= — empties the field separator for this command, so leading and trailing whitespace on the line is not trimmed.
  • read — reads one line into the variable, returning non-zero at end-of-file, which ends the loop.
  • -r — raw: do not treat backslashes as escapes. Without it, \n in the input gets mangled.
  • || [[ -n "$line" ]] — the subtle one. If the final line has no trailing newline, read stores it but still returns non-zero, so the loop would drop it. This clause says "keep going if we did read something".

The naive alternatives — for line in $(cat f) — split on spaces rather than newlines and glob-expand the results. They are simply broken.

for f in dir/*.ext; do [ -f "$f" ]

Globbing, and matching nothing

  • Unquoted, a pattern like dir/*.ext is expanded by the shell itself before the loop ever runs — one word per matching file.
  • When nothing matches, bash's default behaviour is not to drop the word: the pattern is left as its own literal text, spelled exactly as written, and handed to the loop as if it had matched.
  • [ -f "$f" ] turns that literal-text case into false the same way it would for any other non-existent file, so the loop body only ever runs on a real match.

The alternative is shopt -s nullglob, which makes a non-matching pattern expand to zero words instead of one literal one, so the loop runs zero times on its own and needs no [ -f ] guard. Either shape works; this script picks the one that needs no global shell-option change.

Signals — and the minus sign that matters

  • A negative PID means the process group. kill -TERM -1234 signals every process in group 1234, not just the leader. This is how you reach a leaf's own children — a test runner it spawned — which would otherwise be orphaned and keep running.
  • -0 sends no signal at all. It only checks whether the process still exists, so it is used to poll "is it gone yet?".
  • -TERM is the polite request: "please clean up and exit". A program can catch it. -KILL cannot be caught or ignored — the kernel destroys the process immediately, with no chance to clean up.

The universal pattern is TERM, wait briefly, then KILL only if still alive. Reaching for KILL first leaves temp files and half-written state behind.

Where the versions come from

The capability index is not a changelog anyone maintains. A version is an annotated git tag: the tag’s message is the capability’s name, its date is the tag’s own date, and the scripts listed under it are computed from the feat: and fix: commits in its range. Nothing is declared twice, so nothing can disagree.

Cutting one is not a separate chore — it happens when a pull request lands, because that is the only moment that knows both that a capability shipped and what it was. Three things about the layer are worth knowing:

  • It is optional. Built from a tree with no git — a tarball, a shallow checkout, the copied sandbox the doc tests build in — the page comes out without an index and without the per-script badges, rather than failing. The absence is the signal that git was unreadable, and make docs-check says so loudly when the tree does have tags.
  • No shas, no counts. Neither ever reaches the page. Both change on every commit, and docs-check demands a byte-identical rebuild — so embedding either would turn the check red after every commit until someone re-ran make docs. “Unreleased” is a yes-or-no for the same reason.
  • Version sort, not alphabetical. v0.9 sorts after v0.10 lexically, which would bury the newest release in the middle of the list. The build reads tags with git’s own -v:refname ordering, and the checker re-derives the expected order and compares.

Two invariants are worth re-reading on any change, since most of this page rests on them: that the four exit codes still mean the same four things everywhere, and that build-verify-prompt.sh still has no parameter through which a developer leaf's rationale could reach a verifier.
