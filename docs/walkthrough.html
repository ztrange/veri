Why this exists

Ask an agent for a feature and you get the code, then tests written to agree with the code it just wrote — green on the first run, because they were derived from the implementation rather than from what the implementation was supposed to do. veri exists to take that order away from the model. Four claims, each one linked to the part of this page that shows it.

Strict TDD, not vibe coding. Work happens in steps, and every step runs Red → Green → Refactor in that order: one short-lived leaf per phase, each exiting when its phase is done. No phase can be skipped or reordered, because what the next step is comes from the committed ledger rather than from the model that would rather move on. Stage 2 is that loop, three scripts deep.

veri is built with itself. Every capability on this page was scoped, tested and landed by a veri run against this repository, 32 issues so far — the same order, under the same blind verification, as everything described below. The figure is counted out of git when this page is built, not typed into it, so it cannot quietly go stale.

Verification is blind by construction. Whether a test is a real test is decided by a second agent, and it is handed only the phase, the spec and the path to the test. build-verify-prompt.sh has no parameter for the developer’s rationale — there is no argument to put it in, so there is nothing for it to leak through.

You can watch it, and a hang is an outcome. Every phase is narrated to the issue thread as it happens, and progress lives in a committed ledger, so a run that dies is resumed by reading the repository rather than reconstructed from a transcript. A leaf that goes quiet is not waited on indefinitely: supervise.sh watches a heartbeat and kills what stops writing, and classify-bail.sh turns the result into a labelled failure — the methodology said no, or the plumbing broke.

What veri actually is

veri solves GitHub issues under strict TDD discipline. You point it at one issue; it plans the work, then drives each step through Red → Green → Refactor, and hands you a draft pull request. The name comes from the part that makes it unusual: every test is checked by a second, independent agent that never sees the author's reasoning and must run the test itself to form an opinion.

It is not an application. It is a skill — a directory that Claude Code loads — and it is made of exactly two kinds of thing.

The division of labour

Everything in veri is either judgement or mechanism, and the two are kept in physically separate places:

LayerWhere it livesWhat it doesTested?
The conductorSKILL.md A procedure written in English that Claude follows. Decides what the plan is, what a step means, when to move on. All judgement.No — it is prose
The scriptsscripts/*.sh Small deterministic tools the conductor calls. Kill a hung process, parse a verdict, tick a checkbox. No judgement at all.Yes — make test

That line is the entire design philosophy: the model decides, the scripts enforce. Anything that must be exact and repeatable is pulled out of the fuzzy part and into a shell script with a unit test behind it. So the guarantees you can actually rely on all live in the 1401 lines this page reproduces in full.

One more role, because it appears constantly:

  • A leaf is one short-lived claude -p subprocess that performs exactly one step — write the failing test, write the implementation, apply one refactor — then exits. Leaves never persist and never share memory.

The exit-code contract

Learn this before any single script, because it is the API between all of them. Unix programs return a small integer on exit; zero conventionally means success. veri assigns four specific meanings and holds to them everywhere:

CodeMeansIn practice
0 okSuccess, or PASS The leaf finished cleanly; the verifier approved; a checkbox was ticked.
1 noA clean negative The leaf ran and failed; the verifier said REJECT. A real answer — the system worked and the answer was no.
2 brokenNo answer could be obtained The leaf hung and was killed; the verdict was unparseable; the arguments were wrong. Something is broken, so there is no answer.
3 noneNothing to do No unchecked step remains; no checkbox matched. Not an error — a specific, expected, empty result.
Why this matters more than it looks

The gap between 1 and 2 is the most important distinction in veri: the difference between the methodology spoke (a blind verifier legitimately refused the work — a process failure) and the plumbing broke (no verdict at all — a system failure). veri reports, retries and blames those differently. Keeping them apart at the bottom of the stack is why that is possible at the top.

Where the TDD loop lives

Nothing in that map mentions Red, Green or Refactor — and no script does either. The methodology belongs to the conductor, written out in SKILL.md as English. What the scripts underneath it see is the same three beats every time: a developer leaf writes something, a blind verifier judges it, and one integer decides what happens next. Which phase it is changes only the prompt and the rubric.

Which means the five stages are not one step. They are one phase. A step is that pipeline run three times over, and the loop you are looking for is the column-to-column arrow:

Four things that only become visible once the loop is drawn:

  • Three phases, three blind verdicts, one step. Stage 1 runs once per step; stages 2 and 3 run once per phase — more, when a phase is revised. The verifier is a fresh agent every time, so nothing it approved earlier carries over. A step that was already satisfied takes one verdict, not three: the pin is an exit from Red, not a fourth phase.
  • The ledger ticks at Green, not at the end. The moment the implementation is blind-approved, the tick and the code go into one commit — so git history and the checklist cannot disagree even if the run dies during Refactor.
  • Refactor is the asymmetric one. It loops transforms inside the phase, committing each, and takes a single verdict on the settled result. Verifying each transform separately would multiply the cost of the expensive half without changing what the suite already proves — the suite is the objective gate throughout, and the verdict only asks whether the result is up to standard.
  • None of this is in a script. No file under scripts/ knows there are three phases, what order they come in, or that Refactor loops. Phase is a string the conductor passes down — verify.sh red…, green…, refactor…, pin… — which is exactly the split the division of labour promised: the model decides, the scripts enforce.

How the data moves

The last two sections say which scripts exist and in what order they repeat. This says what actually travels between them — because in veri the interesting content is not the calls, it is what crosses each boundary: a file on disk, a line of stdout, or a single exit code that chooses the next branch.

Three things in that picture are worth naming, because they are the design and not just the plumbing.

  • The supervisor never blocks on the leaf. It watches a log file’s modification time (activity, so it is alive) and an rc file’s existence (so it finished on its own). Both are ordinary files, and the leaf cooperates with neither.
  • The verifier’s prompt is built from two inputs. The spec and the test path — there is no third arrow into build-verify-prompt.sh, which is exactly why the developer’s rationale cannot reach the agent judging it.
  • The verdict is parsed from stdout, not read from an exit status. claude -p exits 0 whether it approves or refuses, so the judgement lives in the text and only becomes an integer at parse-verdict.sh.

Stage 0 · prepare the target

Before the first commit

veri litters the repository it works in: leaf logs, prompts, completion markers, the blind spec. All of it lives under .tdd/, and only one file there — the ledger — belongs in git. One script makes the target repo agree, once, before any cycle can commit.

Three scripts run here, in order, before any cycle exists — all of them touching the target rather than veri's own machinery. The first, issue-worktree.sh, gives the run a checkout of its own. The second, ensure-run-state-ignored.sh, exists because of how Green commits: git add -A, so that the ticked ledger and the step's code land in one commit. Without an ignore rule, that same -A would sweep every leaf log and prompt into history on the first step. veri's own .gitignore carried the rule; a fresh repo does not.

#!/usr/bin/env bash
# issue-worktree.sh — the linked git worktree an issue branch lives in.
#
# The conductor used to `git switch -c tdd/<n>-<slug>` in whatever checkout /tdd was
# invoked from, which drags that checkout off the default branch for the whole run: anything
# symlinked or served out of it (a user-level skill link, a dev server) silently starts seeing
# the issue branch. This creates a *linked worktree* instead — a second working directory that
# shares the one .git object store — and prints its absolute path, so the run can `cd` there
# and leave the caller's checkout exactly where it was.
#
# Usage:   issue-worktree.sh <n> <slug>
#          issue-worktree.sh --remove <n>
# Output:  the worktree's absolute path on stdout, exit 0.
set -euo pipefail

A linked worktree is a second working directory backed by the same .git object store as an existing checkout — its own directory, its own HEAD, its own branch checked out, but no second copy of history. This script exists because switching branches in place is the dangerous move here: the caller's checkout is often the primary clone a user-level skill link points at, so anything that reads through that link — another conductor's run, a dev server — would silently start seeing the issue branch mid-run. A worktree sidesteps that: the caller's checkout never leaves its default branch, only the new directory this script prints the path to does.

set -euo pipefail, as everywhere else. 


# --show-toplevel is the root of the checkout we were called from, with symlinks resolved
# (on macOS a /var/... path comes back as /private/var/...). Resolved is what we want: git
# reports worktree paths that way too, so the path we print matches what `git worktree list`
# will say about it.
root="$(git rev-parse --show-toplevel)"

git rev-parse --show-toplevel answers with the root of the checkout this script was called from, symlinks resolved — on macOS a path under /var/… comes back as /private/var/…, because /var is itself a symlink there. Resolved is what's wanted: git worktree list reports paths the same way, and the idempotence check further down is a plain string comparison against that report — two spellings of the same path would make a worktree that already exists look like one that doesn't. 


# wt_path <n> — where issue <n>'s worktree lives. The layout is stated once, here, because both
# halves of this script need it and a create that answered with a different path than the remove
# went looking for would be a silent no-op. `.tdd/` is already git-ignored, so nesting a worktree
# under it needs no new ignore rule.
wt_path() { printf '%s\n' "$root/.tdd/wt/$1"; }

wt_path() states the on-disk layout — .tdd/wt/<n> — exactly once, because both the create path below and --remove compute it from the same function. Two independent spellings of this path drifting apart would be silent: a remove that computed a different path than create used would find nothing there and no-op, rather than fail loudly. Nesting under .tdd/ costs no new ignore rule — ensure-run-state-ignored.sh already ignores everything under it. 


# --remove <n> takes the worktree back out again, once its branch is merged or a human says so.
# It is answered here, before the positional <n> <slug> parsing below, because that parsing
# would otherwise read the flag itself as the issue number.
if [[ "${1:-}" == "--remove" ]]; then
  n="${2:?usage: issue-worktree.sh --remove <n>}"
  path="$(wt_path "$n")"

  # Never destroy work. `git status --porcelain` prints one line per change — staged, unstaged
  # or untracked — and nothing at all when the tree is clean, so a non-empty answer is the
  # whole test. Asking before removing rather than letting `git worktree remove` refuse for us
  # is what makes this exit 2, "no answer could be obtained", instead of git's own 1: a
  # worktree with changes in it is not a removal that failed, it is one we must not attempt.
  if [[ -n "$(git -C "$path" status --porcelain)" ]]; then
    echo "issue-worktree: $path has uncommitted changes — refusing to remove it" >&2
    exit 2
  fi

  # No --force: with the tree clean git has nothing to object to, and leaving the safety net
  # in place means a change that lands between the check above and here still stops us.
  # >&2 keeps any chatter off stdout.
  git worktree remove "$path" >&2
  exit 0
fi

--remove is answered before the positional <n> <slug> parsing below runs at all — otherwise that parsing would read the flag itself as the issue number and die on a usage message that names the wrong problem. The issue number is then pulled out with the same required-argument assertion used throughout.

git status --porcelain is the clean test: one line per changed file — staged, unstaged or untracked — and nothing at all when the tree is clean, so a non-empty answer is the whole condition. It is asked before calling git worktree remove, rather than letting git refuse on its own, and that ordering is what makes a dirty worktree exit 2 here instead of whatever git's own removal failure would have been: nothing was actually attempted with git, so this is not a removal that failed — it is one that must never be attempted, which is exactly the "no answer could be obtained" code, not a process failure's 1.

No --force

With the tree already confirmed clean, git has nothing left to object to, so --force is never passed. That keeps the safety net live right up to the last moment: a change landing between the status --porcelain check above and the git worktree remove call below still stops the removal, because git re-checks for itself before it will act. 


# ${1:?msg} — expand $1, but if it is unset or empty, die with msg on stderr instead of
# silently building a branch called `tdd/-`. The first argument carries the whole usage line
# and the rest just name themselves, which is how every other script here does it.
n="${1:?usage: issue-worktree.sh <n> <slug>}"
slug="${2:?missing <slug>}"

branch="tdd/$n-$slug"
path="$(wt_path "$n")"

The create path's own two required-argument assertions: unlike a missing --remove target, a missing <n> or <slug> here dies through bash's own exit status for an unset ${1:?…} expansion, not through a code this script chose — a reminder that "exit 2" is this script's vocabulary for its own deliberate refusals, not a blanket description of everything that can go wrong. 


# git's own registry of worktrees — asked once here, questioned twice below. `worktree list
# --porcelain` prints one block per registered worktree, blank-line separated: a
# `worktree <absolute-path>` line first, then `HEAD <sha>`, then `branch <full-ref>` (absent
# when that worktree is detached).
#
# Captured into a variable rather than piped into each reader: `set -o pipefail` above would
# let git's exit code — including the SIGPIPE it takes when a reader stops early — decide the
# answer instead of the reader's. Each question below feeds it back in with <<<, a here-string,
# which hands one string to a command as its stdin without a pipeline.
registry="$(git worktree list --porcelain)"

git worktree list --porcelain prints one blank-line-separated block per registered worktree: a worktree <path> line, then HEAD <sha>, then branch <ref> (absent when that worktree is detached). It is captured into registry once and asked twice below, rather than re-run or piped into each reader: under pipefail, feeding it through a pipe would let the reader's early exit deliver git a SIGPIPE and turn that into the pipeline's reported failure, when nothing here has actually gone wrong.

Each question below feeds the captured text back in with <<<, a here-string: it hands one string to a command as its stdin with no pipe and no subshell, which matters for checkout_holder below — a loop on the left of a pipe runs in a subshell and any variable it sets vanishes when the pipe closes; a loop reading a here-string runs in the current shell and its variables live on. 


# Idempotent: a second call for the same issue — a resume, or a conductor re-entering step 1 —
# answers with the path it already made instead of dying on `git worktree add`'s "already
# exists". grep -x -F asks the registry for that exact `worktree <path>` line, whole and
# literal (-F: no regex, so a `.` in the path is a dot). Asking git rather than `[[ -d $path ]]`
# matters — a leftover directory git no longer knows about is not a worktree we can hand back,
# and it must fall through to the add below.
if grep -qxF "worktree $path" <<<"$registry"; then
  printf '%s\n' "$path"

# checkout_holder <branch> — the path of the worktree that has <branch> checked out, or nothing
# at all when no worktree does. Walks the registry line by line, remembering the path of the
# block it is inside, and answers with it when a branch line names the one asked about.
#
# `read -r key value` splits each line on whitespace into the first word and *all* the rest, so
# a path containing spaces still arrives whole in $value; -r stops backslashes being eaten.
# `local` keeps the walk's bookkeeping out of the rest of the script. The closing `return 0`
# pins the no-match answer to success: a while loop exits with the status of the last command
# its *body* ran (not the `read` that ended it), which here is an unmatched `if` and so happens
# to be 0 already — but it would be 1 if that line were ever reworked into a bare `[[ ]]`, and
# `set -e` would then kill the script on the ordinary "nobody holds this branch" case.
checkout_holder() {
  local key value seen=""
  while read -r key value; do
    case "$key" in
      worktree) seen="$value" ;;
      branch) if [[ "$value" == "refs/heads/$1" ]]; then printf '%s\n' "$seen"; return 0; fi ;;
    esac
  done <<<"$registry"
  return 0
}

checkout_holder() answers a question grep alone cannot: not whether a branch appears in the registry, but which worktree's block it appears in — the branch line that names it is several lines below the worktree line that names the path, in a different block for every other worktree in between. So it walks the registry itself, remembering the most recent worktree line as it goes and answering with that remembered path the moment a branch line matches.

read -r key value differs from the safe line reader used elsewhere in one detail: two variables, not one, so the split lands on the first run of whitespace — key gets one word, value gets everything left on the line, which is what lets a worktree path containing a space survive intact. The case "$key" in … esac dispatch is the whole body: worktree updates seen, branch compares against the one asked about.

# Seconds-since-epoch of $1's last modification — the heartbeat sensor. There is no portable
# `stat`: GNU/coreutils spells it `stat -c %Y`, BSD/macOS spells it `stat -f %m`. The two
# must be tried one at a time, into a variable, with the answer validated — NOT chained with
# `||` inside one `$( )`. On GNU, `-f` is not a format flag at all; it means --file-system,
# so `stat -f %m FILE` reads `%m` as a second *filename* and prints a `  File: "…"` block to
# stdout for the real one before exiting non-zero. Chained, that block joins the fallback's
# digits in the same substitution and reaches the caller's `$(( ))`, where `set -u` kills the
# supervisor on the unset word `File`. Assigning each attempt separately overwrites instead
# of appending, and the digit test rejects anything that is not a plain count of seconds.
mtime_of() {
  local m
  m="$(stat -c %Y "$1" 2>/dev/null)" || m="$(stat -f %m "$1" 2>/dev/null)" || m=""
  # No readable mtime (neither spelling, or the log vanished) → report "just touched". The
  # heartbeat then never fires and the hard timeout, which needs only `date`, still bounds
  # the leaf. The opposite default (0) would read as decades of silence and kill every leaf.
  case "$m" in ''|*[!0-9]*) m="$(now)" ;; esac
  printf '%s\n' "$m"
}

mtime_of is the heartbeat sensor: seconds since the log was last written to. There is no portable spelling of "ask the filesystem for a file's mtime" — GNU/coreutils is stat -c %Y, BSD/macOS is stat -f %m — so both have to be tried. The nine-line comment above the function is here because the previous version of this idea — the two attempts chained with || inside one $( … ), falling back to a bare 0 — shipped for years and then broke the instant it met a real Linux runner.

What one $( ) with || inside it can hide

On GNU coreutils, -f is not a format flag at all — it means --file-system. stat -f %m FILE reads %m as a second filename, finds only FILE, and prints a filesystem block for it — a line starting File: "…" and more — to stdout, then exits non-zero because %m itself does not exist. On BSD/macOS, where -f really is the format flag, that same command just prints the mtime and the chain never reaches its second link — which is why four years of macOS-only runs never saw this.

Chained inside one command substitution, the failed attempt's block and the fallback's digits land in the same string. The caller does $(( t - $(mtime_of "$log") )); bash's arithmetic expansion treats every bareword in that string as a variable to look up, and the first one it meets is File — unset, and fatal under this script's set -u. The supervisor dies before it can choose any of its own exit codes.

The bug this avoids

The tempting alternative is to interpolate the value into the program text: awk "/$matcher/ { … }". That is an injection vulnerability — the matcher would be parsed as awk code, not compared as data.   BEGIN { m = ENVIRON["MATCHER"]; done = 0 }
  {
    if (!done && $0 ~ /^[[:space:]]*-[[:space:]]\[ \]/ && (m == "" || index($0, m) > 0)) {

The awk program is three rules:

  • BEGIN — before any input: read the matcher, clear a done flag.
  • The bare block runs for every line. Its condition is a three-way and: not yet done, the line looks like an unchecked box, and either the matcher is empty or index($0, m) > 0 — a literal substring search, not a regex. If it holds, sub() replaces the first [ ] with [x].

Telling empty from unset is what the two expansions here are for, and they differ by one character. def blockers(body):
    """The issue numbers named under the `## Blocked by` heading, up to the next heading.
    A section reading `None.` names none, and so does a body with no such section."""
    section = re.search(r"^## Blocked by$(.*?)(?=^## |\Z)", body, re.M | re.S)
    return [int(n) for n in re.findall(r"#(\d+)", section.group(1))] if section else []

blockers() pulls the issue numbers out of one issue's ## Blocked by section. re.search(r"^## Blocked by$(.*?)(?=^## |\Z)", body, re.M | re.S) is doing two jobs at once: re.M makes ^/$ match at line boundaries rather than only at the start and end of the whole string, so the heading itself can be matched on its own line, and re.S makes . match newlines too, so the lazy (.*?) can span the multi-line body of the section. The lookahead (?=^## |\Z) stops that capture at the next heading, or at the end of the body if there isn't one — without consuming it, so a second call against the same body could find the next section too. A ## Blocked by section reading None., or no such section at all, yields no #<n> matches either way, which is exactly "no blockers".

    here rather than run as early returns so the function reads as the definition it is."""
    number = issue["number"]
    still_open = number in open_issues
    opted_in = any(l.get("name") == label for l in issue.get("labels", []))
    unclaimed = number not in claimed
    unblocked = all(n not in open_issues for n in blockers(issue.get("body", "")))

solvable() names its four conditions as four local variables — still_open, opted_in, unclaimed, unblocked — and returns their conjunction, rather than the more common style of four early return False lines. Text & I/O

>   >>   <   <<<   2>&1   2>/dev/null

Redirection

  • > file — send stdout to the file, truncating it to empty first. That truncation happens the instant the line is parsed, before the command runs — the classic way to destroy a file you meant to read.
  • >> file — append instead.
  • < file — feed the file in as stdin.
  • <<< "$str" — a here-string: hand a variable to a command as its stdin, with no pipe and no temp file. Unlike a pipe, the command on the left of a here-string is not a separate process, so a loop reading one can set variables the rest of the script still sees afterwards.
  • 2>&1 — "make stream 2 go wherever stream 1 currently goes". The & means "this is a stream number, not a filename". Order matters: it copies the current destination of stdout, so it must come after any >.
  • 2>/dev/null — discard stderr, for a command expected to complain.

The convention veri holds to throughout: stdout is data, stderr is commentary. That is what lets a script's output be piped straight into the next one while its status messages still reach a human.

while IFS= read -r line || [[ -n "$line" ]]

Reading lines without corrupting them

  • IFS= — empties the field separator for this command, so leading and trailing whitespace on the line is not trimmed.
  • read — reads one line into the variable, returning non-zero at end-of-file, which ends the loop.
  • -r — raw: do not treat backslashes as escapes. Without it, \n in the input gets mangled.
  • || [[ -n "$line" ]] — the subtle one. If the final line has no trailing newline, read stores it but still returns non-zero, so the loop would drop it. This clause says "keep going if we did read something".

The naive alternatives — for line in $(cat f) — split on spaces rather than newlines and glob-expand the results. They are simply broken.

for f in dir/*.ext; do [ -f "$f" ]

Globbing, and matching nothing

  • Unquoted, a pattern like dir/*.ext is expanded by the shell itself before the loop ever runs — one word per matching file.
  • When nothing matches, bash's default behaviour is not to drop the word: the pattern is left as its own literal text, spelled exactly as written, and handed to the loop as if it had matched.
  • [ -f "$f" ] turns that literal-text case into false the same way it would for any other non-existent file, so the loop body only ever runs on a real match.

The alternative is shopt -s nullglob, which makes a non-matching pattern expand to zero words instead of one literal one, so the loop runs zero times on its own and needs no [ -f ] guard. Either shape works; this script picks the one that needs no global shell-option change.

Signals — and the minus sign that matters

  • A negative PID means the process group. kill -TERM -1234 signals every process in group 1234, not just the leader. This is how you reach a leaf's own children — a test runner it spawned — which would otherwise be orphaned and keep running.
  • -0 sends no signal at all. It only checks whether the process still exists, so it is used to poll "is it gone yet?".
  • -TERM is the polite request: "please clean up and exit". A program can catch it. -KILL cannot be caught or ignored — the kernel destroys the process immediately, with no chance to clean up.

The universal pattern is TERM, wait briefly, then KILL only if still alive. Reaching for KILL first leaves temp files and half-written state behind.

Where the versions come from

The capability index is not a changelog anyone maintains. A version is an annotated git tag: the tag’s message is the capability’s name, its date is the tag’s own date, and the scripts listed under it are computed from the feat: and fix: commits in its range. Nothing is declared twice, so nothing can disagree.

Cutting one is not a separate chore — it happens when a pull request lands, because that is the only moment that knows both that a capability shipped and what it was. Three things about the layer are worth knowing:

  • It is optional. Built from a tree with no git — a tarball, a shallow checkout, the copied sandbox the doc tests build in — the page comes out without an index and without the per-script badges, rather than failing. The absence is the signal that git was unreadable, and make docs-check says so loudly when the tree does have tags.
  • No shas, no counts. Neither ever reaches the page. Both change on every commit, and docs-check demands a byte-identical rebuild — so embedding either would turn the check red after every commit until someone re-ran make docs. “Unreleased” is a yes-or-no for the same reason.
  • Version sort, not alphabetical. v0.9 sorts after v0.10 lexically, which would bury the newest release in the middle of the list. The build reads tags with git’s own -v:refname ordering, and the checker re-derives the expected order and compares.

Two invariants are worth re-reading on any change, since most of this page rests on them: that the four exit codes still mean the same four things everywhere, and that build-verify-prompt.sh still has no parameter through which a developer leaf's rationale could reach a verifier.
