What veri actually is

veri solves GitHub issues under strict TDD discipline. You point it at one issue; it plans the work, then drives each step through Red → Green → Refactor, and hands you a draft pull request. The name comes from the part that makes it unusual: every test is checked by a second, independent agent that never sees the author's reasoning and must run the test itself to form an opinion.

It is not an application. It is a skill — a directory that Claude Code loads — and it is made of exactly two kinds of thing.

The division of labour

Everything in veri is either judgement or mechanism, and the two are kept in physically separate places:

LayerWhere it livesWhat it doesTested?
The conductorSKILL.md A procedure written in English that Claude follows. Decides what the plan is, what a step means, when to move on. All judgement.No — it is prose
The scriptsscripts/*.sh Small deterministic tools the conductor calls. Kill a hung process, parse a verdict, tick a checkbox. No judgement at all.Yes — make test

That line is the entire design philosophy: the model decides, the scripts enforce. Anything that must be exact and repeatable is pulled out of the fuzzy part and into a shell script with a unit test behind it. So the guarantees you can actually rely on all live in the 606 lines this page reproduces in full.

One more role, because it appears constantly:

  • A leaf is one short-lived claude -p subprocess that performs exactly one step — write the failing test, write the implementation, apply one refactor — then exits. Leaves never persist and never share memory.

The exit-code contract

Learn this before any single script, because it is the API between all of them. Unix programs return a small integer on exit; zero conventionally means success. veri assigns four specific meanings and holds to them everywhere:

CodeMeansIn practice
0 okSuccess, or PASS The leaf finished cleanly; the verifier approved; a checkbox was ticked.
1 noA clean negative The leaf ran and failed; the verifier said REJECT. A real answer — the system worked and the answer was no.
2 brokenNo answer could be obtained The leaf hung and was killed; the verdict was unparseable; the arguments were wrong. Something is broken, so there is no answer.
3 noneNothing to do No unchecked step remains; no checkbox matched. Not an error — a specific, expected, empty result.
Why this matters more than it looks

The gap between 1 and 2 is the most important distinction in veri: the difference between the methodology spoke (a blind verifier legitimately refused the work — a process failure) and the plumbing broke (no verdict at all — a system failure). veri reports, retries and blames those differently. Keeping them apart at the bottom of the stack is why that is possible at the top.

Where the TDD loop lives

Nothing in that map mentions Red, Green or Refactor — and no script does either. The methodology belongs to the conductor, written out in SKILL.md as English. What the scripts underneath it see is the same three beats every time: a developer leaf writes something, a blind verifier judges it, and one integer decides what happens next. Which phase it is changes only the prompt and the rubric.

Which means the five stages are not one step. They are one phase. A step is that pipeline run three times over, and the loop you are looking for is the column-to-column arrow:

Four things that only become visible once the loop is drawn:

  • Three phases, three blind verdicts, one step. Stage 1 runs once per step; stages 2 and 3 run once per phase — more, when a phase is revised. The verifier is a fresh agent every time, so nothing it approved earlier carries over. A step that was already satisfied takes one verdict, not three: the pin is an exit from Red, not a fourth phase.
  • The ledger ticks at Green, not at the end. The moment the implementation is blind-approved, the tick and the code go into one commit — so git history and the checklist cannot disagree even if the run dies during Refactor.
  • Refactor is the asymmetric one. It loops transforms inside the phase, committing each, and takes a single verdict on the settled result. Verifying each transform separately would multiply the cost of the expensive half without changing what the suite already proves — the suite is the objective gate throughout, and the verdict only asks whether the result is up to standard.
  • None of this is in a script. No file under scripts/ knows there are three phases, what order they come in, or that Refactor loops. Phase is a string the conductor passes down — verify.sh red…, green…, refactor…, pin… — which is exactly the split the division of labour promised: the model decides, the scripts enforce.

How the data moves

The last two sections say which scripts exist and in what order they repeat. This says what actually travels between them — because in veri the interesting content is not the calls, it is what crosses each boundary: a file on disk, a line of stdout, or a single exit code that chooses the next branch.

Three things in that picture are worth naming, because they are the design and not just the plumbing.

  • The supervisor never blocks on the leaf. It watches a log file’s modification time (activity, so it is alive) and an rc file’s existence (so it finished on its own). Both are ordinary files, and the leaf cooperates with neither.
  • The verifier’s prompt is built from two inputs. The spec and the test path — there is no third arrow into build-verify-prompt.sh, which is exactly why the developer’s rationale cannot reach the agent judging it.
  • The verdict is parsed from stdout, not read from an exit status. claude -p exits 0 whether it approves or refuses, so the judgement lives in the text and only becomes an integer at parse-verdict.sh.

Stage 0 · prepare the target

Before the first commit

veri litters the repository it works in: leaf logs, prompts, completion markers, the blind spec. All of it lives under .tdd/, and only one file there — the ledger — belongs in git. One script makes the target repo agree, once, before any cycle can commit.

This is the first script the conductor runs that touches the target rather than veri's own machinery, and it exists because of how Green commits: git add -A, so that the ticked ledger and the step's code land in one commit. Without an ignore rule, that same -A would sweep every leaf log and prompt into history on the first step. veri's own .gitignore carried the rule; a fresh repo does not.

# or the empty string when absent. -F keeps the glob literal (no regex), -x forbids a partial-line
# match so `x.tdd/*` does not count as `.tdd/*`, -n prefixes each hit with `<lineno>:` — `head -1`
# takes the first hit and `cut` keeps the number, which is what the ordering check below compares.
# `|| true` is load-bearing under `pipefail`: absent the line, grep exits 1 and the whole pipeline
# inherits it, which `set -e` would turn into the script dying instead of reporting "not there".
where() { grep -nxF "$1" "$gitignore" | head -1 | cut -d: -f1 || true; }

where() replaces what used to be a plain has() boolean: it returns not whether a line is in $gitignore but which line number it first appears on, so the order of the three lines becomes something the script can compare. -n on grep prefixes each hit with <lineno>:; head -1 takes the first match and cut keeps the number in front of the colon.

Resolved: refused, not repaired

Anything short of that — one line missing, or the three lines out of order — used to be invisible to the old sentinel-only check. It no longer is, and the fix is not to patch it up: appending a fourth line cannot mend either failure, because git only ever reads a rule top to bottom and a second .tdd/* appended after an existing negation cannot retroactively change what precedes it. Stage 1 · read the ledger

Where a cycle begins

Before anything runs, the conductor asks one question: what is the next thing to do? The answer comes from a committed markdown checklist, and from the smallest script in the suite.

veri writes its plan to a ledger — a file at .tdd/issue-<n>.md committed to git alongside the code. It is an ordinary markdown checklist:

.tdd/issue-42.md the ledger
# Plan for #42 — add rate limiting to the public API

- [x] reject a request over the per-minute limit with 429
- [ ] include a Retry-After header on the rejection
- [ ] count limits per API key, not per IP

This file is the source of truth for what is done — not the GitHub issue, which is only a human-facing mirror. Because it is committed in the same commit as the code for that step, git history and the checklist cannot disagree.

That is what makes a run resumable: if veri dies halfway, re-running it reads this file and continues from the first unticked line.

Two things in here are load-bearing rather than descriptive. Exit 3 is documented as a signal, not an error — "the loop is complete / nothing remains to resume". And the note that the checkbox grammar matches tick-criterion.sh is the contract that lets the text printed here be handed straight back later as the thing to tick. 

set -euo pipefail

re='^[[:space:]]*- \[ \] (.*)$'

set -euo pipefail is the strict-mode header: exit on error, error on unset variables, and let a pipeline fail if any stage does. Eleven of the twelve scripts open this way.

The regex is stored in a variable because of a bash quirk: the pattern on the right of =~ must be unquoted to be treated as a pattern at all. Quoting it makes it a literal string that matches nothing. Assigning it to re and writing =~ $re bare is the idiomatic way around that.

The pattern reads: optional indentation, then - [ ] with exactly one space between the brackets, then capture everything else as group 1. 


while IFS= read -r line || [[ -n "$line" ]]; do
  if [[ "$line" =~ $re ]]; then
    printf '%s\n' "${BASH_REMATCH[1]}"
    exit 0
  fi
done

The loop is the full four-part safe line reader. A ledger is human-edited markdown, so it may well end without a trailing newline — the || [[ -n "$line" ]] clause is what stops the last step being invisible.

On a match, BASH_REMATCH[1] holds the captured description; the script prints it and exits 0 immediately. Steps are done in order, so there is no reason to look further.

The design payoff

What it prints is the step's own text — and that same string is later handed to tick-ledger.sh as the substring to search for when checking the step off. The output of reading is the input to writing, so the two cannot drift apart. No IDs, no line numbers, no index to keep in sync. 


exit 3

Falling off the end means no unchecked box was found anywhere: every step is done. That is 3.

Why 3 and not 1

"Every step is complete" is not a failure — it is the successful end of the loop and the signal to go open the pull request. But it is not a success either, because there is no step to return. A third code lets the conductor write one unambiguous branch: 0 run a cycle, 3 open the PR, anything else something is wrong. Had this returned 1, "we finished the issue" would be indistinguishable from "the script broke".

Stage 2 · run a leaf

Launching something you do not trust

The conductor needs a developer leaf to write a failing test. That leaf is an LLM subprocess that might take five minutes, might finish in ten seconds, and might hang forever. Three scripts turn that into a bounded, observable operation.

These three nest inside one another, outermost first — and the outermost is the only one the conductor is ever allowed to call:

supervise.sh — the watchdogsince v0.3 · changed v0.4

The heart of veri, and the most systems-heavy script in it. The problem: you are about to start a process that will run for minutes doing real work, and you must distinguish three outcomes a plain cmd && … cannot tell apart — it finished, it failed, or it is never going to finish.

It does that with two independent clocks:

  • Heartbeat — has the leaf produced any output recently? A sliding silence window. Catches a genuine hang.
  • Hard timeout — has it run too long regardless of activity? An absolute wall-clock cap. Catches a leaf that chatters but never converges.

Everything else is machinery to run those two clocks against a live process.

#!/usr/bin/env bash
# supervise.sh — launch one leaf under a heartbeat + hard-timeout watchdog.
#
# This is the one choke point where stuck-detection policy lives (ADR-0002): every leaf is
# launched through here, never directly. The supervisor spawns the leaf in the background
# and watches it two ways:
#   * heartbeat — activity on the leaf's progress log within a window tells "slow but
#     working" from "hung". A leaf silent past the window is killed.
#   * hard timeout — a leaf that exceeds the wall-clock cap is killed even if still noisy.
# A killed leaf is retried up to VERI_STUCK_RETRIES times (default 1) on a fresh attempt; if
# it still can't recover it is reported as `killed-stuck`, which the conductor turns into a
# clean bail.
#
# Usage:
#   supervise.sh <name> <cmd> [args...]
#
# The leaf's combined stdout+stderr is captured to `.tdd/<name>.log` (the progress log the
# heartbeat watches) and echoed to this script's stdout on completion, so a verifier leaf
# can be piped straight into parse-verdict.sh.
#
# Status: exit 0 success · 1 leaf-failure · 2 killed-stuck. A one-line status (with the
# kill cause) is written to stderr.
#
# Tunables (env): VERI_HEARTBEAT silence window secs (default 45) · VERI_TIMEOUT hard cap
# secs (default 900) · VERI_POLL poll interval secs (default 1) · VERI_STUCK_RETRIES extra
# attempts after the first when a leaf is killed-stuck (default 1).

A twenty-six-line header, and worth reading as design documentation rather than preamble. It states the invariant the whole system depends on: "every leaf is launched through here, never directly". Lines 39–40 derive two filenames from <name>: a log, about to serve as the heartbeat sensor, and an rc file, about to serve as the completion signal. Neither is obvious yet; both are the crux of what follows. 


mtime_of() {  # seconds-since-epoch of $1's last modification, portable across BSD/GNU
  stat -f %m "$1" 2>/dev/null || stat -c %Y "$1" 2>/dev/null || echo 0
}
now() { date +%s; }

mtime_of is the heartbeat sensor. It asks the filesystem when a file was last modified, in seconds since the epoch. The || chain exists because there is no portable stat: macOS and BSD spell it -f %m, Linux and GNU spell it -c %Y. Try one, fall back, fall back again to 0. Each failed attempt's complaint is swallowed with 2>/dev/null.

The idea worth stealing

The heartbeat is not a signal the leaf sends. There is no protocol, no keepalive, no cooperation from the leaf at all. It is the modification time of the log file — which the operating system updates for free, every time the leaf writes a byte. "Is it alive?" becomes "was this file touched recently?", which costs one stat per second and works on any program, whether or not it knows it is being watched.

  for _ in 1 2 3 4 5; do kill -0 "$pid" 2>/dev/null || return 0; sleep 0.1; done
  kill -KILL -"$pid" 2>/dev/null || kill -KILL "$pid" 2>/dev/null
}

Three ideas packed into four lines, all covered by the signals entry:

  • The minus sign on line 48. -"$pid" — a negative PID — signals the whole process group. This matters because claude spawns children: a test runner, a compiler. Signalling only the parent orphans those, and they keep running and keep consuming the machine.
  • The poll on line 50. kill -0 sends nothing at all; it only tests whether the process still exists. Five times, check if it is gone — return 0 the moment it is — otherwise wait 100 ms. A grace period of at most half a second.
  • The escalation. -TERM first, which a program can catch and handle cleanly. Only if it is still alive does line 51 send -KILL, which cannot be caught. Politeness first, force second.

The loop variable is named _ — a convention meaning "this value is never used". The loop runs five times; that is all it is for.

  • "$@" — the leaf command and its arguments, each staying one argument.

The part veri is named after

The most cryptic two lines in veri, and worth decoding slowly. Take ltrim:

The bug this avoids

The tempting alternative is to interpolate the value into the program text: awk "/$matcher/ { … }". That is an injection vulnerability — the matcher would be parsed as awk code, not compared as data. Routing it through the environment keeps the program text constant and the value as data.

The awk program is in single quotes, so the shell expands nothing inside it — $0 reaches awk as awk's "whole current line", not as the shell's script name. 

  BEGIN { m = ENVIRON["MATCHER"]; done = 0 }
  {
    if (!done && $0 ~ /^[[:space:]]*-[[:space:]]\[ \]/ && (m == "" || index($0, m) > 0)) {
      sub(/\[ \]/, "[x]")
      done = 1
    }
    print
  }

The awk program is three rules:

  • BEGIN — before any input: read the matcher, clear a done flag.
  • The bare block runs for every line. Its condition is a three-way and: not yet done, the line looks like an unchecked box, and either the matcher is empty or index($0, m) > 0 — a literal substring search, not a regex. If it holds, sub() replaces the first [ ] with [x].

Text & I/O

>   >>   <   2>&1   2>/dev/null

Redirection

  • > file — send stdout to the file, truncating it to empty first. That truncation happens the instant the line is parsed, before the command runs — the classic way to destroy a file you meant to read.
  • >> file — append instead.
  • < file — feed the file in as stdin.
  • 2>&1 — "make stream 2 go wherever stream 1 currently goes". The & means "this is a stream number, not a filename". Order matters: it copies the current destination of stdout, so it must come after any >.
  • 2>/dev/null — discard stderr, for a command expected to complain.

The convention veri holds to throughout: stdout is data, stderr is commentary. That is what lets a script's output be piped straight into the next one while its status messages still reach a human.

while IFS= read -r line || [[ -n "$line" ]]

Reading lines without corrupting them

  • IFS= — empties the field separator for this command, so leading and trailing whitespace on the line is not trimmed.
  • read — reads one line into the variable, returning non-zero at end-of-file, which ends the loop.
  • -r — raw: do not treat backslashes as escapes. Without it, \n in the input gets mangled.
  • || [[ -n "$line" ]] — the subtle one. If the final line has no trailing newline, read stores it but still returns non-zero, so the loop would drop it. This clause says "keep going if we did read something".

The naive alternatives — for line in $(cat f) — split on spaces rather than newlines and glob-expand the results. They are simply broken.

Signals — and the minus sign that matters

  • A negative PID means the process group. kill -TERM -1234 signals every process in group 1234, not just the leader. This is how you reach a leaf's own children — a test runner it spawned — which would otherwise be orphaned and keep running.
  • -0 sends no signal at all. It only checks whether the process still exists, so it is used to poll "is it gone yet?".
  • -TERM is the polite request: "please clean up and exit". A program can catch it. -KILL cannot be caught or ignored — the kernel destroys the process immediately, with no chance to clean up.

The universal pattern is TERM, wait briefly, then KILL only if still alive. Reaching for KILL first leaves temp files and half-written state behind.

Where the versions come from

The capability index is not a changelog anyone maintains. A version is an annotated git tag: the tag’s message is the capability’s name, its date is the tag’s own date, and the scripts listed under it are computed from the feat: and fix: commits in its range. Nothing is declared twice, so nothing can disagree.

Cutting one is not a separate chore — it happens when a pull request lands, because that is the only moment that knows both that a capability shipped and what it was. Three things about the layer are worth knowing:

  • It is optional. Built from a tree with no git — a tarball, a shallow checkout, the copied sandbox the doc tests build in — the page comes out without an index and without the per-script badges, rather than failing. The absence is the signal that git was unreadable, and make docs-check says so loudly when the tree does have tags.
  • No shas, no counts. Neither ever reaches the page. Both change on every commit, and docs-check demands a byte-identical rebuild — so embedding either would turn the check red after every commit until someone re-ran make docs. “Unreleased” is a yes-or-no for the same reason.
  • Version sort, not alphabetical. v0.9 sorts after v0.10 lexically, which would bury the newest release in the middle of the list. The build reads tags with git’s own -v:refname ordering, and the checker re-derives the expected order and compares.

Two invariants are worth re-reading on any change, since most of this page rests on them: that the four exit codes still mean the same four things everywhere, and that build-verify-prompt.sh still has no parameter through which a developer leaf's rationale could reach a verifier.
