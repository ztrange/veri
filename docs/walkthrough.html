What veri actually is

veri solves GitHub issues under strict TDD discipline. You point it at one issue; it plans the work, then drives each step through Red → Green → Refactor, and hands you a draft pull request. The name comes from the part that makes it unusual: every test is checked by a second, independent agent that never sees the author's reasoning and must run the test itself to form an opinion.

It is not an application. It is a skill — a directory that Claude Code loads — and it is made of exactly two kinds of thing.

The division of labour

Everything in veri is either judgement or mechanism, and the two are kept in physically separate places:

LayerWhere it livesWhat it doesTested?
The conductor SKILL.md A procedure written in English that Claude follows. Decides what the plan is, what a step means, when to move on. All judgement. No — it is prose
The scripts scripts/*.sh Small deterministic tools the conductor calls. Kill a hung process, parse a verdict, tick a checkbox. No judgement at all. Yes — make test

That line is the entire design philosophy: the model decides, the scripts enforce. Anything that must be exact and repeatable is pulled out of the fuzzy part and into a shell script with a unit test behind it. So the guarantees you can actually rely on all live in the 543 lines this document covers.

There is a third role worth naming before we start, because it appears constantly:

  • A leaf is one short-lived claude -p subprocess that performs exactly one step — write the failing test, write the implementation, apply one refactor — and then exits. Leaves never persist and never share memory. Every time you see a script launching something, it is launching a leaf.

The exit-code contract

Before any single script, learn this, because it is the API between all of them. Unix programs return a small integer when they exit. Zero conventionally means success and anything else means failure — but veri assigns four specific meanings and uses them consistently across every script:

CodeMeansIn practice
0 ok Success, or PASS The leaf finished cleanly; the verifier approved; a checkbox was ticked.
1 no A clean negative The leaf ran and failed; the verifier said REJECT. This is a real answer — the system worked and the answer was no.
2 broken No answer could be obtained The leaf hung and was killed; the verdict was unparseable; the arguments were wrong. Something is broken, so there is no answer.
3 none Nothing to do No unchecked step remains in the ledger; no checkbox matched. Not an error — a specific, expected, empty result.
Why this matters more than it looks

The gap between 1 and 2 is the most important distinction in veri. It is the difference between the methodology spoke (a blind verifier legitimately refused the work — a process failure) and the plumbing broke (we never got a verdict at all — a system failure). veri reports those differently to a human, retries them differently, and blames them differently. Keeping them apart from the very bottom of the stack is why that is possible at the top.

Map of the eleven scripts

The scripts form a small dependency tower — the ones you call are compositions of the ones you don't. Read in the order data actually flows through a single cycle, they group into five stages, and this document is organised as those five stages:

Stages 1 to 4 are the happy path of one step. Stage 5 is the exceptional exit, and can be reached from any of the others. When stage 4 completes, the conductor loops back to stage 1 for the next unchecked step — that loop is what turns one cycle into a whole issue.

Before walking them, here is the syntax. Every construct used anywhere in the eleven scripts is below, once, with an anchor — and from here on, the first time a construct appears in a script it is linked back like this.

Reference · the syntax

The bash primer

Roughly thirty constructs account for all 543 lines. They are grouped by what they do, not by which script uses them, because nearly every one recurs across several.

Header & safety

#!/usr/bin/env bash

Shebang

The first line of every script. It tells the kernel which interpreter to run the file with when you execute it directly. Using /usr/bin/env bash rather than a hard path like /bin/bash means "find bash on the user's PATH" — which matters on macOS, where /bin/bash is a frozen 2007-era version 3.2 and the modern one lives elsewhere via Homebrew.

All 11 scripts, line 1.

set -euo pipefail

Strict mode

Bash's defaults are dangerously forgiving — a failed command is ignored and execution barrels on. This line turns on three separate corrections:

  • -e — exit immediately if any command returns non-zero. Fail fast instead of continuing on corrupt state.
  • -u — error on an unset variable instead of quietly substituting an empty string. Catches typos in variable names, which are otherwise invisible.
  • -o pipefail — a pipeline fails if any stage fails. By default a | b reports only b's status, so a crash in a vanishes.

9 of 11 scripts. Read it as "make bash behave like a normal language".

set -uo pipefail

Strict mode without -e

The same, deliberately omitting -e. Used where non-zero exits are expected data rather than errors — a script whose whole job is watching something else fail cannot afford to die the moment it does.

supervise.sh only, and that omission is the point of it.

set +e … rc=$? … set -e

Temporarily disabling fail-fast

With -e on, a command that returns non-zero kills the script before you can inspect the code. In bash, - turns an option on and + turns it off (backwards from what you would guess). So this brackets one command: switch fail-fast off, run it, capture its status into a variable, switch fail-fast back on.

Wherever you see this, the exit code is meaningful information, not a malfunction — the script wants to branch on it.

run-leaf.sh, verify.sh (twice).

Variables & expansion

"$var"

Quoting — the one habit that matters most

An unquoted variable in bash is not a value. Before running the command, the shell splits it on whitespace and expands any * or ? as a filename pattern. A variable holding my file.txt becomes two arguments; one holding * becomes every file in the directory.

Wrapping it in double quotes suppresses both, making the variable behave like a single value the way it would in any other language. Practically every variable reference in these scripts is quoted, and the few that aren't are marked with a comment explaining why.

Everywhere. Treat an unquoted $x as a bug until proven otherwise.

"${1:?usage: …}"

Required-argument assertion

Reads positional argument 1, but if it is unset or empty, prints the message to stderr and aborts the script immediately. It is an inline precondition check — a one-token replacement for an if block that would otherwise be four lines.

The exit status on failure is 1 from the shell itself, so a script wanting a specific code for bad arguments still validates separately.

Opening lines of nearly every script — this is how they declare their signature.

"${2:-default}"

Default value

The forgiving sibling of :?. Evaluates to $2 if it is set and non-empty, otherwise to default. It does not assign anything — it is an expression producing a value.

This is how every tunable in veri works: "${VERI_TIMEOUT:-900}" means "whatever the environment says, else 900". That single idiom is what makes the scripts testable — a test can set VERI_TIMEOUT=2 and not wait fifteen minutes.

All tunables; every optional argument.

"${VAR:-}"

The empty-default guard

A default of nothing at all. It looks pointless, but under set -u merely reading an unset variable is a fatal error. This says "if unset, give me the empty string, and do not abort" — the standard way to test whether an optional environment variable was provided.

${CLAUDE_BIN:-claude}, ${VERIFY_LEAF_ARGS:-}, ${GH_REPO:-}.

$( … )

Command substitution

Runs the command inside as a child process and evaluates to whatever it wrote to stdout, as a string. This is how shell scripts call each other and get an answer back — x="$(cat file)" puts a file's contents in a variable.

Two consequences worth holding onto. First, it is a separate process, so it cannot modify the caller's variables. Second — and this catches everyone — it strips all trailing newlines from what it captures. Scripts that need the newline back add it explicitly with printf '%s\n'.

Everywhere. The backtick form ` … ` means the same thing but doesn't nest; it is not used here.

$?   $!   $@   $#   $0

Special parameters

  • $? — exit status of the most recently completed command. It is overwritten by the next command, so capture it immediately or lose it.
  • $! — process ID of the most recent background job.
  • $@ — all positional arguments. Quoted as "$@" it expands to one properly-separated word per argument, which is what you almost always want; unquoted it re-splits them and mangles anything containing a space.
  • $# — how many arguments there are.
  • $0 — the script's own path, used to locate sibling files.

$? and $! carry the load in supervise.sh.

${v//search/replace}

Substring replacement

Replaces occurrences of search in $v. A double slash replaces all of them; a single slash ${v/a/b} replaces only the first. Like every parameter expansion, it produces a new string — it never modifies $v, and it certainly has no connection back to any file the value came from.

Crucially it is a literal replacement. That is why veri templates prompts with this instead of sed: an issue body is arbitrary human text full of &, \ and /, all of which sed treats as special and would corrupt.

build-verify-prompt.sh — the whole templating engine is four of these.

${v#pat}   ${v##pat}   ${v%pat}   ${v%%pat}

Prefix and suffix stripping

Remove a matching pattern from one end of a string. # cuts from the front, % from the back; doubling the character makes the match greedy (longest) instead of lazy (shortest).

Mnemonic: on a US keyboard # sits left of %, matching which end each one bites. These build the whitespace-trimming helpers and the "first token of a line" extraction in parse-verdict.sh, with no external process involved.

parse-verdict.sh heavily; supervise.sh.

printf -v name '%s\n' "${arr[@]}"

Printf into a variable

Ordinary printf writes to stdout; the -v flag writes the result into the named variable instead. It avoids a $( … ) subshell — and, importantly here, avoids that construct's newline-stripping, so a deliberately-trailing newline survives.

parse-verdict.sh, rejoining the reason lines.

$'\n'

ANSI-C quoting

Inside ordinary quotes, \n is a backslash followed by an n. The $'…' form interprets escapes the way C does, so this is a genuine newline character. Needed when a newline must appear inside a pattern rather than in output.

parse-verdict.sh, splitting the reason on its last line.

VAR=value command

Per-command environment

Setting a variable on the same line as a command exports it only for that one command, without leaking into the rest of the script. The usual way to hand a value to a program that reads its environment rather than its arguments.

tick-criterion.sh, passing the matcher to awk.

Tests & arithmetic

[[ … ]]

Conditional expression

Bash's test construct. (The older [ … ] is literally a command named [ and has sharp edges around empty values; [[ … ]] is parsed by the shell and is safer.) The operators used in veri:

  • -f path — a regular file exists
  • -r path — the file is readable
  • -n "$s" — the string is non-empty · -z "$s" — it is empty
  • "$a" == "$b" — string equality
  • -ge -lt — numeric comparison (inside [[ ]], unlike (( )), you cannot use > for numbers — it would mean redirect)

All over. [[ -f "$rcfile" ]] is the heart of the watch loop.

[[ "$s" =~ regex ]]  →  BASH_REMATCH

Built-in regular expressions

Bash matches POSIX extended regular expressions natively, with no grep subprocess. After a successful match, the array BASH_REMATCH holds the results: index 0 is the whole match, 1 the first parenthesised capture group, and so on.

The right-hand side must be unquoted to be treated as a pattern — quoting it makes it a literal string. That is why these scripts assign a regex to a variable and then write =~ $re bare.

parse-verdict.sh, next-unchecked.sh.

(( … ))

Arithmetic evaluation

Integer maths with C-like syntax. Inside, variables need no $ and the normal comparison operators work: (( t - t0 >= timeout )) reads exactly as it would in any language.

One inversion to remember: it follows C truthiness, not shell truthiness. A result of zero is "false" and so returns exit status 1. Harmless in an if, but (( count++ )) as a bare statement under set -e will kill your script when the count is zero. veri sidesteps it entirely with x=$(( x + 1 )).

supervise.sh — both clocks and the retry counter.

case "$x" in … esac

Pattern dispatch

Bash's switch. Each branch is pattern) commands ;;, patterns are glob-style (not regex), | separates alternatives, and *) is the catch-all default. There is no fall-through — ;; ends a branch.

classify-bail.sh is essentially nothing else; also the status→exit-code mapping in supervise.sh.

cmd1 || cmd2  ·  cmd1 && cmd2

Short-circuit chaining

|| runs the right side only if the left failed; && only if it succeeded. Used as a compact if/else, and as a fallback chain: try_bsd || try_gnu || echo 0 tries each in turn until one works.

A second, subtler use: a command on the left of || is exempt from set -e, because its failure is being handled. That is why cmd || true is the idiom for "let this one fail harmlessly".

The portability fallbacks and kill attempts in supervise.sh.

Arrays

arr=( a b c )  →  "${arr[@]}"

Arrays, and why they exist

Parentheses build an array; "${arr[@]}" expands it to one quoted word per element. This is the only correct way to hold a list of command arguments in bash.

The reason it matters: if you keep arguments in a plain string and pass $args, the shell re-splits it on whitespace, so an argument containing a space silently becomes two. An array preserves the boundaries you meant. veri builds the verifier's command-line flags this way.

verify.sh (leaf flags), tick-issue-criterion.sh (repo flags).

"${!arr[@]}"   ${#arr[@]}   "${arr[@]:n}"

Indices, length, slice

  • "${!arr[@]}" — the indices, not the values. The leading ! means "give me the keys"; this is how you loop with a counter.
  • ${#arr[@]} — the number of elements. (On a plain string, ${#s} is its character length.)
  • "${arr[@]:n}" — a slice from index n onward.

parse-verdict.sh, which treats the leaf's output as an array of lines.

"${arr[@]+"${arr[@]}"}"

The empty-array guard

Deeply ugly, and load-bearing. In bash 4.3 and earlier — which includes the macOS system bash — expanding an empty array under set -u counts as an unset variable and aborts the script.

The ${x+…} form means "if x is set, produce this, otherwise produce nothing at all". Wrapping the array in it makes an empty array expand to zero arguments instead of exploding. You only need it where the array is legitimately allowed to be empty.

tick-issue-criterion.sh, where --repo may be absent.

Text & I/O

>   >>   <   2>&1   2>/dev/null

Redirection

Every process starts with three numbered streams: 0 stdin, 1 stdout, 2 stderr. Redirection rewires them.

  • > file — send stdout to the file, truncating it to empty first. That truncation happens the instant the line is parsed, before the command runs — the classic way to destroy a file you meant to read.
  • >> file — append instead.
  • < file — feed the file in as stdin.
  • 2>&1 — "make stream 2 go wherever stream 1 currently goes". The & means "this is a stream number, not a filename". Order matters: it copies the current destination of stdout, so it must come after any >.
  • 2>/dev/null — discard stderr, for a command expected to complain.

The convention veri holds to throughout: stdout is data, stderr is commentary. That is what lets a script's output be piped straight into the next one while its status messages still reach a human.

Every script.

while IFS= read -r line || [[ -n "$line" ]]

Reading lines without corrupting them

The canonical safe line-reader. Four independent pieces, each fixing a different default:

  • IFS= — empties the field separator for this command, so leading and trailing whitespace on the line is not trimmed.
  • read — reads one line into the variable, returning non-zero at end-of-file, which ends the loop.
  • -r — raw: do not treat backslashes as escapes. Without it, \n in the input gets mangled.
  • || [[ -n "$line" ]] — the subtle one. If the final line has no trailing newline, read stores it but still returns non-zero, so the loop would drop it. This clause says "keep going if we did read something".

The naive alternatives — for line in $(cat f) — split on spaces rather than newlines and glob-expand the results. They are simply broken.

parse-verdict.sh, next-unchecked.sh.

printf '%s\n' "$x"

printf, and why not echo

echo is inconsistent between shells and platforms: some interpret \n and some do not, and a value beginning with - may be eaten as a flag. printf behaves identically everywhere, and takes an explicit format string, so you control exactly whether a trailing newline appears.

That control is used deliberately: printf '%s\n' restores the newline that $( … ) stripped, while printf '%s' writes a value with no trailing newline at all.

Everywhere data is emitted. echo survives only for fixed literal status strings.

a | b  ·  tee file  ·  "${PIPESTATUS[0]}"

Pipes, tee, and recovering a lost status

a | b connects a's stdout to b's stdin, running both concurrently. tee file sits in the middle: it copies its input to a file and passes it along, letting you save a stream without interrupting it.

But a pipeline reports only the last command's exit status, so the status of a is lost. PIPESTATUS is an array holding the status of every stage, so "${PIPESTATUS[0]}" recovers the first one. It is overwritten by the very next command, so it must be read immediately.

run-leaf.sh — how the leaf's real exit code survives being teed.

:  ·  : > file  ·  while :;

The null command

: is a builtin that does nothing and always succeeds. Two uses appear here: : > file truncates a file to empty (all the work is done by the redirection; the command is just a placeholder), and while :; is an infinite loop, exited from the inside with break.

supervise.sh: both, on adjacent lines.

tmp="$(mktemp)"

Temporary files

Atomically creates a uniquely-named file and prints its path. Using a predictable name like /tmp/myfile instead is both a race condition and a security hole — two concurrent runs collide, and an attacker can pre-create the path. Always paired with a trap so it gets cleaned up.

run-leaf.sh, tick-issue-criterion.sh.

trap 'rm -f "$tmp"' EXIT

Cleanup handlers

Registers a command to run when a signal fires. The pseudo-signal EXIT fires whenever the script terminates — normal end, an set -e abort, or an explicit exit. It is bash's finally block, and the reliable way to guarantee a temp file is removed no matter how the script ends.

run-leaf.sh, tick-issue-criterion.sh.

cmd <<'EOF' … EOF

Here-documents

Feeds a literal block of text to a command as stdin, ending at the delimiter word. Quoting the delimiter — <<'EOF' rather than <<EOF — disables all expansion, so $ and backticks inside stay literal.

Worth knowing chiefly for the constraint it creates: a here-document occupies stdin. A script that needs stdin for real data cannot use one to supply a program — which is exactly why extract-result.sh passes its Python via -c instead.

The test suites; deliberately avoided in extract-result.sh.

awk 'BEGIN{…} {…} END{…}'

awk, and getting data into it safely

A line-oriented text processor: the program is a set of condition { action } rules run against every input line, plus optional BEGIN and END blocks. $0 is the whole current line, print emits it, sub() does one replacement, and index(a,b) finds a literal substring.

Getting shell values into awk is where scripts go wrong: interpolating them into the program text is an injection bug, since the value would be parsed as code. The safe route is the environment, read back with ENVIRON["NAME"]. And exit 3 inside awk becomes awk's exit status, which the shell can branch on.

tick-criterion.sh, entirely.

exec python3 -c '…'

Replacing the process

exec replaces the running shell with the named program rather than starting a child. The new program inherits the same process ID, the same stdin, and returns its exit status directly to whoever called the script. One process instead of two, and nothing in the script can run afterwards — there is nothing left to run in.

extract-result.sh, handing off to Python.

Processes & signals

name() { …; }

Functions

Arguments arrive as $1, $2 … exactly as in a script, and the "return value" is an exit status, not a value — to return data you print it and the caller captures it with $( … ).

Variables are global by default unless declared local. supervise.sh uses that deliberately: its attempt_once function sets status and reason for the main loop to read, which is how it returns four values from something that can only return an integer.

supervise.sh, parse-verdict.sh.

( cmd ) &  →  pid=$!

Subshells and background jobs

Parentheses run commands in a subshell — a forked child with its own copy of all variables, so nothing inside can affect the parent. A trailing & puts the job in the background: the shell starts it and moves immediately to the next line rather than waiting.

That non-waiting is the whole basis of supervision. You cannot watch a process you are blocked on. $! then gives you its PID so you can watch and, if necessary, kill it.

supervise.sh — the single most important line in veri.

set -m  …  set +m

Job control & process groups

Every process belongs to a process group, and signals can be sent to a whole group at once. Non-interactive scripts normally have job control off, so a background job stays in the script's own group — meaning you cannot signal the job without signalling yourself.

set -m turns job control on, which puts each background job in its own new process group, taking its children with it. Enabling it just around the launch is the prerequisite for killing a whole process tree in one signal.

supervise.sh, bracketing the leaf launch.

kill -TERM -$pid  ·  kill -0 $pid

Signals — and the minus sign that matters

kill sends a signal; it does not necessarily kill.

  • A negative PID means the process group. kill -TERM -1234 signals every process in group 1234, not just the leader. This is how you reach a leaf's own children — a test runner it spawned — which would otherwise be orphaned and keep running.
  • -0 sends no signal at all. It only checks whether the process still exists, so it is used to poll "is it gone yet?".
  • -TERM is the polite request: "please clean up and exit". A program can catch it. -KILL cannot be caught or ignored — the kernel destroys the process immediately, with no chance to clean up.

The universal pattern is TERM, wait briefly, then KILL only if still alive. Reaching for KILL first leaves temp files and half-written state behind.

supervise.sh's kill_tree.

wait "$pid"

Reaping a child

Blocks until the named background process finishes. A finished process that has not been waited for stays in the process table as a zombie — this is the call that clears it.

Note what it cannot do here: because it blocks, it is useless for monitoring. veri calls it only after deciding the leaf is done, purely to clean up. Detecting completion has to happen another way — see the rc-file trick.

supervise.sh, one line, after the watch loop ends.

Stage 1 · read the ledger

Where a cycle begins

Before anything runs, the conductor asks one question: what is the next thing to do? The answer comes from a committed markdown checklist, and from the smallest script in the suite.

veri writes its plan to a ledger — a file at .tdd/issue-<n>.md that is committed to git alongside the code. It is an ordinary markdown checklist:

.tdd/issue-42.mdthe ledger
# Plan for #42 — add rate limiting to the public API

- [x] reject a request over the per-minute limit with 429
- [ ] include a Retry-After header on the rejection
- [ ] count limits per API key, not per IP

This file is the source of truth for what is done — not the GitHub issue, which is only a human-facing mirror. Because it is committed in the same commit as the code for that step, git history and the checklist can never disagree. That is what makes a run resumable: if veri dies halfway, re-running it reads this file and continues from the first unticked line.

next-unchecked.sh

The text of the first unchecked step

Nothing. It is a pure text filter.
next-unchecked.shL14–25 of 25
set -euo pipefail

re='^[[:space:]]*- \[ \] (.*)$'

while IFS= read -r line || [[ -n "$line" ]]; do
  if [[ "$line" =~ $re ]]; then
    printf '%s\n' "${BASH_REMATCH[1]}"
    exit 0
  fi
done

exit 3

Twelve lines, and every one of them is a construct from the primer. Reading it in order:

  • The regex is stored in a variable so that =~ $re can reference it unquoted — quoting the pattern on the right of =~ would make it a literal string and match nothing. It says: optional indentation, then - [ ] with exactly one space in the brackets, then capture everything else as group 1.
  • The loop is the full four-part safe line reader. A ledger is human-edited markdown, so it may well end without a trailing newline — the || [[ -n "$line" ]] clause is what stops the last step being silently invisible.
  • The first match wins. BASH_REMATCH[1] holds the captured description, and the script prints it and exits immediately. Steps must be done in order, so there is no reason to look further.
  • Falling off the end means done. Reaching line 25 means no unchecked box was found anywhere, and it exits 3.
Why 3 and not 1

"Every step is complete" is not a failure — it is the successful end of the loop, and the signal to go open the pull request. But it is not a success either, because there is no step to return. Giving it a third code lets the conductor write one unambiguous branch: 0 run a cycle, 3 open the PR, anything else something is wrong. Had this returned 1, "we finished the issue" would be indistinguishable from "the script broke".

The design payoff

Notice what the script prints: the step's own text. That same string is later handed to tick-ledger.sh as the substring to search for when checking the step off. The output of reading is the input to writing, so the two can never drift apart — no IDs, no line numbers, no index to keep in sync.

Stage 2 · run a leaf

Launching something you do not trust

The conductor now needs a developer leaf to write a failing test. That leaf is an LLM subprocess that might take five minutes, might finish in ten seconds, and might hang forever. Three scripts turn that into a bounded, observable operation.

These three nest inside one another, outermost first — and the outermost is the only one the conductor is ever allowed to call:

the nestingstage 2
supervise.sh          watches the clock, owns the log, kills what hangs
  └─ run-leaf.sh      actually invokes `claude -p`, streaming
       └─ extract-result.sh   recovers the final answer from the stream

supervise.sh — the watchdog

This is the heart of veri and the most systems-heavy script in it. The problem it solves: you are about to start a process that will run for minutes doing real work, and you must distinguish three outcomes that a plain cmd && … cannot tell apart — it finished, it failed, or it is never going to finish.

It does this with two independent clocks:

  • Heartbeat — has the leaf produced any output recently? A sliding silence window. This catches a genuine hang.
  • Hard timeout — has it run too long regardless of activity? An absolute wall-clock cap. This catches a leaf that is chattering but never converging.

Everything else in the file is machinery to run those two clocks against a live process.

Line 27 is set -uo pipefail — strict mode with -e deliberately left out, the only script in veri that does this. It has to be: this script's entire job is to run a command that is expected to fail sometimes and observe how. With -e on, the supervisor would die alongside the first leaf that returned non-zero, which is precisely the event it exists to report.

Line 30 takes the leaf's <name> with a required-argument assertion, and line 31's shift then discards argument 1 and renumbers the rest, so that from here on "$@" is exactly the command to run and nothing else. Line 32 checks at least one argument survived, using || as a compact "if that failed, do this" — and note it exits 2, because a bad invocation is a broken caller, not a failed leaf.

Lines 33–36 are the tunables, each a ${VAR:-default}. Lines 39–40 name two files derived from <name>: a log, which is about to serve as the heartbeat sensor, and an rc file, which is about to serve as the completion signal.

Three helpers

mtime_of() {  # seconds-since-epoch of $1's last modification, portable across BSD/GNU
  stat -f %m "$1" 2>/dev/null || stat -c %Y "$1" 2>/dev/null || echo 0
}
now() { date +%s; }

kill_tree() {
  kill -TERM -"$pid" 2>/dev/null || kill -TERM "$pid" 2>/dev/null
  # brief grace, then make sure it is gone
  for _ in 1 2 3 4 5; do kill -0 "$pid" 2>/dev/null || return 0; sleep 0.1; done
  kill -KILL -"$pid" 2>/dev/null || kill -KILL "$pid" 2>/dev/null
}

mtime_of is the heartbeat sensor, and it contains the single best idea in the script. It asks the filesystem when a file was last modified. The || chain exists because there is no portable stat: macOS and BSD spell it -f %m, Linux and GNU spell it -c %Y. Try the first, fall back to the second, fall back to 0. Each failed attempt's complaint is swallowed with 2>/dev/null.

The idea worth stealing

The heartbeat is not a signal the leaf sends. There is no protocol, no keepalive, no cooperation from the leaf at all. It is just the modification time of the log file — and the operating system updates that for free, every time the leaf writes a byte. "Is it alive?" reduces to "was this file touched recently?", which costs one stat per second and works on any program, whether or not it knows it is being watched.

kill_tree is the escalation. Three separate ideas are packed into four lines, all covered by the signals card:

  • The minus sign on line 48. -"$pid" — a negative PID — means signal the whole process group. This matters because claude spawns children: a test runner, a compiler. Signalling only the parent orphans those, and they keep running and keep consuming the machine. The || fallback to a plain "$pid" covers the case where the group does not exist.
  • The polling loop on line 50. kill -0 sends nothing at all; it only tests whether the process still exists. So this reads: five times, check if it is gone — return 0 the moment it is — otherwise wait 100 ms. A grace period of at most half a second.
  • The escalation. -TERM first, which a program can catch and handle cleanly. Only if it is still alive after the grace period does line 51 send -KILL, which cannot be caught. Politeness first, force second, is how every well-behaved process manager works.

Note also the loop variable is named _ — a convention meaning "this value is never used"; the loop runs five times, that is all.

The launch — and the rc-file trick

This is the densest moment in veri. Taken one piece at a time:

Lines 56–57 reset the state. : > "$log" truncates the log to empty — all the work is done by the redirection, and : is just a placeholder command that does nothing. rm -f removes any stale rc file (-f meaning "do not complain if it is not there"). Both matter because this function can be called a second time on a retry, and stale state would make the new attempt look instantly finished.

Line 62's set -m turns on job control just for the launch, which is what places the background job in its own process group. Without this line the leaf would share the supervisor's group, and kill_tree's group-kill would signal the supervisor itself. It is switched off again two lines later — on for exactly one statement.

Line 63 is the launch. Reading it left to right:

  • ( … ) & — a subshell, run in the background. The background part is the entire point: the script does not wait, so it can go on to watch. You cannot supervise something you are blocked on.
  • "$@" — the leaf command and its arguments, correctly quoted, each argument staying one argument.
  • >"$log" 2>&1 — stdout to the log, then stderr to wherever stdout now goes. All leaf output, of both kinds, lands in the one file the heartbeat is watching. Had the order been reversed, stderr would have gone to the terminal and its activity would not have counted as a heartbeat.
  • ; echo $? > "$rcfile" — the trick. $? is the leaf's exit status, and the instant the leaf exits on its own, the subshell writes that number into a small file.
Why not just use wait?

Because wait blocks — and blocking is the one thing a watchdog cannot do. The supervisor needs to check two clocks every second, so it can never sit still waiting for an answer.

So instead of asking, it lets the finished process leave a note. The existence of the rc file means "I finished by myself"; its contents are the status. The watch loop just checks whether the note has appeared yet. It is a non-blocking completion signal built out of nothing but a file — and it also cleanly distinguishes the leaf chose to exit from we killed it, because a killed leaf never reaches the echo.

Line 68 initialises the three variables the watch loop will set. They are deliberately global: a bash function can only return an integer, so attempt_once communicates its four-way result by assigning to status and reason for the caller to read.

An infinite loop that checks three conditions each second, in priority order, and breaks out on the first that holds.

1 · Did it finish on its own? (L71–75) The note has appeared. Read it — with a || echo 1 fallback in case of a partial write — and map the leaf's own status: zero becomes success, anything else becomes failure. Note what this preserves: a leaf that chose to exit non-zero is a 1, a real answer. Only a leaf we had to kill becomes 2.

2 · Has the hard cap blown? (L77–79) (( … )) gives real integer maths where variables need no $, so t - t0 >= timeout reads like any other language. Total elapsed time, regardless of how busy the leaf has been.

3 · Has it gone quiet? (L80–87) silence is now minus the log's last-modified time — note $( … ) nested inside the arithmetic, which is allowed and evaluates first. If that exceeds the window, the leaf has produced nothing for too long and is killed.

A one-character decision with a comment three lines long

Line 84 tests silence > heartbeat, strictly greater — not >=. The reason is that date +%s has only whole-second resolution, so at a second boundary the subtraction can read about one second high. With >=, a perfectly healthy leaf that had just been relaunched could be measured at exactly the window and killed for it.

Strict > buys one second of slack, which is enough to absorb the rounding while a genuine hang keeps climbing and still trips. This is the kind of bug that only appears under real timing, on someone else's machine — and there is a test pinning it.

Line 91 reaps the child. By now the leaf is finished or killed, so wait no longer blocks meaningfully; it clears the zombie entry from the process table. The || true is the standard swallow-the-error idiom — the process may already have been reaped, and failing here would be noise.

Line 99 carries the whole policy. Read it as: "if the status is not killed-stuck, break". Two budgets that must never be confused

This retry is the liveness axis: the leaf never produced an answer. Elsewhere veri has a second, entirely separate budget — REVISE_BUDGET, the verdict axis: the leaf produced an answer and the blind verifier rejected it.

Collapsing them would be a real bug. Retrying a rejected verdict is just hammering the same wall; retrying a hang is reasonable. And they classify differently when they run out — a spent liveness budget is a system failure, a spent verdict budget is a process failure. Keeping them apart here is what makes that distinction available in stage 5.

The closing case maps the status string to veri's exit codes, with a defensive *) branch treating any unforeseen state as broken rather than as success — failing closed. Then the last three lines execute the stdout/stderr contract exactly: the status line, including a ${reason:+ — $reason} that appends the separator only if a reason exists, goes to stderr; the leaf's entire captured output goes to stdout; and the exit code carries the verdict.

That last arrangement is what lets a caller write out="$(supervise.sh …)" and get clean leaf output with none of the supervisor's own chatter mixed in — which is exactly what verify.sh does in the next stage.

Why the leaf streams — the heartbeat's other half

Line 44 is where the supervisor's design and this script's design meet. The flag is --output-format stream-json, and it is not about the format:

Output modeWhat the log file doesWhat the supervisor concludes
text (default) Nothing at all until the very end, then everything at once Silent for minutes → kills a perfectly healthy leaf
stream-json One JSON event per line, continuously, as the leaf works mtime keeps moving → correctly reads it as alive

In text mode a working leaf and a hung leaf are indistinguishable — both produce no output. Streaming is what makes the 45-second silence window a real measurement rather than an arbitrary guess, and it is why the default heartbeat can be so much shorter than the 900-second timeout.

The pipeline on line 44 sends the stream through tee, which writes it to the temp file and passes it on to stdout — where the supervisor captures it as the log. One stream, two consumers, no buffering delay.

But piping loses the exit status of the first stage: the pipeline reports tee's status, and tee almost always succeeds. So line 45 reads "${PIPESTATUS[0]}" — the array of per-stage statuses — to recover what claude actually returned. It must be read on the very next line, because the next command overwrites it. And the whole pipeline is bracketed in set +e … set -e, because with pipefail active a failing leaf would abort the script before line 45 ever ran.

Line 49's bare printf '\n' guarantees the appended result starts on a fresh line even if the stream ended mid-line, and line 50 appends the clean final answer. Line 52 then exits with the leaf's own status — so the supervisor is judging the leaf, not this wrapper.

exec python3 -c '
import sys, json

result = None
for line in data.splitlines():
    s = line.strip()
    if not s.startswith("{"):
        continue
    try:
        obj = json.loads(s)
    except ValueError:

        result = obj["result"]          # last result event wins

else:
    sys.stdout.write(result if result.endswith("\n") else result + "\n")
'

Three decisions here are worth more than the code itself.

Why Python at all. Parsing JSON in pure bash is a known-bad idea, and jq — the usual answer — is not installed by default anywhere. Python 3 is present on every macOS and essentially every Linux box veri would run on. This is a dependency judgement, not a language preference.

Why exec, and why -c instead of a here-document. exec replaces the shell with Python rather than spawning a child, so Python inherits the same stdin and its exit status goes straight back to the caller. And the program is passed as a -c argument specifically because a here-document would occupy stdin — the very channel the event stream is arriving on. The comment on line 14 of the source calls this out; it is a constraint, not a style choice.

Note the program is wrapped in single quotes, so the shell performs no expansion on it — the $ and backslashes inside are safe. That is also why the Python uses double quotes internally: single ones would end the shell string.

Why it tolerates everything. The loop skips lines that do not begin with {, and wraps json.loads in a try. A stream can carry log noise, partial lines from a killed process, or a warning banner; none of that should crash extraction. It keeps the last result event, since a resumed session can emit more than one.

The passthrough is the testability hook

If no result event is found, the script writes its input straight back out unchanged. That single if result is None branch is what lets every test in the suite replace claude with a stub that just echoes plain text: extraction becomes a no-op, and the rest of the pipeline behaves identically. A pure-JSON parser would have forced every test to construct valid stream-json.

Stage 3 · verify the claim

The part veri is named after

A developer leaf has written a test and says it fails correctly. You cannot ask the author — it will defend its own work. So veri asks a different agent that has never seen the author's reasoning, and requires it to run the test itself.

The obvious way to build this is to instruct the verifier not to look at the developer's rationale. veri does something stronger: it makes the rationale structurally unable to arrive. Three scripts compose into one verb, and the guarantee lives in the shape of the first one's arguments.

Why not sed

The comment on line 38 flags a real trap. sed 's/{{SPEC}}/'"$spec"'/' is the reflexive way to do this, and it is wrong here: sed is a pattern engine, so & in the replacement expands to the whole match, \1 to a capture group, and a / anywhere in the value ends the command. An issue body is arbitrary human text — file paths, URLs, shell snippets — and will contain all three.

Bash's ${v//a/b} is a literal replacement with no pattern language in the replacement half, so the spec arrives verbatim. The general lesson: reach for sed when you want a pattern, and parameter expansion when you want a string.

The verifier leaf is launched with --disallowedTools Write Edit MultiEdit NotebookEdit. It may read every file in the repository and run the test command, but it cannot modify anything.

  • ${1%%[![:space:]]*} — from $1, cut the longest suffix starting at the first non-space character. What survives is exactly the leading whitespace.
  • ${1#"…"} — remove that whitespace from the front of $1.

So: compute the leading whitespace, then strip it. rtrim is the mirror image with # and % swapped. Both are done entirely in the shell — no sed, no tr, no subprocess.

Lines 35–40: the last VERDICT: wins. The loop iterates over "${!lines[@]}" — the indices, not the values — and records the index of every match without stopping, so vidx ends up at the last one. That is deliberate: a model may well write "my verdict is leaning toward REJECT" while reasoning, and only the final block is authoritative. The character-class spelling [Vv][Ee][Rr]… is how you get a case-insensitive match in bash 3.2.

Line 47 re-runs the match on the winning line purely to repopulate BASH_REMATCH, which the loop's later iterations overwrote. Then line 51 takes the first token with ${tail%%[[:space:]]*} and line 52 upper-cases it through tr, so pass, Pass and PASS all land in the same branch.

Exit-code-as-verdict

Line 53's case converts the verdict word into 0 / 1 / 2. The source comment names why this is the right shape: it mirrors how a test itself reports. A passing test exits 0, a failing one exits non-zero — and now the verifier's judgement arrives in the same currency, so the conductor branches on it exactly as it would on a test run.

# Inline reason = the verdict line after the word, with a leading separator stripped.
inline="${tail#"${tail%%[[:space:]]*}"}"   # drop the first (verdict) token
inline="$(ltrim "$inline")"
for sep in '—' '–' '-' ':'; do inline="${inline#"$sep"}"; done
inline="$(ltrim "$inline")"

# Following reason = the lines after the verdict line, with a leading REASON: label
# stripped from the first of them. This is the common, multi-line-capable form.
following=""
if (( vidx + 1 < ${#lines[@]} )); then
  rest=( "${lines[@]:vidx+1}" )
  if [[ "${rest[0]}" =~ ^[[:space:]]*[Rr][Ee][Aa][Ss][Oo][Nn]:[[:space:]]*(.*)$ ]]; then
    rest[0]="${BASH_REMATCH[1]}"
  fi
  printf -v following '%s\n' "${rest[@]}"
fi

# Prefer a non-empty following block; otherwise the inline reason. Trim the edges
# (including blank leader/trailer lines) but preserve internal line breaks.
reason="$following"
reason="$(rtrim "$reason")"
[[ -z "$reason" ]] && reason="$inline"
reason="$(ltrim "$reason")"
reason="$(rtrim "$reason")"

# A leaf often wraps its verdict block in a ``` (or ~~~) code fence; the opening fence
# sits above the VERDICT line and is ignored, but the closing fence trails the reason.
# Drop a trailing fence-only line so it doesn't leak into the mirrored reason.
fence_re='^[[:space:]]*(```|~~~)[[:space:]]*$'
last="${reason##*$'\n'}"
if [[ "$last" =~ $fence_re ]]; then
  if [[ "$reason" == *$'\n'* ]]; then reason="${reason%$'\n'*}"; else reason=""; fi
  reason="$(rtrim "$reason")"
fi

printf '%s\n' "$reason"
exit "$code"

The second half handles the reason, and every branch here defends against one specific way a model formats an answer:

  • Two accepted shapes. The reason may be inline (VERDICT: REJECT — the test errors on import) or on following lines after a REASON: label. Both are parsed; the following block is preferred when non-empty, since it is the documented form and can span multiple lines.
  • Line 62 strips whichever dash the model chose. The loop walks an em dash, an en dash, a hyphen and a colon, removing at most one of each from the front. Models are inconsistent about this and the separator should not end up in text mirrored to GitHub.
  • Line 68 slices the array from just past the verdict line with "${lines[@]:vidx+1}", and line 73 rejoins it with printf -v — writing straight into a variable, which avoids $( … ) eating the trailing newline.
  • Lines 87–92 remove a trailing code fence. ${reason##*$'\n'} takes the text after the last newline — the final line — and if it is nothing but ``` or ~~~, drops it. The opening fence sits above the VERDICT line and is ignored naturally; only the closing one trails into the reason.

None of this is elegant, and it does not need to be. It is a boundary layer between a probabilistic producer and a deterministic consumer, and every clause is a real observed failure mode with a test behind it. Extracting it here is what keeps that mess out of the conductor.

Stage 4 · record the result

One transform, two destinations

The verifier said PASS. Now the step must be marked done — in the committed ledger, which is the truth, and in the GitHub issue, which is the mirror. Both edits are the same edit, and veri writes it once.

This stage is the clearest example in the repository of a structural habit worth naming: a pure transform in the middle, with thin I/O wrappers on the outside. The transform is unit-tested exhaustively and knows nothing about files or networks; the wrappers know about files and networks and contain almost no logic.

tick-criterion.sh — the transform

Usage
tick-criterion.sh <matcher> < body.md > new.md

Flips the first unchecked - [ ] containing <matcher> to - [x]

tick-criterion.shL12–24 of 24
set -euo pipefail

MATCHER="${1:-}" awk '
  BEGIN { m = ENVIRON["MATCHER"]; done = 0 }
  {
    if (!done && $0 ~ /^[[:space:]]*-[[:space:]]\[ \]/ && (m == "" || index($0, m) > 0)) {
      sub(/\[ \]/, "[x]")
      done = 1
    }
    print
  }
  END { if (!done) exit 3 }
'

Line 14 is the security-relevant line. MATCHER="${1:-}" awk '…' uses per-command environment to hand the matcher to awk, and the awk program reads it back with ENVIRON["MATCHER"].

The bug this avoids

The tempting alternative is to interpolate the value into the program text: awk "/$matcher/ { … }". That is an injection vulnerability — the matcher would be parsed as awk code, not compared as data. Since the matcher here is a step description that ultimately came from a GitHub issue body, it is untrusted input containing arbitrary punctuation.

Routing it through the environment keeps the program text constant and the value as data. Note the awk program is in single quotes, so the shell expands nothing inside it — $0 reaches awk as awk's "whole current line", not as the shell's script name.

The awk program itself is three rules:

  • BEGIN — before any input: read the matcher, set a done flag.
  • The bare block runs for every line. The condition is a three-way and: not yet done, the line looks like an unchecked box, and either the matcher is empty or index($0, m) > 0 — a literal substring search, not a regex. If it holds, sub() replaces the first [ ] with [x].
  • print is outside the if, and that placement is the whole contract: every line is emitted, modified or not. This is a filter that changes exactly one line and passes the rest through byte-for-byte.
  • END — if nothing was ticked, exit 3. awk's exit status becomes the script's, so a caller can branch on it.

3 again, and for the same reason as in stage 1: "no box matched" is not a crash and not a success. It usually means the matcher drifted from the step text, which a caller may want to treat as benign or fatal depending on context — so the script reports it precisely and lets the caller decide.

tick-ledger.sh — the local wrapper

tick-ledger.shL11–18 of 18
set -euo pipefail

file="${1:?usage: tick-ledger.sh <ledger-file> <matcher>}"

Eight lines, and the only two that do anything are the last two — but their order is load-bearing.

Why not just pipe it

The obvious one-liner is tick-criterion.sh "$m" < "$file" > "$file". That destroys the ledger. As the redirection card notes, > file truncates the target the instant the shell sets up the command — before the reader has read a byte. You get an empty file.

So line 17 runs the transform to completion, capturing the entire result into memory first. Only then does line 18 write it back. And the || exit $? means that if the transform failed — exit 3, nothing matched — the script exits with that same code and line 18 never runs, leaving the ledger untouched rather than rewritten with unchanged content.

Note that $? here is read on the same line as the command that set it — one line later it would already have been overwritten.

It is worth contrasting this against build-verify-prompt.sh, which has the same read-into-memory-and-transform shape but no write-back. That single > "$file" is the entire difference between a script that modifies a file and one that only reads it.

The conductor calls this and then commits the ledger in the same commit as the step's code. That atomicity is what makes resume trustworthy: git history and the checklist cannot disagree, because they land together or not at all.

tick-issue-criterion.sh — the remote wrapper

tick-issue-criterion.shL14–39 of 39
set -euo pipefail

n="${1:?usage: tick-issue-criterion.sh <issue-number> <matcher>}"
matcher="${2:-}"

HERE="$(cd "$(dirname "$0")" && pwd)"

repo_args=()

  repo_args=(--repo "$GH_REPO")
fi

new="$(printf '%s' "$body" | "$HERE/tick-criterion.sh" "$matcher")" || {

  if [[ "$status" -eq 3 ]]; then
    echo "tick-issue-criterion: no unchecked criterion matched '$matcher' on #$n" >&2
  fi
  exit "$status"
}

printf '%s' "$new" > "$tmp"
gh issue edit "$n" "${repo_args[@]+"${repo_args[@]}"}" --body-file "$tmp" >/dev/null

The same three moves as tick-ledger.sh — read, transform, write back — with a network on both ends instead of a file. gh is GitHub's CLI; --json body -q .body fetches just the issue body as raw text.

Line 26 contains the ugliest expression in veri, and it is there for a concrete reason. "${repo_args[@]+"${repo_args[@]}"}" is the empty-array guard: when GH_REPO is unset the array is empty, and on bash 4.3 and earlier — the macOS system bash — expanding an empty array under set -u aborts the script. The guard makes it expand to no arguments at all instead.

Lines 28–34 handle the failure explicitly rather than with a bare || exit $?. The { … } block captures the status, and when it is 3 it writes a human-readable explanation to stderr naming both the matcher and the issue — then exits with the original code either way. Worth the extra six lines here because this failure means the ledger's wording and the issue's wording have drifted, which a human has to reconcile.

Lines 36–39 write back through a temp file rather than passing the body as a command-line argument. Issue bodies are long and contain newlines, quotes and backticks; --body-file sidesteps both argument-length limits and every quoting hazard. The mktemp + trap pair guarantees cleanup, and >/dev/null discards gh's success chatter — this script's stdout is not a data channel and should stay silent.

Stage 5 · or bail

Stopping in a way someone can act on

Not every run finishes. When veri gives up, the one thing that determines what a human does next is why — and that answer is too important to be improvised each time.

Sixteen lines and a single case. Mechanically it is a lookup table; the interesting question is why it exists at all when the conductor could just decide.

CauseWhere it comes fromClass
killed-stuck supervise.sh exited 2 after its retry budget system
no-verdict verify.sh exited 2 — unparseable, or the verifier hung system
revise-exhausted A step spent its REVISE_BUDGET and the verifier still says REJECT process

The distinction is the one the whole exit-code convention has been building toward:

  • A system failure means the plumbing broke — a leaf hung, a verdict was gibberish. veri could not do its job. Someone should look at the logs.
  • A process failure means the methodology spoke — everything worked exactly as designed, and a blind verifier looked at the work three times and refused it. Nothing is broken. The approach was wrong, or the step was too big.

Those demand completely different human responses, which is why the label is worth computing deterministically rather than letting a language model phrase it fresh each time. A model asked to characterise its own failure will drift — and it has an obvious bias toward "the tooling let me down."

Fail closed on an unknown cause

The *) branch exits 2 rather than guessing a default. An unrecognised cause token means the conductor passed something the design does not account for, and quietly labelling that system would bury a real gap behind a plausible word. Refusing to answer surfaces it. This is the same fail-closed instinct as the defensive *) branch in supervise.sh: when the state is unforeseen, treat it as broken, never as fine.
