# PRD 029 requirements: an older case a step supersedes is adapted, not a dead end

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status: DRAFT, from the 2026-11-13 efficiency analysis. Mario handed the decisions to the
planning session on 2026-11-13 ("keep going by yourself … solve the stoppers"), so D1–D5 are that
session's calls, each with the alternative it rejected. 029.1 carries rows and is built by hand by
the same session. 029.2 to 029.4 are outlines; nothing is filed.**

## The goal

A run stops bailing when a step legitimately changes what an older test case pins. Today the
green leaf may not edit tests, so it reports the older case as superseded; the step has one free
reroute to act on such a report, and once that is spent every later report is answered with
`revise`, which green cannot act on. The run bails `revise-exhausted`, and a resume adds by hand
the step the run could have added itself: a test-only step, ahead of the stuck one, that adapts the
older case.

Target: no bail whose resume does nothing but add a test-only step ahead of the stuck step
(6 of the 61 bails read; see *Facts*). The acceptance criteria are the behaviours that force it.

## What this PRD does not hold

- **`⟦replaces-case⟧`**: it covers a bash case swapped for a pytest one (ADR-0027), not this.
- **The revise budget's size** (`REVISE_BUDGET`): the dead end is the route, not the count.
- **Bails that are system failures**: PRD 012 and the fixes already landed (#3746, #3696).
- **How a plan is written**: 029.4 changes what the plan verifier is shown, not the planner.

## Decisions

| ID | Decision | Why, and what was rejected |
|---|---|---|
| D1 | The fix leaves never delete, rename or merge a case, and are told that a case which now asserts the same thing as another stays. The older case is still rewritten to pin the criterion. | On the `red` and `supersede` routes the edited case is red evidence: verify-red requires it to fail on the unmodified code. Rejected: telling the leaf to change only what the criterion makes false, which the first draft of 029.1 did; a review showed such a case can pass on the unmodified code, which those routes send to verify-pin or reject. Adapting without pinning is the `supersede-diff` route's job. Also rejected: a guard script, which catches the deletion after the leaf has spent its attempt. |
| D2 | A superseded-case report made after the step's free reroute is spent becomes a test-only step inserted ahead of the current one, by the route script, as its `fixture` route already inserts one. It does not count against the free reroute. | Every resume did exactly this by hand. Rejected: a second free reroute, which keeps the dead end one report further on. |
| D3 | The inserted step is an ordinary step with its own blind verification, and counts toward `VERI_STEP_GROWTH`. | #3618 shows a reported case can be a real regression; the verifier, not the route, judges the edit. The growth budget is the existing bound on a run that keeps adding steps. |
| D4 | The exhausted leaf gets a third answer: a test-only step ahead of this one. | It is the answer the six bails needed and could not give. |
| D5 | The plan verifier is shown the test cases that touch the files a plan's steps name, and the planning rule is widened to inputs, fakes and call sequences. It comes last. | It prevents the class at the source but is the largest change and would not have caught #3758; D1 to D4 make the run recover whatever the plan missed. |

## 029.1 — the fix leaves delete no case

**What you get:** a `red-contradicted` or `red-supersede` leaf edits the named older cases and
removes no case, so the step's own Red case survives it.

**Depends on:** nothing.

| ID | Requirement | Why |
|---|---|---|
| OC1 | `prompts/develop-red-supersede.md`, in the paragraph after `{{CASES}}`, tells the leaf to delete, rename or merge no case, in the named files or any other, and that a case which now asserts the same thing as another, the step's own new case included, stays as it is. | D1; the deletion is what the verifier rejected, spending the step's one free reroute. |
| OC2 | `prompts/develop-red-contradicted.md` carries the same instruction for its one named case, in the paragraph after `{{CASE}}`. | The same failure (#3686, #3771). |
| OC3 | `prompts/develop-red-contradicted.md`'s numbered item tells the leaf to update the case in its suite's own style and to create no suite and no new case; it no longer says "add it" or "create one". | The item contradicted the prompt's own opening ("NO new test"). |
| OC4 | `prompts/develop-red-contradicted.md` is a graded unit with rows of its own. | Its wording caused bails and nothing graded it. |
| OC5 | Neither prompt tells the leaf which case is the step's own: the instruction is unconditional. | The rendered prompt does not name the step's Red case (`build_develop_prompt.py`), so a rule that depended on knowing it could not be followed. |
