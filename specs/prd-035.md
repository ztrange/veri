# PRD 035 requirements: what each phase of a run costs, and what it catches

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status: written 2026-11-16 against `0abc3aec0e`. D1–D8 are Mario's answers of 2026-11-16 to
three rounds of questions. 035.1 and 035.2 carry rows; 035.3 to 035.7 are outlines. Nothing is
filed and nothing has landed. `--json`, `<issue>.metrics.json` and every JSON key named below are
working names.**

## The goal

After some weeks of runs, Mario can decide for every phase of a run (red, green, refactor, each
verifier, grading, adjudication, preflight, the suite, CI, the merge) whether to keep it, reinforce
it or remove it, from numbers: how long it takes, what it costs when it runs an agent, how often it
fails, and what its failures led to.

Veri computes those numbers itself and writes them where a program outside veri (a dashboard) can
read them, so the definition of each metric lives in one repository.

## What this PRD does not hold

- **The dashboard.** It lives in `ztrange/veri-dashboard`; reading the new file is that
  repository's plan. Veri still holds no dashboard path, rule or test (PRD 014).
- **Acting on the numbers.** Switching a verifier off is PRD 018's `VERI_SKIP_VERIFY`; lowering
  what a leaf costs is PRD 024. This PRD changes no budget, no model and no verifier.
- **Rates over many runs.** Veri writes counts per issue; a reader sums them (D4).
- **A model judging whether a phase was useful.** Every metric is computed from events (D3).

## Facts

Read on 2026-11-16 with `origin/main` at `0abc3aec0e`, on the development Mac.

**What veri records.** Every script appends one JSON line per event through `event.sh`
(`veri/event.py`) to `.tdd/events.jsonl` and to the journal,
`$VERI_HOME/runs/<owner>-<repo>/<issue>.jsonl`. Each line carries `ts`, `awake`, `issue`, `actor`,
`phase`, `step`, `event`, `attempt` and `skill_commit`. The events that matter here
(`veri/event_table.py`): `launch` (name, model, effort), `exit` (secs, status, cause), `usage`
(cost, tokens, turns, model, `duration_ms`), `verdict` (PASS, REJECT, malformed), `grading`,
`adjudicated`, `retry`, `relaunch`, `revise`, `bail` (cause, classification), `step-start`,
`step-done`, `step-added`, `done` (wall and awake seconds).

**What veri already computes.** `metrics.sh <n>` (`veri/metrics.py`) folds the events into a
`Fold` (`fold(issue, path, ledger)`, `:645`) and prints it as markdown, saved as
`.tdd/issue-<n>-metrics.md` and put in the PR body. Per phase and per model: attempts, PASS,
REJECT, kills, wall seconds, API seconds, turns, tokens, dollars (`PHASE_COLUMNS`, `:107`). Per
ledger step: the same plus retries and no-verdict (`STEP_COLUMNS`). Also rework and waste, refactor
passes, revise-green outcomes, and the conductor's own spend per session, read from the
conductor's stream log (`conductor_sessions`, `:157`), with a flag for when it cannot be priced.
None of it is written in a form a program can read.

**What a reader outside veri gets today.** `skills/tdd/PUBLISHED.md` publishes two files: the
journal and the optional `report-owed.json`. A dashboard wanting any figure above must fold the
journal itself.

**What the events cannot say today.**

- What a REJECT led to: nothing links it to the fix, the adjudication or the bail that followed.
- Which leaf an `exit`, `usage` or `verdict` belongs to, except by pairing it with the preceding
  `launch` (only `launch` carries `name`); which leaf a `retry` killed.
- Which run of an issue an event belongs to: a journal merges every resume (these 20 hold 137
  `conductor-start`s), and a step is identified by its text, so a reworded step is a new step.
- Anything about most non-leaf phases:

| Phases | Start event | End event | Outcome |
|---|---|---|---|
| Plan, refactor loop, structural pass, merge | none | one event | partly |
| Preflight, push, CI wait and flake rerun, readying the PR, full suite before readying, rebase | none | none | failure only; success writes nothing |
| Baseline suite, claim, worktree setup, spec capture, ledger commit and tick, draft PR, metrics report, release | none | none | none |

- What the conductor spent per phase: its spend is known per session, not per phase.

## 035.1 — `metrics.sh <n> --json` prints the run's metrics as JSON

Mario gets: any script can read what a run's phases and steps took, cost and returned, for every
leaf phase veri has today, without parsing markdown. Depends on nothing.

One capability: the same fold `metrics.md` is printed from, serialized. It adds no new metric.

| ID | Requirement | Why |
|---|---|---|
| MJ1 | `metrics.sh <n> --json` prints one JSON object to stdout and exits 0; `metrics.sh <n>` prints the markdown report exactly as today. | The JSON is a second rendering, not a change to the first. |
| MJ2 | The object is built from the `Fold` that `metrics.fold` returns; the JSON path calls no second fold and reads no event itself. | One definition of each metric: a figure in the JSON and the same figure in `metrics.md` cannot differ. |
| MJ3 | `phases` holds one entry per phase the run launched a leaf for, keyed by phase name, each with `attempts`, `pass`, `reject`, `kills`, `wall_seconds`, `api_seconds`, `turns`, the four token counts and `cost_usd`. | Failure rate, run time and cost per phase are the request (D2, D6). |
| MJ4 | `steps` holds one entry per ledger step, in ledger order, each with the step's text, the keys of MJ3, `retries`, `no_verdict` and `wall_seconds` from `step-start` to `step-done`. | Time and cost add up per step (D2). |
| MJ5 | `conductor` holds `cost_usd`, `turns`, `sessions`, `model`, and `priced` (`true`, `false` when no session carries a price, `"partial"` otherwise) and `estimated`. | The conductor is an agent whose cost belongs to the run (D8); a reader must know when the figure is missing or partial. |
| MJ6 | `total` holds the figures of `metrics.md`'s `| total |` row, and `total.includes_conductor` says whether the conductor's spend is in it. | P7: a cost is the total row, and phase or step rows are never summed. |
| MJ7 | `run` holds `issue`, `outcome` (the outcome `metrics.md` states), `wall_seconds` and `awake_seconds` when the run wrote `done`, and `bails`, a list of `{cause, classification, phase, step}` in order. | Failure by phase needs the bails attributed to a phase. |
| MJ8 | Every count, duration and cost is a JSON number; a figure the fold marks unknown is `null`, never `0` and never a string. | A reader that sums must tell "nothing" from "not known". |
| MJ9 | The object holds no rate, percentage or average. | D4. |
| MJ10 | Exit codes are `metrics.sh`'s own: an argument error or an unreadable log is exit 2 with nothing on stdout, under `--json` as without it. | Exit codes are the API; a half-printed object must not be parseable as a whole one. |
| MJ11 | `SCRIPTS.md`'s `metrics.sh` entry states `--json` and names the top-level keys. Graded by the issue's `## Requirements` row. | The catalogue is where a script's output is looked up. |

## 035.2 — the metrics of every issue are a published file, kept current

Mario gets: the dashboard can show a run's metrics while it runs and after its worktree is gone,
by reading one file. Depends on 035.1.

| ID | Requirement | Why |
|---|---|---|
| MF1 | After an `exit`, `step-done`, `bail` or `done` event whose line carries an issue is appended to the journal, `<issue>.metrics.json` beside that journal holds the object of 035.1 for that issue, computed with that line included. | D5: settled numbers at most one phase behind. |
| MF2 | No other event rewrites the file. | D5: not every event pays for a fold. |
| MF3 | The file is written to a temporary name in the same directory and renamed into place, so a reader never sees part of it. | PRD 030 D5. |
| MF4 | When computing or writing the file fails, the event line is in the journal and in `.tdd/events.jsonl` as if no metrics file existed, the event call exits as it would have, and one stderr line names the file and the error. | Telemetry never bails a run (PRD 014 JR3). |
| MF5 | The file is computed from the journal, so it covers every run of the issue and can be written after the run's worktree is removed. | The journal is the only log that outlives a run. |
| MF6 | A run that writes no journal (no issue, or no `origin` remote) writes no metrics file and prints nothing about it. | It follows the journal's own rule. |
| MF7 | `PUBLISHED.md` lists the file as a third published file: its path, its writer, when it is rewritten, that its keys are append-only and that it carries no version key. Graded by the issue's `## Requirements` row. | A reader may rely only on what the page states (PRD 030 D2, D5). |
| MF8 | `PUBLISHED.md` states each top-level key and each key of a phase, step, conductor, total and run entry, with its type and whether it may be `null`; a case fails, naming the key, when the object 035.1 builds and the page differ in either direction. | The page cannot drift from the code (PRD 030 ET2's rule, applied to this file). |
| MF9 | A case pins that `run_conductor.py`'s behaviour on a leaf's exit is unchanged when the metrics file's directory is not writable. | MF4's failure path, watched to fail. |

Target, not a criterion: a rewrite takes well under a second on a journal of the size measured
above. The PR body quotes the measured time on one real journal, before and after.

## 035.3 — what each REJECT led to (outline)

Mario gets: per verifier phase, how many of its REJECTs were caught, overturned and unresolved
(D3), and per developer phase how many leaves passed first try and how many revise cycles the rest
took. This is the "did it detect a real issue" number. Depends on 035.1.

Likely needs the events to tie a REJECT to what followed (the facts list why they cannot today);
whether that is a new key or a pairing rule in the fold is settled when its rows are written.

## 035.4 — an event names its leaf, its run and its step (outline)

Mario gets: metrics per run of an issue and not only per issue, a step that keeps its identity when
reworded, and per-leaf figures that need no pairing with the preceding `launch`. Depends on
nothing; 035.3 is simpler after it.

## 035.5 — non-leaf phases report their start, end and outcome (outline)

Mario gets: run time and failure rate for the phases the journal is silent on today (the third
facts table). Depends on 035.1 for the phases to appear in the JSON. Sliced by group, each worth
having alone: **a** preflight and the baseline suite; **b** push, draft PR, the full suite before
readying, readying, CI wait; **c** plan, refactor loop, structural pass, rebase, merge, release.

## 035.6 — the conductor's spend per phase (outline)

Mario gets: the agent cost of non-leaf phases. Depends on 035.5 (the phases' start and end).

## 035.7 — `metrics.md` shows the new numbers (outline)

Mario gets: caught, overturned and unresolved counts in the PR body, with no dashboard. Depends on
035.3.
