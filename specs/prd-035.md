# PRD 035 requirements: what each phase of a run costs, and what it catches

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status: written 2026-11-16 against `0abc3aec0e`. D1–D8 are Mario's answers of 2026-11-16 to
three rounds of questions. 035.1 and 035.2 are filed as #4203 and #4204. 035.3 to 035.7 got their
rows on 2026-11-16 against `f93cd156a4`, with O1–O3 settled as recommended (D9–D11) and two calls
the rows needed (D12, D13), under Mario's standing rule to follow the recommendations; none of
035.3–035.7 is filed and nothing has landed. `--json`, `<issue>.metrics.json`, every JSON key and
every new event or key named below are working names.**

## The goal

After some weeks of runs, Mario can decide for every phase of a run (red, green, refactor, each
verifier, grading, adjudication, preflight, the suite, CI, the merge) whether to keep it, reinforce
it or remove it, from numbers: how long it takes, what it costs when it runs an agent, how often it
fails, and what its failures led to.

Veri computes those numbers itself and writes them where a program outside veri (a dashboard) can
read them, so the definition of each metric lives in one repository.

## What this PRD does not hold

- **The dashboard.** It lives in `ztrange/veri-dashboard`; reading the new file is that
  repository's plan. Veri still holds no dashboard path, rule or test (PRD 014).
- **Acting on the numbers.** Switching a verifier off is PRD 018's `VERI_SKIP_VERIFY`; lowering
  what a leaf costs is PRD 024. This PRD changes no budget, no model and no verifier.
- **Rates over many runs.** Veri writes counts per issue; a reader sums them (D4).
- **A model judging whether a phase was useful.** Every metric is computed from events (D3).

## Facts

Read on 2026-11-16 with `origin/main` at `0abc3aec0e`, on the development Mac.

**What veri records.** Every script appends one JSON line per event through `event.sh`
(`veri/event.py`) to `.tdd/events.jsonl` and to the journal,
`$VERI_HOME/runs/<owner>-<repo>/<issue>.jsonl`. Each line carries `ts`, `awake`, `issue`, `actor`,
`phase`, `step`, `event`, `attempt` and `skill_commit`. The events that matter here
(`veri/event_table.py`): `launch` (name, model, effort), `exit` (secs, status, cause), `usage`
(cost, tokens, turns, model, `duration_ms`), `verdict` (PASS, REJECT, malformed), `grading`,
`adjudicated`, `retry`, `relaunch`, `revise`, `bail` (cause, classification), `step-start`,
`step-done`, `step-added`, `done` (wall and awake seconds).

**What veri already computes.** `metrics.sh <n>` (`veri/metrics.py`) folds the events into a
`Fold` (`fold(issue, path, ledger)`, `:645`) and prints it as markdown, saved as
`.tdd/issue-<n>-metrics.md` and put in the PR body. Per phase and per model: attempts, PASS,
REJECT, kills, wall seconds, API seconds, turns, tokens, dollars (`PHASE_COLUMNS`, `:107`). Per
ledger step: the same plus retries and no-verdict (`STEP_COLUMNS`). Also rework and waste, refactor
passes, revise-green outcomes, and the conductor's own spend per session, read from the
conductor's stream log (`conductor_sessions`, `:157`), with a flag for when it cannot be priced.
None of it is written in a form a program can read: `metrics.sh` ignores every argument after the
issue number. The `Fold` holds no list of bails (only the run's last ending mark), no step text and
no flag for whether its total includes the conductor. `fold` cannot read a journal with no worktree
beside it: it raises `FileNotFoundError` looking for the run's end (`metrics.py:657`).

**What a reader outside veri gets today.** `skills/tdd/PUBLISHED.md` publishes two files: the
journal and the optional `report-owed.json`. A dashboard wanting any figure above must fold the
journal itself.

## 035.1 — `metrics.sh <n> --json` prints the run's metrics as JSON

Mario gets: any script can read what a run's phases and steps took, cost and returned, for every
leaf phase veri has today, without parsing markdown. Depends on nothing.

One capability: the same fold `metrics.md` is printed from, serialized. It adds no new metric.

| ID | Requirement | Why |
|---|---|---|
| MJ1 | `metrics.sh <n> --json` prints one JSON object to stdout and exits 0; `metrics.sh <n>` prints the markdown report exactly as today. | The JSON is a second rendering, not a change to the first. |
| MJ2 | The object is built from the `Fold` that `metrics.fold` returns: the JSON path reads no event, ledger or log itself, and a figure the `Fold` lacks today (MJ4's step text, MJ6's flag, MJ7's bails) becomes a field of it. | One definition of each metric: a figure in the JSON and the same figure in `metrics.md` cannot differ. |
| MJ3 | `phases` holds one entry per phase the run launched a leaf for, keyed by phase name, each with `attempts`, `pass`, `reject`, `kills`, `wall_seconds`, `api_seconds`, `turns`, the four token counts and `cost_usd`. | Failure rate, run time and cost per phase are the request (D2, D6). |
| MJ4 | `steps` holds one entry per step the events name, in the order `metrics.md` lists them, each with the step's text, the keys of MJ3, `retries`, `no_verdict` and `wall_seconds` from `step-start` to `step-done`. | Time and cost add up per step (D2). |
| MJ5 | `conductor` holds `cost_usd`, `turns`, `sessions`, `model`, and `priced` (`true`, `false` when no session carries a price, `"partial"` otherwise) and `estimated`. | The conductor is an agent whose cost belongs to the run (D8); a reader must know when the figure is missing or partial. |
| MJ6 | `total` holds the figures of `metrics.md`'s `| total |` row, and `total.includes_conductor` says whether the conductor's spend is in it. | P7: a cost is the total row, and phase or step rows are never summed. |
| MJ7 | `run` holds `issue`, `outcome` (the outcome `metrics.md` states), `wall_seconds` and `awake_seconds` when the run wrote `done`, and `bails`, a list of `{cause, classification, phase, step}` in order. | Failure by phase needs the bails attributed to a phase. |
| MJ8 | Every count, duration and cost is a JSON number; a figure the fold marks unknown is `null`, never `0` and never a string. | A reader that sums must tell "nothing" from "not known". |
| MJ9 | The object holds no rate, percentage or average. | D4. |
| MJ10 | Exit codes are `metrics.sh`'s own: an argument error or an unreadable log is exit 2 with nothing on stdout, under `--json` as without it. | Exit codes are the API; a half-printed object must not be parseable as a whole one. |
| MJ11 | `SCRIPTS.md`'s `metrics.sh` entry states `--json` and names the top-level keys. Graded by the issue's `## Requirements` row. | The catalogue is where a script's output is looked up. |

## Rules every row below inherits

- **A new key or event** is declared in `skills/tdd/scripts/veri/event_table.py` and in
  `skills/tdd/JOURNAL.md`'s table in the same change (the case that keeps the two equal fails
  otherwise), and a writer that breaks its declared format exits 2 under `VERI_EVENT_STRICT=1`, as
  every event does. Keys and events are only added (JOURNAL.md: append-only); a new key is optional
  (`?`), so every line already in a journal stays valid.
- **An old journal still folds.** A journal written before a sub-PRD lands folds without error;
  each row says what the fold prints for it.
- **Every new figure is a field of the `Fold`** (MJ2), lands in `<issue>.metrics.json` by MF1's
  rewrite, and is stated in `skills/tdd/PUBLISHED.md` with its type and nullability (MF8's case
  fails until it is). So every sub-PRD below depends on 035.2, and each issue that adds a key edits
  `PUBLISHED.md` (graded).
- **No row adds a rate** (D4, MJ9): where a rate is the point, the row adds its numerator and its
  denominator as counts.

## 035.3a — what each verifier REJECT led to

Mario gets: per verifier phase, how many of its REJECTs were caught, flipped, overturned,
unresolved, pending or untracked (D3 as D12 amends it): the "did it detect a real issue" number.
Depends on 035.2. Does not: show the counts in `metrics.md` (035.7a); judge any REJECT by a model;
follow a REJECT across a reworded step (035.4c); change what a verifier, revise loop or bail does.

| ID | Requirement | Why |
|---|---|---|
| MO1 | `verdict` gains the optional key `tree` (format `sha`): the work tree the verifier judged, the before tree `verify.py`'s tree guard took (`leaf_tree_guard.Guard.tree`). It is absent when the guard took none (`Guard.tree` empty). `event_table.py` and `JOURNAL.md`'s `verdict` row declare it. | "A revise changed the tree" (D3) is unknowable without it, and the guard already computes it before every verifier leaf. |
| MO2 | The fold pairs each `verdict` line whose `verdict` is `REJECT` with the first later `verdict` `PASS` line of the same `step` and `phase` (the context keys) in the journal, across resumes and restarts. `malformed` verdicts are neither a REJECT nor a PASS. | D9: the outcome is derived, on the pairing `route_green_rejects` already uses for green. |
| MO3 | A REJECT whose paired PASS carries a `tree` different from its own is **caught**; the same `tree`, **flipped**. | D12. |
| MO4 | A REJECT with no paired PASS is **overturned** when a `bail` with `cause=revise-impossible` and the same `step` follows it, **unresolved** when any other `bail` follows it, and **pending** when no `bail` follows it. | D12: the run's later history decides, and a run still going decides nothing yet. |
| MO5 | A REJECT whose paired PASS exists but where either line lacks `tree` is **untracked**, never caught or flipped. Every REJECT of a journal written before MO1 lands that has a paired PASS is untracked; one without is overturned, unresolved or pending by MO4. | Old logs fold without a guess (D12). |
| MO6 | Each `phases.<phase>` entry gains `rejects`, an object with `caught`, `flipped`, `overturned`, `unresolved`, `pending` and `untracked`, each a JSON number; the six sum to that entry's `reject`. A phase with no REJECT has all six at `0`. | One count per outcome, and a sum a reader can check against MJ3's `reject`. |
| MO7 | Each `steps` entry gains the same `rejects` object over that step's REJECTs. | Per ledger step, as D2 keeps metrics. |
| MO8 | A case pins each outcome on a hand-built journal: a REJECT, a `revise`, a PASS on another tree (caught); a REJECT and a PASS on the same tree (flipped); a REJECT and a `bail cause=revise-impossible` (overturned); a REJECT and a `bail cause=revise-exhausted` (unresolved); a REJECT alone (pending); a REJECT and a PASS without `tree` (untracked). | Each outcome watched on its own. |
| MO9 | `PUBLISHED.md` states `rejects` and its six keys under the phase and step entries, and names the six outcomes in one sentence each. Graded by the issue's `## Requirements` row. | A reader may rely only on what the page states. |
