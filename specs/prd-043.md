# PRD 043 requirements: recorded deviations

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status (2026-11-23): written against `main` at `da06a64ac0`. D1–D6 are the owner's answers of
2026-11-23. Rows exist for 043.1 only; 043.2 onward are outlines.**

## The goal

Some of veri's process rules stop a run that is doing correct work. The run bails, a human resumes
or re-plans it, and the work lands a day later. This PRD lets the conductor proceed past a
whitelisted rule, once per run, when the adjudicator (ADR-0035) judges the refusal wrong for this
case. Every such deviation is recorded and is reviewed before the merge. The human keeps a finger on
the pulse by reading the recorded deviations and their verdicts. Those verdicts later decide which
rules to prune; no automation does it.

**Target, in prose and forced by no criterion:** fewer bails of correct work. In the sample under
*Facts*, 7 of 14 bails were a rule blocking correct work. The rows below are the behaviours that
force it.

## Decisions

| ID | Decision | Answer |
|---|---|---|
| D1 | Where a deviation is judged | At the bail. A new first sub-step of `skills/tdd/BAIL.md` sends a bail whose refusing rule is whitelisted to the adjudicator, which may answer `deviate`. The bail must name the refusing rule's ID, since a cause alone (`revise-exhausted`) cannot tell a waivable refusal from a non-waivable one. |
| D2 | What `deviate` lets the run do | The rule's own resume action, stated once per rule in its whitelist entry, for the refusing step only. The run writes a ⟦human-owed⟧ ledger line naming the rule ID, the adjudicator's one-line reason and the action taken. |
| D3 | Where the review verdict lives | In the committed ledger. On OK, vmerge commits the tick on the PR branch before the merge, with `⟦reviewed ok⟧` appended, and updates the PR body to match, since `run-finished.sh` blocks on an unticked ⟦human-owed⟧ line there. NOT OK becomes a comment on the issue and goes to the human; nothing merges. No `deviation-reviewed` event: `events.jsonl` lives in the run's worktree, which may be gone at merge time. |
| D4 | Budget | `VERI_DEVIATION_BUDGET`, default 1 per run, its own axis (ADR-0020): a 13th budget. A deviation is not a no-answer, a rejection or a missing verdict. |
| D5 | Whitelist v1 | Waivable: the graded-prose fence (`graded-edit-outside-skill-edit`), the test freeze (`tests-frozen.sh`), verify-pin's fail-at-base requirement, and pin-recheck (struck once #4710 "pin-recheck findings after a refactor become ⟦human-owed⟧ review lines instead of re-pin steps or needs-user bails" lands). Never waivable: the blind verifier's inputs; a verify-green or verify-refactor REJECT of production code; exit-code semantics; `supervise.sh`; the committed ledger; the skill snapshot pin; a missing or obsolete target, or a real spec gap. `scope-check.sh` is not listed: it never bails. |
| D6 | Split | 043.1 the whole pipeline for one rule, the graded-prose fence, which bails directly, plus ADR-0037 extending ADR-0035. Then one sub-PRD per rule, the test freeze next. |

The spec also makes these calls, unasked:

- **The whitelist is a list in `ADJUDICATE.md` read by a script**, like *Eligible causes*: one
  bullet per rule ID. A rule not on it is never waived, whatever the adjudicator answers.
- **A `deviate` launch also counts against `VERI_ADJUDICATE_BUDGET`**: it is one adjudication. The
  deviation itself spends `VERI_DEVIATION_BUDGET`. Either one spent means a plain bail.
- **The graded-prose fence's resume action is a reroute, not a skip.** `SKILL.md`'s plan rules say
  only a `⟦skill-edit⟧` step signs a graded unit. So a deviation keeps the step's commit and appends
  one `⟦skill-edit⟧` step for the changed units, which regrades them. A unit that fails its grade
  bails there as it does today.

## 043.1: a graded-prose fence bail can be a recorded deviation

**What the human gets:** a run whose green or refactor step had to touch a graded unit no longer
bails `graded-edit-outside-skill-edit` when the adjudicator judges the edit needed. It goes on,
regrades the unit in a `⟦skill-edit⟧` step it adds, and the PR carries one ⟦human-owed⟧ line that
vmerge's review must pass before the merge. Depends on nothing.

| ID | Requirement | Why |
|---|---|---|
| WV1 | `skills/tdd/ADJUDICATE.md` holds a *Waivable rules* section read by a script: one bullet per rule, `` - `<rule-id>`: `` then the bail cause that names it and its resume action. In 043.1 it lists only `graded-edit`, for the cause `graded-edit-outside-skill-edit`. | D1, D5: the rule ID is stable and the list is the whole whitelist. |

## 043.2 (outline): the test freeze can be a recorded deviation

**What the human gets:** a step that had to edit a frozen test no longer spends `REVISE_BUDGET` to a
`revise-exhausted` bail when the edit is needed. Blocked by 043.1. A `tests-frozen.sh` refusal today
is a REJECT (exit 1), not a bail (`SKILL.md:836-842`, `955-962`), and the later `revise-exhausted`
bail does not say which rule refused. So 043.2 first makes that bail carry the rule ID
`tests-frozen`. Open for filing: whether the waiver fires at the first refusal or only at the
exhausted bail. Recommended: at the bail, as D1 says.

## 043.3 (outline): verify-pin's fail-at-base requirement

**What the human gets:** a pin whose test cannot fail at the branch base, for a stated reason the
adjudicator accepts, no longer bails the run. Blocked by 043.1. The REJECT is routed by
`pin-reject-route.sh` (`prompts/verify-pin.md:16-26`, `PIN.md:84-105`).

## 043.4 (outline): pin-recheck, only if #4710 has not landed

**What the human gets:** a recheck finding no longer bails `needs-user`. Dropped if #4710 "pin-recheck
findings after a refactor become ⟦human-owed⟧ review lines instead of re-pin steps or needs-user
bails" lands first, since that makes every finding a review line already.

## What this PRD does not hold

- **`deviation-breakdown.sh`, a pruning report or a cron.** The owner reads the ledgers' deviation
  lines and their `⟦reviewed ok⟧` marks directly. Pruning a rule is a human decision, filed by hand.
- **A `deviation-reviewed` event** (D3).
- **Any rule D5 names never waivable.**
- **Spend.** No CI, runner or paid-service change. One adjudicator leaf per deviation, at most
  `VERI_DEVIATION_BUDGET` per run.
