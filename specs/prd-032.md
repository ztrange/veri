## The goal

A veri run complies more closely with Farley's *Modern Software Engineering* (fast, trustworthy
feedback; managed complexity), Beck's *TDD by Example* and *Tidy First?* (triangulation, baby
steps, tidy before the change), and Fowler's *Refactoring* (smells, named refactorings, two hats).

Each sub-PRD is one practice the books call for that veri does not enforce today, stated as
something a run does that can be seen from outside.

## What this PRD does not hold

- **What veri already does better than its origin**, which nothing here may weaken: a blind
  verifier per phase that reruns the tests; a red prediction written to a file before the run and
  checked by `red-divergence.sh`; unrequired code proven by mutation probe; two hats enforced
  through git (a non-`refactor:` commit in the refactor range resets it); tests frozen after Red;
  a blind-verified plan.
- **Fake It.** Rejected on purpose: ADR-0021, "Green is Obvious Implementation".
- **Seams and characterization tests**: PRD 031.
- **Cutting what a run costs**: PRD 012 and 024. Every sub-PRD here adds work to a run and says
  how much; see *Cost*.
- **Docs reconciled against the delivered range, a code-shape snapshot per delivery, numeric
  cohesion and coupling trends, an issue-level acceptance test in domain language, step order by
  red-bar patterns**: found by the comparison, judged low value for now, not planned. They are
  listed in *Facts* so they are not re-derived.

## PRD 032.2: the plan verifier rejects a predicate step with no counter-case beside it

**What you get:** a plan whose step makes an outcome depend on a condition is rejected before any
leaf runs unless the very next step pins the outcome when the condition does not hold, so the
code is triangulated by plan instead of by an overfit flag at green.

**Depends on:** nothing.

A **predicate step** is a Red/Green step whose criterion makes an outcome depend on a condition of
the input or state ("when", "if", "only", "unless", a threshold); its **counter-case** is a step
whose criterion states the outcome when that condition does not hold. The prose lands in two
graded units: `prompts/verify-plan.md` (rows in `skills/tdd/scripts/prompts/REQUIREMENTS.md`) and
`skills/tdd/SKILL.md` *2. Scope & plan → the ledger* (rows in `skills/tdd/REQUIREMENTS.md`).

| ID | Requirement | Why |
|---|---|---|
| PQ1 | `prompts/verify-plan.md` says to REJECT a plan holding a predicate step whose next Red/Green step in the ledger is not its counter-case; the reason names the predicate step and its condition. | Beck: triangulation; the pair adjacent so the second green generalises the first. |
| PQ2 | The same check is not a REJECT when an earlier step of the plan is the counter-case, or when a committed test case the verifier finds in the repository already pins the outcome when the condition does not hold. | The other side is often today's behaviour, already pinned; demanding a step for it would plan a pin. |
| PQ3 | The check applies to Red/Green steps only: a `⟦diff-checked⟧`, `⟦full-suite⟧`, `⟦human-owed⟧` or `⟦phases: …⟧` line is never a predicate step or a counter-case. | Those lines have no failing test to triangulate. |
| PQ4 | `SKILL.md` *2.
