# PRD 032 requirements: a run is held to Farley, Beck and Fowler where it is not yet

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status: approved by Mario on 2026-11-15, section by section: the eight practices, the five left
out and D1–D5 "accept all"; 032.1's rows "accept with numeric thresholds and the cap"; overlaps,
cost and open items "accept with all three additions". Written that day from his ask and a
comparison with the harness veri came from (whtlnv/my-skills at `08461e9`). 032.1 carries rows;
the rest are outlines. Nothing is filed.**

## The goal

A veri run complies more closely with Farley's *Modern Software Engineering* (fast, trustworthy
feedback; managed complexity), Beck's *TDD by Example* and *Tidy First?* (triangulation, baby
steps, tidy before the change), and Fowler's *Refactoring* (smells, named refactorings, two hats).

Each sub-PRD is one practice the books call for that veri does not enforce today, stated as
something a run does that can be seen from outside.

## What this PRD does not hold

- **What veri already does better than its origin**, which nothing here may weaken: a blind
  verifier per phase that reruns the tests; a red prediction written to a file before the run and
  checked by `red-divergence.sh`; unrequired code proven by mutation probe; two hats enforced
  through git (a non-`refactor:` commit in the refactor range resets it); tests frozen after Red;
  a blind-verified plan.
- **Fake It.** Rejected on purpose: ADR-0021, "Green is Obvious Implementation".
- **Seams and characterization tests**: PRD 031.
- **Cutting what a run costs**: PRD 012 and 024. Every sub-PRD here adds work to a run and says
  how much; see *Cost*.
- **Docs reconciled against the delivered range, a code-shape snapshot per delivery, numeric
  cohesion and coupling trends, an issue-level acceptance test in domain language, step order by
  red-bar patterns**: found by the comparison, judged low value for now, not planned. They are
  listed in *Facts* so they are not re-derived.

## PRD 032.1: a refactor is judged against a published smell catalogue

**What you get:** every `refactor:` commit of a run names the refactoring it applied, and a
verifier that rejects a refactor for design names the smell and where it is. You can read why.

**Depends on:** nothing.

| ID | Requirement | Why |
|---|---|---|
| SM1 | `skills/tdd/SMELLS.md` exists and lists smells, each with: a name, a threshold stated as a number wherever a diff can show one (function length, nesting depth, parameter count), so that two readers of the same diff agree whether it is met, and one or more named refactorings that answer it. | D2; numbers by Mario's decision of 2026-11-15, seeded from my-skills' (`refactor/SKILL.md:26-36`) and tuned after 20 runs. Rejected: judgments, which are today's "up to standard" under another name. |
| SM2 | `SMELLS.md` states, as rules of their own: search for an existing helper before adding one; do not reverse a refactor made earlier in the same run; in test code, expected values stay literal and are never computed by the code under test. | The transform guards and test-code rules the comparison found absent. |
| SM3 | The rendered `develop-refactor` prompt contains `SMELLS.md`'s catalogue, and tells the leaf to name, for each transform, the smell it answers and the refactoring applied. | D2: the developer works to the standard it is judged by. |
| SM4 | Each `refactor:` commit's subject or body names the refactoring applied, by its catalogue name. | Fowler: named refactorings; the history says what was done. |
| SM5 | The rendered `verify-refactor` prompt contains the same catalogue, and tells the verifier that a design REJECT must name one catalogue smell and the file and symbol where it is met. The phrase "up to standard" is gone from `prompts/verify-refactor.md`. | D3. |
| SM6 | `verify-refactor`'s existing rejections for behaviour (a loosened assertion, a changed test, a non-`refactor:` commit in the range, a red suite) are worded as they are today. | Nothing that works is weakened. |
| SM7 | A refactor leaf that finds no catalogue smell in the step's files reports that and commits nothing; the verifier does not reject the absence of a transform when it finds none either. | Refactoring is not owed where nothing smells; `VERI_REFACTOR_BUDGET` stays a ceiling, not a quota. |
| SM8 | No input of `build-verify-prompt.sh refactor` is added: the catalogue is a file of the skill snapshot, not a run input. | The verifier is blind by construction. |
| SM9 | `SMELLS.md` is a graded unit with rows of its own, and `develop-refactor.md` and `verify-refactor.md` are regraded. | Wording that decides verdicts is graded. |
| SM10 | `skills/tdd/SMELLS.md` is at most 60 lines, pinned by a case. | It is added to two prompts on every step; Mario, 2026-11-15. |
