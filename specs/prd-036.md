# PRD 036 requirements: test runs and conductors sized to the machine

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status (2026-11-17): written against `ad5e14de69`. D1–D14 are Mario's answers of 2026-11-17,
each passed through `vjudge` first. Nothing is filed. Rows exist for 036.1 and 036.2 only;
036.3–036.5 are outlines. `VERI_CORE_WAIT_WARN`, `VERI_LOAD_PERSIST`, `VERI_LOAD_RAMP`, the N
value `max` and every event name below are working names.**

## The goal

Under `/vdev`, Mario sets N conductors and veri keeps the machine from drowning: test runs queue for
the machine's cores instead of oversubscribing them, and when the hardware still cannot keep up,
veri says so loudly, lowers N if it persists, and on request finds the highest N the machine holds.

Target, stated in prose and forced by no criterion: on the development Mac, no test-case timeout or
killed-stuck leaf caused by load at the N Mario sets.

## What this PRD does not hold

- **A ceiling on N derived from cores or memory.** Rejected (D3, D6): conductors are not the
  bottleneck; Mario ran more than 8 alongside 2–3 test runs. Too high is where the hardware cannot
  keep up, observed, never computed in advance.
- **Refusing or clamping an N Mario sets.** Veri warns (D7); only a persisting signal lowers N
  (D9), and only `max` raises it (D12).
- **Spend.** No CI, runner or paid service changes.

## Facts

load average 2.29 / 2.32 / 2.44 with no conductor running, 20 entries in `~/.veri-pytest-legs`
(liveness not checked).

- **Conductors.** `dispatch.sh` (`veri/dispatch.py`) keeps N live, N read from

  (`skills/vdev/SKILL.md`, *The slot decision*: "Never change N on your own"). Nothing in it reads
  load, cores or memory.
- **Test runs.** A leg's workers are `hw.physicalcpu` (affinity count off macOS) minus the workers
  other live legs registered under `~/.veri-pytest-legs`, floor 1, computed once at start

  on the one-per-machine lock (`veri/full_run_lock.py`, #2195). A subset leg
  (`make test TESTS=…`) takes 1 worker when none are free, and `make unit` always starts 4: N
  conductors' leaves oversubscribe the machine.
- **A waiting leg already freezes its supervisor.** The wait marker of #3989 stops a supervised
  leaf's hard timeout and silence window while its waiter is alive.
- **Load has been fought with timeouts.** #2480, #2479, #2592, #2748, #2910, #2940, #3521 and #3833
  each loosened a timeout under load; none limited concurrency. #3479 (a review starts suites
  beyond `make unit` only while no conductor baseline runs) is the one capacity gate.
- **Push exists.** vdev sends a notice as one `PushNotification` where the session has the tool
  (`skills/vdev/REQUIREMENTS.md` D98).

## Rules every row below inherits

- The core budget is the machine's physical cores; a leg's share is what it registered under
  `~/.veri-pytest-legs`, and a dead pid holds no share (unchanged).
- A wait is the #3989 kind: a marker naming the waiter's pid and start time, so a supervised leaf's
  hard timeout and silence window are frozen while it waits, and the wait counts toward no per-case
  timeout.
- `VERI_PYTEST_WORKERS=<n>` still overrides, used as given, and never waits.

## 036.1 — a subset leg waits for a free core

What Mario gets: N conductors' leaves no longer run more test workers than the machine has cores;
an extra leaf's test run queues instead.

Depends on: nothing.

| ID | Requirement | Why |
|---|---|---|
| HW1 | A `make test` leg (subset or full) that finds no free core waits until one frees, instead of starting with 1 worker. | The floor of 1 is how N leaves oversubscribe the machine. |
| HW2 | While it waits, it prints one stderr line naming the cores in use and the pids holding them, once. | A silent wait looks like a hang. |
| HW3 | A waiting leg writes the #3989 wait marker, so `supervise.sh` freezes the leaf's hard timeout and silence window. | A queued test is not a stuck leaf. |
| HW4 | When cores free, the leg takes min(the workers it would have taken, free cores) and registers that count. | The budget holds the sum of live legs at or below the cores. |
| HW5 | A leg records how long it waited, as an event `core-wait` with the seconds. | 036.3 reads it as a signal. |
| HW6 | A full run still takes the one-per-machine lock first, and waits for cores only after holding it. | Two waits in the other order could deadlock against a subset leg. |
| HW7 | `VERI_PYTEST_WORKERS` set, the leg neither waits nor checks the budget. | The override stays an override. |

## 036.2 — `make unit` joins the core budget

What Mario gets: the fast tier stops adding 4 workers on top of a saturated machine.

Depends on: 036.1 (its wait path).

| ID | Requirement | Why |
|---|---|---|
| HW8 | `make unit` takes min(4, free cores) workers and registers them under `~/.veri-pytest-legs`. | It starts 4 unconditionally today. |
| HW9 | `make unit` with no free core waits as HW1–HW3 say. | Same cause, same cure. |
| HW10 | `make unit` never takes the full-run lock. | Unchanged; the lock is for full runs. |

## 036.3 — a strong warning when the hardware cannot keep up (outline)

Depends on 036.1. Five signals: a `core-wait` above `VERI_CORE_WAIT_WARN` (300 s); macOS memory
pressure above normal; a pytest per-case timeout; a leg's `VERI_PYTEST_IDLE` self-end (#4254); a
killed-stuck leaf. On the first one while at least 2 conductors are live, `dispatch.sh` prints one
line naming the signal, the run or case it came from, the live N and "may be load"; vdev sends it as
a `PushNotification`. It is printed again only after the signal clears and fires again.
`role-state.sh dev`, raising N while a signal is active, prints the same warning and still writes N.

## 036.4 — veri lowers N while the signal persists (outline)

Depends on 036.3. A signal that fires again within `VERI_LOAD_PERSIST` (30 min) of the warning
lowers N by 1, never below 1, written to the role state file with `veri (load)` as who asked, and
pushed with the old N, the new N and the signals. It repeats per window. No live run is stopped
(P8). Veri never raises N back; the push says how Mario does. vdev's "Never change N on your own"
gains this one exception, in the same change.

## 036.5 — `max`: veri finds the highest N the machine holds (outline)

Depends on 036.4. `role-state.sh dev max` sets N to `max`. From the live count, `dispatch.sh` raises
N by 1 after each `VERI_LOAD_RAMP` (30 min) with no signal, while the solvable queue holds more
issues than are live. The first signal lowers N by 1 (036.4), ends the ramp for good and holds N
there, pushed as the found ceiling. `max` again probes again.
