## The goal

040.1 **moves the operator's after-run review into the run**: a blind verifier reads the whole
branch, once, after the last step and before the PR is readied, and a REJECT becomes one repair step
inside the run instead of a NOT OK review, a hand-fix agent and another review after it. It is not
an extra layer on top of that review; it is that review, done by veri before the operator sees the
PR.

040.2–040.4 close what a step's own verifiers let through and a whole-branch read finds late: code
a step never wrote, a row or doc sentence the run wrote that the code does not bear out, and a test
that asserts less than its criterion.

**Success measure, stated in prose and forced by no criterion:** the share of veri runs whose first
operator review is NOT OK falls. If it does not fall, `verify-branch` is dropped. Speed is not a
goal: the stage costs about one leaf per run (D7).

How it is read (D9, D10): from git, with no hand log. A run's first review counts as NOT OK when
commits land on its PR branch after the run's `✅ Done` comment; the same query over merged PRs gives
the baseline. The last 10 runs before 040.1 lands are compared with the first 10 after. No veri file
records a review's verdict today (`git grep -n -i 'review\|not ok' skills/tdd/scripts/veri/report.py
skills/tdd/scripts/veri/metrics.py` at `0e439c164d` returns nothing), hence the git proxy; a log the
operator keeps by hand is the fallback only if the proxy proves noisy. 040.2–040.4 are read the same
way after 040.1's window, each NOT OK finding attributed to the slice of its class (D14).

## What this PRD does not hold

- **Speed or cost savings.** 040.1 adds a leaf; it is judged only by the success measure.
- **A new model knob** (D6).
- **Mutation testing inside 040.1.** That is 040.5, an outline (D1, D13).
- **Spend.** No CI, runner or paid service changes; the leaf runs on the subscription (D7).
- **An end-of-run docs pass** (D15).
- **A read relative to the working directory**, the fourth finding on PR #4478 (*Facts*): no slice
  catches that class.

## 040.1 — `verify-branch`: a blind verifier judges the whole branch before readying

What the owner gets: the review the operator runs after a run, done inside it. A blind verifier
reads the whole branch against the issue's criteria once the last step is done, and a REJECT costs
one repair step in the run instead of a NOT OK review, a hand fix and a second review.

Depends on: PR #4436 (`run-pr.sh`), merged; `veri/run_pr.py` is on `main`. Worth having if no later
slice ships: it is the review itself.
