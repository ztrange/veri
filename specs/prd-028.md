# PRD 028 requirements: CI is the branch's full run where CI runs on pull requests

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status (2026-11-17): 028.1 landed on 2026-11-14 as `v0.1351` (PR #3779), built by hand, test-first. 028.2 (#4018) and 028.3 (#4017) are closed, through PR #4178. Nothing is open. Mario handed the decisions to the planning session on 2026-11-13 ("keep going by yourself … solve the stoppers"), so D1–D8 are that session's calls, each with the alternative it rejected. The script kept its working name, `branch-suite.sh`. Two things 028.1's reviews added beyond its rows: a `wait-ci.sh` exit 0 that saw no checks ticks nothing, and the tick's ledger commit is made only when a line was ticked.**

## The goal

A run stops paying for the same full suite twice. At the Draft PR step the conductor runs the
repository's full suite locally, readies the PR, and then waits for CI to run the same suite again.
Where a workflow runs on pull requests, CI's run becomes the branch's full run and the local one is
not made.

Target: the Draft PR step makes no local full run on a repository whose CI runs on pull requests,
which removes about 14 % of a session's wall time (see *Facts*). The acceptance criteria are the
behaviours that force it, never the seconds.

This is the second half of `v0.1339`, which did the same for the rebased tip's run
(`VERI_REBASED_TIP_SUITE`, `rebased-tip-suite.sh`).

## What this PRD does not hold

- **Fewer conductor requests at the Draft PR step**: PRD 027.7 (`specs/prd-027.md`) fuses that
  step's fixed calls. This PRD removes a test run, not a request.
- **The preflight baseline's full run**: `v0.1337` (`VERI_BASELINE_FULL_TIER=reuse`).
- **How long the full suite takes**: PRD 009 and PRD 012.
- **CI on a draft PR.** The workflow stays skipped on drafts.

## 028.1 — the branch's full run is CI's where CI runs on pull requests

**What you get:** a run on a repository with CI on its pull requests reaches "ready for review"
without a local full-suite run, and CI's result is what ticks `⟦full-suite⟧`.

**Depends on:** nothing.

`branch-suite.sh` is the working name.

| ID | Requirement | Why |
|---|---|---|
| BS1 | `$S/branch-suite.sh` prints one line, `ci` or `local`. With `VERI_BRANCH_SUITE` set to either word it prints that word. Unset, it prints `ci` when `VERI_CI_ON_PR` is `1`, or when `VERI_CI_ON_PR` is unset and a workflow under `.github/workflows/` of the current directory triggers on pull requests; otherwise `local`. | D2, D3. |
| BS2 | It exits 2, naming the variable and its value on stderr, when `VERI_BRANCH_SUITE` is set to anything else or `VERI_CI_ON_PR` is neither `0` nor `1`. | Exit 2 is "no answer"; a typo must not silently pick a mode. |
| BS3 | `VERI_BRANCH_SUITE` is an entry of `tunables.TABLE`, and preflight's tunables check refuses a bad value before any leaf launches. | A bad knob is caught where every other one is. |
| BS4 | One function answers "does CI run on pull requests here" (`VERI_CI_ON_PR`, else the workflows in the tree) and validates `VERI_CI_ON_PR`; `rebased_tip_suite.py`, the new module and `wait_ci.py` call it and hold no copy of the check. | D8. |
| BS5 | `DRAFT-PR.md` tells the conductor to settle the mode by running `$S/branch-suite.sh` at the root of the run's worktree each time the run enters the step, and that "under `VERI_BRANCH_SUITE=local`" or "`ci`" always means what the script printed. | The same rule the rebased-tip mode has. |
| BS6 | Under `local` the step is today's: the branch's own full run on every entry, its flake check, its `⟦suite-repair⟧` step, the `full-tier-time.sh --record` and the tick before readying. | A repository without CI on its PRs loses nothing. |
| BS7 | Under `ci` the step makes no full run of the branch on entry and no `full-tier-time.sh --record`, and goes on to sub-step 1. | D1. |
| BS8 | Under `ci`, when sub-step 1 rebased the branch and the rebased-tip mode is `local`, the rebased tip's local run is made and handled as today, and its green result ticks `⟦full-suite⟧` before readying as today. | The two knobs stay independent; a local run that was made is still a verdict. |
| BS9 | Under `ci`, when no local full run was made on the head being readied, no `⟦full-suite⟧` line is ticked before `pr-ready.sh`. After the first `wait-ci.sh` exits 0 the conductor ticks each `⟦full-suite⟧` line and its issue criterion as the step does today, and commits the ledger before the `metrics:` commit. A CI that is red, timed out or unread ticks nothing. | D5; a criterion met by "the suite passes" is never ticked unproven. |
| BS10 | Under `ci` a run that comes back to the step after a `⟦ci-repair⟧` step makes no local full run either; the pushed head's `wait-ci.sh` is its verdict, and a second red bails `ci-red` as today. | D6. |
| BS11 | The sentences that state the full suite as the run's guarantee say which run proves it in each mode: `SKILL.md`'s guarantee bullet and its row GD16, `DRAFT-PR.md`'s rows DP3, DP12, DP13 and DP90, and `CLAUDE.md`'s paragraph on when `make test` runs. | The prose and the behaviour change together. |
| BS12 | `SCRIPTS.md` has a catalogue entry for `$S/branch-suite.sh`: what it prints, the two variables it reads and its exit codes. | The catalogue is where a conductor looks a script up. |

## 028.2 — a red CI gets a flake check before it spends the repair step

**What you get:** a run whose readied PR goes red on CI in a test that passes alone re-runs the
failed job once, and on a green re-run goes on as on a green CI, the flake named in the PR body,
instead of spending its one `⟦ci-repair⟧` step on nothing to repair.

**Depends on:** 028.1 (landed, `v0.1351`). Overturns row DP52.

Basis, carried from `19acba12f1` (40 PRs, measured; see *Facts*): 1 of the 3 CI reds was in a file
the branch does not touch (#3697). Cost: one more `ubuntu-latest` CI job (about 240 s, the median)
per re-run, at most `VERI_CI_FLAKE_RERUNS` per run (default 1); the cheaper option, `0`, is
today's: the run spends its `⟦ci-repair⟧` step's leaves instead.

DP52 today is quoted in *Facts for 028.2 and 028.3*. It is replaced by: a conductor re-runs a
failed CI job only through `$S/ci-flake.sh`, at most once per head and `VERI_CI_FLAKE_RERUNS`
times per run, and only after every test target the failed log names has passed alone; a red
re-run is a real red. Its reason, that a real failure must never read as a flake, is kept by
D11: a red that reproduces locally is never re-run, and a re-run that is red again is real.

| ID | Requirement | Why |
|---|---|---|
| CF1 | `VERI_CI_FLAKE_RERUNS` (created here) is an entry of `tunables.TABLE`: default `1`, a whole number ≥ 0, refusal "a whole number". `run_conductor.main`'s launch check refuses a bad value with exit 2, naming the variable and its value, before preflight. At `0` no CI job is ever re-run and every red takes today's path. | D12; a typo must not silently pick a bound, and `0` restores DP52's behaviour. |
| CF2 | `$S/ci-flake.sh <n> <head-sha> <run-id> '<alone-cmd>' <log-file>` (created here, by the port convention) reads test targets from `<log-file>`, the saved output of `gh run view <run-id> --log-failed`: the targets `rerun-alone.sh` would read from the same runner output without gh's per-line prefix. It runs each once, alone, through `<alone-cmd>` with the target as `$1`. | D11, D13; a CI log names the same failures as a local red. |
| CF3 | `ci-flake.sh` exits 3, running nothing and writing no event, when issue `<n>`'s `ci-rerun` events since its last `conductor-start` number `VERI_CI_FLAKE_RERUNS` or more, or when any `ci-rerun` event of issue `<n>` names `<head-sha>`. | D12; a head red after its re-run is a real red, and the bound is per run. |
| CF4 | It exits 1, with no event and no re-run, when the log names no target or a target stays red alone. | D11; a red that reproduces locally is real. |
| CF5 | It exits 0 when every target passed alone and `gh run rerun <run-id> --failed` was accepted: it has written one `ci-rerun head=<head-sha> run=<run-id> files=<targets>` event, dropped `<head-sha>`'s CI wait marks as `wait-ci.sh --fresh-window <head-sha>` does, and printed the targets one per line. It writes no `suite-flake` event. | The re-run gets its own deadline; nothing is called a flake before the re-run answers. |
| CF6 | It exits 2 on bad arguments, an unreadable `<log-file>`, a `<head-sha>` that is not 40 hex, or `gh` refusing the re-run; no `ci-rerun` event is written for a re-run that was not accepted. | Exit 2 is "no answer", never a verdict. |
| CF7 | After a `ci-flake.sh` exit 0, `wait-ci.sh` on that head answers from the re-run's check runs: a check run that completed before the `ci-rerun` event was written is never its exit 0 or exit 1. | Otherwise the first wait reads the failed attempt and calls the re-run red. |

Draft PR` sub-step 2, says that at every `wait-ci.sh` exit 1 (after `pr-ready.sh`, after the `metrics:` push, after a CI-conflict rebase or an adjudicated `retry`) and before the red takes its `⟦ci-repair⟧` step or its `ci-red` bail, the conductor saves `gh run view <run-id> --log-failed` to `.tdd/ci-failed.log`, reads `<alone-cmd>` with `$S/detect-test-command.sh --tier "one test file"` and, unless that exits 3, runs `ci-flake.sh`. Exit 0 runs the same `wait-ci.sh` line again; exit 1, 2 or 3, or no `one test file` line, takes today's path unchanged. | D11, D14; one rule at every place a CI red is read. |
| CF9 | The same section says that a `wait-ci.sh` exit 0 after a re-run is a flake: the conductor writes `ci-flake head=<sha> run=<run-id> files=<targets>`, names the targets in the PR body, and goes on as after any green wait, including row DP101's `⟦full-suite⟧` tick under `VERI_BRANCH_SUITE=ci`. Its exit 1 takes the `⟦ci-repair⟧` step or the `ci-red` bail as today (rows DP50, DP51); exit 2 and 3 as at any wait. | A green re-run is CI's proof; a red one is a real red with its one repair. |
| CF10 | A green re-run appends no `⟦ci-repair⟧` step; a re-run is counted only by `VERI_CI_FLAKE_RERUNS`, never by `REVISE_BUDGET`, `VERI_ADJUDICATE_BUDGET` or row DP50's `⟦ci-repair⟧` count. | D12; budgets on separate axes are never merged. |
