# PRD 028 requirements: CI is the branch's full run where CI runs on pull requests

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status: DRAFT, from the 2026-11-13 efficiency analysis. Mario handed the decisions to the
planning session on 2026-11-13 ("keep going by yourself … solve the stoppers"), so D1–D8 are that
session's calls, each with the alternative it rejected. 028.1 carries rows; 028.2 and 028.3 are
outlines. Nothing is filed: 028.1 is built by hand, test-first, by the same session.**

## The goal

A run stops paying for the same full suite twice. At the Draft PR step the conductor runs the
repository's full suite locally, readies the PR, and then waits for CI to run the same suite again.
Where a workflow runs on pull requests, CI's run becomes the branch's full run and the local one is
not made.

Target: the Draft PR step makes no local full run on a repository whose CI runs on pull requests,
which removes about 14 % of a session's wall time (see *Facts*). The acceptance criteria are the
behaviours that force it, never the seconds.

This is the second half of `v0.1339`, which did the same for the rebased tip's run
(`VERI_REBASED_TIP_SUITE`, `rebased-tip-suite.sh`).

## What this PRD does not hold

- **Fewer conductor requests at the Draft PR step**: PRD 027.7 (`specs/prd-027.md`) fuses that
  step's fixed calls. This PRD removes a test run, not a request.
- **The preflight baseline's full run**: `v0.1337` (`VERI_BASELINE_FULL_TIER=reuse`).
- **How long the full suite takes**: PRD 009 and PRD 012.
- **CI on a draft PR.** The workflow stays skipped on drafts.

## Decisions

The planning session's calls on 2026-11-13, under Mario's hand-over.

| ID | Decision | Why, and what was rejected |
|---|---|---|
| D1 | Under mode `ci` the Draft PR step makes no local full run of the branch: the PR is readied and the first `wait-ci.sh` is the branch's full-suite verdict. | CI runs the same command in a quarter of the time. Rejected: keeping the local run as a pre-check, which is the cost this PRD removes. |
| D2 | The mode is its own knob, `VERI_BRANCH_SUITE` (`local` or `ci`), settled by its own script. `VERI_REBASED_TIP_SUITE` is not reused. | The two runs answer different questions (is the branch green; did the rebase break it), and one knob over both would make them one decision (ADR-0020's reasoning). |
| D3 | Unset, the mode is `ci` where a workflow triggers on pull requests and `local` otherwise, by the same reading `rebased-tip-suite.sh` makes; `VERI_CI_ON_PR` answers in the tree's place. | The fallback Mario chose for `v0.1339`: a repository without CI on its PRs keeps its only full run. Rejected: default `local` as a trial, since one environment variable reverts it. |
| D4 | The PR is readied before any full run has passed. | Readying is what starts CI. Rejected: dispatching the workflow on the draft, which needs a `workflow_dispatch` trigger other repositories do not have. The cost: 2 of 40 PRs would have been readied red and repaired in the open, as 3 of 40 already are today. |
| D5 | Under `ci` the `⟦full-suite⟧` line is ticked after the first green `wait-ci.sh` and committed before the `metrics:` commit, so the step's existing push and second `wait-ci.sh` carry it. | No new push and no cancelled CI run. Rejected: ticking before readying, which would tick a criterion no run has proven. |
| D6 | A red CI is handled exactly as today: one `⟦ci-repair⟧` step, a second red bails `ci-red`. | The path exists and is tested. The one repair attempt now also covers what the local run used to catch (2 of 40 issues). |
| D7 | The flake check for a red CI is a later sub-PRD (028.2), not part of 028.1. | 028.1 is worth having without it: today's CI reds have no flake check either. |
| D8 | Whether CI runs on pull requests is decided by one function, used by `rebased-tip-suite.sh`, the new script and `wait-ci.sh`. | Three copies of one rule drift; two exist already. |

## 028.1 — the branch's full run is CI's where CI runs on pull requests

**What you get:** a run on a repository with CI on its pull requests reaches "ready for review"
without a local full-suite run, and CI's result is what ticks `⟦full-suite⟧`.

**Depends on:** nothing.

`branch-suite.sh` is the working name.

| ID | Requirement | Why |
|---|---|---|
| BS1 | `$S/branch-suite.sh` prints one line, `ci` or `local`. With `VERI_BRANCH_SUITE` set to either word it prints that word. Unset, it prints `ci` when `VERI_CI_ON_PR` is `1`, or when `VERI_CI_ON_PR` is unset and a workflow under `.github/workflows/` of the current directory triggers on pull requests; otherwise `local`. | D2, D3. |
| BS2 | It exits 2, naming the variable and its value on stderr, when `VERI_BRANCH_SUITE` is set to anything else or `VERI_CI_ON_PR` is neither `0` nor `1`. | Exit 2 is "no answer"; a typo must not silently pick a mode. |
| BS3 | `VERI_BRANCH_SUITE` is an entry of `tunables.TABLE`, and preflight's tunables check refuses a bad value before any leaf launches. | A bad knob is caught where every other one is. |
| BS4 | One function answers "does CI run on pull requests here" (`VERI_CI_ON_PR`, else the workflows in the tree) and validates `VERI_CI_ON_PR`; `rebased_tip_suite.py`, the new module and `wait_ci.py` call it and hold no copy of the check. | D8. |
| BS5 | `DRAFT-PR.md` tells the conductor to settle the mode by running `$S/branch-suite.sh` at the root of the run's worktree each time the run enters the step, and that "under `VERI_BRANCH_SUITE=local`" or "`ci`" always means what the script printed. | The same rule the rebased-tip mode has. |
| BS6 | Under `local` the step is today's: the branch's own full run on every entry, its flake check, its `⟦suite-repair⟧` step, the `full-tier-time.sh --record` and the tick before readying. | A repository without CI on its PRs loses nothing. |
| BS7 | Under `ci` the step makes no full run of the branch on entry and no `full-tier-time.sh --record`, and goes on to sub-step 1. | D1. |
| BS8 | Under `ci`, when sub-step 1 rebased the branch and the rebased-tip mode is `local`, the rebased tip's local run is made and handled as today, and its green result ticks `⟦full-suite⟧` before readying as today. | The two knobs stay independent; a local run that was made is still a verdict. |
| BS9 | Under `ci`, when no local full run was made on the head being readied, no `⟦full-suite⟧` line is ticked before `pr-ready.sh`. After the first `wait-ci.sh` exits 0 the conductor ticks each `⟦full-suite⟧` line and its issue criterion as the step does today, and commits the ledger before the `metrics:` commit. A CI that is red, timed out or unread ticks nothing. | D5; a criterion met by "the suite passes" is never ticked unproven. |
| BS10 | Under `ci` a run that comes back to the step after a `⟦ci-repair⟧` step makes no local full run either; the pushed head's `wait-ci.sh` is its verdict, and a second red bails `ci-red` as today. | D6. |
| BS11 | The sentences that state the full suite as the run's guarantee say which run proves it in each mode: `SKILL.md`'s guarantee bullet and its row GD16, `DRAFT-PR.md`'s rows DP3, DP12, DP13 and DP90, and `CLAUDE.md`'s paragraph on when `make test` runs. | The prose and the behaviour change together. |
| BS12 | `SCRIPTS.md` has a catalogue entry for `$S/branch-suite.sh`: what it prints, the two variables it reads and its exit codes. | The catalogue is where a conductor looks a script up. |
