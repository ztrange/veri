# PRD 033 requirements: development carries on through a GitHub outage

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status (2026-11-17): decisions settled with Mario on 2026-11-16 in four rounds of questions; D14–D19 settled on 2026-11-17 when 033.2 was re-outlined on top of PRD 034. 033.1 is closed (#4166, through #4154–#4157). 033.2 carries rows (OL1–OL15) and is not filed; 033.3, 033.4 and 033.5 are outlines with no rows. 033.2 waits on PRD 034.1 (landed); 033.3 waits on PRD 034.4 (`stack-land.sh`, specified in a parallel PR, not built). Nothing is open.**

## The goal

When merges keep failing because GitHub is having an incident, the dev session finds that out from
GitHub's own status page, and is then authorized to work locally and land later. Development
carries on; once GitHub is back the outage's work lands on the protected `main` through one pull
request, and nothing is ever pushed to `main` directly.

How far "locally" reaches is set by the use case, not capped here: merges first, then live runs,
then new runs. Each is a sub-PRD worth having if the next never ships.

## What this PRD does not hold

- **A merge call that errored but landed** (the 502 on PR #3486): #4059 "PRD 020.3: a merge that
  errored is never re-merged over a landed PR".
- **Bounds on `queued-merge.sh`'s network calls**: #3984 "PRD 021.15".
- **Transient 5xx and rate limits on a single call**: already retried (`veri/github.py`
  `refusal_kind`, `wait-ci.sh`, `dispatch.sh`).
- **An outage of the model API**: P10 of `operator/PRINCIPLES.md`.
- **Red CI, a rebase conflict, a refused push, a billing block**: the status page explains none of
  them; `vmerge` handles each today.

## Cost

No paid API. The status API is free and unauthenticated: one read per unexplained `merge-failed`,
and during an outage one read per `VERI_GITHUB_STATUS_POLL` (default 300 s). No leaf, no CI job, no
added CI time beyond the script's own unit cases. 033.3's recovery landing is one `gates` run over the
whole outage's work in place of one per run.

## PRD 033.1: the dev session knows from GitHub's status page when it may work locally

**What you get:** after a merge fails for no reason `vmerge` names, the session tells you in one
line whether GitHub has had an incident on what the merge needs for 30 minutes. If so it stops
trying to merge, keeps the Done runs in order, and merges them when the incident closes.

**Depends on:** nothing. Worth having alone: today a failed merge has no route at all, and the
session cannot tell an outage from a fault of its own.

## PRD 033.2: during an outage a reviewed run joins the local stack, gated, with the push deferred

**What you get:** while `.tdd/github-outage` exists, a finished and reviewed run is joined onto the
local stack branch by the same join as on a healthy day, minus every GitHub call, and the next run
builds on it. The commits stay unpushed until recovery (033.3). A merge that needs the full suite
runs it locally, or records that an Opus or better session skipped it.

**Depends on:** 033.1; PRD 034.1 (landed). Worth having alone: the work is no longer held behind
a dead merge, and until 033.3 ships the operator pushes the stack and lands it as a slice by hand.

**Not split further:** the join, its local gate and the trailers that record the gate's result are
one capability; a join without its gate is an unproven merge, and a gate without a record leaves
the recovery unable to tell which merges were proven. Filing may still cut it into issues (OL1 to
OL7, OL8 to OL11, OL12 to OL15).

**Replaces:** VO6's hold and VO7's merge-on-exit for a reviewed run; OL13 and OL14 name the rows
reworded.

**Calls made while writing the rows (2026-11-17), none yet marked by Mario:** the gate (OL4) runs
before the stack moves, as D8 says; the freeze (OL9) is written by a red gate only when a skipped
join sits among the unpushed commits, because only then is the red not the candidate's own (the

## PRD 033.4: a live run keeps going through an outage (outline)

**What you get:** a run that was mid-way when GitHub went down finishes its steps instead of
stopping at its next issue comment, and its issue writes land after recovery.

**Depends on:** 033.1; 033.3 (the replay needs the landing's commits for the closing comment).

Holds D18: one append-only queue file of issue writes (comment, label, close) that `comment.sh`
and the issue mirror append to while `.tdd/github-outage` exists; its replay in order on recovery,
