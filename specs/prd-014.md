# PRD 014 requirements: veri writes its state down, and a dashboard reads it

This is the requirements list for PRD 014 (#546). The format is `specs/utility-skills.md`'s: each
row makes one claim a reviewer, a grader or a test can mark true or false; **Why** is never shown
to the grader; IDs are stable, and a dropped row leaves a gap. Rows that change graded prose are
applied in a ⟦skill-edit⟧ step.

**Status: veri's part is done.** 014.1 to 014.6 landed here. 014.7 and 014.8 (the dashboard) moved
to `ztrange/veri-dashboard` on 2026-11-11, with their rows and open issues.

## The goal

The operator wants a beautiful, real-time dashboard shaped like `/vstatus` and `/vreport`, served
by a lightweight background process that only reads files. veri's components write those files as
they work, as a side effect. The dashboard develops in its own lane and touches the main project
only to adjust what is collected and stored.

## How it ships

Eight small sub-PRDs, each worth having if the next never ships. Children are titled
`PRD 014.<k>: …`, so `/vreport` counts them under this PRD. Every sub-PRD now carries rows
(operator, 2026-11-07, so the mu lane has the whole chain queued); where 014.5 or 014.6 teaches
something that changes a later row, that row and its open issue are edited before mu reaches it.

| sub-PRD | what you get when it lands | depends on | rows |
|---|---|---|---|
| 014.1 | The old docs and dashboard are gone | — | RM |
| 014.2 | A run's events outlive its worktree, in one place on the machine | — | JR |
| 014.3 | `/vstatus` answers from local files, with no model and no GitHub wait | 014.2 | VS |
| 014.4 | The conductor's routine comments come from one script, and each is an event | 014.2 | CM |
| 014.5 | `/vreport` gets the same treatment, except its "owed" reading | 014.3 | VR |
| 014.6 | The journal is a published interface, pinned by a roster suite and a fixture | 014.2 | JI |
| 014.7 | The dashboard exists, and its first page is a live `/vstatus` (in `ztrange/veri-dashboard`) | 014.3, 014.6 | DB, there |
| 014.8 | The dashboard gains the `/vreport` panel (in `ztrange/veri-dashboard`) | 014.5, 014.7 | DP, there |

014.1 and 014.2 can run at once. 014.3 and 014.4 can too: they touch different files except
`event.py`'s roster.

## What it costs today

Measured 2026-10-30 at `4fcf2d9ed5`, one sample each, with other conductors and suites running on
the machine, so these are upper-end readings rather than a clean baseline.

| read `/vstatus` makes | wall | CPU | what the wait is |
|---|---|---|---|
| `report-cache.sh refresh` (cache 14 h old, 1,409 issues) | 6 m 15 s | 37 s | `gh` fetching `body` and `comments` |
| `status.sh --json` | 10.7 s | 2.6 s | `issue_states()`, one `gh issue list --limit 1000` |
| `metrics.sh <n>`, per running run | 0.75–1.36 s | about the same | local |
| the subagent the skill requires past three reads | not measured | | a model turn over figures a script could print |

The bottleneck is GitHub and the model, not computing over local files. Three more facts shape the
design:

- **A merged run's events are destroyed.** `events.jsonl` is ignored by git, and
  `queued_merge.py:119` removes the worktree holding it. `~/.veri/` does not exist on this machine.
- **Two figures are parsed back out of agent-posted prose.** `report_cache.py:34-51` reads wall time
  and lane from the `### 📊 Metrics` comment, which is why the cache must fetch every comment.
- **The conductor writes every routine comment by hand.** #2691's thread holds 14 of them.
  `skills/tdd/SKILL.md` mentions comments on 36 lines, `BAIL.md` on 6, `STOPPING.md` on 4. What that
  costs in tokens is not measured; 014.4's first child measures it.

## 014.2: the journal

One issue. Adopts #546 decision 6 and extends it from an archive to the live path, so a reader
watches one directory and never hunts through worktrees.

| ID | Requirement | Why |
|---|---|---|
| JR1 | Every line `event.sh` appends to `.tdd/events.jsonl` is also appended, byte for byte, to `$VERI_HOME/runs/<owner>-<repo>/<issue>.jsonl` (`VERI_HOME` defaults to `~/.veri`). | Events survive worktree removal, and a reader has one place to look. |
| JR2 | The per-run `.tdd/events.jsonl` keeps its format and path; every existing reader of it is unchanged. | The run's own log must not depend on the journal. |
| JR3 | A failed journal write prints one stderr line naming the path and does not change `event.sh`'s exit code. | Telemetry must never bail a run, and a loud failure beats a silent one. |
| JR4 | Writing to the journal starts no process, and a line under `PIPE_BUF` is one `O_APPEND` write. | Conductors share a file only per issue, but a resume can overlap; a torn line would poison every reader. |
| JR5 | `hermetic_environment` points `VERI_HOME` at the case's `tmp_path`, and a case proves a suite run leaves the real `~/.veri` untouched. | Otherwise every test run writes fake runs into the operator's journal. |
| JR6 | The conductor emits `conductor-start` with `pid` and `started`; a reader tells a live run with `kill -0` on that pid and the same start-time check as the lock. | Liveness must not need a worktree's `conductor.pid`. |
| JR7 | A `plan` event with `steps=<n>` is emitted when the ledger is written and each time it grows. | Events say which steps finished but not how many exist (#546 decision 10). |
| JR8 | The `done` event carries `pr`, `wall_seconds`, `awake_seconds` and `lane`; a merge through `queued-merge.sh` emits `merged` with `pr`, `tag` and the tag's message. | These are what `/vstatus` now reads from comments and `gh`. |
| JR9 | Nothing deletes from `$VERI_HOME`, and leaf transcripts are never copied there. | Append-only is the promise (#546 decision 4); transcripts are not veri's format (decision 11). |

## 014.3: instant `/vstatus`

Two issues: the renderer, then the skill edit that uses it. The target is under a second on this
machine with five live runs, measured with `make profile` and quoted in the PR; per CLAUDE.md it is
not a criterion. The criteria are behaviours that force it: no `gh`, no model.

**Decision taken:** the Queue section reads a GitHub snapshot and prints its age, refreshing in the
background, which overturns `/vstatus`'s "never build the report from a stale cache". The
alternative, blocking on GitHub, keeps today's wait.

| ID | Requirement | Why |
|---|---|---|
| VS1 | `status.sh --report` prints the four sections `/vstatus` defines (Landed, Running, Queue, Waiting), with their deltas, from the journal, local tags and the snapshot. | One deterministic report, replacing a model assembling figures. |
| VS2 | With `gh` refusing, `status.sh --report` exits 0 and prints the same report. | This is the behaviour that makes it instant, and it is testable without a clock. |
| VS3 | Queue's first line states the snapshot's age. With no snapshot, Queue says so and the other three sections still print. | A stale figure is acceptable only when labelled. |
| VS4 | `status.sh --report` starts one detached `report-cache.sh refresh` when the snapshot is older than `VERI_SNAPSHOT_MAX_AGE` (default 60 s) and none is running, and never waits for it. | The next ask is fresh, and this one is not slowed. |
| VS5 | Moved to 014.5: the snapshot refresh fetches no `comments`; wall time and lane come from the journal (JR8). | Comments are the likely bulk of the 6 m 15 s, but `/vreport` reads them from the same cache until 014.5, and the refresh runs detached, so it does not slow the report. Confirm with `make profile` on the child. |
| VS6 | Running's awake wall time is the last event's `awake` minus the run's first. | `/vstatus` names this helper as missing and asks for `pmset` parsing, yet every event already carries `awake`. |
| VS7 | ETAs come from the journal's finished runs, under the existing rule, and read "no rate yet" below three. | History before the journal is lost; the rule recovers after three finished runs. |
| VS8 | `/vstatus` runs `status.sh --report`, prints it verbatim, and spawns no subagent. Exit 2 is reported and stops it. | The skill's whole cost becomes one command and its output. |
| VS9 | `.tdd/status-last` holds what the deltas need (time and queue counts), written only after a report printed. | A failed report must not swallow a delta. |

## 014.4: comments from one script

One issue per comment family, smallest first, so each landing saves something and a bad choice is
cheap to stop. Agents keep what only they know: a bail's question, refactor follow-ups, a park's
options.

| ID | Requirement | Why |
|---|---|---|
| CM1 | The first child measures what the conductor spends composing routine comments across five finished runs, and the PR states it. If it is negligible, the rest of 014.4 is rewritten to serve data alone. | The saving is unmeasured, and the case for it should be a number. |
| CM2 | `comment.sh <issue> <kind> [--note-file <path>]` renders the comment from the journal and ledger, posts it through `github.py`, and emits a `comment` event with `kind` and `url`. Exit 2 when GitHub gives no answer. | One call replaces a composed comment, and the thread stays the mirror of the journal. |
| CM3 | Families, in order: `✅ Step done`; `✅ Done` with Metrics; `🔴 Red` with `🔎 verify-red`; `🟢 Green`, `🛠️ Refactor`, `🔎 verify-green`, `🔎 verify-refactor` and `🔎 verify-<phase> (revised)`; `🗺️ Plan`, `🗺️ verify-plan`, `▶️ Resuming`; `⛔ Bailed`, `⏹️ Stopped`. `⏸️ Parked`, `♻️ Revise`, `📌 Already satisfied` and `⛔ Preflight refused` stay composed by the agent. | Most frequent first, and the ones carrying agent notes last. The verify family was split in two, and the start comment dropped, when filing on 2026-11-07: no start comment exists. |
| CM4 | A rendered comment's heading stays what `skills/vdev/`, `skills/vbail/`, `skills/vmerge/`, `run_conductor.py`, `stop-reason.sh` and `comment-class.sh` match today. | They branch on those headings (`veri-dev` and `veri-merge` were renamed since this row was written). |
| CM5 | Each family's `skills/tdd/` prose replaces its composing instructions with the one call, applied in a ⟦skill-edit⟧ step and regraded. | Graded prose moves through the graded path. |

Seven issues: 014.4a measures (CM1), and 014.4b to 014.4g are the six families of CM3 in order,
each blocked by 014.4a and by the family before it. 014.4b also lands `comment.sh` (CM2). If

## 014.5: instant `/vreport`

Same shape as 014.3, in three issues: the narrower refresh, the renderer, then the skill edit that
uses it. The "owed" reading stays a model call, since it judges prose, cached by `updatedAt` as
today. Measured 2026-11-07 at `010499da1d`, one sample: one `/vreport` cost a sonnet subagent
93,827 tokens and 85 s, with every PRD's owed answer stale. The target is that an ask with no PRD
updated since its last reading spawns no subagent; the criteria are the behaviours that force it.

| ID | Requirement | Why |
|---|---|---|
| VR1 | `report-cache.sh refresh` fetches `comments` only for `PRD`-titled issues and for issues closed in the last 7 days; every cached issue keeps its other fields, and `wallSeconds`, `lane` and `links` are unchanged for those issues. | This is VS5, narrowed: comments are the bulk of the 6 m 15 s, yet `links` needs them on PRDs and the lane rates need them on the last week's closures, mu's included, which this machine's journal does not hold. |
| VR2 | `report.sh --report` prints one block per open `PRD`-titled issue, ordered by PRD number, with solved, left (solvable now, waiting on a named blocker, held by no lane), ETA and owed, as `/vreport` defines them, from the snapshot, `.tdd/report-owed.json` and `solvable-issues.sh`. | One deterministic report, replacing a model assembling figures. |
| VR3 | With `gh` refusing and a snapshot present, `report.sh --report` exits 0 and prints the same report; it states the snapshot's age on its first line, and with no snapshot it says so and exits 2. | A stale figure is acceptable only when labelled; the report has nothing to show without the snapshot. |
| VR4 | A PRD whose cached `updatedAt` differs from the one stored in `.tdd/report-owed.json` (or has none) prints `owed: stale` instead of a figure, and `report.sh --stale` lists those PRDs' numbers, one per line. | The skill knows which PRDs need a model reading without reading any itself. |
| VR5 | `report.sh --store-owed <prd> <file>` stores the owed answer in `<file>` under that PRD with its current cached `updatedAt`, preserving every other PRD's entry. | The skill's subagent writes through one call, never by hand-editing JSON. |
| VR6 | `/vreport` runs `report.sh --stale`, sends only those PRDs' bodies to one subagent for the owed reading, stores each answer with `--store-owed`, then prints `report.sh --report` verbatim; with no stale PRD it spawns no subagent. Exit 2 is reported and stops it. | The skill's cost becomes one command plus a reading only where a PRD changed. |

Logic goes in a new module `skills/tdd/scripts/veri/report.py` behind a `report.sh` shim, per the
`status.sh` convention. VR1 is the first issue, VR2 to VR5 the second, VR6 (a ⟦skill-edit⟧ of
`skills/vreport/SKILL.md`, regraded) the third.

## 014.6: the journal as a published interface

Two issues: the roster and its suite, then the fixture. Keys and events are append-only, with no
schema version (#546 decisions 4, 16).

| ID | Requirement | Why |
|---|---|---|
| JI1 | `skills/tdd/JOURNAL.md` names every event veri emits and, for each, the keys it carries and what each key means. | A reader outside veri needs one place to learn the format. |
| JI2 | A `tree_audit` case collects every event name emitted under `skills/` (`event.sh` call sites and `event.mark` calls) and fails, naming it, on one `JOURNAL.md` does not document. | A new event cannot ship undocumented. |
| JI3 | One journal captured from a real finished run on this machine is committed at `fixtures/journal/` with a note naming its run, commit and date. | The dashboard tests against what veri really writes, not what its authors remember. |
| JI4 | A case fails when an event name or key that appears in the fixture is missing from `JOURNAL.md`. | Removing or renaming a documented key breaks the published contract, and the case says which. |
| JI5 | No event carries a schema version key. | Append-only means a reader never needs to branch on a version (decision 16). |

JI1 and JI2 are the first issue, JI3 to JI5 the second.

## Boundaries with other PRDs

- **PRD 013 (#2668) GS4–GS5** push a run's events to a side ref so a second machine can read them.
  The journal is machine-local and neither needs nor blocks that. Until then, a run on another
  machine is invisible to `/vstatus` and the dashboard. Since 2026-11-07 mu builds the dashboard
  on its own machine, so mu's runs are missing from this machine's journal: the dashboard is
  developed against JI3's fixture, and 014.5's lane rates still come from comments (VR1).
- **PRD 012 (#1770) RC2** adds a recovery mode to `status.sh`, and **BG4** has `/vstatus` sum refactor
  passes. Whichever lands second rebases; none depends on the other.

## Considered and set aside

- **A database or a daemon that owns state.** Append-only files plus a tail reader need no
  invalidation (#546 decision 13), and veri must run with no service up.
- **A daemon that keeps the GitHub snapshot fresh.** One detached refresh per ask is enough for
  `/vstatus`; the dashboard process will refresh for itself.
- **Copying events only at worktree removal.** Simpler, but it loses a crashed run and serves no live
  reader.
- **A sub-PRD issue per `.k`.** Titles carry the grouping, so parent issues would be bookkeeping.
