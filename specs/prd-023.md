## 023.2: CI starts with a warm bytecode cache

**You get:** CI's workers import compiled modules and pre-rewritten test files saved by the last
push to `main`, instead of compiling all of them on every run. **Depends on:** nothing.

Estimated saving: part of the 14.8 s before the first case (locally, cold collection of the whole
suite took 40.1 s and warm 9.8–10.1 s): a guess until the PR body quotes CI before and after.
Cost: no runner minutes (the repo is public); cache storage within GitHub's free 10 GB per repo.

| ID | Requirement | Why |
|---|---|---|
| CA1 | `skills/tdd/scripts/veri/content_mtimes.py` (created) sets the modification time of every file `git ls-files` lists in the working tree to a value derived from that file's blob id, so two checkouts holding the same content give it the same mtime, and a changed file gets a different one. | Python and pytest accept a cached `.pyc` only when its header's mtime and size match the source's. |
| CA2 | `content_mtimes.py` run outside a git working tree exits 2 with one stderr line, and changes no file. | Exit codes are the API. |
| CA3 | `ci.yml`'s `gates` job runs `content_mtimes.py` after checkout and before `make test`. | A fresh checkout's mtimes would void every restored `.pyc`. |
| CA4 | The job sets `VERI_PYCACHE` to one path that is the same on every run, restores it from `actions/cache` before `make test`, under a key naming the runner OS and the Python version, falling back to the newest cache saved under that prefix. | The leg's manifest keys `.pyc` files by absolute path. |
| CA5 | The cache is saved only by a run on a push to `main`; a `pull_request` run restores and never saves. | See *Decisions*. |
| CA6 | A case proves that with sources stamped by `content_mtimes.py`, a test file and a `veri/` module each changed after their `.pyc` was cached run their new content in the next leg run. | A stale cache would turn a red change green; the leg's sha256 manifest is the guard, and this pins it under the new mtimes. |
| CA7 | The comment above `ci.yml`'s cache steps says what is cached, why mtimes are set from content, and that only `main` saves. | A decision that looks like a bug is explained where it is made. |
| CA8 | CLAUDE.md's paragraph under the *Commands* table says CI restores the bytecode cache the last push to `main` saved; `REQUIREMENTS.md` § `CLAUDE.md` gains row CM84 for it and `GRADED`'s `CLAUDE.md` line is re-signed. | CLAUDE.md states what CI runs and what it costs (CM13). |

## 023.5: process cases copy one template repository

**You get:** a process case that needs an empty repository gets a copy of one built once per
pytest worker, instead of running `git init` itself. **Depends on:** nothing.

Estimated saving: 20–60 s per full run (a guess from 2026-11-10, carried); it falls on `make test`
and CI only, since `make unit` runs no `process` case.

| ID | Requirement | Why |
|---|---|---|

| TR2 | `new_repo` makes each repository after a worker's first by copying one it built once in that worker; a case with an in-process spy on `repo_builder.git` sees no `init` call on a second `new_repo` in the same worker. | The saving is the `git init` per case; a call count is observed through the one wrapper (CLAUDE.md, *Testing idiom*). |

## What the 2 s goal implies

`make unit` is 30–45 times its target: 5,497 cases took 57 s (the owner, carried) to 68 s (pytest's
own figure at load 12–21, `3b95202b60`). Warm collection alone is 3.8–4.0 s per worker, and every
one of the four workers collects all 5,724 cases of `tests/py/unit`, so collection by itself is
twice the target before a case runs. The fixed cost per case was about 2 ms after #3615; what is
left is the cases' own bodies and collection.

No open sub-PRD closes that gap. 023.2, 023.5, 023.7, 023.8–023.18 and 023.9 shorten `make test`
and CI; 023.10 shortens every shim start, which `make unit`'s small cases do not make; 023.8 and its
siblings, like the four PRs of 2026-11-15, move cases into `make unit` and lengthen it. A 2 s
`make unit` needs one of: far fewer cases in the tier the per-step leaves run, cases selected by
what a change can affect (`affected-suites.sh` already names suites per change), or a target that
is not wall time on a loaded machine. Which one is settled (2026-11-15, see *Decisions*): "2 s" is
`make unit` plus a change's affected suites, with a looser target for the whole `make test`; every
row above holds under it.
