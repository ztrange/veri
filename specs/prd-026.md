# PRD 026 requirements: one dev session decides and merges; a decisions session holds what needs the human

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status: DRAFT. Settled with Mario on 2026-11-11. Every sub-PRD is an outline; rows are cut at
filing. Nothing is filed.**

## The goal

Today two operator sessions run veri: `vdev` drives the runs, and `vcoord` watches it, holds the
queue and priority, judges, merges, and asks the human. Every event worth text in the dev session
becomes a message to the coordinator (P4), which the coordinator reads, holds and relays. Fusing
the two removes that relay: one dev session decides and merges itself.

What the coordinator gave the human, a place where decisions wait, moves to a separate
**decisions session**. It holds only the items that need the human, notifies them, waits as
long as it takes, sends the answers to the dev session, and clears its own context so the next
item starts from nothing.

## PRD 026.1: a decisions session holds what needs the human

**What you get:** one session, beside the operator sessions, where every decision waiting on you
is listed. You get a push when an item arrives, answer there whenever you like, and the session
sends your answers on and starts clean for the next one. Today's vcoord feeds it, so this is
worth having even if the fusion never ships.
**Depends on:** nothing.

Outline:

- A new skill, `vdecide`, holds the decisions session's role. Every message that feeds the
  session tells it to load `vdecide` first, since a cleared session remembers nothing.
- The queue is `.tdd/decisions.md`: one entry per item, written in full as P4 asks (what is being
  decided, the options in words, what each costs), with the issue it is tied to, if any.
- The feeding role (vcoord here, vdev after 026.2) opens the session with `start_session`
  (`user_asked`) on a human turn, in its own permission mode, and records the session's id in its
  handoff.
- A new item is appended to the file, sent to the session with `SendMessage`, and pushed once
  with `PushNotification`.
- When the human answers, the session sends the answers to the feeding role, then calls
  `clear_session("self")`. The feeding role removes the item from the file once it observes its
  own action on the answer, and clears the session when the self-clear was dropped.
- An item `vjudge` can settle never enters the queue.

## PRD 026.2: vdev takes over vcoord's duties

**What you get:** one dev session that launches, judges, sets priority, refills, merges and
feeds the decisions session. No coordinator is needed to run veri.
**Depends on:** 026.1.

Outline:

- vdev takes vcoord's queue and priority over `solvable-issues.sh`, the `parked` handling, merge
  rulings, refills, and the `vjudge` gate on every question.
- vdev's D8 list of stop-and-ask cases becomes "queue for the decisions session and keep running
  the rest": nothing a run can continue without is asked while other work is takeable (P5).
- vdev's handoff carries the decisions session's id and the queue's path as state.
- Investigation, reviews and merges go to subagents (P6), so the fused session's context grows
  only by conclusions.

## PRD 026.3: vcoord is retired, and the principles speak of one role

**What you get:** the repo describes the operator model that is actually run.
**Depends on:** 026.2.

Outline:

- `skills/vcoord/` and its `GRADED` entries are removed; every reference to vcoord in skills,
  specs that are still open, README and CLAUDE.md is rewritten or dropped.
- P4 loses its "when a coordinator is attached" clause. P13 covers vdev ↔ decisions session and
  machine ↔ machine messages. `operator/REQUIREMENTS.md` rows follow.
- Memory rules that only applied to the coordinator (watch quietly, coordinator messages the dev
  session, never block on the question box) are re-homed in vdev or vdecide, or deleted when the
  fusion makes them moot (PRD 020's rule: the repo is the only copy).
