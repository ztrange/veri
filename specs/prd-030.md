# PRD 030 requirements: the journal is the one file veri promises a reader

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status: draft, written 2026-11-14. D1–D9 are Mario's answers of that day to two rounds of
questions. 030.1 and 030.2 carry rows; 030.3 to 030.5 are outlines. `PUBLISHED.md` and
`event_table.py` are working names. 030.1's rows were rewritten on 2026-11-15 against `cde4e1adb1`
(see *What changed overnight*); D1–D9 stand.**

## The goal

A reader outside veri (a dashboard) can rely on what veri writes without reading veri's code, and
veri cannot break that reader by accident.

Veri promises exactly one file, the journal, because it is the only one that is live and costs veri
nothing: it is written as each event happens. Everything else a reader wants (lanes, parked issues,
the queue, a PRD's children, the text of an open decision) is GitHub's, and the reader asks GitHub
itself. Veri does no work whose only purpose is to keep a file fresh for a reader.

Today the promise is half kept: `skills/tdd/JOURNAL.md` documents 45 events, but only the 22 that
one captured run happened to emit have their keys checked, and nothing in the code says which keys
an event carries.

## What this PRD does not hold

- **The dashboard.** It lives in `ztrange/veri-dashboard`. That it stops reading
  `report-cache.json` and starts reading GitHub is that repository's plan. Veri still holds no
  dashboard path, rule or test (PRD 014, *014.7 and 014.8*).
- **New events for a reader's sake** (a lane at run start, `parked`): see *Open*.
- **Events reaching a second machine**: PRD 013 (GS4–GS5).
- **`/vreport` and `/vstatus`**: they keep reading `report-cache.json` exactly as today.

## Facts

Read on 2026-11-14 with `origin/main` at `1e637c522c` (veri) and `aa3c5fd` (veri-dashboard), on
the development Mac.

**What the three candidate files are.**

| File | Contents | Freshness on this machine | Cost to veri |
|---|---|---|---|
| `$VERI_HOME/runs/<owner>-<repo>/<issue>.jsonl` (`VERI_HOME` defaults to `~/.veri`) | one JSON line per event of a run; 269 runs, 37 MB | live | none: `event.py` writes it right after `.tdd/events.jsonl`, same bytes |
| `.tdd/report-cache.json` | a copy of GitHub: 1,895 issues and the landed tags; 3.3 MB | 47 hours old | a GitHub fetch per refresh, made only by `/vreport` and `/vstatus` |
| `.tdd/report-owed.json` | per PRD, the work its text names that no issue covers; 4 KB | 47 hours old | a subagent per changed PRD, inside `/vreport` |

**The journal.**

- One write path: `event.mark` → `append` → `line` (`veri/event.py`); `event.sh` goes through the
  same `main`. Each line carries `ts` and `awake` as JSON numbers, then `issue`, `actor`, `phase`,
  `step`, `event`, `attempt`, `skill_commit` and the event's own keys, every one a JSON string.
- No table of events or keys exists in code. `event.CONTEXT` lists the common keys; the only
  write-time check is the `structural-pass` refusal.
- Guards: `test_journal_event_roster.py` checks event *names* found by a regex scan of `skills/`
  against `JOURNAL.md`; `test_journal_fixture_keys.py` checks *keys*, but only those in
  `fixtures/journal/3277.jsonl`, which holds 22 of the 45 documented events;
  `test_journal_no_schema_version.py` refuses a version key. No test takes keys from the emitting
  code.
- `JOURNAL.md` names only `.tdd/events.jsonl`. The journal's path is stated for a reader only in
  `specs/prd-014.md` (JR1) and `fixtures/journal/README.md`. `JOURNAL.md` is not a graded unit.
- A run with no issue or no `origin` remote writes no journal, without a word.

**The two JSON files.**

- `report-cache.json`: top-level `cache_format` (2), `fetched_at`, `issues`, `landed`, `since`.
  `SCRIPTS.md` documents the top-level and `landed` keys, not an issue record; no test pins the
  shape. Written atomically (`report_cache.py`).
- `report-owed.json`: `{<prd>: {updatedAt, answer: {count, sections}}}`. Its path is relative to
  the working directory, and it is overwritten in place with `open("w")` (`prd_report.py`), so a
  reader can catch it half-written.

**What the dashboard reads today** (`serve.py`): the journal events `plan`, `step-done`, `launch`,
`verdict`, `usage`, `bail`, `done`, `merged`; `report-cache.json`; `report-owed.json`. It reads no
`gh` and no git. Four defects against today's files: it globs `runs/*.jsonl` where veri writes one
directory deeper; it raises on a live run's `usage` event (it reads a `name` key that event lacks);
it raises on any malformed line; it raises when `VERI_HOME` is unset. Its journal fixture is a
byte copy of veri's from 2026-11-11; its cache fixture is hand-written.

**What a reader wants, and where it is.**

| Wanted | Source |
|---|---|
| running runs, step progress, cost, bails with cause, done, merged, history | the journal |
| current lanes (`taken:<lane>`), parked (`parked`), the queue, a PRD's children | GitHub labels and issues |
| an open decision | the journal says a run bailed `needs-user`; the question is in the GitHub comment |
| owed work per PRD | only `report-owed.json` |

## What changed overnight

Read on 2026-11-15 with `origin/main` at `cde4e1adb1`, after the architecture rounds of
2026-11-14/15 landed.

- `veri/journal_schema.py` reads `JOURNAL.md`'s table (`kinds`, `fields`, `optional`) and finds the
  Python calls that write an event with `ast` (`writer_calls`).
- `tests/py/unit/test_journal_fields_audit.py` fails when a Python writer passes a literal key its
  event's row in `JOURNAL.md` does not list. This is half of the old ET6, with the page as the
  source of truth where D3 makes the code the source.
- That audit found five events veri writes that `JOURNAL.md` has no row for: `grading`,
  `unpinnable-missing`, `prose-owed-waived`, `suite-flake`, `skill-edit-no-author`. They sit in its
  `UNDOCUMENTED_KINDS` list. `event_roster`'s regex scan misses them, so veri emits at least 50
  events, not 45.
- Still missing: any check of a key written through `event.sh` from a shell script or the
  procedure's prose; any check in the other direction (a documented key nothing writes); any check
  at write time; which keys are required, stated anywhere but in a row's prose.
- `veri/event_log.py` is the journal's reader inside veri. Nothing in 030.2 is affected:
  `PUBLISHED.md` does not exist, and `event.journal_path(clone, issue)` is the one place the
  journal's path is computed.

D3 stands (the table lives in code): 030.3 needs a format per key, which a prose table cannot
carry. So the audit that exists is kept and repointed at the table, and `journal_schema`'s reading
of the page becomes the page's side of the comparison.

## Decisions

| | Decision | Rejected |
|---|---|---|
| D1 | The journal is the only file veri promises. `report-cache.json` is private: its shape may change freely. | Publishing the cache too. It is fresh only when someone runs `/vreport`, so a near-real-time reader would need veri to poll GitHub for it. |
| D2 | One document, `skills/tdd/PUBLISHED.md`, names the published set, each file's path, writer and rules, and names what is private. `JOURNAL.md` stays the event table and is linked from it. | Growing `JOURNAL.md` to hold the rules for other files. |
| D3 | A table in code declares every event, its keys and which are required. `JOURNAL.md` is checked against it. Under the test suite an event written with an undeclared event name or key, or without a required key, fails; in a real run the event is written as today. | Refusing the event at run time: a logging mistake would bail a run (JR3's rule, telemetry never bails). |
| D4 | Journal values stay strings (`ts` and `awake` stay numbers). The table adds a declared format per key (whole number, decimal, URL, a closed list of values) and the tests check it. | Writing typed JSON values: it changes existing keys, which append-only forbids. |
| D5 | Every published file is append-only in its keys and is written so a reader never sees half of it. `cache_format` stays a private detail of the cache. | Versioning the journal (PRD 014 JI5 stands). |
| D6 | Veri keeps the real captured journal and adds a generated sample holding one line per declared event, checked against the table. | Waiting for real runs to emit all 45 events; the rare ones may never appear in one capture. |
| D7 | The dashboard's four defects are filed as one issue in `ztrange/veri-dashboard`, once 030.2 is on `main` so the issue can cite the page. Mario approved the filing on 2026-11-14. | Fixing them from a veri session: work in another repository is not a veri session's call. |
| D8 | `report-owed.json` is published as **optional**: it may be absent or old, and each entry carries when it was computed. | Not publishing it, which leaves a reader no way to show owed work, since only a model computes it. |
| D9 | Veri adds no event for a reader's sake now: lane and parked come from GitHub labels. | Two new events (lane at run start, `parked`). Kept under *Open*; append-only makes them addable later. |

## 030.1 — an event's keys are declared in code, and the page cannot drift from them

Mario gets: no event can ship with a key the published page does not name, and no documented key
can vanish unnoticed, for every event veri emits and not the 22 a capture holds. Depends on nothing.

| ID | Requirement | Why |
|---|---|---|
| ET1 | `veri/event_table.py` holds one table: for every event veri emits, its keys and, per key, whether it is required. It imports no other veri module. | The emitter, the tests and the page need one answer to "what does this event carry", and a table with no imports can be read alone. |
| ET2 | A case fails, naming the event and key, when the table and `JOURNAL.md`'s table differ in either direction: an event or key in one and not the other. The page is read through `journal_schema.kinds` and `journal_schema.fields`, not a second parser. | The page is the contract a reader sees; the table is what the code obeys. Either drifting breaks the promise. |
| ET3 | With `VERI_EVENT_STRICT=1`, `event.sh` and `event.mark` exit 2 and write nothing, naming the event and key on stderr, for an event name not in the table, a key not declared for it, or a required key that is missing. | A wrong event must fail somewhere before it ships. |
| ET4 | Without `VERI_EVENT_STRICT`, the same calls write the line and exit as today, printing nothing more. | Telemetry never bails a run (PRD 014 JR3). |
| ET5 | The `hermetic_environment` fixture sets `VERI_EVENT_STRICT=1`, so every case that emits an event checks it against the table. | The suite already emits most events through the real code path; this makes each of those emissions a check. |
| ET6 | `test_journal_fields_audit.py` compares the literal event names and keys of Python writer calls against the table, not against `JOURNAL.md`, and its two ratchet lists (`UNDOCUMENTED`, `UNDOCUMENTED_KINDS`) are gone. | One source of truth; with the page tied to the table by ET2, a ratchet list is a second place a gap can hide. |
| ET7 | `test_journal_fixture_keys.py` checks the fixture against the table, not against `JOURNAL.md`. | The same. |
| ET8 | `run_conductor.py` neither sets nor forwards `VERI_EVENT_STRICT`, and a case pins that a run's leaf environment does not carry it. | A strict run would turn a logging mistake into a bail. |
| ET9 | `SCRIPTS.md`'s `event.sh` entry states the strict mode and its exit 2. Graded by the issue's `## Requirements` row. | The catalogue is where a script's exits are looked up. |
| ET10 | The table and `JOURNAL.md` each hold the five events veri writes that the page has no row for today: `grading`, `unpinnable-missing`, `prose-owed-waived`, `suite-flake`, `skill-edit-no-author`, with the keys their writers pass. | ET2 cannot pass while the page is missing events the code emits. |
| ET11 | A `tree_audit` case collects every `event.sh <name> key=…` call site in a `.sh` or `.md` file under `skills/` whose event name and keys are literal, and fails, naming the site, on an event name or key the table does not declare. | Events the conductor types from the procedure's prose never run under the suite, and the Python audit cannot see them; their keys are only visible at the call site. |

## 030.2 — one page says what a reader may rely on

Mario gets: a page to hand the dashboard's author, with the journal's path and the rules, and a
guard that keeps it true. Depends on nothing; worth having without 030.1.

| ID | Requirement | Why |
|---|---|---|
| PB1 | `skills/tdd/PUBLISHED.md` lists the published files: the journal, and `report-owed.json` marked optional. For each: its path and how the path is resolved, which script writes it, and when. | A reader needs one place, and today the journal's path is only in a spec. |
| PB2 | It states the journal's path as `$VERI_HOME/runs/<owner>-<repo>/<issue>.jsonl` with `VERI_HOME` defaulting to `~/.veri`, and that a run with no issue or no `origin` remote writes none. | The dashboard globbed one directory too shallow for lack of this sentence. |
| PB3 | It states the journal's line shape: one JSON object per line, `ts` and `awake` numbers, every other value a string, the common keys in order, and that the events and their keys are `JOURNAL.md`'s. | The page must be enough to write a parser. |
| PB4 | It states the rules: events and keys are only ever added; no schema version; a reader ignores an event or key it does not know and survives a line that is not valid JSON. | Append-only is a promise on both sides: veri adds, the reader tolerates. |
| PB5 | It names what is private and may change without notice: `report-cache.json`, `.tdd/status-last`, `conductor.pid`, the worktree's `.tdd/events.jsonl` path, and every other file under `.tdd/`. | A reader that knows what not to read does not break when it changes. |
| PB6 | It says nothing of any reader: no dashboard name, path or rule. | Veri never knows the dashboard exists (PRD 014). |
| PB7 | A case fails when the path `PUBLISHED.md` states for the journal differs from the one `event.py` writes to, read from the code and not retyped in the test. | A page that states a path is a page that can go stale. |
| PB8 | `JOURNAL.md` opens by naming the journal's path and pointing at `PUBLISHED.md`, and keeps `.tdd/events.jsonl` as the run's own copy. | The event table is where a reader lands first. |

## Outlines

- **030.3: every key has a declared format.** The table gains a format per key (whole number,
  decimal, URL, a closed list); strict mode checks it; `JOURNAL.md` shows it. The open-ended lists
  (`bail`'s `cause`) are closed or marked open. Depends on 030.1.
- **030.4: a sample journal with one line per declared event.** Generated from the table,
  committed beside the real capture, regenerated and checked by a case. Depends on 030.1.
- **030.5: `report-owed.json` is safe to read.** Written atomically, at a path that does not depend
  on the working directory, its shape pinned by a case and stated in `PUBLISHED.md`. Depends on
  030.2.

## Open

- **A lane at run start and a `parked` event** (D9's alternative). Recommendation: not now. Needed

- **Whether `JOURNAL.md` and `PUBLISHED.md` become graded units.** Recommendation: no. ET2 and PB7
