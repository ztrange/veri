# PRD 030 requirements: the journal is the one file veri promises a reader

The format is `specs/utility-skills.md`'s: each row makes one claim a reviewer, a grader or a test
can mark true or false; IDs are stable, and a dropped row leaves a gap.

**Status (2026-11-17): every sub-PRD is filed and closed: 030.1a #3836, 030.1b #3837, 030.2 #3835, 030.3 #4019, 030.4 #4020, 030.5 #4021, 030.6 #4022. Nothing is open; D10's deferral (the lane at run start, the `parked` event) stands. D1–D9 are Mario's answers of 2026-11-14 to two rounds of questions. `PUBLISHED.md`, `event_table.py`, `VERI_EVENT_STRICT`, `journal_sample.py` and `sample.jsonl` are working names. 030.1's rows were rewritten on 2026-11-15 against `cde4e1adb1` (see *What changed overnight*); D1–D9 stand.**

## The goal

A reader outside veri (a dashboard) can rely on what veri writes without reading veri's code, and
veri cannot break that reader by accident.

Veri promises exactly one file, the journal, because it is the only one that is live and costs veri
nothing: it is written as each event happens. Everything else a reader wants (lanes, parked issues,
the queue, a PRD's children, the text of an open decision) is GitHub's, and the reader asks GitHub
itself. Veri does no work whose only purpose is to keep a file fresh for a reader.

Today the promise is half kept: `skills/tdd/JOURNAL.md` documents 45 events, but only the 22 that
one captured run happened to emit have their keys checked, and nothing in the code says which keys
an event carries.

## What this PRD does not hold

- **The dashboard.** It lives in `ztrange/veri-dashboard`. That it stops reading
  `report-cache.json` and starts reading GitHub is that repository's plan. Veri still holds no
  dashboard path, rule or test (PRD 014, *014.7 and 014.8*).
- **New events for a reader's sake** (a lane at run start, `parked`): see D10.
- **Events reaching a second machine**: PRD 013 (GS4–GS5).
- **`/vreport` and `/vstatus`**: they keep reading `report-cache.json` exactly as today.

| | Decision | Rejected |
|---|---|---|
| D1 | The journal is the only file veri promises. `report-cache.json` is private: its shape may change freely. | Publishing the cache too. It is fresh only when someone runs `/vreport`, so a near-real-time reader would need veri to poll GitHub for it. |
| D2 | One document, `skills/tdd/PUBLISHED.md`, names the published set, each file's path, writer and rules, and names what is private. `JOURNAL.md` stays the event table and is linked from it. | Growing `JOURNAL.md` to hold the rules for other files. |

| ID | Requirement | Why |
|---|---|---|

the path `event.journal_path` builds. `JOURNAL.md` has 45 event rows (`grep -c` of its row

`test_journal_no_schema_version.py`), so a second file there is checked by both without a change

(`fixtures/journal/README.md`).

**`report-owed.json`.**

- Written only by `report.sh --store-owed <prd> <file>` (`prd_report._store_owed`), which
  `/vreport` runs once per PRD a subagent read (`skills/vreport/SKILL.md`, step 2); the skill
  forbids writing the file any other way.
- Path: `prd_report.OWED = ".tdd/report-owed.json"`, relative to the working directory, for the
  writer and for both readers (`--stale`, `--report`). `report_cache.refresh` resolves its own file
  from `run_dir.main_tree_from_files()` instead.
- Written in place: `open(OWED, "w")` then `json.dump`, so the file is empty, then partial, until
  the dump ends. `report_cache.refresh` writes with `tempfile.mkstemp` in `.tdd/` and `os.replace`.
- Shape: `{<prd>: {"updatedAt": <the PRD issue's updatedAt in the cache>, "answer": <the file's
  JSON, unchecked>}}`. `--report` reads `answer["count"]` and `answer["sections"]`; nothing checks
  either at store time. No entry says when it was computed.
- A missing file: `--report` reads it as `{}` (`prd_report._owed`), so every PRD prints
  `owed: stale`; `--stale` opens it unguarded (`prd_report._print_stale` calls `_load(OWED)`), so
  the `FileNotFoundError` reaches `entry.exit_code` and the script exits 2 instead of listing every
  PRD. No case covers that: `grep -n "^def test_.*stale\|missing"
  skills/tdd/scripts/tests/py/unit/test_prd_report.py` finds three `stale` cases, each of which
  writes the file first, and no `missing` one.
- An entry with no `answer` key (the older shape) counts as stale in both readers.

## 030.3 — every key has a declared format

**You get:** a reader can parse every value of every event by a format the page states, and the
captured journal is checked value by value, not only key by key. **Depends on:** 030.1a (#3836).

The write-time check of formats is 030.6, so this piece stands without 030.1b.

| ID | Requirement | Why |
|---|---|---|
| FM1 | `veri/event_table.py` declares one format for every key of every event and for each string common key (`issue`, `actor`, `phase`, `step`, `event`, `attempt`, `skill_commit`), from a closed set the module defines: `whole` (decimal digits only), `decimal` (digits with at most one `.`), `url` (starts `https://` or `http://`), `sha` (7 to 40 lowercase hex digits), `json` (parses as JSON), `text` (any string), and a list of values (one of the values listed). | D4: values stay strings, and the format says how to read one. |
| FM2 | The table states per key whether the empty string is a valid value; a key not so marked is invalid when empty, whatever its format. | `merged`'s `tag` is empty when no tag was cut, while an empty `pr` is a broken line; a format alone cannot tell them apart. |
| FM3 | A case fails, naming the file, line, event, key and value, when a value in `fixtures/journal/*.jsonl` does not match its key's declared format. | The real capture is the first evidence that the declared formats are the ones veri writes. |
| FM4 | `JOURNAL.md` states every key's format, every list's values written out; a case fails, naming the event and key, when the format the page states differs from the table's. The page is read through `journal_schema`, which gains the reader for it, not a second parser. | The page is the contract a reader sees (ET2's reasoning, for formats). |
| FM5 | No key is declared with an open-ended list: a key whose values the page lists is a list format, and a key with no fixed set of values is `text`. `JOURNAL.md` ends no list with `…`. | A list a reader cannot trust to be complete is no format. |
| FM6 | The table's values for `bail`'s `cause` are exactly the keys of `classify_bail.CATEGORIES`, and for its `classification` exactly `process` and `system`; a case fails naming each cause in one and not the other. `event_table.py` still imports no veri module (ET1): the case reads both. | `bail`'s `cause` is the one list open today, and `classify-bail.sh` already refuses a cause it does not know. |
| FM7 | `PUBLISHED.md` states that each key has a format stated in `JOURNAL.md`, that a list may gain values as events and keys may (D5), and that a reader treats a value it does not know as it treats a key it does not know. `skills/tdd/REQUIREMENTS.md`'s `## skills/tdd/PUBLISHED.md` section gains this row, and `skills/tdd/GRADED` is re-signed. | Append-only applies to values once a list is closed; the reader must be told to tolerate a new one. |

## 030.5 — `report-owed.json` is safe to read

**You get:** a reader of the owed answers never sees half a file, finds it at one place whichever
directory `/vreport` ran in, and can tell from the page what a missing file and an old entry mean.
**Depends on:** 030.2 (#3835).

The file keeps its path in the main working tree and every key it has (D5), so nothing here needs
a reader to change.

| ID | Requirement | Why |
|---|---|---|
| OW1 | `report.sh --store-owed` writes the new file under a temporary name in the same `.tdd/` directory and renames it over `report-owed.json`. With the rename made to fail by a case, the previous file is byte-identical, no temporary file is left in `.tdd/`, and the script exits 2. | D5: a reader never sees half of a published file; today an `open("w")` empties it first. |
| OW2 | `--store-owed`, `--stale` and `--report` all use `<main working tree>/.tdd/report-owed.json`, the main working tree found by `run_dir.main_tree_from_files()` as `report_cache.refresh` finds it: run from a linked worktree or a subdirectory, the store writes, and the reads read, that file. | A path relative to the working directory puts the file wherever `/vreport` happened to run. |
| OW3 | With no `report-owed.json`, `report.sh --stale` prints the number of every active PRD and exits 0, and `--report` prints `owed: stale` for each, as it does today. | A missing file means no answer is stored yet, which is not a failure; today `--stale` exits 2 on it. |
| OW4 | Each entry `--store-owed` writes carries `computedAt`, the UTC time of the store as `YYYY-MM-DDTHH:MM:SSZ`, beside `updatedAt` and `answer`, whose meaning is unchanged; an entry without `computedAt` is read as before and is not stale for that reason. | D8: each entry says when it was computed. A new key is an addition, and older files stay readable. |
| OW5 | `--store-owed` exits 2, naming the answer file on stderr, and leaves `report-owed.json` byte-identical when the answer is not a JSON object holding `count`, a whole number of 0 or more, and `sections`, a list of strings. | The readers index `count` and `sections`; today any JSON is stored, so the shape the page states would not hold. |
| OW6 | `PUBLISHED.md`'s section on `report-owed.json` holds a JSON example of the file with one entry; a case fails, naming the key, when the keys of that example differ, at any level, from those of a file `--store-owed` writes in the case. | The page states the shape and the writer makes it; a case keeps the two from drifting. |
