# PRD 012 requirements: a run's preconditions, checked; usage, paced

This is the requirements list for PRD 012 (#1770). Its child issues cite the IDs below, so it
lives on `main`, where a leaf can read it. The format is `specs/utility-skills.md`'s: each row
makes one claim a reviewer, a grader or a test can mark true or false; **Why** is never shown to
the grader; IDs are stable, and a dropped row leaves a gap. When a skill is written, its rows
move to `skills/<name>/REQUIREMENTS.md`.

**Status: draft.** Children are filed only after the operator reviews this file, and stay
un-opted-in (no opt-in label) until the issue queue drains.

The milestone has three parts:

| part | what | built as |
|---|---|---|
| 1. Permissions | #1770 as drafted: one probe per dependency a run uses, all failures in one table, a per-clone record | code (`/tdd`), rows PM below |
| 2. Test command | the repo declares a fast tier and a full tier, both resolve, and both run green with exit 0 on the default branch's tip | code (`/tdd`), rows TC |
| 3. Pacing | launches stop while the 5-hour window burns faster than 20 points an hour, or the weekly window faster than 15 points a day | code (`/tdd`), rows PC; prose, rows VP |
| — | `veri-doctor`, the operator skill that runs parts 1 and 2 on demand and reports | prose, rows DR |

## TC: the test-command check (code, built by veri under `/tdd`)

| ID | Requirement | Why |
|---|---|---|
| TC1 | `check-test-command.sh [repo-root]` resolves both tiers with `detect-test-command.sh --tier fast` and `--tier all`. A tier that resolves to nothing (exit 3) is a failing row whose fix names the `veri: fast tests: <cmd>` / `veri: all tests: <cmd>` CLAUDE.md line and `.veri/test-command` as the two places to declare it. | A run today learns at preflight that it has no command, and then asks a human (SKILL.md *Detecting the test command*). |
| TC2 | A fast tier that resolves to the same command as the full tier is reported as a row `fast tier = full tier`, which does not fail the check. | Every green and refactor verdict runs the fast tier; when it is the full suite each verdict pays the full suite's time. Legal, but the operator should know. |
| TC3 | Each tier runs once, in a detached worktree of the default branch's tip under `.tdd/`, through `detach-command.sh`. The row passes iff the command exits 0. A non-zero exit fails the row, and the found column carries the exit code and the last non-empty line of the output. | A red baseline makes the conductor refuse to start (CLAUDE.md, `make test`). Finding it now costs one suite run, not a run's planning. |
| TC4 | Each tier's row carries its wall time. The time never fails the row. | Wall time is observed, not gated (CLAUDE.md: CI's `timeout-minutes` is the only wall-clock gate). |
| TC5 | The check removes the worktree it made on every exit path, and leaves the target repo's tree, index and branches as it found them. | It is a read of the repo's health, not a write. |
| TC6 | The report is PM3's table — dependency, found, fix — with PM4's exit codes: any failing row exit 2, all passing exit 0. | One table and one contract for every precondition. |
| TC7 | Port convention (`status.sh` worked example), as PM8. | |

Considered and set aside: probing the failure path (does the command exit non-zero when a test
fails?). Doing that needs a failing test written in the repo's own language and runner, which
is a project fact the check cannot know (P12). Every run's Red verdict already observes it.

## PC: the pacing decision (code, built by veri under `/tdd`)

| ID | Requirement | Why |
|---|---|---|
| PC1 | `usage-pace.sh record <window> <percent-used> <resets-at>` appends one sample (`at`, `window`, `percent`, `resets_at`) to `.tdd/usage.jsonl` in the main working tree. `<window>` is `5h` or `weekly`. A malformed argument is exit 2, and nothing is written. | The decision must be computed from committed-format data, so it can be tested without a model or the desktop app. |
| PC2 | `usage-pace.sh check [--no-weekly]` prints one line and exits 0 when a launch is allowed, 1 when it is held (`hold until <iso> — <window> +<n> pts in <span>, budget <b>`), 2 when it has no sample younger than 15 minutes for a rule it applies. | Exit codes are the API: a hold is a real answer, a stale read is no answer. |
| PC3 | The 5-hour rule: the window's points used in the trailing 60 minutes are at most `VERI_PACE_5H_PER_HOUR` (default 20). There is no flag that turns it off. | Mario: "the 5h restriction we may want to keep as an always on rule." |
| PC4 | The weekly rule: the weekly window's points used in the trailing 24 hours are at most `VERI_PACE_WEEKLY_PER_DAY` (default 15). `--no-weekly` skips it. | Mario: "Sometimes we do want to exceed the 15%." |
| PC5 | Points used in a trailing span are the latest sample minus the newest sample at or before the span's start; with no sample that old, the oldest sample counts as the start. A sample whose percent is lower than the one before it marks a window reset, and samples before a reset count as 0. | Sparse samples must make the rule stricter, never looser; a reset must not read as negative burn. |
| PC6 | `hold until` is the earliest time at which, with no further burn, the held rule would pass, or the window's `resets_at` if that is sooner. | The waiter needs a time to block until (P3), not a re-poll. |
| PC7 | A set-but-empty or non-integer `VERI_PACE_5H_PER_HOUR` / `VERI_PACE_WEEKLY_PER_DAY` is exit 2. | Same as every other tunable. |
| PC8 | `.tdd/usage.jsonl` keeps only samples younger than the longest span plus one hour; `record` drops older ones. | Unbounded run-state growth. |

## VP: `veri-pace`, the skill that applies PC (prose)

| ID | Requirement | Why |
|---|---|---|
| VP1 | Invoked as `/veri-pace` by the dev session before every launch (D2, D6) and by the coordinator on each watch event; never on a timer (P3). | The launch is the only thing pacing can stop (P8): a running conductor keeps spending whatever pacing says. |
| VP2 | It reads the account's plan windows with the desktop app's usage tool, and records the `5-hour limit` and `Weekly · all models` windows through `usage-pace.sh record`. | Per-model weekly windows (Fable) count toward the all-models one; pacing that one covers them. |
| VP3 | Usage status `not_applicable` (an API key, Bedrock, Vertex) means no plan limits: it allows the launch and says so once per session. Status `unavailable`, or no usage tool in the session, holds the launch: it says why in one line and re-reads at the next event. | Fail closed: the 5-hour rule is always on, and a rule that cannot be read is not a pass. |
| VP4 | On exit 1 the dev session does not launch, waits with a blocking wait until the printed time, then re-runs `/veri-pace`. The hold is one line to the coordinator (or the human with none attached): `Pace hold until <time> — <reason>`. | An important event by P4; a hold re-printed on every event is noise. |
| VP5 | The weekly rule is lifted only by the human, for a stated span, as `--no-weekly` until that time. The coordinator records the lift and its expiry in its state, so a handoff carries it (H4). No lift exists for the 5-hour rule. | The lift is a spend decision, the human's; its expiry is state, not rule (P2). |
| VP6 | Near its top, the skill says it obeys `operator/PRINCIPLES.md` and reads it first. | F11, GR6. |
| VP7 | `veri-dev` and `veri-coord` each gain one line pointing to `/veri-pace`, and copy none of its rules. | A copied rule drifts (D10). |

## DR: `veri-doctor`, check a project before veri runs in it (prose)

| ID | Requirement | Why |
|---|---|---|
| DR1 | Invoked as `/veri-doctor [repo-root]`, default the current repository's main working tree. | One command answers "can veri run here?". |
| DR2 | It runs the permission check with `VERI_RECHECK_PERMISSIONS=1` (PM), then `check-test-command.sh` (TC), and prints both tables as they come, then one line: `ready` or `not ready — <k> rows to fix`. | The human fixes everything in one round (PM3). |
| DR3 | It also reports the machine's floors the conductor refuses on (bash 5+, the Python floor) by running the same checks preflight runs. | A refusal at launch is the same finding, later. |
| DR4 | It grants nothing: it never runs a fix command, creates a label, or edits a settings file or CLAUDE.md. Each fix is shown for the human to run. | Out of scope in #1770; a settings edit is the human's. |
| DR5 | It reads every project fact (labels, test commands) from the target repo's CLAUDE.md through the scripts, naming none itself (P12). | |
| DR6 | Near its top, the skill says it obeys `operator/PRINCIPLES.md` and reads it first. Raw output (a red suite's log) goes to a subagent that returns at most 10 lines (P6). | |
