# PRD 012 requirements: cutting what veri costs to run

This is the requirements list for PRD 012 (#1770). Its child issues cite the IDs below, so it
lives on `main`, where a leaf can read it. The format is `specs/utility-skills.md`'s: each row
makes one claim a reviewer, a grader or a test can mark true or false; **Why** is never shown to
the grader; IDs are stable, and a dropped row leaves a gap. When a skill's rows are applied,
they move to `skills/<name>/REQUIREMENTS.md`. Rows that change graded prose are applied in a
⟦skill-edit⟧ step (PRD 011, K).

**Status: draft.** The operator settled every decision below in a grilling session on
2026-10-23/24, and part 7 on 2026-10-29. Children are filed after the operator reads this file, and stay un-opted-in
until the issue queue drains.

**Scope: optimizations only** (operator, 2026-10-29). Every part here cuts tokens, or spend wasted
on a run that cannot finish. Pacing (PC, VC), the judge and autonomous mode (JD), relative plan
growth (BG1, BG2) and run state on GitHub (GS) moved to PRD 013 (#2668, `specs/prd-013.md`) with their
IDs unchanged, so this file keeps gaps at 1, 3, 6, BG1–BG2 and slices 1, 2, 6, 7, 9, 12.

| part | goal | rows |
|---|---|---|
| 2. Recovery | `/clear` then `/vcoord` or `/vdev` resumes with nothing lost: the conversation is always redundant | RC |
| 4. Run cost | conductor restarts, revise and refactor rules set from measured runs | CR, BG |

## 2. Recovery

| ID | Requirement | Why |
|---|---|---|
| RC1 | Each role keeps `.tdd/role-<role>.state` in the main working tree: N and its ceiling, the lane, timed N changes, order overrides, weekly pacing and its expiry, each pending human decision in full, each message sent but not yet acked, the session id, `recovered-at`, the context at recovery end (the reset baseline, RC11), and the times of recent resets. The role writes it at the moment one of these changes, never at reset time. | After an hour idle, asking for a handoff re-writes the whole conversation at the cache-write price; a `/clear` discards it for free. That is only safe when the conversation holds nothing of its own. |
| RC2 | `/vcoord` and `/vdev` with no arguments recover from the role state file plus one command: a recovery mode of `status.sh` that prints, in a fixed compact form, the taken runs and whether each one's conductor is running (pid), the bailed runs and their class, open PRs and their merge state, a held merge lock, and the role's pending decisions and unacked messages. Recovery re-asks each pending decision once and re-sends or checks each unacked message. | Operator: "decide to clear the context and re-run vcoord and expect the run to resume gracefully." A deterministic report keeps a reset's fixed cost low (RC10) and makes RC3 testable; several turns of live reads would not. |
| RC3 | A slice proves RC2: a role cleared mid-queue reaches the same next action as before the clear. | The invariant is only real when it is tested. |
| RC4 | `veri-handoff` and the `--resume <file>` arguments are removed once RC3 passes, with their H rows. | Nothing ever needs a handoff. |
| RC5 | The coordinator resets itself at a quiet point (no merge in flight, no launch half done, no decision mid-answer) once its growth since the reset baseline (RC11) reaches 0.85 × `VERI_RESET_GROWTH_COORD` (default 70000 tokens); at 2 × that knob it resets at once, even mid-task. After 50 minutes without a turn it also resets, and stays cleared until its next incoming message (RS4). A reset writes `.tdd/reset-request-coord` and clears itself; the resetter (RS1–RS3) wakes it. | Each reset re-writes the floor and re-reads the state; each request without one re-reads the growth. The optimum growth is √(2·K·g / r): K a reset's fixed cost, g the growth per request, r the cache-read price; with today's handoff (K ≈ 150k units, g ≈ 0.8k) it is about 70k, with cost flat near it (+1% at 60k, +11% at 140k), so the session waits for a quiet point and the 2× line only stops drift. Growth, not context size, so a smaller floor leaves the knob valid; one knob per role so each floor can be tuned. Fifty minutes keeps the deciding turn inside the one-hour cache: a cold turn re-writes the whole context once before clearing. |
| RC6 | Before RC5, RC8 and RS1–RS4 are built, four spikes are run and recorded: (a) a cleared desktop session starts a turn on a message from another session; (b) a delivered message `/vcoord <lane>` loads the skill; (c) a session the role started keeps running, and can still message the role, after the role clears itself; (d) a session started on the operator's `/vcoord` turn is created at once, not proposed as a card. RC5, RC8 and RS1–RS4 are dropped if (a) or (c) fails. | All four are facts about the harness nobody has observed. A session clears itself with the app's own clear, so no `/clear`-as-a-message spike is needed. |
| RC7 | Filed early: #2310. At start each operator role switches off, for its own session only, every claude.ai connector its skill does not list as needed. | Connectors' tool definitions (~20k tokens on the coordinator, 2026-10-23) are paid on every turn. |
| RC8 | The dev session resets itself by RC5's rule with its own knob, `VERI_RESET_GROWTH_DEV` (default 70000 tokens); its quiet point is no launch half done and no merge in flight, and its marker is `.tdd/reset-request-dev`. | The dev session grows like the coordinator and has its own floor, so it has its own knob. |
| RC9 | No reset happens without at least one launch, merge or decision since the role's last recovery ack, nor more than `VERI_RESET_MAX_PER_HOUR` (default 2) in an hour. A refused reset is reported to the operator and never retried in a loop. | Recovery itself adds context; a recovery that cost more than the arm point would reset forever. |
| RC10 | Once RC4 lands, a reset's fixed cost is measured from real resets (RC2's command in place), and the three growth knobs' defaults are re-derived from it. | The 70k default assumes today's handoff; without one, loading the skills and reading the state still cost something, so the drop is measured, not assumed. |
| RC11 | One function measures a session's growth: its current context minus its baseline, both read from the transcript's usage. The baseline is the context at the role's recovery ack, not at its first request. A hook calls it on each turn and injects the arm or hard-limit reminder; it acts only for session ids registered in a role state file and exits silently for any other. The usage tool's context reading is the cross-check. | The model cannot count its own context, and a reminder the model must ask for is skipped under load; a hook fires every turn. Counting from recovery end keeps recovery's own reads out of the growth (RC9). Registered ids keep every other session in the repo untouched. |

### RS: the resetter (prose, `veri-coord` and `veri-dev`)

| ID | Requirement | Why |
|---|---|---|
| RS1 | On the operator's `/vcoord` or `/vdev` turn, each role starts one resetter session on Haiku and keeps it until the role ends, then archives it. | The app refuses a session start on a turn another session's message started, and a self-proposed start waits for a click, so a resetter per reset would mostly fail to start. |
| RS2 | The resetter waits in the background for the role's reset marker. Then it waits until the role is idle and its context has dropped, and only then sends `/vcoord <lane>` or `/vdev <lane>`. | A message that arrives before the queued clear runs drops the clear. |
| RS3 | The recovered role sends the resetter `ack`. With no ack within a timeout, the resetter reads `recovered-at`, re-sends a bounded number of times, then notifies the operator. After an ack it waits for the next marker; it never clears itself. | A failed reset is noticed instead of leaving a role silent. Clearing would erase the resetter's instructions and its wait, so the next reset would have no resetter unless re-armed, a step that can fail exactly when it is needed; its growth per reset is a few thousand Haiku tokens. |
| RS4 | After an idle reset (RC5), a hook makes the cleared role's next incoming message run recovery before anything else. | Resuming at once would write the floor now and again, cold, at the next message. |

## 4. Run cost

### CR: conductors

Basis: the conductor is 50–70% of a run's cost (#1668, #1653, #1720, #1915, #1719); on #1915
its context grew from 88k at turn 1 to 169k at turn 75. A restart re-writes the floor (~88k at
the cache-write price) and saves 0.1× the growth per later turn, so mid-issue restarts rarely
pay early; CR2 restarts at the growth that pays for one. Shrinking the floor is #2075 and #2218 (labelled `priority` on 2026-10-23).

| ID | Requirement | Why |
|---|---|---|
| CR1 | `metrics.sh <n>` reports the conductor's context at its first turn and at its largest. Filed early: #2309. | The floor's size is watched from run to run. |
| CR2 | When a conductor's growth since its first turn (RC11's function) passes 0.85 × `VERI_RESET_GROWTH_CONDUCTOR` (default 70000 tokens), the dev session stops it at its next ledger commit (`stop-run.sh --mode ledger`) and relaunches `run-conductor.sh <n>`, recording a `conductor-restart` event. | One growth rule for every role, so there is one measurement, not three. On #1915 (≈1.08k per turn) the optimum is about 65–80k; a ledger commit is the conductor's quiet point. |
| CR3 | The conductor's model is a knob, `VERI_MODEL_CONDUCTOR`, defaulting to Opus; the run records which model its conductor ran on. Filed early: #2308. Whether to trial a cheaper conductor is the operator's decision once it lands. | The conductor is 50–70% of a run's cost and its model is hard-coded (`run_conductor.py:204`), so no trial is possible without a code change. |

### BG: budgets

Basis (848 metrics reports): 85.6% of steps need no revise cycle; the exhausted path lands 55
of 61 runs; the three `revise-exhausted` bails repeated the same reason, so a larger budget
would not have saved them. `VERI_REFACTOR_BUDGET` stopped a pass in 1 of 598 runs; 72.7% of
passes landed nothing.

| ID | Requirement | Why |
|---|---|---|
| BG3 | `REVISE_BUDGET` stays 2 per step and phase, and the judge (PRD 013) does not raise it. A REJECT whose reason repeats the previous attempt's goes straight to the exhausted leaf. Filed early (the second sentence): #2311. | A third attempt on a repeated reason repeats it. |
| BG4 | Every metrics report shows refactor passes, transforms, passes that landed nothing and stop reasons, per step and per issue, and `/vstatus` sums them. | The operator wants to know refactor turns per issue before deciding to raise the budget after the quality passes. |
| BG5 | Decided 2026-10-24, filed as #2305: a step's refactor does an out-of-scope candidate that changes one of the step's own files, under a cover leaf. The share of passes stopping `structural-owed` (19% before ADR-0031) is reported once 30 runs have #2305. | Measured on the 51 runs after ADR-0031: for 8 of 11 out-of-scope candidates (73%) a later step changed the named code before the structural pass did, a median of 3 steps. |
| BG6 | No refactor in a PR, per-step or structural pass, changes only files the issue's commits never touched. A candidate beyond that bound, and every candidate the structural pass leaves not done (`uncovered`, `transform-rejected`, `budget spent`, `no predicate`), is listed in one issue per run, labelled `refactor` and `candidate`, never opted in. The coordinator grooms these with `veri-groom --refactor-owed` (GONE / FOLDS-INTO-OTHER / LIVE, live ones consolidated per module) and decides what is opted in. A new ADR records this partial reversal of ADR-0031's "never files". | Operator, 2026-10-24: a PR growing out of its issue's scope is undesirable, and an out-of-scope refactor is filed for the coordinator to groom and decide. Unlike the 118 refactor-owed issues before ADR-0031 (one per candidate, straight into the queue), this is at most one per run, outside the queue: 2 of the 51 runs after ADR-0031 had a leftover (#1980, #2206), and none had a candidate beyond the bound. |

## 7. Operator-session traffic

Basis: the dev session (CLI) and the coordinator (desktop), 2026-10-29 13:10–15:45, measured
from their transcripts. Dev: 96 Opus requests, 10.49M cache-read tokens, 29.9k output tokens;
coordinator: 48 requests, 5.16M cache-read, 8.5k output. At cache read 0.1×, cache write 1.25×
and output 5× the input price, cache reads are 78% and 80% of each session's cost; the text
the operator reads is 1.2k and 1.1k characters. Each request re-reads the whole context (median
112k dev, 110k coordinator), so the cost is the number of wakes × context, and context growth is
RC5/RC8's. Of those wakes:

- **Acks:** 7 bare acks from the coordinator (13:15, 13:59, 14:03, 14:18, 14:33, 14:39, 14:48)
  each cost it 2 requests (`SendMessage`, then `.`) and woke the dev session for a 1-request
  turn that did nothing: about 2M cache-read tokens, 13% of both sessions.
- **Watchers:** the dev session waits on four kinds of hand-armed Monitor (`watch-runs.sh`,
  `until [ -f …/issue-<n>.md ]` before the next launch, `while kill -0 <pid>` per queued merge,
  `until [ -f …/conductor.pid ]; sleep 45; watch-runs.sh`), and the coordinator runs its own
  `watch-runs.sh` over the same conductors. A `watch-runs.sh` under Monitor wakes twice per exit
  (the line, then "stream ended": 14:43:36 then 14:46:19). Wakes that only re-armed: coordinator
  13:40, 14:30, 15:15, 15:45; dev 13:45, 14:43, 15:16; about 1.6M cache-read tokens, 8%. An issue
  costs the dev session 6–8 wakes at 110–150k each, most of them launching or re-arming.
- **Inline investigation:** re-cutting #2543's ledger took the dev session 9 requests at about
  145k each (14:47:05–14:48:12, 1.31M cache-read), the first 5 sequential `grep`/`sed` calls
  learning how `add-ledger-step.sh` takes `instead-of` and where `tests_frozen.py` keeps its
  fixture constant; 14:01:21–14:01:44 was 3 more sequential greps of `tests_frozen.py`. None of
  `add-ledger-step.sh`, `queued-merge.sh`, `watch-runs.sh`, `solvable-issues.sh` or
  `stop-run.sh` answers `--help` (each exits 2).
- **Fixed floor:** the coordinator's 124k context was 94k fixed (38.9k system tools, 24.0k MCP
  tools, 12.4k system prompt, 10.6k memory files, 8.6k skills) and 29k conversation. MCP tools
  are RC7's; memory files are the operator's own (see *Outside veri* below).

| ID | Requirement | Why |

No other message between operator sessions is answered with an `ack`; a message gets a reply only when the receiver has a ruling, an instruction or a correction to send. P13, `veri-coord` C4 and its *Instructing the dev session* section, and `veri-dev`'s "reply `ack`" change to say so. | Operator, 2026-10-29: "we do not need an ack for every message … i only asked for ack on the comms check when starting vcoord / vdev session or after a reset." ### Outside veri

The operator's own memory (`~/.claude/projects/<veri>/memory/`, 80 files, a 86-line,
10,139-byte `MEMORY.md` index) is loaded on every request of every operator session, and is not
under version control. Trimming it is the operator's, not a slice: a memory that restates a rule a

## Considered and set aside

- **Restarting conductors per step or per N runs**: the floor dominates; CR2 restarts at the
  growth that pays for one restart.
- **A ratio to the floor** (`VERI_CONDUCTOR_RESTART_RATIO`, RC5's "growth reaches the floor"):
  the optimum growth moves at most with the square root of the floor (through K, which
  re-writes it), so a ratio over-corrects when the floor shrinks; a knob per role is tuned instead.
- **A detached bash resetter**: it cannot message a desktop session.
- **A resetter started and archived per reset**: the app refuses most of those starts (RS1).
- **A resetter that clears itself after each ack**: it would need re-arming after every reset
  (RS3).
- **The dev session as the coordinator's waker**: a resetter can retry and alert; the dev
  session may itself be mid-reset.
- **A judge-raised `REVISE_BUDGET`, or an unbounded refactor budget now**: neither budget binds
  on the measured runs. The refactor budget is revisited after the code-quality passes.
- **Checking that a failing test fails the command**: project code quality, not setup.
- **A structural pass that may touch any file**: the PR would grow beyond its issue. Out-of-bound work is filed for grooming instead (BG6).
- **Removing watchers from one role only**: the dev session's own waits (ledger, merge, re-arm)
  were most of its wakes, so one dispatcher replaces them (OT3) rather than the coordinator's
  copy alone.
- **No watcher at all**: the dev session would have to poll or be woken by the human; a blocking
  script that exits only on judgment is P3 already.
- **Keeping acks for delivery confirmation**: the effect read from state confirms it (OT2) at no
  extra wake.
