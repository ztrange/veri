# PRD 012 requirements: autonomy, pacing, recovery, and a run's state on GitHub

This is the requirements list for PRD 012 (#1770). Its child issues cite the IDs below, so it
lives on `main`, where a leaf can read it. The format is `specs/utility-skills.md`'s: each row
makes one claim a reviewer, a grader or a test can mark true or false; **Why** is never shown to
the grader; IDs are stable, and a dropped row leaves a gap. When a skill's rows are applied,
they move to `skills/<name>/REQUIREMENTS.md`. Rows that change graded prose are applied in a
⟦skill-edit⟧ step (PRD 011, K).

**Status: draft.** The operator settled every decision below in a grilling session on
2026-10-23/24. Children are filed after the operator reads this file, and stay un-opted-in
until the issue queue drains.

| part | goal | rows |
|---|---|---|
| 1. Pacing | the coordinator keeps the 5-hour window under 20% per hour of the window, always, and the weekly window under 15% per day when asked, by moving N between 1 and a ceiling | PC (code), VC (veri-coord) |
| 2. Recovery | `/clear` then `/vcoord` or `/vdev` resumes with nothing lost: the conversation is always redundant | RC |
| 3. Judge | a rebuilt `veri-judge` decides what the operator would, from his measured history, and an autonomous coordinator mode acts on it | JD |
| 4. Run cost | conductor restarts, plan growth, revise and refactor rules set from measured runs | CR, BG |
| 5. Preconditions | a project is checked once for every permission and every test-command declaration a run needs | PM (#1770), TC, DR |
| 6. Run state on GitHub | any machine can tell an issue's state and resume its run from GitHub alone | GS |

Build order: 1, 2, 3, 4, 5, 6. Parts 1–2 cut cost at once; 3 is needed by GS8; 6 is the largest.

Filed outside this milestone on 2026-10-24, because they cut every run's cost now: #2258
(develop-green probes its own guards), #2259 (verify-green names every unrequired item in one
REJECT), #2260 (a refactor that landed nothing launches no verify-refactor).

## 1. Pacing

### PC: the pacing decision (code, built by veri under `/tdd`)

| ID | Requirement | Why |
|---|---|---|
| PC1 | `usage-pace.sh record --5h <pct> <resets-at> --weekly <pct> <resets-at> --conductors <k>` appends one sample (`at`, both windows' percent and reset time, live conductors) to `.tdd/usage.jsonl` in the main working tree. A malformed argument is exit 2 and writes nothing. | The decision is computed from data on disk, so it is testable without a model or the desktop app, and a fresh session reads the same history (RC1). |
| PC2 | `usage-pace.sh n [--weekly]` prints `N=<k> — <reason>` and exits 0; exit 2 when the newest sample is older than 15 minutes. | Exit codes are the API: a stale reading is no answer. |
| PC3 | The 5-hour cap is absolute: percent used ≤ 20 × h, where h = ⌈(now − (resets_at − 5 h)) / 1 h⌉, from 1 to 5. Over the cap, N = 1. | Operator: "5h usage should be kept under 20% × hour index from 1 to 5 in the 5h window." The window's start comes from the usage reading's own reset time. |
| PC4 | With `--weekly`, the weekly cap is absolute too: percent used ≤ 15 × d, d = ⌈(now − (resets_at − 7 d)) / 24 h⌉, from 1 to 7. Over the cap, N = 1. | Operator: "when pacing, weekly usage kept below 15% a day." |
| PC5 | Under the caps, N is derived from the last 24 h of samples: r = Δpercent ÷ conductor-hours, counted only over spans inside one window (a lower percent or a changed `resets_at` starts a new window). N_5h = ⌊20 ÷ r_5h⌋; with `--weekly`, N_weekly = ⌊(15 ÷ 24) ÷ r_weekly⌋. With under 2 conductor-hours of data, N is the ceiling. | Operator: "n should be derived from what it has been able to sustain in average recently." |
| PC6 | N = clamp(min(N_5h, N_weekly when `--weekly`), 1, `VERI_MAX_CONDUCTORS`), default 5. N never goes to 0. | Pacing stops no running conductor (P8), so 0 and 1 have the same effect, and hard stops are not wanted. Operator: "max 5 unless I explicitly say so." |
| PC7 | A set-but-empty or non-integer `VERI_PACE_5H_PER_HOUR` (default 20), `VERI_PACE_WEEKLY_PER_DAY` (default 15) or `VERI_MAX_CONDUCTORS` (default 5) is exit 2. | Same as every other tunable. |
| PC8 | `record` drops samples older than 25 h. | Run state must not grow without bound. |

### VC: the coordinator's pacing mode (prose, `veri-coord`)

| ID | Requirement | Why |
|---|---|---|
| VC1 | Pacing is always on in the coordinator. On each watch event it reads the account's plan windows with the desktop app's usage tool, records them with `usage-pace.sh record`, and computes N with `usage-pace.sh n`. | The coordinator runs in the desktop app, which is the only place usage can be read; the dev session runs in the CLI. |
| VC2 | When N changes, the coordinator sends the dev session `N=<k> — <reason>` (P13), and tells the human only in a P4 one-liner. The dev session applies it at its next slot decision (D7). | The dev session launches; the coordinator only sets the count. |
| VC3 | Usage status `not_applicable` (an API key, Bedrock, Vertex) turns pacing off, said once. `unavailable` keeps the last N and re-reads at the next event. | No plan limit, no pacing; a missed reading must not undo the last decision. |
| VC4 | `/vcoord --pace-weekly` turns the weekly rule on; it is off by default. Its state is kept in the role state file (RC1). | Operator: "keeping under 15% a day is optional." |
| VC5 | Raising `VERI_MAX_CONDUCTORS` above 5 is the human's alone (JD3). | It is a spend decision, and 5 is above what veri sustains today. |

## 2. Recovery

| ID | Requirement | Why |
|---|---|---|
| RC1 | Each role keeps `.tdd/role-<role>.state` in the main working tree: N and its ceiling, the lane, timed N changes, order overrides, weekly pacing and its expiry, each pending human decision in full, and each message sent but not yet acked. The role writes it at the moment one of these changes, never at reset time. | After an hour idle, asking for a handoff re-writes the whole conversation at the cache-write price; a `/clear` discards it for free. That is only safe when the conversation holds nothing of its own. |
| RC2 | `/vcoord` and `/vdev` with no arguments recover from the role state file plus live reads (`status.sh`, open PRs, issue labels and pointer comments, GS). Re-asks each pending decision once, re-sends or checks each unacked message. | Operator: "decide to clear the context and re-run vcoord and expect the run to resume gracefully." |
| RC3 | A slice proves RC2: a role cleared mid-queue reaches the same next action as before the clear. | The invariant is only real when it is tested. |
| RC4 | `veri-handoff` and the `--resume <file>` arguments are removed once RC3 passes, with their H rows. | Nothing ever needs a handoff. |
| RC5 | The coordinator resets itself at a quiet point (no merge in flight, no launch half done, no decision mid-answer) when its last turn was more than an hour ago (the cache is cold) or its conversation tokens reach its fixed floor (its context at start, read with the usage tool). First it sends the dev session `ping` and waits for `pong`; with no `pong` it does not reset. Then it asks the dev session to send it `/vcoord <lane>` with its next message, and clears itself. | A cold turn re-writes the whole context anyway; a reset turns every later turn cheaper. Operator: "make sure the vdev session is responding before clearing itself." |
| RC6 | Before RC5 is built, two spikes are run and recorded: a cleared desktop session starts a turn on a message from another session; a CLI session receiving the message `/clear` executes it. RC5 is dropped if the first fails; the second, if it passes, lets the coordinator reset the dev session the same way. | Both are facts about the harness nobody has observed. |
| RC7 | At start each operator role switches off, for its own session only, every claude.ai connector its skill does not list as needed. | Connectors' tool definitions (~20k tokens on the coordinator, 2026-10-23) are paid on every turn. |

## 3. Judge and autonomous mode (`veri-judge`, rebuilt; `veri-coord`)

The current `veri-judge` (PR #2157) is replaced, not edited. Basis: 617 owner replies to agent
questions in human-driven veri sessions, 2026-08-08 to 2026-10-23, classified per reply; of the
349 that settled a recommendation, 79% accepted it: requirement 100% (18), merge 97% (30),
scope 86% (101), priority 80% (45), process 78% (58), design 73% (64), spend 43% (28). Every
spend override cut recurring real-money cost or asked to use more plan capacity.

| ID | Requirement | Why |
|---|---|---|
| JD1 | Every operator role runs `/veri-judge` on a question before it reaches the human. `operator/PRINCIPLES.md` gains P15 saying so. | Neither `veri-coord` nor `veri-dev` mentions the judge today, so nothing makes a role use it. |
| JD2 | The judge acts on its own recommendation and records it (JD6), unless the question is on JD3's list. | 79% acceptance; 21 rebukes were for asking or narrating when the agent should have acted. |
| JD3 | Always the human's: any real-money spend, recurring or one-off, from $0 (CI minutes, runners, scheduled jobs, paid APIs, extra usage); `VERI_MAX_CONDUCTORS` above 5; anything in another repository; repository visibility and anything that exposes code. | Operator: "I'd not authorize autonomous spending of 10 USD." Every recurring-cost proposal on record was overridden (2026-09-11, 10-06, 10-15). |
| JD4 | With no recommendation, or one whose evidence it cannot name, the judge investigates once — one subagent on the cheapest adequate model, at most 10 lines back — then decides on what it found. | Operator: "if the issue has no recommendation or the certainty is low, the agent should investigate." |
| JD5 | A question still not clear-cut after JD4 is not guessed: an issue's question parks the issue (GS7) and the next one is taken; a question about no issue goes in the role state file (RC1) and is asked once. | A wrong guess on a real tension costs more than a park. |
| JD6 | A decision about one issue is a comment on it naming the rule applied and the option not taken. A decision about no issue (N, order, weekly pacing, model knobs, merge order, session upkeep) is one line in `.tdd/decisions.jsonl`: question, decision, rule, time, who decided. `/vstatus` lists the decisions since the last ask. | Decisions survive a `/clear` (RC1), and the operator audits a batch afterwards instead of approving each one first. |
| JD7 | Before judging, the judge looks for an earlier decision of the same question in both places and follows it unless its facts changed. | A question decided once is never asked again. |
| JD8 | Its rules come from the owner's overrides, each row's Why citing the override's date: veri fixes veri through a filed issue; diagnose before filing; an established tool over an in-house one; file complete issues the first time; use plan capacity rather than idle it; raise a run's budget only to its projected need. | Rules mined from what the operator did, not from what an agent inferred he would say. |
| JD9 | `/vcoord --auto` is the autonomous mode: it rules on parked issues (GS8), on decisions a ledger step asks for, and on a run's open questions, through the judge. Without `--auto`, those go to the human. | Operator: "a fully autonomous mode that is able to decide most of the open decisions … it should be able to unblock a parked issue." |
| JD10 | The skill obeys `operator/PRINCIPLES.md`, names no project fact (P12), restates no other skill's rule (P2), and has a requirements list and `GRADED` signature. | The current skill has neither, and copies dev-session rules. |

## 4. Run cost

### CR: conductors

Basis: the conductor is 50–70% of a run's cost (#1668, #1653, #1720, #1915, #1719); on #1915
its context grew from 88k at turn 1 to 169k at turn 75. A restart re-writes the floor (~88k at
the cache-write price) and saves 0.1× the growth per later turn, so mid-issue restarts rarely
pay. Shrinking the floor is #2075 and #2218 (labelled `priority` on 2026-10-23).

| ID | Requirement | Why |
|---|---|---|
| CR1 | `metrics.sh <n>` reports the conductor's context at its first turn and at its largest. | The floor's size is watched from run to run. |
| CR2 | When a conductor's current context exceeds `VERI_CONDUCTOR_RESTART_RATIO` (default 2) × its first-turn context, the dev session stops it at its next ledger commit (`stop-run.sh --mode ledger`) and relaunches `run-conductor.sh <n>`, recording a `conductor-restart` event. | A restart pays only once the growth is about the size of the floor; the relaunch is an ordinary resume from the committed ledger. |

### BG: budgets

Basis (848 metrics reports): 85.6% of steps need no revise cycle; the exhausted path lands 55
of 61 runs; the three `revise-exhausted` bails repeated the same reason, so a larger budget
would not have saved them. `VERI_REFACTOR_BUDGET` stopped a pass in 1 of 598 runs; 72.7% of
passes landed nothing.

| ID | Requirement | Why |
|---|---|---|
| BG1 | `VERI_STEP_GROWTH` becomes relative: a ledger may grow by `⟦added⟧` steps up to 50% (tunable) of the steps it had when its plan verifier passed. | Operator: "I'd balk at growing an issue more than 50% from a well established plan." |
| BG2 | At that limit the judge decides: added steps that serve the issue's own criteria continue the run (the plan was incomplete), recorded on the issue; added steps that serve work no criterion names are split off into a new issue filed with `veri-file`, and the run finishes without them. | The split the operator usually agrees to, made without asking. |
| BG3 | `REVISE_BUDGET` stays 2 per step and phase, and the judge does not raise it. A REJECT whose reason repeats the previous attempt's goes straight to the exhausted leaf. | A third attempt on a repeated reason repeats it. |
| BG4 | Every metrics report shows refactor passes, transforms, passes that landed nothing and stop reasons, per step and per issue, and `/vstatus` sums them. | The operator wants to know refactor turns per issue before deciding to raise the budget after the quality passes. |
| BG5 | Decided 2026-10-24, filed as #2305: a step's refactor does an out-of-scope candidate that changes one of the step's own files, under a cover leaf. The share of passes stopping `structural-owed` (19% before ADR-0031) is reported once 30 runs have #2305. | Measured on the 51 runs after ADR-0031: for 8 of 11 out-of-scope candidates (73%) a later step changed the named code before the structural pass did, a median of 3 steps. |
| BG6 | No refactor in a PR, per-step or structural pass, changes only files the issue's commits never touched. A candidate beyond that bound, and every candidate the structural pass leaves not done (`uncovered`, `transform-rejected`, `budget spent`, `no predicate`), is listed in one issue per run, labelled `refactor` and `candidate`, never opted in. The coordinator grooms these with `veri-groom --refactor-owed` (GONE / FOLDS-INTO-OTHER / LIVE, live ones consolidated per module) and decides what is opted in. A new ADR records this partial reversal of ADR-0031's "never files". | Operator, 2026-10-24: a PR growing out of its issue's scope is undesirable, and an out-of-scope refactor is filed for the coordinator to groom and decide. Unlike the 118 refactor-owed issues before ADR-0031 (one per candidate, straight into the queue), this is at most one per run, outside the queue: 2 of the 51 runs after ADR-0031 had a leftover (#1980, #2206), and none had a candidate beyond the bound. |

## 5. Preconditions

### PM: the permission check (#1770)

PM1–PM9 are #1770's R1–R9 as its body states them, renumbered only to avoid PRD 011's R rows.
Slices are #1770's five.

### TC: the test-command check (code, built by veri under `/tdd`)

| ID | Requirement | Why |
|---|---|---|
| TC1 | `check-test-command.sh [repo-root]` resolves both tiers with `detect-test-command.sh --tier fast` and `--tier all`. A tier that resolves to nothing (exit 3) is a failing row whose fix names the `veri: fast tests: <cmd>` / `veri: all tests: <cmd>` CLAUDE.md lines and `.veri/test-command`. | A run today learns at preflight that it has no command, and then asks a human. |
| TC2 | A fast tier equal to the full tier is a row `fast tier = full tier` that does not fail the check. | Every green and refactor verdict then pays the full suite's time; legal, but the operator should know. |
| TC3 | Each tier runs once in a detached worktree of the default branch's tip under `.tdd/`, through `detach-command.sh`. The row passes iff the command exits 0; a non-zero exit fails it, with the exit code and the output's last non-empty line. | A red baseline makes the conductor refuse to start. |
| TC4 | Each tier's row carries its wall time, which never fails the row. | Wall time is observed, not gated. |
| TC5 | The check removes its worktree on every exit path and leaves the repo's tree, index and branches as it found them. | It reads the repo's health; it writes nothing. |
| TC6 | The report is PM3's table with PM4's exit codes: any failing row exit 2, all passing exit 0. | One table and one contract for every precondition. |
| TC7 | Port convention (`status.sh` worked example), as PM8. | |

The check never verifies that a failing test makes the command fail: that is the project's code
quality, and every run's Red verdict observes it. This part checks capabilities and setup only.

### DR: `veri-doctor` (prose)

| ID | Requirement | Why |
|---|---|---|
| DR1 | Invoked as `/veri-doctor [repo-root]`, default the current repository's main working tree. | One command answers "can veri run here?". |
| DR2 | It runs the permission check with `VERI_RECHECK_PERMISSIONS=1`, then `check-test-command.sh`, prints both tables, then one line: `ready` or `not ready — <k> rows to fix`. | One round of fixes clears everything. |
| DR3 | It reports the machine floors the conductor refuses on (bash 5+, the Python floor) by running preflight's own checks, and every status label GS1 names that the repo lacks, with its `gh label create` line. | A refusal at launch is the same finding, later. |
| DR4 | It grants nothing: no fix command run, no label created, no settings file or CLAUDE.md edited. | Granting is the human's. |
| DR5 | It names no project fact (P12) and obeys `operator/PRINCIPLES.md`; a red suite's log is read by a subagent returning at most 10 lines (P6). | |

## 6. Run state on GitHub

Basis: the ledger, its refactor-pending marks, the branch and the draft PR are already on
origin. Local only today: `.tdd/events.jsonl` (costs, budgets, the skill pin, the timeout),
the claim between unlabelling and the draft PR, and takeover, which `issue-worktree.sh`
refuses until a human runs `git branch <b> origin/<b>` (`py/issue_worktree.py:179-185`).

| ID | Requirement | Why |
|---|---|---|
| GS1 | An issue a run takes carries exactly one status label: `veri:running` at claim, `veri:done` when its PR is readied, `veri:merged`, `veri:bailed` on a first bail, `veri:parked` on a second, `veri:stopped` from `veri-stop`. | Operator: "the status of the development is easily queryable." |
| GS2 | The label names are defaults in the scripts, overridable from the target repo's CLAUDE.md; veri never creates a label (DR3 reports a missing one). | P12, and #1770's "labels are reported, never created". |
| GS3 | One pointer comment per run, written at claim and edited in place at each push: branch, PR, side ref (GS4), step k/n and phase, machine, last push time, and the resume command `/tdd <n>`. | It directs an agent with no context, and closes the window in which only a local pid marked the claim. |
| GS4 | The run's machine-local records — its lines of `events.jsonl`, `issue-<n>-skill-commit`, the recorded timeout and proof files — are pushed with each ledger push to `refs/veri/runs/<n>`, never merged, and deleted once the PR reads MERGED. | Rebase-merge puts every commit on `main` as itself, so logs committed on the branch and `git rm`-ed later would stay in `main`'s history. |
| GS5 | `metrics.sh` and resume read GS4's ref when the local files are missing. | A second machine's report would otherwise miss the first machine's costs. |
| GS6 | `issue-worktree.sh` adopts origin's branch without being told when the pointer says the run stopped (bailed, parked, stopped or usage limit); `--take-over` adopts it regardless; otherwise it refuses as today. | Any machine resumes a stopped run, and two machines never work one live run. |
| GS7 | A park comment states the open question in full, the options and what each costs, what the judge's investigation found (JD4), and a recommendation. | Anyone can answer it without the conversation that parked it. |
| GS8 | A parked issue returns when the human replies with a decision and relabels it, or when `/vcoord --auto` posts a ruling and relabels it (JD9). On resume the conductor reads the comments after the park comment and applies the decision, as a ledger amendment if needed. | The decision lives on GitHub, whoever made it. |

## Considered and set aside

- **Pacing as a separate skill** (`veri-pace`): it would duplicate the usage read and fight
  the coordinator over N. It is a coordinator mode.
- **Rolling 60-minute and 24-hour windows**: replaced by absolute caps indexed from the
  windows' own reset times (PC3, PC4).
- **N = 0 over a cap**: pacing stops no running conductor, so 0 and 1 have the same effect.
- **Restarting conductors per step or per N runs**: the floor dominates; CR2's ratio rule pays
  only when growth is about the size of the floor.
- **Issue as the state store**: the issue holds a pointer and labels; the records go on a ref.
- **Logs committed on the run's branch and `git rm`-ed before merge**: they stay in `main`'s
  history under rebase-merge.
- **Editing the current `veri-judge`**: it was synthesised from guesses about the operator,
  and its defaults contradict his measured answers.
- **A judge-raised `REVISE_BUDGET`, or an unbounded refactor budget now**: neither budget binds
  on the measured runs. The refactor budget is revisited after the code-quality passes.
- **Checking that a failing test fails the command**: project code quality, not setup.
- **A structural pass that may touch any file**: the PR would grow beyond its issue. Out-of-bound work is filed for grooming instead (BG6).
