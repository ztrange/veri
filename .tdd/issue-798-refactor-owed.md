### veri.github.gh_rest_list requests `gh api <rest-path>?page=1`, `page=2`, … and answers every page's body back to back with no separator, stopping at the first page that is a bare `[]`, which is not part of the answer ⟦criterion 1⟧
- test-only | the `SCRIPTS`/`sys.path` preamble at the top of `tests/py/test_github.py` is the same one eleven other `tests/py/test_*.py` files carry, so it could move into a shared `tests/py/conftest.py`. That would change mostly files this cycle did not write, so it is out of scope here.
### veri.github.gh_rest_list requests `<rest-path>&page=N` when the rest path already holds a `?` ⟦criterion 1⟧
- test-only | in `test_github.py`, the argv list each case writes into the `fake_gh` answers dict is written out again in the `calls ==` assertion; a small helper that builds the `gh api <path><sep>page=N` argv for pages 1..N would remove that repetition
### veri.github.gh_rest_list stops at the first page matching a caller-given empty pattern, such as wait-ci.sh:80's `"check_runs": *\[ *\]`, and does not include that page ⟦criterion 1⟧
- test-only | in skills/tdd/scripts/tests/py/test_github.py, every pagination case lists the same argv twice: once as the keys of the fake_gh answers and again in the expected `calls` list. A shared helper (for example `page_argv(path, sep, n)`) could build both and remove the repetition across the four gh_rest_list cases.
### veri.github.gh_rest_list is a no-answer when any page's `gh api` call fails, a failure on page 2 included, with gh's stderr passed through ⟦criterion 1⟧
- test-only | fold the inline `fake_run` in `test_gh_rest_list_is_a_no_answer_when_page_two_fails_with_gh_stderr_passed_through` (skills/tdd/scripts/tests/py/test_github.py:102-121) into `fake_gh` (:20-38). To do that, `fake_gh` writes the faked stderr to `sys.stderr` when `stderr` is not `subprocess.PIPE`, so the new case calls `fake_gh` like the other four cases and is also covered by its `Popen` guard.
