### wait-ci.sh exits 0 when the given sha's own check runs and statuses have all succeeded, even while the PR rollup still shows a previous head's failed or pending checks ⟦criterion 1⟧
- wait-ci.sh sha_state now repeats rollup_state's pass/pending/red classification and its passing set ("success","neutral","skipped" vs "SUCCESS","NEUTRAL","SKIPPED"); a shared classifier needs an extraction across two python -c snippets whose rules differ (the rollup reads all-SKIPPED and empty as pending), so it is not plain duplication removal

- wait-ci.sh sha_state's `pages if isinstance(pages, list) else [pages]` is dead code under `gh api --paginate --slurp`

### wait-ci.sh exits 3, never 0, when every one of the given sha's own check runs concluded skipped ⟦added⟧ ⟦criterion 1⟧
- wait-ci.test.sh: the race, redsha, quietsha and skippedsha cases repeat the same body (a green `rollup` at `$sha`, then `sha_runs`, then `waited … 60 60 "$sha"`, then an exit-code assert). It could become one helper such as `sha_case <name> <want-exit> <runs…>`, but that would rewrite three cases from earlier cycles to take out one instance from this cycle, and each case's failure message is specific to it.
- wait-ci.sh: `rollup_state` and `sha_state` hold two parallel Python classifiers (upper-case versus lower-case conclusions, and each has its own "all skipped is pending" rule). They are not merged because the order of their checks differs: the rollup checks pending before red, and the sha check checks red before pending. Unifying them would change behaviour, so it is not a pure refactor.
### wait-ci.sh exits 1 when a legacy status context of the sha, read from `gh api repos/<owner>/<repo>/commits/<sha>/status`, is in a failure or error state, even when the sha's check runs all succeeded ⟦criterion 1⟧
- wait-ci.test.sh: the pair `sha_head X; sha_runs X "$(sha_run gates completed '"success"')"` still repeats 3 times in this cycle's two cases (statussha loop, unstatus, nostatuses), so a further helper could remove it
### wait-ci.sh exits 3 when a legacy status context of the sha, read from its `/status` endpoint, is still pending, even when the sha's check runs all succeeded ⟦criterion 1⟧
- the pending case in `wait-ci.test.sh` (sha_head, sha_runs success, sha_statuses, waited) repeats the loop body of the failure/error legacy-status case with a different expected exit code. Folding the two into one table of state→exit would merge two separately named criteria into one case, so I did not apply it.
- in `sha_state` in `wait-ci.sh`, the embedded python reads `s.get("state")` over `statuses` twice, in the red test and in the pending test. It could build a `states` list once, the way `outcomes` is built for the check runs. That is a readability extraction, not removal of duplicated behaviour, so under this phase's rules I report it and do not apply it.
