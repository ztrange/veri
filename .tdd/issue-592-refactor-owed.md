### wait-ci.sh reads check-runs spread over more than one page through that stub and reaches the same verdict as with the same check-runs on one page ⟦criterion 3⟧
- the page loop in `wait-ci.sh` `sha_state` (`gh api …check-runs?page=$page` until a page's `check_runs` comes back empty) repeats `gh_rest_list`'s loop in `lib/github.sh`. The two stop on different things: `gh_rest_list` stops on a bare `[]`, while check-runs arrives as an object. Sharing one loop would need a new "what counts as an empty page" parameter that no test asks for, and `wait-ci.sh` would have to start sourcing `lib/github.sh`. That is extracting across files, which this phase does not allow.
- the proxy-refusing `gh` stub is written out separately in `wait-ci.test.sh`, `invisible-work.test.sh`, `workqueue.test.sh`, `solvable-issues.test.sh`, `parallel-conductors.test.sh` and `unit/github.test.sh`, each with its own copy of the proxy's 403 line and its own page parsing. It could become one shared test helper, but that is extracting a module across suites, which this phase does not allow.
