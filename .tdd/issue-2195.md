# Plan for #2195 — Concurrent full test suites oversubscribe the machine and time out slow cases; run one full suite at a time

- [x] Two concurrent full runs serialise: while one full `make test` run (the pytest leg launched as a full run) is running its suites, a second full run started from a different working tree waits for the first to finish before starting its own suites, writes once (not repeatedly) that it is waiting and on whom — the holder's pid and working tree — and then runs normally and exits as its suites decide; the lock lives under the user's machine-wide veri state (the user's home, like ~/.veri-pytest-legs), never under a clone or worktree. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [x] A full run holds the lock for the whole run and releases it on every exit path: after the holder exits normally, exits red, or is ended by SIGTERM, SIGINT or SIGHUP, a waiting full run starts its suites. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [x] `VERI_TEST_LOCK=0` disables the lock: with the lock held by a live full run, a full run started with VERI_TEST_LOCK=0 starts its suites at once without waiting and writes no waiting message. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 2⟧
- [x] Every verifier leaf (`verify-*`) runs with `VERI_TEST_LOCK=0` in its environment, set where the leaf is launched, so a verifier's own suite never waits on a lock its mutation broke; a developer leaf does not get it. Pinned by a case that launches a verify leaf through the launcher with a stub and sees `VERI_TEST_LOCK=0` in its environment, and one showing a developer leaf (`develop-*`) does not get it ⟦added⟧ ⟦criterion 6⟧
- [x] A killed holder's lock is taken over: a lock whose recorded holder pid no longer answers `kill -0` (the holder was SIGKILLed and never released it) does not make a new full run wait; the new run takes the lock and runs its suites. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [x] `make unit` is not affected: with the full-run lock held by a live full run, a fast-tier run (`make unit`'s pytest leg) starts its suites at once without waiting and writes no waiting message. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [ ] A waiting run's wall time counts toward nothing that could bail it: with the lock held by a live full run for longer than 1 s, a waiting full run whose per-case limit is 1 s (`--timeout=1` / VERI_PYTEST_TIMEOUT=1) still passes once the holder releases, because the wait happens before any per-case timeout starts. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 2⟧
- [ ] A case that holds the full-run lock forever (a live holder that never releases it) starts a waiting full run under a bound of at most 120 s and sees that waiting run fail (timed out or killed) within the bound instead of hanging; the case itself carries @pytest.mark.timeout(n) with n at most 120. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 3⟧
- [ ] Every case under skills/tdd/scripts/tests/py/ that exercises the full-run lock carries a per-case @pytest.mark.timeout(n) with n at most 120, or bounds every wait on a subprocess it starts at 120 s or less, so a mutation that breaks the lock's release or wait turns the case red instead of hanging the run; test-only, no production change ⟦diff-checked⟧ ⟦criterion 3⟧
- [ ] A full `make test` started by a process that already holds the full-run lock (a suite running `make test` nested) does not wait on it: the holder exports a marker its descendants see (one that survives helpers stripping VERI_* names), a run under that marker whose holder is alive and recorded in the lock skips the lock, and a run with no such ancestor still waits; the branch carries a nested-run case, bounded by @pytest.mark.timeout of at most 120 s, that finishes inside its bound while the outer run holds the lock ⟦diff-checked⟧ ⟦criterion 4⟧
- [ ] The lock's tunables (`VERI_TEST_LOCK` and any other the lock reads) are read through the shared tunable reader, as `test_tunable_reads` requires of every `VERI_*` read; covered by `test_tunable_reads` passing in the full-suite run ⟦full-suite⟧ ⟦criterion 5⟧
- [ ] The full-run lock and `VERI_TEST_LOCK=0` are documented in CLAUDE.md's Testing idiom beside the other `VERI_PYTEST_*` tunables: at most one full `make test` per machine, a second waits naming the holder's pid and working tree, a dead holder's lock is taken over, `make unit` never waits, the wait comes before any per-case timeout, and `VERI_TEST_LOCK=0` turns it off ⟦diff-checked⟧ ⟦criterion 2⟧
