# Plan for #2195 — Concurrent full test suites oversubscribe the machine and time out slow cases; run one full suite at a time

- [ ] Two concurrent full runs serialise: while one full `make test` run (the pytest leg launched as a full run) is running its suites, a second full run started from a different working tree waits for the first to finish before starting its own suites, writes once (not repeatedly) that it is waiting and on whom — the holder's pid and working tree — and then runs normally and exits as its suites decide; the lock lives under the user's machine-wide veri state (the user's home, like ~/.veri-pytest-legs), never under a clone or worktree. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [ ] A full run holds the lock for the whole run and releases it on every exit path: after the holder exits normally, exits red, or is ended by SIGTERM, SIGINT or SIGHUP, a waiting full run starts its suites. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [ ] A killed holder's lock is taken over: a lock whose recorded holder pid no longer answers `kill -0` (the holder was SIGKILLed and never released it) does not make a new full run wait; the new run takes the lock and runs its suites. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [ ] `make unit` is not affected: with the full-run lock held by a live full run, a fast-tier run (`make unit`'s pytest leg) starts its suites at once without waiting and writes no waiting message. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 1⟧
- [ ] A waiting run's wall time counts toward nothing that could bail it: with the lock held by a live full run for longer than 1 s, a waiting full run whose per-case limit is 1 s (`--timeout=1` / VERI_PYTEST_TIMEOUT=1) still passes once the holder releases, because the wait happens before any per-case timeout starts. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 2⟧
- [ ] `VERI_TEST_LOCK=0` disables the lock: with the lock held by a live full run, a full run started with VERI_TEST_LOCK=0 starts its suites at once without waiting and writes no waiting message. Pinned by a medium case with real processes, @pytest.mark.process ⟦criterion 2⟧
- [ ] The full-run lock and `VERI_TEST_LOCK=0` are documented in CLAUDE.md's Testing idiom beside the other `VERI_PYTEST_*` tunables: at most one full `make test` per machine, a second waits naming the holder's pid and working tree, a dead holder's lock is taken over, `make unit` never waits, the wait comes before any per-case timeout, and `VERI_TEST_LOCK=0` turns it off ⟦diff-checked⟧ ⟦criterion 2⟧
