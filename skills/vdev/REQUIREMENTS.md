## skills/vdev/SKILL.md

| ID | Requirement | Why |
|---|---|---|
| D1 | Invoked as `/vdev [<lane>] [N] [--resume <file>]`. N defaults to 1. It carries standing merge permission in the project repo for the runs it finishes; it never merges in another repo. | Mario, 2026-10-18: both operator skills always include merge permission. |
| D2 | It keeps exactly N conductors running while the solvable list is non-empty. | Idle slots were the recurring waste. |
| D3 | Each conductor is a detached `run-conductor.sh <n>`, never a conductor run inline. | An inline conductor costs ~60k tokens per issue in the session. |
| D4 | *Launching* says launches go through `$S/dispatch.sh`, which launches the next issue only after the previous launch's ledger exists; the skill arms no ledger wait of its own. | A claim appears only ~10 minutes into a run; the hand-armed `until` Monitor cost a wake per launch. |
| D5 | On each exit it routes by fact: ✅ Done → review, then `vmerge` on OK; a bail → `vbail`; no closing comment → P10. The text never says either skill does not exist. | Stale prose sends the role down the fallback path. |
| D6 | After every merge, park or exit it recounts and refills to N. | |
| D7 | It applies the coordinator's changes to N or to the order at the next slot decision. | |
| D8 | It stops and asks only for: red CI it cannot fix, a ⟦human-owed⟧ step, an unresolvable conflict, a decision a ledger step asks for. | |
| D9 | It does not file, groom or reprioritise issues, and does not edit veri's scripts. | Those are the coordinator's job, and a veri fix is an issue for veri. |
| D10 | Where it describes reporting to the coordinator, it says that with a coordinator attached each event P4 lets it speak about goes to the coordinator, not to the human, unless it stops and asks (D8). It says so as a pointer to P4, never a copy of P4's rule. | 2026-10-20: the mu dev session re-stated a pending decision to Mario about 15 times. A copied rule drifts from P4. |
| D11 | Before merging a ✅ Done run, whether on its own OK or on a coordinator's merge instruction, it sends the coordinator every caveat its review found of three kinds: a test never watched failing, a change to a guard or other product code outside the issue's stated scope, a departure from the issue's wording. It merges only after a reply that names each caveat. A review with no such caveat says so in the same report. | 2026-10-20: a merge order crossed the dev session's caveat report about 6 times. |
| D12 | Every conductor launch, a resume included, appends its output with `>>` to `.tdd/conductor-<n>.log` in the target repo's main working tree, the file `stop-reason.sh` and `metrics.sh` read. No launch truncates it. | 2026-10-20: every mu run's log sat in a scratchpad, so `stop-reason.sh` answered "no conductor log" for each one. A `>` on resume destroys the first launch's evidence. |
| D13 | It parks an issue only through the park script, passing the number of every issue or PR that must land first as the script's blockers, and on resume reads the parked set through the parked-set script, never from a handoff or memory; un-parking runs `release-issue.sh <n>`, never a bare removal of the `parked` label. | The parked set and each park's cause live on GitHub, so a context reset or another machine rebuilds them from there (Mario, 2026-10-21: "we do not depend on the local memory to resume a bail"); the coordinator un-parks from the blocker numbers, so a park without them is never reported ready. |
| D14 | At start, when its session has tools from any MCP server, the dev session tells the human once, in one line, the launch line that starts it without them: `claude --strict-mcp-config --mcp-config '{"mcpServers":{}}'`. It changes no setting itself. | The CLI has no per-session connector switch, and the dev session needs no MCP server; a launch flag is the only way to leave them out. |
| D15 | The *Watching* section names `$S/dispatch.sh` as the blocking watch of P3, run as one background command, never under a Monitor and never a hand-written script, and says that it takes N and the launch order from `.tdd/role-dev.state` (`.tdd/role-dev-<lane>.state` in a lane), that `--target <N>` replaces only N (order overrides still apply), and that `--target 0` holds dispatch: the watch keeps reporting exits and launches nothing. | A Monitor wakes on the line and again on "stream ended"; a background command wakes once (2026-10-29). A hold that stops the watch would leave exits unreported (#3520). |
| D16 | The *Watching* section lists the lines `dispatch.sh` prints (`done <n> <pr-url>`, `bail <n>`, `silent-exit <n>`, `merge-failed <pr-url>`, `stalled <n>`, `queue-empty`) and says it launches and re-arms without printing. | The dev session must not wait for events the script never prints, nor expect a line per launch. |
| D17 | *Starting* has a bullet saying that when the user's instructions in this session forbid writing in a repository other than the session's, the dev session asks the human once whether veri may fast-forward its own clone before each new run and records the answer with `update-veri.sh --consent yes\|no`; it asks only when no record exists and never edits the user's instructions. | The self-update needs no approval by default, and a user whose rules forbid it is asked once, not on every run. |
| D18 | In the *Caveats before any merge* bullet (skills/vdev/SKILL.md, the review brief), a review may not report "no coverage" or "coverage lost" from the diff alone: before the claim it searches the whole test tree, including directories the diff never touches, for the behaviour's name, and the claim carries the `file:line` where coverage was found (then it is not a finding) or the search term it used and found nothing for. | A move-shaped change deletes assertions in one file and adds them in another; a diff-only review reports coverage lost that exists (2026-10-29). |
| D19 | The *Caveats before any merge* bullet says a GitHub call refused with `rate limit exceeded` while `gh api rate_limit` still reports quota hit GitHub's secondary limit, and to use REST rather than wait for the reset. | The obvious diagnostic misleads, and the reset belongs to a limit never reached. |
| D20 | It runs `vmerge`, `vbail` and `vjudge` through a subagent on the cheapest model that can do the job, briefed to return at most 10 lines, reading the skill at `<base dir>/../<skill>/SKILL.md`. | The body stays out of a long-lived context. |
| D21 | It loads `vhandoff` itself, by reading `<base dir>/../vhandoff/SKILL.md`. | It needs the role's own state. |
| D22 | `<lane>` is an optional first word naming the lane: `/vdev mu [N] …` runs every read (`solvable-issues.sh`, `status.sh` included) and every conductor launch with `VERI_LABEL=ready-for-agent:mu`; with no lane word, plain `ready-for-agent`; and the session states the lane in its first line of output. (The `<lane>` bullet.) | Two sessions on different lanes must not take each other's issues, and the reader must see which lane this is. |
| D23 | Every finding its review of a ✅ Done run makes is one of two things: blocking, fixed on the PR's branch before merge (a criterion with no test red when its behaviour is removed, a behaviour failure or regression, a surviving mutant in a guard, an exit-code path or data-deleting or data-overwriting code, a doc miss as D24 defines it), or a line in the PR body. It says a review finding is never filed as an issue. | 2026-11-02: about 15 of 57 open issues were review notes filed after merge (#2941, #2946, #2967 among them). |
| D24 | When a run's PR adds or renames a phase, subcommand, flag or event, the review searches the script's usage string, `SCRIPTS.md`, `REVISE.md`, the `REQUIREMENTS.md` rows and the prompt templates for the name. Any site that omits it or still states the old behaviour blocks the merge. | #2923, #2946, #2956, #2975: doc drift merged, then filed as issues. |
| SIB1 | Sibling skills are read from the real directory of the base dir (symlink resolved with `cd -P`/`realpath`), not from the path the harness reports. |
| D25 | Wherever it briefs a review, hand-fix or merge subagent, the brief says mutations (edit a file, run the suite, restore it) run only in a scratch clone or the run's own worktree, never in the primary clone. | 2026-11-06: PR 3139 (#3107) review ran a mutation loop in the primary clone after a skipped `cd`. |
| D26 | The same briefs say that every `cd` in a chained command makes the whole command fail when the `cd` fails (`&&` or `set -e`), and that a `;` never follows a `cd` or a guard whose failure would change where the next command runs. | `git check-ignore .tdd` exited 1, the `cd $C` was skipped and the `;` ran the loop in the primary clone. |
| D27 | The same briefs have the subagent check `git -C <primary clone> status --porcelain` is empty before it reports, and report any output as dirt; they forbid concurrent background jobs that share a scratch file. | The reviewer reported "main clone has no changes" unchecked; a background job sharing `$R/orig.py` restored the PR's `suite_red_resume.py` over the primary clone, and #3110 was refused at preflight. |
| D29 | A *Resetting* section says: on `role-growth.sh`'s arm line (growth since recovery ≥ 0.85 × `VERI_RESET_GROWTH_DEV`, default 70000 tokens) the dev session resets at the next quiet point — no launch half done, no merge in flight; on its reset-now line (2 × the knob) it resets at once, even mid-task. It no longer names a 200k context threshold or `/vhandoff dev` as its reset. | The dev session grows like the coordinator and has its own floor, so its own knob (RC8, RC5). |
| D28 | The dev session is the only role that watches run state, and it sends the coordinator, when one is attached, one message per conductor exit, bail or merge (P4). | Same as C20: one watcher, and the coordinator learns of exits from the dev session. |
| D30 | In *Launching*, next to the launch command, it says every conductor launch, a resume included, is followed by `$S/detach-leaf.sh $S/restart-conductor.sh <n> >> .tdd/restart-<n>.log 2>&1 < /dev/null`, which restarts that run's conductor at its next ledger commit once its growth reaches 0.85 × `VERI_RESET_GROWTH_CONDUCTOR`; that `dispatch.sh` starts it itself for every launch it makes, so the dev session runs it only for a launch made by hand; and that a restart is not an exit to route. | The conductor is 50–70% of a run's cost and its growth is re-read on every turn; detached, a restart costs the dev session no wake (CR2); `dispatch.sh` launches without printing, so the dev session has no moment to start it. |
| D35 | *The slot decision* step 1 applies any change the coordinator sent (a new N, a timed N now due or expired, an order override) and sends the coordinator no reply for it (P13). | The reply woke the coordinator for a 1-request turn that did nothing (2026-10-29). |
| D40 | *Routing an exit*, the **No closing comment** bullet, names the resume command line once usage is back: `$S/detach-leaf.sh $S/run-conductor.sh <n> >> .tdd/conductor-<n>.log 2>&1 < /dev/null`, run from the target repository's main working tree. | The bullet said "resume the run" with no command, and a `>` instead of `>>` destroys the first launch's log (D12). |
| D36 | The *Watching* section says the dev session arms no other wait for conductors, ledgers or merges: no `watch-runs.sh`, no `until [ -f … ]`, no `while kill -0 <pid>`. | One watcher instead of four kinds (2026-10-29). |
| D37 | *Routing an exit* says that after routing a `dispatch.sh` line the dev session starts `dispatch.sh` again as one background command. | `dispatch.sh` exits on each judgment event; without a restart no slot is refilled (P5). |
| D38 | *The slot decision* step 1 says an N change or an order override from the coordinator is written to the role state file, that `dispatch.sh` without `--target` reads N, a timed N and the overrides from `.tdd/role-dev.state` (`.tdd/role-dev-<lane>.state` in a lane) at each slot decision so nothing is restarted, and that an N of 0 in that file holds dispatch while it keeps watching exits, a later positive N resuming launching. | N and the order are read from the file at every decision, not fixed as an argument at launch; an N of 0 must hold launches without losing the watch (#3520, #3229). |
| D39 | *Launching* says the dev session announces each launch recorded in `.tdd/dispatch.log` since its last turn as `Started #<n> — <title>` (to the coordinator when one is attached, P4). | `dispatch.sh` prints nothing per launch, so the announcement comes from its log. |
