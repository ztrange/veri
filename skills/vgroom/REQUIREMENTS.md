## skills/vgroom/SKILL.md

| ID | Requirement | Why |
|---|---|---|
| GR1 | Invoked as `/vgroom [<issue>...\|<range>...\|--refactor-owed]`; no argument runs the sweep over every open issue (GR13); ids and ranges (GR17) and `--refactor-owed` narrow it. Stated under `## Invocation`. | The old no-argument mode skipped unlabelled issues, then opted-in ones, trackers and refactor-owed items, so each needed its own request (2026-11-17). |
| GR2 | One read-only subagent returns one line per issue: ready / needs-rewrite / needs-split / gone / duplicate / needs-human, plus proposed labels. `ready` means the body already meets `../vfile/SKILL.md`'s issue body; `needs-rewrite` names what it lacks. | |
| GR3 | Under `## Applying outcomes`, mechanical outcomes are applied without asking: adding or removing a label, closing an issue with a reason, and editing its `Blocked by`. A consolidated refactor issue (`--refactor-owed`, alone or in the sweep) is also filed without asking and its sources closed, unless it is big-impact: it changes a script's entry-point contract (arguments, exit codes, output lines or events), edits graded prose, or touches files in more than one module; a big-impact one is shown to the human first and filed only on their yes. Nothing else is mechanical: filing any other new issue (a split one included), rewriting criteria, and any other outcome are shown to the human first and applied only on their yes. | Grooming changes queue state cheaply and reversibly on its own; a small consolidated refactor is behaviour-preserving work the human approves anyway (Mario, 2026-11-17), while new work and contract-changing refactors enter the queue only with a human's yes (PR #2118 review). |
| GR4 | A split or a criteria rewrite is shown to the human first unless they said "go"; `/vgroom` with no argument is a "go". | |
| GR5 | `--refactor-owed` classifies each item GONE / FOLDS-INTO-OTHER / LIVE on `main`, consolidates the live ones into one issue per module, or one per deliverable where a module's items hold more than one, and closes the sources. | ~5–6 such items are filed per day. |
| GR6 | Near its top, the skill says it obeys `operator/PRINCIPLES.md` and reads it first. | PR #2061's prose passed GR1–GR5 without it, so no principle reached the skill. |
| GR7 | Every subagent brief the skill writes asks for a return of at most 10 lines (P6), and says that all writes stay in the project repo and that a fix belonging elsewhere is reported, not made (P11, in its words). | PR #2061's brief asked for one line per issue, unbounded, and carried no repo boundary. |
| GR9 | The skill says where `--refactor-owed` items come from, and reads the triage label set from the target repo's CLAUDE.md, naming no project fact (P12). | PR #2061 left both undefined. |
| GR10 | Before labelling an issue ready, the groom runs `$S/stale-rows.sh <issue>`. Exit 1 parks the issue with `park-issue.sh`, naming the row, the unit and the failing line it printed, and the issue is not labelled ready. Exit 0 and exit 3 go on to the input check under `## Before labelling ready`, and exit 2 is reported and leaves the issue as it was. The groom never rewrites a requirement row. | A characterisation row whose unit moved on is otherwise handed out, bails at scoping, and is handed out again on every refill (#2312, #2314). Owner, 2026-11-25 (D6): the input check runs before labelling ready too. |
| GR11 | Under `## Labelling bugs`, the groom proposes the priority label for a bug that charges a repeat cost in money, time or tokens each time it occurs (a wasted leaf, a retry, a slow suite, a re-run), the low-risk label for a bug that charges no repeat cost and whose harm is small, and neither for any other bug. A bug that charges a repeat cost is never low-risk. | A bug that burns budget keeps burning it until solved, while a harmless one should not jump plain issues. "Any waste" would make nearly every bug priority. |
| GR12 | During triage it finds every issue titled `PRD <nnn>.<k>: …` with no GitHub parent, sets the parent to the issue titled `PRD <nnn>: …` through the sub-issues API, and reports each one set. An issue whose parent is a different issue is reported and left; a PRD number with no PRD issue is reported and nothing is set. | On one target repo, 11 PRD children had no parent and were found only because a human asked. |
| GR13 | Under `## The sweep`, no argument grooms every open issue, whatever its labels, except an issue GR14 leaves out (a `taken:` label on an issue carrying neither `parked` nor `bailed`): issues without the opt-in label (bare or scoped), issues already opted in (GR15), `parked` and `bailed` issues, a `taken:` one included (`### Parked and bailed issues`), refactor-owed items (the `--refactor-owed` consolidation, run as part of the sweep) and PRD trackers (GR12, GR16). Typing it is the human's say-so to opt in every issue it ends ready, an issue carrying the `draft` label excepted, which is only reported as the draft row says. `needs-rewrite` is rewritten into vfile's issue body, keeping intent, `Blocked by` lines and requirement rows, and re-triaged once (a second `needs-rewrite` becomes `needs-human`); `needs-split` is filed as separate issues and the original closed; `ready` gets the opt-in label, the kind label for a bug and the GR11 label after GR10's check; `needs-human` stays without the opt-in label and is shown; none of these outcomes is applied to a `draft` issue. Every issue in scope gets one report line, and the report ends with GR23's table, then the tally. | Grooms that only proposed labels and rewrites left most unlabelled issues untouched (Mario, 2026-11-07); a no-argument sweep on 2026-11-17 still left 5 refactor-owed issues and 7 trackers. Owner, 2026-11-25: a draft is underspecified by design and only a `/vplan` promotes it; the unready issues end in one table. Owner, 2026-11-25 (D4): parked and bailed issues are revisited, and #4770, `taken:` and `parked`, went ungroomed (2026-11-26). |
| GR14 | *Invocation* says the no-argument sweep leaves out every issue carrying a `taken:` label (any lane) and neither `parked` nor `bailed`, and reports each one as skipped, naming why: grooming under a live run would race it. (The no-argument bullet.) | A claimed issue lacks the opt-in label, so the sweep took it in; grooming must not touch an issue a run holds, and a silent skip hides that it was left. A parked or bailed run is not live, and #4770 (`taken:main`, `parked`) went ungroomed on 2026-11-26 because every `taken:` issue was skipped. |
| GR15 | Under `## The sweep`, an already opted-in issue is groomed too: triage re-checks it as gone, duplicate, stale rows (`$S/stale-rows.sh`, GR10's exits) and still meeting vfile's issue body. The groom removes its opt-in label only with a reason stated in that issue's report line, and never otherwise. | Opted-in issues went stale unseen after labelling; an unexplained un-label would silently drop work from the queue. |
| GR16 | Under `### Missing PRD parents` or a section beside it, a PRD tracker (`PRD <nnn>: …`) is groomed in the sweep: its missing-parent check as GR12 says, and when every slice it plans is filed and closed and no slice waits on a decision or data, it is closed with that reason; a tracker with unfiled slices is reported with them, not closed; a slice filed as a `draft` counts as filed and not done, so its tracker stays open. The sweep's report has one line headed `Closed PRDs:` naming each tracker this sweep closed, by number and title, or `none`. | 7 trackers were left untouched on 2026-11-17, 4 of them fully done and closable; a draft slice is still owed work. Owner, 2026-11-26: a groom closes fully done PRDs and says that it did. |
| GR17 | Under `## Invocation`, arguments are one or more issue ids written flexibly (`4261`, `#4261`, `4261 4262`, `4261,4262`) and inclusive ranges (`4260-4270`, `4260..4270`); closed or missing numbers in a range are skipped and reported in one line; any explicit argument grooms exactly those issues, whatever their labels. | The human asked for flexible ids and ranges (2026-11-17). |
| GR18 | Under `## --refactor-owed`, step 2 says a consolidated issue is written in the issue body `../vfile/SKILL.md` states (`## The issue body`), a refactor's criteria being structural predicates, each with a runnable check where one exists. | The section named no body shape, so a consolidated issue's criteria were held to no rule of vfile's (#4580). |
| GR19 | Under `## --refactor-owed`, step 2 says the sites a consolidated issue lists under `## Problem` are found by searching the default branch for the smell the source items describe, across the whole module or tree its goal names, never copied from the source items' locations alone. | On a target repo, both source items of a consolidated issue named one test file, and 16 more copies sat in 10 other test files nobody searched (#4580). |
| GR20 | Under `## --refactor-owed`, step 2 says that before filing, each criterion is checked as `../vfile/SKILL.md`'s *Before filing* check 2 states: every input it names exists, and its literal rule meets its goal, so a check that counts or searches reads every file holding a listed site, not one of them. A criterion that fails the check is rewritten before the issue is filed. | That issue's check counted one file, so the run finished its criteria with the goal unmet; vfile's check exists and the consolidation never ran it (#4580). |
| GR21 | Under `## The sweep`, the sweep never adds the opt-in label to, rewrites, splits or closes an issue carrying the `draft` label, and reports each one; a draft is changed only by a `/vplan` the human said yes to under `### The plan offer`. | A draft is underspecified by design; opting one in lets a run take it. Only a `/vplan` promotes it. Owner, 2026-11-25 (D3): a lapsed draft is offered `/vplan`, never promoted automatically. |
| GR22 | Under `## The sweep`, every open issue the no-argument sweep leaves without the opt-in label carries exactly one reason from a closed list the section states: taken by a live run (a `taken:` label on an issue carrying neither `parked` nor `bailed`); blocked by an open issue it names (`#N`); draft waiting on the condition its `## Not ready` names; needs a human decision on a question stated in full, a park on a question to the human included; parked or bailed with the cause its label's comment names unresolved; folded into an issue it names (`#N`); not planned now (a draft whose `## Not ready` condition no longer holds, not yet planned). No other reason is allowed: an issue that fits none is groomed until it is ready or fits one. | The owner wants a groom to end with every issue ready or holding a valid reason (2026-11-25); without a closed list "left for the human" absorbs anything. Owner, 2026-11-25 (D4): a park on a question to the human is needs-human; a `taken:` issue that is parked or bailed holds no live run, so taken would be a second reason for it. |
| GR23 | The sweep's report ends with one table of every open issue left without the opt-in label, one row each, columns: the issue's number, its title and its reason from GR22's list; then the tally. | One place to read why the queue is not ready; a reason scattered across per-issue lines is missed. |
| GR24 | The sweep is stateless: it keeps, writes and reads no marker of when an issue was last groomed, and re-reads every open issue in its scope on every run, so an issue whose blocker closed, whose park cause landed or whose draft condition lapsed is groomed on the next sweep. | A marker can drift from the issue (P1); re-reading costs one triage subagent per sweep. |
| GR25 | Under `### Parked and bailed issues`, the fix a `parked` or `bailed` issue waited on has landed when its newest `### ⏸ Parked` or `### ⛔ Bailed` comment written by the repository's `OWNER` or a `COLLABORATOR` (the comment's `author_association`) names at least one issue or PR (`#N`) other than the issue itself and its own run's PR (the PR saying `Closes #<issue>`), every issue it names is closed and every PR it names is merged; a comment naming none has not landed. | Owner, 2026-11-25 (D4): the label comes off when the fix it waited on has landed. A named issue or PR is checkable over REST, a cause in prose alone is not, so a guess never releases an issue; an untrusted author's comment could otherwise put an issue on the queue, and the run's own PR is the claim, not the fix. |
| GR26 | Under `### Parked and bailed issues`, a `parked` or `bailed` issue whose fix has landed is released with `$S/release-issue.sh <issue>`, never by taking a label off by hand, and then groomed as an issue already opted in (GR15). | `release-issue.sh` adds the opt-in label and removes `parked`, `bailed` and the lane's `taken:` claim together; removing `parked` by hand left an issue claimed and unlabelled, which nothing ever took back (its header). |
| GR27 | Under `### Parked and bailed issues`, a `release-issue.sh` exit 2 (another lane's claim, or no answer from gh) is reported in the issue's report line and leaves the issue as it was, its reason parked or bailed. | Exit 2 means no answer was obtained (CLAUDE.md, *Exit codes are the API*); a half-released issue must not be groomed as released. |
| GR28 | Under `### Parked and bailed issues`, an issue whose newest trusted `### ⏸ Parked` comment holds a `#### Question` heading (a `park-issue.sh --question-file` park) is never released by the sweep, whatever it names; its reason is needs-human. | Owner, 2026-11-25 (D4): one parked on a question to the human stays parked; landing a named issue does not answer the question. |
| GR29 | Under `### Parked and bailed issues`, a `parked` or `bailed` issue the sweep does not release is only reported: the sweep never adds the opt-in label to, rewrites, splits or closes it, and its report line and table row name the cause its comment states. | Its run's ledger and draft PR still stand on the body as captured, so a rewrite or opt-in under them would change what a resume continues; the report is what the human acts on. |
| GR30 | Under `## Before labelling ready`, once `stale-rows.sh` exits 0 or 3, a read-only subagent runs `../vfile/SKILL.md`'s *Before filing* check 2 (*Check the inputs*) on the issue's acceptance criteria: every input a criterion names exists, and its literal rule meets its goal. | Owner, 2026-11-25 (D6): an issue labelled ready must pass the check an issue filed by `/vfile` passes; a criterion whose literal rule missed its goal let a run finish with the goal unmet (#4580). |
| GR31 | Under `## Before labelling ready`, a criterion that fails the input check makes the issue `needs-rewrite` (`## The sweep` step 2), its report line naming the criterion and what failed, and the issue is not labelled ready. | Owner, 2026-11-25 (D6): a failure is `needs-rewrite`, so the sweep's one rewrite and re-triage fix it, and a second failure becomes `needs-human`. |
| GR32 | Under `## Before labelling ready`, an input check whose subagent returns no answer is reported and leaves the issue as it was, neither labelled ready nor rewritten. | No answer is not a pass; labelling ready on it would skip the check (CLAUDE.md, *Exit codes are the API*: never collapse no answer into a result). |
| GR33 | Under `### The plan offer`, after the report's table, the sweep asks the human one question naming, by number and title, every `draft` issue whose `## Not ready` condition no longer holds (a blocker it names closed, a PR it names merged), and offering each a `/vplan <issue>`; a sweep with no such draft asks nothing. | Owner, 2026-11-25 (D3): a draft whose reason lapsed is offered a plan, not only named "promotable". One question after the table keeps the sweep's mechanical work from waiting on the human. |
| GR34 | Under `### The plan offer`, each draft the human says yes to is planned by `/vplan <issue>`, run in the same session after the sweep's report, one draft at a time. | `/vplan` settles open decisions with the human, so it runs where the human is, and one plan at a time keeps each plan's questions apart. |
| GR35 | Under `### The plan offer`, a draft the human says no to, or does not answer about, is not planned; its row in the report's table keeps the reason not planned now, and the next sweep offers it again. | Owner, 2026-11-25 (D2): not planned now covers a declined and a not-yet-offered plan, and the sweep is stateless (D1, GR24), so a declined plan is offered again. |
