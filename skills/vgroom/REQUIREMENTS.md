## skills/vgroom/SKILL.md

| ID | Requirement | Why |
|---|---|---|
| GR1 | Invoked as `/vgroom [<issue>...\|--refactor-owed]`; no argument runs the sweep (GR13). | The old no-argument mode skipped unlabelled issues, so repeated grooms labelled few issues. |
| GR2 | One read-only subagent returns one line per issue: ready / needs-rewrite / needs-split / gone / duplicate / needs-human, plus proposed labels. `ready` means the body already meets `../vfile/SKILL.md`'s issue body; `needs-rewrite` names what it lacks. | |
| GR3 | Mechanical outcomes are applied without asking: adding or removing a label, closing an issue with a reason, and editing its `Blocked by`. Nothing else is mechanical: filing a new issue (a consolidated or split one included), rewriting criteria, and any other outcome are shown to the human first and applied only on their yes. | Grooming changes queue state cheaply and reversibly on its own; new work enters the queue only with a human's yes (PR #2118 review: filing was treated as mechanical, and the grader judged the old wording both ways). |
| GR4 | A split or a criteria rewrite is shown to the human first unless they said "go"; `/vgroom` with no argument is a "go". | |
| GR5 | `--refactor-owed` classifies each item GONE / FOLDS-INTO-OTHER / LIVE on `main`, consolidates the live ones into one issue per module, or one per deliverable where a module's items hold more than one, and closes the sources. | ~5–6 such items are filed per day. |
| GR6 | Near its top, the skill says it obeys `operator/PRINCIPLES.md` and reads it first. | PR #2061's prose passed GR1–GR5 without it, so no principle reached the skill. |
| GR7 | Every subagent brief the skill writes asks for a return of at most 10 lines (P6), and says that all writes stay in the project repo and that a fix belonging elsewhere is reported, not made (P11, in its words). | PR #2061's brief asked for one line per issue, unbounded, and carried no repo boundary. |
| GR9 | The skill says where `--refactor-owed` items come from, and reads the triage label set from the target repo's CLAUDE.md, naming no project fact (P12). | PR #2061 left both undefined. |
| GR10 | Before labelling an issue ready, the groom runs `$S/stale-rows.sh <issue>`. Exit 1 parks the issue with `park-issue.sh`, naming the row, the unit and the failing line it printed, and the issue is not labelled ready. Exit 0 and exit 3 go on as before, and exit 2 is reported and leaves the issue as it was. The groom never rewrites a requirement row. | A characterisation row whose unit moved on is otherwise handed out, bails at scoping, and is handed out again on every refill (#2312, #2314). |
| GR11 | Under `## Labelling bugs`, the groom proposes the priority label for a bug that charges a repeat cost in money, time or tokens each time it occurs (a wasted leaf, a retry, a slow suite, a re-run), the low-risk label for a bug that charges no repeat cost and whose harm is small, and neither for any other bug. A bug that charges a repeat cost is never low-risk. | A bug that burns budget keeps burning it until solved, while a harmless one should not jump plain issues. "Any waste" would make nearly every bug priority. |
| GR12 | During triage it finds every issue titled `PRD <nnn>.<k>: …` with no GitHub parent, sets the parent to the issue titled `PRD <nnn>: …` through the sub-issues API, and reports each one set. An issue whose parent is a different issue is reported and left; a PRD number with no PRD issue is reported and nothing is set. | On one target repo, 11 PRD children had no parent and were found only because a human asked. |
| GR13 | Under `## The sweep`, no argument grooms every open issue carrying none of the triage labels except PRD trackers. Typing it is the human's say-so to opt in every issue it ends ready. `needs-rewrite` is rewritten into vfile's issue body, keeping intent, `Blocked by` lines and requirement rows, and re-triaged once (a second `needs-rewrite` becomes `needs-human`); `needs-split` is filed as separate issues and the original closed; `ready` gets the opt-in label, the kind label for a bug and the GR11 label after GR10's check; `needs-human` stays unlabelled and is shown. Every issue in scope gets one report line, and the report ends with the tally. | Grooms that only proposed labels and rewrites left most unlabelled issues untouched (Mario, 2026-11-07). |
