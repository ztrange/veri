## skills/vmerge/SKILL.md

| ID | Requirement | Why |
|---|---|---|
| M1 | Invoked as `/vmerge <issue-or-PR>`. It merges with the standing permission `vdev` carries in the project repo, or with explicit permission; never in another repo. | |
| M2 | It merges only when all of these hold: the last comment is ✅ Done; the ledger has no unchecked step and no `⟂ refactor pending`; every ⟦human-owed⟧ line is ticked. | |
| M3 | An unticked ⟦human-owed⟧ line gets one read-only review subagent. NOT OK goes to the human. | |
| M4 | It takes the merge lock with `$S/merge-lock.sh take --pid <driver> --owner <token>` before its first write, where `<driver>` is the long-lived process driving the merge (`$PPID` in an agent session's Bash call) and `<token>` is an owner token of the merge's own, one per merge, so two merges driven from one session exclude each other and only the holder can release; it releases with `$S/merge-lock.sh release --pid <driver> --owner <token>` on every exit path; a merge that stops on a conflict or a refused push leaves the lock held and says so, for a human to clear with `$S/merge-lock.sh release --force`. | One merge lands at a time, and a stopped merge is visible instead of letting the next one rebase onto half-finished work. |
| M5 | If `main` moved, it rebases and force-pushes with `--force-with-lease` pinned to the recorded sha, and the push names the destination ref explicitly, `git push --force-with-lease=<branch>:<recorded sha> origin +HEAD:refs/heads/<branch>`. | The bare form silently clobbers; with no refspec git resolves the destination from the local branch ref, so a rebase whose local branch ref lags HEAD (detached HEAD or another worktree) is refused as non-fast-forward. |
| M6 | An empty or missing CI rollup is a pass only when `$S/wait-ci.sh` itself exits 0 on it, which it does when `VERI_CI_ON_PR=0` says no check will come or, `VERI_CI_ON_PR` unset, when no workflow triggers on `pull_request` (under `VERI_CI_ON_PR=0`, `queued-merge.sh` first runs the full test command on the rebased tree only when its rebase moved the tip, and the skill's manual steps 1-5 run no full suite); `VERI_CI_ON_PR=1`, or unset with such a workflow, makes it not a pass: the merge waits on it or hands it to the human, and never merges on it. | `SKILL.md` step 3 said "never merge on" an empty rollup while `wait-ci.sh` and `queued-merge.sh` merge on one under `VERI_CI_ON_PR=0`; a reader of either got the opposite answer. |
| M7 | The CI wait is `$S/wait-ci.sh`, called again on exit 3, capped at 2× the average of the last 5 runs, and at 10 minutes. | "30 min is too much." The wait is a blocking script (P3), not a wait the agent improvises. |
| M8 | A zero-step CI failure with a payments annotation goes to the human as billing. | |
| M9 | It runs the pre-merge gate command the target repo's CLAUDE.md names, when it names one, and refuses to merge while `$S/prose-owed.sh` lists any unit or gives no answer (T6). The skill itself names no make target (P12). | A missing or failing check never reads as "nothing owed": in PR #2166 a wrong script path printed nothing. |
| M10 | Deleting the branch, cutting the tag and removing the worktree each happen only after `state == MERGED` is read. | Deleting an open PR's head closes it (PR #74). |
| M11 | The tag step cuts `vN.M` (chosen with `--sort=-v:refname`, the capability in the issue's words as message) only for a feature/fix PR whose diff changes shipped behaviour, one minor bump per issue, and cuts none for a docs-only, test-only or refactor-only diff, classified by the diff, never by the issue label or the PR title prefix; a `fix:` title or `bug` label on a test-only or docs-only diff is no-tag. | `operator/MAINTAINING.md` "Versions are tags"; PR #3536 (test-only, labelled bug) and PR #3547 (docs-only) were hand-corrected. |
| M12 | It reports one line: PR url, merge sha, and the tag or `no tag`. | A no-tag merge needs a defined report. |
| M13 | It does not merge a run that ended with an open question for the human. | Merging would answer the question for them. |
| M14 | A merge that stops because CI is red, or because a gate before the merge refuses, releases the merge lock before it exits; only a conflict or a refused push (M4) keeps it held. | A red-CI stop otherwise blocks every later merge until the lock is removed by hand (#2224 waited 31 min). |
| M15 | The merge's Gates and CI steps run under `$S/merge-lock.sh gate --pid <driver> --owner <token> -- …` and its rebase and push under `$S/merge-lock.sh gate --keep --pid <driver> --owner <token> -- …`, and the merge-lock section lists the red-CI and refused-gate stops among those that release the lock. | A release rule only stated in prose is skipped; the gate in the command releases the lock whatever the reader does. |
| M16 | Before it rebases, it fetches `origin` and checks that the worktree's HEAD contains the remote branch's head (`git merge-base --is-ancestor origin/<branch> HEAD`); when it does not, it stops before the rebase and the push, pushes nothing and reports it, as a refused push does. | A lease pinned to a sha the worktree lacks matches the remote, and the force-push silently drops that commit; an unfetched `origin/main` rebases onto a stale main. |
| M17 | After the rebase and before the push, the merge runs `$S/grade-prose.sh --convert` at the worktree root and commits any GRADED line it rewrote, so the merged tree's `prose-owed.sh` exits 0 without a person recomputing a signature while reading a conflict. | A rebase onto a moved `main` changes the formula a GRADED line was signed under; re-signing by hand mid-conflict is error-prone. |
| M18 | It keeps the merge's owner token in `$(git rev-parse --git-common-dir)/veri-merge-<pr>.token`, written when the lock is taken and read by every later `gate` and `release` call; the file is removed by the release itself (the script, not a prose step), never while the lock's holder record still names its owner with a live pid; the token is never held only in a shell variable. | A shell variable does not survive between an agent's Bash calls; the git dir is outside every worktree the merge removes; a prose-only removal left 7 files from merged PRs 3464-3562. |
| M19 | A lost or unreadable owner token stops the merge and is reported to the human; the merge never runs `merge-lock.sh release --force`. | `--force` frees any holder's lock, so a merge that lost its token would free another merge's lock (PR 3162). |
| M20 | The release of the merge lock comes before the worktree's removal, or reads nothing from the worktree. | The release of PR 3146 could not read its token once step 7 had removed the worktree. |
| M21 | Before the merge step it reads the PR body and stops, releasing the lock, when it lacks `Closes #<n>` for the run's issue, naming the missing line. | A body edited after the ready PATCH can lose the keyword, and the issue then stays open. |
| M46 | *Steps* step 4 (*Merge*) says that before the merge call, for a run's PR, it runs `$S/run-finished.sh <n>`; on its exit 1 or exit 2 it does not merge, releases the lock and tells the human what it printed. (Step 4.) | A run that is not finished must not merge; the stale mutation-record pin it once named is removed (PRD 044.1). |
| M22 | Step 1 rebases with `$S/rebase-onto-default.sh --graded-only` under `$S/merge-lock.sh gate --keep …`, which resolves a conflict confined to `GRADED` files by keeping one row per unit; after `grade-prose.sh --convert`, it regrades every unit `$S/prose-owed.sh` then lists, and commits those rows before the push. | Two PRs re-signing different units conflicted on nearly every merge on 2026-11-10 (#3534, #3533, #3548); a unit changed on both sides must be regraded, and no other. |
| M23 | *Steps* step 5 (*Read `state`*) says that after a merge call that errors, the PR's `state` is re-read over the settle window `queued-merge.sh` uses (`VERI_MERGE_SETTLE_READS` reads, `VERI_MERGE_SETTLE_SLEEP` seconds apart) before anything else, and a `MERGED` read is treated as success. (Step 5.) | PR #3486: the merge returned `502 Bad Gateway` but landed. |
| M24 | The same step says no retry rebases or pushes a PR whose head is an ancestor of origin/main (`git merge-base --is-ancestor <head> origin/main`); such a PR is reported to the human and the lock released. (Step 5.) | The #3486 retry force-pushed a head equal to a main commit; GitHub closed the PR as CLOSED, and its issues never auto-closed. |
| M25 | *Steps* step 1 says that when the lease's branch comes from a shell variable, the variable is braced before the colon (`--force-with-lease=${B}:<sha>`, never `$B:<sha>`), since zsh reads a colon after a bare name as a modifier. (Step 1.) | #1592: the lease lost `:f` and git reported a fake non-fast-forward. |
| M26 | *Steps* step 4 (*Merge*) says the merge call never passes `--admin`, and a merge the repository's rules refuse stops, releases the lock and is reported to the human. (Step 4.) | No rule forbade bypassing the repository's ruleset. |
| M27 | *Steps* step 6 (*Tag*) says that when the issue's title describes the failure, the tag message states the capability the change gives instead, e.g. #2204 "…words don't split…" → "Conductors and leaves run SKILL.md's bash blocks under bash, whatever the user's login shell". (Step 6.) | A bug title as a tag reads as if the bug shipped (operator ruling, 2026-10-23). |
| M28 | *Report* says the merge sha reported is the commit on main, with that commit's subject next to it. (*Report*.) | #714: a note pointed at a sha the rebase merge had rewritten. |
| M29 | *Preconditions* lists: no process has a file open or its working directory inside the run's worktree (`lsof +D <worktree>`); a failed check stops the merge like any other precondition. (*Preconditions* list.) | #159: concurrent rebases left the worktree stale. |
| M30 | *Steps* step 1 states the ancestor check itself: after the fetch and before the rebase and the push, the PR's head is read fresh with `gh api repos/{owner}/{repo}/pulls/<pr> --jq .head.sha` (REST), and when it is an ancestor of `origin/main` nothing is pushed, the lock is released and the PR is reported to the human. (Step 1.) | Step 5 said a later retry runs the check; a retry starts at step 1, which did not state it (review of PRD 020.3). |
| M34 | The merge-lock section says a `take` that exits non-zero means the lock was not taken: the merge stops before its first write, releases nothing, and reports `take`'s stderr to the human, never running `merge-lock.sh release --force` itself. (The merge lock section.) | vmerge is the other caller of `take`, which can now give up on a lock that never frees; `--force` frees any holder's lock, which is why a lost token never runs it either. |
| M31 | It says that where the target repository's `CLAUDE.md` names a stack branch (`$S/stack-branch.sh` exits 0), a reviewed run is joined to the stack with `$S/queued-merge.sh`, not merged, and that the review's OK is the gate to join, not CI. | PRD 034 C2: the per-issue review is where defects are caught, and CI runs on the stack's tip. |
| M33 | *Preconditions* says that for a pull request whose base is the stack branch, an unticked `⟦full-suite⟧` line does not count as an unchecked step; every other unticked line still fails the precondition. | A stacked run never ticks its `⟦full-suite⟧` line, since CI on the stack's tip is that run (PRD 034 D4, D7); counting it would refuse every join. |
| M32 | It says a join makes no CI wait and no merge call, cuts no tag and closes no issue: the issue closes, and its tag is cut, when the slice holding it lands on the default branch. | PRD 034 D3, C3: an operator who expects a tag or a closed issue after a join would read a correct join as a failure. |
| M35 | It says that a join refused because the stack is red (`queued-merge.sh` exit 1 naming the red commit) is retried after the stack is green, and that the culprit search, `$S/stack-culprit.sh <sha>` on the commit the refusal names, is the next step. | PRD 034 D12: the run is Done and joins once the freeze lifts; until 034.5 the operator acts by hand. |
| M36 | It says that `$S/stack-revert.sh <n>` reverts a culprit on top of a red stack, its hand fix included when one was pushed; that the issue then keeps its labels and waits for `$S/release-issue.sh <n>` to return to selection; and that a revert exit 1 leaves the stack frozen for the human. | PRD 034 D16, D17: a reverted issue is not retried unseen, and a revert that later work depends on is a human's call; until 034.5 the operator acts by hand. |
| M37 | *Joining a stack* says that while `.tdd/github-outage` exists in the target repository's main working tree the join is offline: the same `$S/queued-merge.sh <pr-url> <worktree> <branch> -` call joins onto the local stack branch, gated by the full suite on the rebased tip, and pushes nothing, confirms nothing and deletes no remote branch; its exit 0 is reported as the PR url and `joined offline, no tag`, its exits 1 and 2 as for an online join. | PRD 033.2a, OL14, D8. |
| M38 | *Joining a stack* says that a slice is landed by `$S/stack-land.sh`, never by `queued-merge.sh`; when it lands (the cut is 100 or more commits ahead of the default branch, or the stack is idle); that a red stack refuses it; and that exit 1, 2 and 3 are reported, never retried blind. | The operator's instruction until the dev session lands slices itself. |
| M39 | After a landing the stack is carried by `$S/stack-carry.sh <cut>`, which `stack-land.sh` runs itself; an exit 1 leaves the stack as it was for the human; and a run is never rebased by hand across a landing, since it carries itself at its join. | The operator's instruction until the dev session lands slices itself. |
| M40 | The tags of a slice are cut by `$S/stack-tag.sh <slice-pr-url>`, which `stack-land.sh` runs, by the commit types of each issue; the operator rewords a failure-phrased title with `--message`. | The operator's instruction until the dev session lands slices itself. |
| M41 | It says the token file of a merge that is waiting on `take` survives another merge's `take`, so a lost token still means a real loss. | Observed on PRs #4357 and #4364: a take deleted a waiting merge's token. |
| M43 | *Preconditions* says that for a pull request whose base is the stack branch and whose head branch is not a run's (`tdd/<n>-…`), the `✅ Done` and committed-ledger bullets do not apply, and instead its body has `Closes #<n>`, the review's OK is the gate, and every commit of `origin/<stack>..<head>` has a subject ending `(#<n>)` for the issue `Closes` names (one that does not is a failed precondition, named); the human-owed, open-question and `lsof` bullets still apply. | A hand-built pull request has no run, so no `✅ Done` comment or ledger exists to read (PRD 034 D31), and a hand commit without the number lets a slice cut mid-issue (PRD 034 C10). |

| M47 | Step 4 reads the PR body over REST (`gh api repos/{owner}/{repo}/pulls/<pr> --jq .body`) before checking for `Closes #<n>`, never `gh pr view`. | `gh pr view` is GraphQL, refused in a Claude Code cloud session; the body check would fail and block every merge there. |
| M48 | For an unticked ⟦human-owed⟧ line carrying `⟦deviation <id>⟧`, the read-only review subagent judges whether the deviation was right, reading the step's diff and the rule's purpose from `ADJUDICATE.md`'s *Waivable rules*.
