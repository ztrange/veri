# vmerge — land one finished run

Obeys `operator/PRINCIPLES.md` under the veri clone root (`git -C <base dir> rev-parse --show-toplevel`); read it first.

`$S` is `skills/tdd/scripts/`, reached from this skill's base directory as `../tdd/scripts/`.

## Invocation and permission

Invoked as `/vmerge <issue-or-PR>`; resolve the argument to the issue, its PR and its worktree.

Merging is allowed under the standing permission that `vdev` carries in the project repo, or under explicit permission from the user. Never merge in another repo, whatever the argument names.

## Joining a stack

First run `$S/stack-branch.sh <repo root>`. Exit 3 (no stack branch named): merge as the rest of this skill says. Exit 2: stop and report its stderr to the human. Exit 0: the target repository's `CLAUDE.md` names a stack branch, and a reviewed run whose PR has that branch as its base is **joined** to the stack, not merged (a PR based on the default branch is still merged as below). The review's OK is the gate to join, not CI. Check *Preconditions* below, then run `$S/queued-merge.sh <pr-url> <worktree> <branch> -` alone, and nothing of *The merge lock* or *Steps*: the script takes and releases the lock itself, rebases onto the stack, runs the fast tier and `prose-owed.sh`, pushes the stack and confirms the PR reads merged. Its exit 0 is joined (report the PR url and `joined, no tag`), exit 1 is a clean refusal (a conflict, a red fast tier, a unit owing a grade or an unticked line, named on stderr: report it to the human; a refusal because the stack is red is below), exit 3 is a PR already merged into the stack (nothing to do: report it), and exit 2 is no answer (report its stderr; never retry it blind).

While `.tdd/github-outage` exists in the target repository's main working tree the join is **offline**: the same `$S/queued-merge.sh <pr-url> <worktree> <branch> -` call joins onto the local stack branch, gated by the full suite on the rebased tip, and pushes nothing, confirms nothing and deletes no remote branch. Its exit 0 is reported as the PR url and `joined offline, no tag`; its exits 1 and 2 as for an online join. During the outage, pass `--skip-suite <model-id> <reason>` before the PR url only on your own judgement, read from your own model id, that the full suite's hardware cost outweighs its gain, and only when that id names `opus` or `fable`: a model below Opus never skips, and the script refuses any other id (exit 2). The join records the skip on its commit as `Veri-Suite: skipped <model-id> <reason>`. An offline join refused because `.tdd/stack-local-red` freezes the local stack (exit 1 naming the file) goes to vdev's *A red stack*.

A join makes no CI wait and no merge call, cuts no tag and closes no issue: the issue closes, and its tag is cut, when the slice holding it lands on the default branch.

A join is refused while the stack is red: `queued-merge.sh` exits 1 with one stderr line naming the red commit (CI's latest answer on the stack failed). The run is done and kept as it is; retry the join after the stack is green, never sooner, and no flag or variable gets a join past the freeze. The next step is the culprit search: run `$S/stack-culprit.sh <sha>` on the commit the refusal names, and report what it prints to the human.

When the one hand-fix attempt on a red stack fails (its review is not OK, `stack-fix.sh` refuses it, or CI is red on the fix's tip), run `$S/stack-revert.sh <n>` for the culprit's issue `<n>`: it reverts the culprit's commits on top of the stack, the hand fix's too when one was pushed, as one commit, and nothing below the tip is rewritten. The reverted issue then keeps the labels its run left and does not return to selection by itself: it waits for `$S/release-issue.sh <n>`, as any bailed issue does. A revert exit 1 (a conflict, a red fast tier or a unit owing a grade) pushes nothing and leaves the stack frozen: report its stderr to the human, whose call it is, and never force it.

A slice of the stack is landed on the default branch by `$S/stack-land.sh`, run in the target repository's clone, never by `queued-merge.sh` and never by hand. It cuts at the stack's newest tested issue end and lands when that cut is `VERI_SLICE_COMMITS` (default 100) or more commits ahead of the default branch, or when the stack is idle (no open pull request onto it, no living conductor); `--now` skips that rule and no other. A red stack refuses it. Exit 0 is landed (report the slice's PR url, merge commit and issues closed it prints). Exit 1 is a clean refusal (a red stack, a rebase conflict, or red CI on the rebased slice), exit 2 no answer (a merge the repository's rules refused, a PR not reading merged in the settle window, or its closed issues still open), and exit 3 nothing to land (no tested cut, or a cut too small while the stack is live): report each one's stderr to the human, and never retry it blind.

After a landing the stack is carried onto the new default branch by `$S/stack-carry.sh <cut>`, which `stack-land.sh` runs itself; a land whose carry-over exits other than 0 or 3 (3: the slice was the whole stack, nothing to carry) is exit 2 naming `stack-carry.sh <cut>` as the command owed. Its exit 1 (a rebase conflict, a tree its check disagrees with, or a stack origin moved) leaves the stack as it was, for the human. A run is never rebased by hand across a landing: it carries itself at its own join.

The tags of a landed slice are cut by `$S/stack-tag.sh <slice-pr-url>`, which `stack-land.sh` runs itself after the landing, never by *Steps* step 6: one annotated `vN.M` per issue of the slice, classified by the commit types of that issue's commits in it (any `feat` or `fix` tags it; `docs`, `test`, `refactor`, `chore` and `plan` alone do not), its message the issue's title. When that title describes the failure rather than the capability, run it again with `--message <n>=<text>` stating the capability, as step 6 says. A tag already on an issue's commit is kept, so a re-run cuts only the missing ones. A landing whose `stack-tag.sh` exits other than 0 or 3 is exit 2 naming the command still owed: report it, and run that command once the cause is fixed.

## Preconditions

Merge only when all of these hold; otherwise stop and tell the human which one failed:

- The last comment on the issue is `✅ Done`.
- The committed ledger has no unchecked step and no `⟂ refactor pending`. For a PR whose base is the stack branch (see *Joining a stack*), an unticked `⟦full-suite⟧` line does not count as an unchecked step: a stacked run never ticks it, since CI on the stack's tip is that run. Every other unticked line still fails this precondition.
- Every ⟦human-owed⟧ line is ticked.
- The run did not end with an open question for the human. Merging would answer it for them, so hand the question back instead.
- No process has a file open or its working directory inside the run's worktree: run `lsof +D <worktree>` from outside the worktree (the call starts in another directory and names the worktree by its absolute path), and read its output, not its exit code (`lsof` can exit 1 while printing lines): any process line it prints is a foreign process. A process still there (a review, a hand fix, another merge) is a failed precondition: stop, do not wait.

A **hand pull request**, one whose base is the stack branch and whose head branch is not a run's (`tdd/<n>-…`), has no run behind it, so the `✅ Done` and committed-ledger bullets do not apply to it. In their place its body has the line `Closes #<n>`, the review's OK is the gate, and every commit of `origin/<stack>..<head>` (after a fetch) has a subject ending `(#<n>)` for the issue that `Closes` line names: a commit that does not is a failed precondition, named by its sha and subject, since a slice is cut only at an issue's end and a commit without the number lets it cut mid-issue. The human-owed, open-question and `lsof` bullets still apply.

An unticked ⟦human-owed⟧ line gets one read-only review subagent (it may read, never write). If it answers OK, tick the line; if NOT OK, the line goes to the human and nothing merges.

## The merge lock

Take the merge lock with `$S/merge-lock.sh take --pid <driver> --owner <token>` before the first write and hold it to the last. A `take` that exits non-zero means the lock was not taken (another holder outlasted its bounded wait, the holder is dead or reused, or the call was refused): stop the merge there, before its first write, release nothing, and report `take`'s stderr to the human; never run `merge-lock.sh release --force` yourself. `<driver>` is the long-lived process driving the merge: `$PPID` in an agent session's Bash call. `<token>` is an owner token of this merge's own, one per merge (a fresh random string); two merges driven from one session share `$PPID`, so only the token tells them apart: they exclude each other, and only the holder can release.

Keep the token in `$(git rev-parse --git-common-dir)/veri-merge-<pr>.token`: write it there when the lock is taken, read it back for every later `gate` and `release` call. The release itself (the script, not a prose step) removes that file, and never while the lock's holder record still names its owner with a live pid; do not remove it by hand. Another merge's `take` leaves it in place while this merge waits on `take`, so a lost token is a real loss. Never hold the token only in a shell variable, which a fresh Bash call loses. A lost or unreadable token stops the merge: report it to the human and never run `merge-lock.sh release --force` yourself. Pass the same `--owner <token>` to every `gate` and `release` call. Release it with `$S/merge-lock.sh release --pid <driver> --owner <token>` on every exit path: success, refusal, failure and interruption alike. A lock left held blocks every other merge.

Run the steps that can refuse under `$S/merge-lock.sh gate --pid <driver> --owner <token> -- <cmd>`: a failing command (any exit but 0 or 3) releases the lock before the merge exits. So a red CI, a refused pre-merge gate command and a refused `prose-owed.sh` all release it. Run the rebase and the push under `$S/merge-lock.sh gate --keep --pid <driver> --owner <token> -- <cmd>`, which keeps the lock on failure. A `gate` runs `<cmd>` only for the lock's holder: one that exits 2 because this merge does not hold the lock (none held, or the holder record names another pid or owner, named on its stderr) ran nothing, so the merge stops there, as for a failed `take`: release nothing, never `release --force`, and report its stderr to the human.

The one exception: a merge that stops on a rebase conflict, a refused push, or a worktree HEAD that lacks the remote branch's head (step 1) leaves the lock held, and says so in its report. A human clears it with `$S/merge-lock.sh release --force` once the cause is dealt with. Every other stop, red CI and a refusing gate included, releases it; a stop that never held the lock (a failed `take`, a `gate` refused for not holding it) has nothing to release.

## Steps

1. **Rebase if `main` moved.** First fetch `origin`. Then the ancestor check: read the PR's head fresh with `gh pr view <pr> --json headRefOid -q .headRefOid` (never a sha recorded in an earlier call) and run `git merge-base --is-ancestor <that sha> origin/main`; when it exits 0 the PR is already on main: push nothing, rebase nothing, release the lock (`$S/merge-lock.sh release --pid <driver> --owner <token>`), report it to the human and stop. Then check that the worktree's HEAD contains the remote branch's head: `git merge-base --is-ancestor origin/<branch> HEAD`. When it does not, stop before the rebase and the push: push nothing, and report it as a refused push (the lock stays held, per the exception above). Then record the PR head sha, rebase onto `origin/main` under `$S/merge-lock.sh gate --keep --pid <driver> --owner <token> -- $S/rebase-onto-default.sh --graded-only`, which resolves a conflict confined to `GRADED` files by keeping one row per unit (any other conflict stops the merge, lock held). Then, at the worktree root, run `$S/grade-prose.sh --convert` and commit any GRADED line it rewrote, then regrade every unit `$S/prose-owed.sh <repo root>` still lists and commit those rows before the push, so the merged tree's `prose-owed.sh` exits 0 without a person recomputing a signature while reading a conflict. Push under `$S/merge-lock.sh gate --keep --pid <driver> --owner <token> -- git push --force-with-lease=<branch>:<recorded sha> origin +HEAD:refs/heads/<branch>`. The push names the destination ref explicitly, so a rebase whose local branch ref lags HEAD (detached HEAD or another worktree) is not refused as non-fast-forward. Never the bare `--force-with-lease`: it silently clobbers a push you have not seen. When the lease's branch comes from a shell variable, brace it before the colon (`--force-with-lease=${B}:<sha>`, never `$B:<sha>`): zsh reads a colon after a bare name as a modifier and drops it, and git then reports a fake non-fast-forward.
2. **Gates.** If the target repo's CLAUDE.md names a pre-merge gate command, run it on the rebased tip under `$S/merge-lock.sh gate --pid <driver> --owner <token> -- <that command>`; when CLAUDE.md names none, skip it. Run `$S/merge-lock.sh gate --pid <driver> --owner <token> -- $S/prose-owed.sh <repo root>`: exit 0 means nothing owed; refuse on exit 1 (it lists units) or any other exit (no answer) (T6).
3. **CI.** Read the check rollup. An empty or missing rollup is a pass only when `$S/wait-ci.sh` itself exits 0 on it: that is `VERI_CI_ON_PR=0` (no check will come; when its rebase moved the tip, `queued-merge.sh` first runs the full test command on the rebased tree, while steps 1-5 here run no full suite) or, `VERI_CI_ON_PR` unset, no workflow triggering on `pull_request`. With `VERI_CI_ON_PR=1`, or unset and such a workflow present, an empty rollup is not a pass: wait or hand it to the human, never merge on it. Wait with `$S/merge-lock.sh gate --pid <driver> --owner <token> -- $S/wait-ci.sh <pr-url> 540 "" "$(git rev-parse HEAD)"` (a red CI releases the lock), and call it again whenever it exits 3. The wait is capped at 2× the average duration of the last 5 runs, and never more than 10 minutes. A failure with zero steps run and a payments annotation is billing: report it to the human as billing and stop; it is not a code failure and is not retried.
4. **Merge** the PR. First read its body (`gh pr view <pr> --json body`) and check it contains the line `Closes #<n>` for the run's issue. When it lacks that line, do not merge: release the lock (`$S/merge-lock.sh release --pid <driver> --owner <token>`), and tell the human which line is missing, naming `Closes #<n>`. Then, for a run's PR (its worktree `.tdd/wt/<n>`), run `$S/run-finished.sh <n>`, which rechecks the *Preconditions* it can read (the run `done`, the ledger, the ⟦human-owed⟧ lines) and that the run's mutation record pins no old text its file no longer holds. On its exit 1, do not merge: release the lock (`$S/merge-lock.sh release --pid <driver> --owner <token>`) and tell the human each line it printed (`stale-pin <file> <line>` among them) and its stderr; on exit 2, do the same with its stderr, since no answer is not a pass. Merge only when the line is present and `run-finished.sh` exited 0. The merge call never passes `--admin`, and a merge is never forced. Whatever the merge call answers, success, an error or a refusal, go straight to step 5 and release nothing here: a merge the repository's rules refuse stops there, step 5 releasing the lock and reporting it to the human, so a `502` mistaken for a refusal still gets the settle read and the lock is released in one place.
5. **Read `state`.** Query the PR and continue only when `state == MERGED`. After any merge call that does not answer success, or answers success but the first read is not `MERGED` (a `502 Bad Gateway` can still land the merge), re-read `state` before anything else, over the settle window `queued-merge.sh` uses: up to `VERI_MERGE_SETTLE_READS` reads (default 10), `VERI_MERGE_SETTLE_SLEEP` seconds apart (default 3); a `MERGED` read is success, and the steps below go on. When the window closes with no read `MERGED` (or no read answering), release the lock (`$S/merge-lock.sh release --pid <driver> --owner <token>`), the one release on this path, report it to the human (as a rules refusal when the merge call's refusal named the repository's rules, else as a merge that did not land) and stop; never call merge again in this pass. No retry rebases or pushes a PR whose head is an ancestor of origin/main: a later retry of this PR is stopped by step 1's ancestor check (`git merge-base --is-ancestor <head> origin/main`) before it rebases or pushes anything, and such a PR is reported to the human and the lock released there. Deleting the branch, cutting the tag (when step 6 cuts one) and removing the worktree each happen only after that read; deleting an open PR's head closes it (PR #74).
6. **Tag.** Choose the next `vN.M` from `git tag --sort=-v:refname` (never plain `sort`: lexically `v0.9` outranks `v0.10`). Cut it only for a feature/fix PR whose diff changes shipped behaviour: one minor bump per issue, an annotated tag whose message is the capability, in the issue's words; push it. When the issue's title describes the failure, the message states the capability the change gives instead, e.g. #2204 "…words don't split…" → "Conductors and leaves run SKILL.md's bash blocks under bash, whatever the user's login shell". Cut none for a docs-only, test-only or refactor-only diff. Classify by the diff, never by the issue label or the PR title prefix: a `fix:` title or `bug` label on a test-only or docs-only diff is no-tag.
7. **Release the lock** with `$S/merge-lock.sh release --pid <driver> --owner <token>`. Do this before the worktree is removed, so the release reads nothing from the worktree (the token file lives in the git common dir, not the worktree).
8. **Clean up.** Delete the branch and remove the worktree.

## Report

Report exactly one line: the PR url, the merge sha, and the tag or `no tag`. The merge sha is the commit on main, with that commit's subject next to it: a rebase merge rewrites every sha, so one read before the merge names no commit on main. Read it with `gh pr view <pr> --json mergeCommit -q .mergeCommit.oid` (for a multi-commit rebase merge, the last commit it put on main), and its subject with `git fetch origin`, then `git log -1 --format=%s <that sha>`.
