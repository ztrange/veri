# The scripts catalogue

Entries for the scripts in `$S` (`<base directory>/scripts`), moved out of SKILL.md. `$S` is defined there.

- `$S/supervise.sh <name> <cmd> [args...]` — **the leaf launcher.** Spawns `<cmd>` under a
  heartbeat + hard-timeout watchdog, owns the `.tdd/<name>.log` progress log, and returns
  the captured output on stdout. **Exit 0 = success, 1 = leaf-failure, 2 = killed-stuck**
  (hung past the heartbeat window or over the hard timeout, **after** its stuck-retry
  budget). A one-line status goes to stderr. Tunables: `VERI_HEARTBEAT` (silence window s,
  default 180), `VERI_TIMEOUT` (hard cap s, default 900), `VERI_STUCK_RETRIES` (extra
  attempts after a killed-stuck, default 1 — the **liveness** axis, independent of both the
  conductor's verdict-axis `REVISE_BUDGET` and its cost-axis `VERI_REFACTOR_BUDGET`).
  Four more choose the **model** each leaf runs on, resolved here through
  `$S/leaf-model.sh` and passed to `claude --model`: `VERI_MODEL` (every leaf),
  `VERI_MODEL_DEVELOPER` (developer leaves only — `develop-*`, `revise-*`),
  `VERI_MODEL_REVISE` (only the developer leaves that redo rejected work — `revise-*` and
  `develop-exhausted` — beating `VERI_MODEL_DEVELOPER` for them) and
  `VERI_MODEL_VERIFIER` (verifier leaves only — `verify-*`, `verify-pin` included). A role
  variable beats `VERI_MODEL`; all four unset means the shipped defaults: sonnet for first-try
  developer leaves and verifiers, opus for the redo leaves and the conductor. The value goes through verbatim, so an alias (`sonnet`, `opus[1m]`) or a full id
  (`claude-sonnet-5`) both work.
  Because leaves **stream** (below), the default
  `VERI_HEARTBEAT` is a real silence window — a working leaf keeps it fresh, a genuinely
  hung one trips it — so just use the defaults; no need to pin heartbeat to the timeout.
  **Every leaf is launched through this — never call `run-leaf.sh` or `claude` directly.**
  It records its own final code in the completion file `.tdd/<name>.exit` on **every** path,
  killed-stuck included — that is what makes a detached launch waitable. And because a
  killed-stuck leaf is relaunched (`VERI_STUCK_RETRIES`), one call can take **more than one**
  `VERI_TIMEOUT` of wall time, which is why the wait below loops rather than naming one long
  timeout. When a `develop-*` or `revise-*` leaf exits, any change it made to a committed
  `.tdd/issue-*-mutations.md` record (an edit, a deletion, a new file) is undone and one
  `mutation-record-restored` event (`name=`, `file=`) goes to `events.jsonl` per record —
  only `mutation-probe` writes that record, except a record the leaf's step names with
  `mutation-record: .tdd/issue-<n>-mutations.md` in its step text (`VERI_STEP`), which is left as the leaf made it; the marker inside backticks, double quotes or single quotes (an apostrophe within a word is not a quote) is ignored, so a step that only quotes it names no record. When a `develop-red…` or `revise-red-…` leaf exits,
  any tracked production file it changed or deleted from the step's uncommitted state is written back and
  one `production-file-restored` event (`name=`, `file=`) goes to `events.jsonl` per file.
  A refused launch exits 2, writes one `launch-refused` event (`name=`, `reason=`) naming the leaf
  and starts no leaf. Causes: a `run-leaf.sh` launch whose prompt file is missing or empty, a
  `run-leaf.sh` launch with no prompt argument, `VERI_STEP` set but empty, an empty `--step`
  value, and a pending `.tdd/stop` of `at-leaf` or `now`.
- `$S/detach-leaf.sh <cmd> [args...]` — **the detaching half of a detached launch.** Runs
  `<cmd>` as the leader of a **new session**, and so of a new process group, then returns at
  once. Every leaf launch below goes through it, and none uses `nohup` — *Launching a leaf*
  says why. Redirections go on the call as usual — the launched process inherits them.
- `$S/wait-leaf.sh <name> [max-seconds]` — **the foreground half of a detached launch.**
  Blocks polling for that completion file and exits with the code recorded in it as soon as
  it lands (0 / 1 / 2, the launcher's own contract), or **exit 3** — nothing to report yet —
  once `max-seconds` pass with no completion file. The default is 540 s, comfortably inside
  Claude Code's 10-minute cap on a single foreground Bash call. On a **3, call it again**:
  the leaf is still running. A 3 with no leaf running means no result was ever recorded —
  never success. A **2** also means the supervisor died without recording a status: no
  completion file, and the pid in `.tdd/<name>.pid` no longer runs a supervisor for that
  name. It takes the killed-stuck branch like any other 2.
- `$S/run-leaf.sh <prompt-file|-> [claude args...]` — the inner leaf invocation. Runs
  `claude -p --output-format stream-json` so the leaf **streams events as it works** (that
  is the supervisor's heartbeat), then appends the clean final result. You always run it
  *via* `supervise.sh`, not on its own. Tunable: `VERI_LEAF_TOOLS` — unset passes
  `--tools Bash,Read,Edit,Write,Grep,Glob` (`DEFAULT_TOOLS`) to `claude`; set non-empty passes
  `--tools <value>`; set empty passes `--tools ""` (`grade-prose.sh` sets it empty, so its grader
  has no tools). A `--tools` in the caller's own arguments wins over all three.
  It always sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` in `claude`'s environment, and sets
  `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` to the leaf's effective timeout, the one
  `supervise.sh` enforces (`VERI_TIMEOUT`, else the run's `.tdd/issue-<n>-timeout`, else 900 s),
  unless the caller already set them.
- `$S/extract-result.sh` — pulls the final result text out of a leaf's stream-json (used
  by `run-leaf.sh`; passes plain text through unchanged).
- `$S/build-develop-prompt.sh <red|green|refactor|cover|transform|diff|structural|predicate|revise|exhausted|reconcile|over-budget|rebase|replaces-report|red-contradicted|red-repair|red-missing|red-supersede|expand|beside|cover-new|dual-stub|migrate|contract-a|contract-b> …` — assemble a **developer** leaf's prompt from a
  versioned template: `red <spec-file> <step-text> <test-cmd>`, `green <spec-file>
  <step-text> <test-cmd> <test-path> <target> <fast-cmd> [<owed-cases>]` (the optional 8th argument
  is the named cases still owed for deletion), `refactor <spec-file> <step-text>
  <test-cmd> <touched-files>`, `revise <phase> <spec-file> <step-text> <test-cmd>
  <reason-file>` (reads `VERI_ISSUE`, the run's issue number, for the `check-earlier` command in the prompt; **exit 2** with one stderr line when it is not a number), `red-repair <case> <report-file> <superseded>…` (the Red leaf that repairs one case the step's own Red wrote, edited in place; never creates a suite), `$S/build-develop-prompt.sh red-missing <spec-file> <step-text> <test-cmd> <reason-file>` (the Red leaf that adds the one case pinning the `MISSING_TEST:` behaviour the reason file names, editing no other case). `revise red` whose reason file is named `verify-pin.reason` and whose `REASON:` line says `stays green` builds no prompt and exits 2 with a stderr line naming `pin-reject-route.sh`. Prints the prompt on stdout; **exit 2** with a diagnostic and **no
  stdout** on an unknown phase or a missing template, spec or reason file — never a partial
  prompt. The mirror of `build-verify-prompt.sh` and its opposite in emphasis: the verifier
  builder is defined by what it **cannot** carry (no rationale parameter, so blindness is
  structural), this one by what it **must** carry — the same instructions on every run of a
  phase, with only the variables changing. **Build every developer prompt with it**; a
  phase's instructions live in its template, not in prose you improvise per cycle.
- `$S/build-verify-prompt.sh [--step '<STEP>'] [--fast-cmd '<CMD>'] [--supersede-base <sha>] <red|green|refactor|pin|plan|rebase|transform|diff> <spec-file> <test-path> [target]` —
  assemble the blind verifier prompt. `--supersede-base <sha>` (hex, 7-40 chars; `diff` phase) points the verifier at `git diff <sha>` for a supersede edit. Used by `verify.sh`; you rarely call it directly.
- `$S/verify.sh [--step '<STEP>'] [--fast-cmd '<CMD>'] [--supersede-base <sha>] <red|green|refactor|pin|plan> <spec-file> <test-path> [target] | diff <spec-file> <branch-base-sha> <step-base-sha>` — the **verify
  verb**: build the blind prompt → launch the verifier leaf **through the supervisor** →
  parse the verdict. Prints the verifier's **reason** on stdout; **exit 0 = PASS, 1 =
  REJECT, 2 = malformed or killed-stuck, or (`pin`) no resolvable merge-base: the branch has no base against `origin/HEAD`, and stderr names `origin/HEAD`**. The `pin` phase is the *already satisfied*
  check: the verifier confirms the test passes now, **fails** under a behaviour-removing
  mutation it applies and then reverts itself, and is behaviour-level — the same trivial
  / over-coupled / too-complex bar as `red`.
- `$S/refactor-owed.sh append|applied|not-done|render|list <file> …` — the structural leftovers a step's refactor leaf reports. `append <file> '<STEP>' [<bounds>]` reads the report on stdin; `applied <file> '<transform>' <sha> '<subject>'` records a candidate as applied, `<subject>` being the applying commit's subject, `"$(git log -1 --format=%s)"`, which `render` prints beside the sha so the row stays readable after a rebase rewrites it; `not-done <file> '<candidate>' <reason>` records a candidate the pass did not apply, which `render` shows under `### Not done`; `render <file>` prints the `## Refactor owed` section; `list <file>` prints each structural transform once. Exit **0** done, **1** a write failed, **2** a missing argument or an unknown verb, **3** `render` or `list` found nothing.
- `$S/refactor-candidates.sh <issue> <owed-file>` — files the one issue listing what a run's structural pass left. It reads `<owed-file>` (`.tdd/issue-<n>-refactor-owed.md`) and lists every `out-of-bounds` and `not-done` row under a heading per module; the issue is titled `Refactor candidates left by #<issue>` and labelled exactly `refactor` and `refactor-owed`, never the opt-in label. A rerun finds the open issue by that exact title and replaces its body instead of filing another. Prints the issue's url on stdout. Exit **0** the url printed, **2** a bad argument (a non-numeric `<issue>`, or not two arguments) or a GitHub failure, **3** nothing out-of-bounds or not done (a missing or empty `<owed-file>`), and no issue filed.
- `$S/mutation-parity.sh <pairs-table>` — proves each row of a `⟦replaces-case⟧` pairs table by applying its mutation: **exit 0** all proven, **exit 1** a REJECT, **exit 2** a bail. A row whose mutation no kept case catches prints `MISSING_TEST: <old>: no kept case fails when its mutation is applied` on stderr; saved to a reason file, that line routes through `wrong-test-route.sh` as `missing`.
- `$S/run-verdict.sh [--step "<STEP>"] [--fast-cmd '<cmd>'] [--supersede-base <sha>] <red|green|refactor|pin|plan> <spec-file> <test-path> [target]`
  — the **verdict launcher**: `verify.sh`'s own call, argument for argument, reached as a
  command rather than as a shell string. This is what `supervise.sh verdict-<phase>` runs;
  it passes every argument, `--supersede-base <sha>` included, through untouched and `exec`s the verify verb, so the step title
  travels in argv and its exit code is `verify.sh`'s.
- `$S/parse-verdict.sh` — extracts `PASS|REJECT` + reason from a leaf's output (used by
  `verify.sh`).
- `$S/tick-issue-criterion.sh <n> "<substring>"` — tick a criterion checkbox in the
  issue body (the human-facing mirror).
- `$S/next-unchecked.sh < .tdd/issue-<n>.md` — print the **first unchecked ledger step**'s
  description; **exit 3** when none remain (the loop-done / nothing-to-resume signal).
- `VERI_STEP=<step> $S/wrong-test-route.sh --spec <spec-file> <green-report> <red-test-id>` — routes a green report's `WRONG_TEST:`, or a report carrying `MISSING_TEST:` (a verify-green REJECT reason, a mutation-parity stderr saved to a file, a revise-green report answering `IMPOSSIBLE`): **exit 0** prints `fixture <path> <name>` (a helper, fixture or shared setup function defined in the test file `<path>` that is not a test case), `missing <behaviour>` (a behaviour no test pins; the report file is the `red-missing` brief), `later <step>` (the behaviour is an open ledger step after `VERI_STEP`: one a `LATER_STEP:` line names, or, with no such line, one whose criterion text (the Nth box, checked or not, under `## Acceptance criteria` in `--spec`, N from the step's `⟦criterion N⟧` marker; a step with no usable marker never matches) contains the `MISSING_TEST:` behaviour or is contained in it, compared case-insensitively), `red <case>` (an existing case other than the step's own that a `CONTRADICTS:` line names; a case named only in the `WRONG_TEST:` text is evidence, so a report that cites one routes to `repair`; a report is exempt from the `SUITE:` line as a `green-wrong-test` (`WRONG_TEST:` with `SUPERSEDED:`) or a `green-wrong-test-contradicts` (`WRONG_TEST:` with `CONTRADICTS:`) format, and a revise of green as `revise-wrong-test` or `revise-wrong-test-contradicts`), `repair <case> <superseded>…` (a case the step's own Red wrote, per its red record or as `<red-test-id>`, with the older cases listed on `SUPERSEDED:` lines) or `supersede <case> <case>…` (two or more older cases named on `SUPERSEDED:` lines, which one `red-supersede` Red updates together), **exit 3** prints `revise`, **exit 2** bad arguments (a missing `--spec` included), or an unreadable ledger behind a `LATER_STEP:` line, or a bare case name (one with no `::`) that is defined in more than one test file or in none. The `red`, `repair` and `supersede` cases it prints carry the test file that defines them, as `<file>::<case>`. `missing <behaviour>` is answered on exit 0 until the step's `"kind": "missing"` `reroute` events in `.tdd/events.jsonl` (with `VERI_STEP`) reach `VERI_MISSING_REROUTE_BUDGET` (default 3); then `missing-exhausted <behaviour>` is printed on **exit 1**. The other four routes (`red`, `repair`, `supersede`, `fixture`) stay free only for the step's first reroute of any kind: a later reroute that would take one of them (a `WRONG_TEST:` or `SUPERSEDED:` report) answers `revise` (exit 3) and spends one `REVISE_BUDGET` attempt. A `fixture` route is taken only when the helper is defined in the step's own test file, the one before `::` in a `<file>::<case>` id; an id with no `::` (the Go and JS names) falls back to searching every test file. A `WRONG_TEST` naming no case (a `WRONG_TEST:` line whose body is not `none`, or a `WRONG_TEST` claim in prose that is neither negated nor quoted) answers `repair <the step's own case>` on exit 0 even once the step's free reroute is spent, once more after it; when the step's `reroute` events after its first already hold a `kind=repair` one it prints `repair-exhausted <case>` on **exit 1**, never `revise`. A `WRONG_TEST:` line whose body is `none`, and `WRONG_TEST` mentioned only negated or quoted, still answer `revise` (exit 3).
- `$S/pin-reject-route.sh [--missing-reroute] <reason-file> <ledger-file> <matcher> <target-test>` — **routes a verify-pin REJECT by script.**
  Under `--missing-reroute`, a reason saying `stays green` ticks nothing, prints `unpinnable-missing` on stdout (neither `retired` nor `revise`), writes one
  `unpinnable-missing` event carrying the matched step, and exits **2** (exit **3**, nothing written, when the matcher
  matches no open step); bad arguments still print nothing on stdout. It runs `tick-ledger.sh --unpinnable` in-process, passing `<target-test>` as its `--case`,
  only for the other reasons or without `--missing-reroute`; when that answers 1 and `--missing-reroute` was given, it runs
  `tick-ledger.sh --already-holds` with the same case. It prints `retired` and exits **0** when either retired the step (` ⟂ retired unpinnable`
  with one `unpinnable-step` event, or ` ⟂ retired already holds` with one `already-holds-step` event, never a `revise`
  event). It prints `revise` and exits **1**, ledger and events untouched, when the reason does not say `stays green` or the target test fails (and,
  under `--missing-reroute`, `--already-holds` also answered 1). **Exit 2** with a usage line on stderr for fewer than four
  arguments (the `<target-test>` included), or no answer; a `<target-test>` that never ran (see `tick-ledger.sh` below) is that answer, printing neither `retired` nor `revise`, ledger and events untouched. Any other tick-ledger code (3, no unchecked step matched) is passed through without printing `retired`.
- `$S/pin-fast-tier.sh '<fast-cmd>'` — run the fast tier over the tree a pin would commit,
  from the worktree. Takes the fast command as its one argument. On failure it writes the
  command's output to `.tdd/verify-pin.reason`. **Exit 0 = the command passed, 1 = it failed
  (output in the reason file), 2 = no command given.**
- `$S/mutation-probe.sh <file> <old> <new> -- <command…> | --before <sha> --keep <test-path> -- <command…>` — mutate `<file>` (`<old>` replaced by `<new>`), run `<command>` against the mutation, restore the file, and write the run's `.tdd/issue-<n>-mutations.md` record, which carries a `context` field: the full source line holding `<old>`. `VERI_MUTATION_ADDRESS_DOMAIN` (unset or empty: no check): when set, a `<old>` or `<new>` holding an email address whose host is not that domain makes the probe exit **2** before it mutates the file, runs the command or writes the record, stderr naming the address and the allowed domain. **Exit 2** also for bad arguments, or no answer.
- `$S/pin-recheck.sh <base-sha>` — re-run each recorded mutation whose file the range touches (a before record's file is its `keep` file):
  **exit 0** every such pin still goes red, printing any that need a look; **exit 1** a pin
  stayed green under its mutation (one that stays green under it on the range's base too is stale, not exit 1), a before-state pin this range disarmed (green at `HEAD`, red on the range's base), or a mutated run did not build, which prints
  `needs a look: <file> (mutation did not build)` on stdout; exit 1 also covers a mutated run
  that exits non-zero when the unmutated run printed nothing, printed as `needs a look`; a
  `needs a look` record from a failed run writes that run's stdout and stderr to stderr,
  limited to its last 40 lines. A `needs a look` line names its reason: `old text gone`, `old text occurs more than once` (the pin is not mutated), `old text moved off its recorded line` (the old text occurs once, on a line other than the record's `context`; the pin is not mutated), `base run failed`, or `mutation and control green`. A record without a `context` field gets the duplicate check only. Pins sharing one file and one reason print one line with a count, not one line each; these pins leave the exit code and the receipt as they were. **Exit 2** no answer, or a base (`git merge-base origin/main HEAD`) that cannot be resolved or replayed (no `origin/main`, the base worktree cannot be created; stderr names the cause), never read as stale or as a disarm, or a before-state pin with a green commit whose replay range names no file (stderr `empty replay range: before <sha> green <sha>`), or a pin's recorded command that cannot run (not found, or `make` with no makefile), which exits 2 naming the pin file and the command, as does a command `make` rejects as a usage error (make exits 2 printing `invalid option` or its usage), which writes no usage text to stderr; an ordinary red base run (the command runs and fails) is not that: it prints `needs a look`; or a pin's `TESTS=<path>` test file that is missing at `HEAD` yet was not deleted by the range (stderr `named test missing at HEAD: <path> (pin file <record>)`); **exit 3** no record touches the range, or every selected pin is retired.
  **Retired:** a pin, whatever its record type (a before record included, its mutated file being its `keep` file), whose every `TESTS=<path>` file the range deletes (`git diff --diff-filter=D <base-sha>..HEAD`) is neither replayed nor mutated; it prints `retired: <record file> <mutated file> <path>` on stdout, one line per deleted path, and counts toward exit 3 when no other pin is selected (receipt written); a live pin in the same range decides the exit (0 or 1). A pin naming several `TESTS=` files, only some deleted, drops the deleted arguments and runs on the rest. The `retired:` line is printed before any later exit 2 in the record loop, so a run that retires one pin and then fails on another prints both.
  **Superseded:** a pin whose test file survives the range, and which a ledger step committed in the range declares retired with `retire-pin: <record file> <mutated file> -- <reason>`, is neither replayed nor mutated; it prints `retired: <record file> <mutated file> <reason>` on stdout, appends a `retired:` line holding the reason to the pin's mutation record file, emits one `pin-retired` event (`reason=`), counts toward exit 3 as a deleted-file retire does, and is not replayed on a later run. A declaration with an empty reason, or naming no pin, exits 2. A pin not so declared is replayed as before.
  **Stale:** a before-state pin that replays green at `HEAD` is replayed again on the range's base, in a detached `git worktree` there that is removed afterwards, also on a failed replay. Red on the base: this range disarmed it, `pin stayed green on the before-state: <keep>` on stderr and exit 1. Green on both, or its `TESTS=<path>` file missing at `HEAD` and at the base without the range deleting it: stale, printed `stale: <record file> <test path>` on stdout (the file part of the `TESTS=` value), with no effect on the exit code; a mutation pin that stays green under its mutation at `HEAD` is replayed the same way: its mutation is applied in the base worktree and the recorded command run there, and green on the base too is stale, printed `stale: <record file> <mutated file>` on stdout, with no effect on the exit code, where red on the base is `pin stayed green under its mutation: <file>` on stderr and exit 1, as it is when the mutated file, or the recorded old text in it, is absent on the base; a range whose only selected pins are stale exits 0 and writes the receipt.
  A before-state pin replays the files changed from its `before` sha to the last commit of its
  issue's ledger (the step's tick), falling back to the record's `green` when the ledger has no
  commit; a before record with no green commit and an empty replay range runs its command instead of exiting 2; replaying a range never fails on a file absent at both of its ends (added after `before`, then deleted by the checked range): the replay skips it rather than exiting 2; `mutation-probe.sh --before` writes no `green` into an `.tdd/issue-<n>-mutations.md` record.
  It removes `.tdd/pin-recheck-ok` at start and writes it, holding `HEAD`'s sha, only on exit 0 or 3: that receipt is what
  `tick-ledger.sh` (a `⟦diff-checked⟧` step) and `clear-refactor-pending.sh` require.
- `$S/tick-ledger.sh [--refactor-pending | --phase <phase> | --phase-owed <phase> | --unpinnable <reason-file> | --already-holds <reason-file>] [--case <id>] .tdd/issue-<n>.md "<substring>"` — check a step off
  in the **committed ledger**, in place (staged + committed together with that step's green
  code). Ticking a `⟦diff-checked⟧` step also re-records, via `tests-frozen.sh rerecord-earlier`, the
  earlier frozen cases its diff changed; **exit 2** can then follow the write of the ledger (the re-record failed). **Exit 2** also refuses a step that names a go-red control (`mutation-probe.sh --before <sha>`, or `the go-red control is <file> at <sha>`) when `.tdd/issue-<n>-mutations.md` holds no `before <sha>` record for that sha and no `file`/`old`/`new` record for that file, naming the missing record and leaving the ledger unmodified; a step with neither wording, a bare mention of "go-red control" included, ticks as before. **Exit 2** also refuses to tick a `⟦diff-checked⟧` step, ledger byte-identical, naming `pin-recheck.sh`, when `.tdd/pin-recheck-ok` is absent, its sha does not resolve, or a path outside `.tdd/` differs between that sha and `HEAD`. **Exit 3** if no unchecked step matched the substring — the file is left untouched,
  so a green commit that ticked nothing says so instead of reading as done.
  Ticking an `⟦added⟧` step also ticks the first still-open line of equal step text (cut at ` ⟂ `) in `.tdd/issue-<n>-added.md`, skipped when that file is missing.
  `--refactor-pending` appends ` ⟂ refactor pending` to that same line in the same write, so
  the green commit records the step as **green but not yet tidied**; that is the flag the
  green PASS ticks with, and the one the pin path must tick without — a pinned step runs no
  refactor loop, so a mark left there would never be cleared. A `⟦replaces-case⟧` step's
  deletion green after a pin PASS is a Green: it ticks with the flag and runs Refactor.
  `--phase <phase>` instead appends ` ⟂ <phase> done` to the first open step listing
  `⟦phases: …⟧` that matches, and leaves its checkbox `[ ]`; once every listed phase is marked
  the step reads as `done` to `ledger-steps.sh` and `next-unchecked.sh` skips it. **Exit 2**,
  ledger byte-identical, for a phase the step does not list or one that is not its next unmarked
  phase; also for a step listing `⟦phases: …⟧` ticked without `--phase`, and for `--phase` given
  with `--refactor-pending`. `--phase-owed <phase>` appends ` ⟂ <phase> owed` instead, under the
  same refusals; an owed phase ends the step, so it and every phase after it are never handed out
  again (see the exhausted-contract paragraph in `<base directory>/PHASED.md`). `--unpinnable <reason-file>` retires the matched step instead of ticking it as green: when the reason file (a verify-pin REJECT, `.tdd/verify-pin.reason`) says the mutation `stays green`, it ticks the step `[x]` with ` ⟂ retired unpinnable` appended, in the same write, and appends one `unpinnable-step` event (`step=`, `reason=` from its `REASON:` line) to `.tdd/events.jsonl`, never a `revise` event, and only when the case named by `--case <id>` passes (run through the repo's one-test-file command (the `veri: one test file:` line of `CLAUDE.md`, as `detect-test-command.sh --tier "one test file"` prints it) given the case id's file path, the part before `::`, or as `make test TESTS="<id>"` when the repo declares none).   tracked. Writes the rule to **both** the worktree's `.gitignore` (committed, so the first
  `git add -A` never sweeps leaf logs into history) and the shared
  `$(git rev-parse --git-common-dir)/info/exclude` (never committed, read by every worktree,
  so the caller's checkout — still on the default branch — stops reporting `.tdd/` as
  untracked). Idempotent in both files; the word on stdout reports the `.gitignore` only,
  `added` when it wrote the rule there, `already present` when it was there — the exclude
  file is ensured either way. Run once per issue right after entering the worktree (step 1).
- `$S/issue-worktree.sh <n> <slug> | --remove <n>` — the **linked worktree the issue branch lives in**.
  Creates (or hands back) `<repo-root>/.tdd/wt/<n>` on branch `tdd/<n>-<slug>`, cut from
  **`origin/<default>` as just fetched** — never from the caller's `HEAD`, and never from the
  **local** branch of that name: that one **lags the remote by design**, since a run executes the skill pinned from
  `origin/<default>` and nothing obliges anyone to pull the primary clone, so a branch cut
  from it starts **stale** and its PR then owes a rebase over everything that landed meanwhile.
  The fetch moves no local branch and touches no working tree. `<default>`'s **name** is read
  from `refs/remotes/origin/HEAD`; when that ref is absent (an origin does not guarantee one) it
  is resolved from the remote itself with `git ls-remote --symref origin HEAD`, and when the
  remote names none either it exits 2 naming `refs/remotes/origin/HEAD` — never a guessed
  `main`. A local `main`/`master` is the fallback only when there is **no origin remote** at all:
  then it supplies both the name and the **base** itself, as before. Prints the worktree's **absolute path on stdout** — the only
  thing on stdout; git's chatter goes to stderr, so the path is safe to capture.
  **Idempotent**: a second call for the same issue prints the same path and creates nothing,
  which is what makes a resume land in the worktree the first run made — a **local** issue
  branch is checked out as it is, with no fetch. Only a **local** branch or a **registered
  worktree** makes a run a resume. A branch **only origin** holds is refused (exit 2) unless
  the run is a resume, even when this clone has fetched it (a remote-tracking ref is not a
  resume) — with one exception, the **own lane**: when the issue carries this lane's `taken:<lane>`
  label (the text after the last `:` of `VERI_LABEL`, `main` without one), the run is a resume and the
  worktree is recreated from origin's branch tip, ledger included; another lane's claim is still
  refused. A refused one creates no branch and no worktree, and names the takeover — `git branch
  tdd/<n>-<slug> origin/tdd/<n>-<slug>` — after which the next run is a resume. A **stale**
  remote-tracking ref, whose branch origin no longer holds, is not a claim: the run cuts fresh
  from `origin/<default>`, as above. **Exit 0** = the path. **Exit 2** = no answer
  could be obtained — either the branch is **already checked out in another worktree** (it names
  that path and touches nothing: **never steal a checkout**, another conductor owns that run),
  or the default branch cannot be named, or fetching it failed — never a silent fallback to the
  stale local ref. And exit 2 when the worktree it would have handed back **holds a live
  conductor**: the pid in `.tdd/conductor.pid` there still answers `kill -0` **and** that
  process's start time matches the one recorded on the lock's second line, so it
  names that pid instead of printing the path (#170) — a second conductor `cd`'ing into a live
  run's worktree reads that run's ledger as its own and `RESUME.md` throws the live leaf's
  uncommitted work away. A lock whose pid is **dead**, or answers but with a start time other than the
  recorded one (a **reused** pid), is a bailed or killed run, still a resume, still the path.
  `$S/issue-worktree.sh --remove <n>` removes the worktree once the PR has landed, and
  **refuses** (exit 2) one holding uncommitted changes.

- `$S/solvable-issues.sh [--repo <owner/name>] [--not-running]` — the **selection layer**: prints the
  numbers of the issues veri may take right now — open, labelled `ready-for-agent`, every
  issue under their `## Blocked by` heading closed, and not already claimed by an open PR
  saying `Closes #<n>` (a still-draft PR on the issue's own run branch, `tdd/<n>-…`, claims nothing: a
  released issue's resume continues it, ADR-0036; the same PR once readied, not a draft, claims it again, since the run is Done) — one per line, in four bands: the `bug`s labelled `priority` first,
  then the other issues labelled `priority`, then the `bug`s, then the rest, each band ascending by number. A bug labelled `low-risk` counts
  as the rest, and `priority` outranks `low-risk`. An issue also **inherits** the band of every
  open issue that names it under `## Blocked by`, transitively, and takes the better of its own
  band and the inherited one: blocking a `priority` bug puts it in the first band, blocking
  another `priority` issue in the second; blocking a plain `bug` lifts nothing. Each printed
  issue whose band was inherited gets one stderr line
  `#<blocker> inherits <band> from #<dependent>`. The band only reorders that
  set, it never enlarges it — the four conditions run first, so a `priority` issue, or a
  blocker of one, that is blocked, claimed or not opted in is still not printed. `VERI_PRIORITY_LABEL` names the
  `priority` label (default `priority`; set-but-empty is **exit 2**, like `VERI_LABEL`),
  and `bug` is GitHub's own. **Exit 0** when it printed at least one,
  **exit 3** with empty stdout when none is takeable (nothing to do, not an error).
  `VERI_GH_JSON=<dir>` reads `issues.json` / `prs.json` fixtures instead of shelling out to
  `gh`, which is what makes it testable with no network. `VERI_GH_DRIVER` picks the route
  every GitHub read and write takes, through `veri/github.py`:
  `rest` (the default when unset) runs only `gh api`, `graphql` runs only the `gh issue` /
  `gh pr` command with no fallback, and `auto` tries GraphQL then REST. Set but empty, or any
  other value, is **exit 2**, with a stderr line naming `VERI_GH_DRIVER` and the value, checked
  at call time. Operations with no GraphQL route — issue edit and create, `gh_rest_list`,
  `gh_json` with no gh args — use REST under every value, and `VERI_GH_JSON` takes precedence
  over it. A Claude Code cloud session, where GraphQL is refused, needs nothing set: the
  default is already `rest`. The conductor does not call this —
  it is rung 2's, driven by the loop branch of this skill.
- `$S/wait-ci.sh <pr-url> [slice-seconds] [total-seconds] [head-sha]` — **wait one bounded slice
  for a PR's checks**, then be called again: *4. Draft PR*'s CI wait. Reads the check runs and
  commit statuses of the PR's head; given `<head-sha>`, a PR still reporting another head reads
  as pending; a `<head-sha>` that is not a full 40-hex sha exits 2 with one stderr line. `<slice-seconds>` (default and cap 540) bounds this call; `<total-seconds>` (cap
  600) bounds the whole wait, and when it is not given it is twice the mean of the last 5
  completed CI runs, capped at 600; 540 when fewer than 5 exist or `gh` cannot answer; the
  slice length when reading them fails otherwise. The deadline does not run only while every
  pending check is `queued` (none `in_progress`), or the PR reports another head: it is
  recorded in `.tdd/ci-deadline-<sha>`, which later calls inherit, by the first call where that
  is not so — a check in progress, no check yet, or only a commit status pending. The first
  queued sighting is recorded in `.tdd/ci-queued-<sha>`. A draft PR records no deadline. **Exit 0** every check completed
  `SUCCESS`, `NEUTRAL` or `SKIPPED`, not all `SKIPPED`. **Exit 1** a completed check concluded
  anything else, or a commit status is `failure`/`error`; the failed check names go on stdout,
  comma-separated. **Exit 2** no answer: bad arguments, a read of the checks that fails and is still failing when the deadline passes (retried with backoff until it; a 4xx other than 403 or 429 exits 2 at once), a
  PR with no checks (or only skipped ones) that conflicts with its base branch (stderr says
  `conflicts with its base branch`), a check still pending past the recorded deadline, an
  unreadable deadline file, or checks that never started — still queued more than
  `VERI_CI_QUEUE_WAIT` seconds after the first call that saw them queued, or a ready,
  mergeable PR whose head has stayed none (no check run, no commit status) for
  `VERI_CI_NO_RUN_WAIT` seconds while a `pull_request` workflow exists (stderr names
  `no CI run for <sha>`, the full 40-hex head). That no-run grace is long enough (default
  600 s) for a slow-to-start CI run to appear, so a finished run is not bailed for a late
  one, and a head still without a run after it exits 2 rather than waiting out the whole CI
  budget. That grace is counted across calls: the first
  call that saw a ready, mergeable PR's head with no check run and no commit status records
  the sighting in `.tdd/ci-none-<sha>`, and later calls for the same sha inherit it, so a
  `VERI_CI_NO_RUN_WAIT` above one slice still exits 2 naming `no CI run for <sha>`; a new head
  starts a new grace, and a sighting of a run clears it. **Exit 3** still
  pending, no check yet, every one `SKIPPED`, or a mismatched head, when the slice runs out.
  With `VERI_CI_ON_PR=0`, a PR whose head has no check runs and no commit statuses exits 0, since
  there is nothing to wait for; checks that do exist are still waited on and read as above. A
  `VERI_CI_ON_PR` other than `0`, `1` or empty is an **exit 2**.
  With `VERI_CI_ON_PR` unset, a PR with no checks in a tree where nothing under
  `.github/workflows/` triggers on `pull_request` or `pull_request_target` exits 0 with a
  warning, since no check will ever come; an explicit `VERI_CI_ON_PR` (`0` or `1`) wins over
  this detection, so `VERI_CI_ON_PR=1` keeps the wait.
  An unreadable read (HTTP 5xx, 403, 429, or no HTTP status) is retried, not counted out: the
  first one records the deadline like a pending read does (not on a draft), and each consecutive
  one sleeps twice the last, from `VERI_POLL`, at most 60 s per sleep; a good read starts the
  sequence over. `VERI_CI_RETRY_BACKOFF=0` keeps every retry sleep at `VERI_POLL`; a value other
  than `0`, `1` or empty is an **exit 2**.
  Tunables: `VERI_POLL` poll interval (default 10 s), `VERI_CI_RETRY_BACKOFF` (`1`, the default,
  doubles the retry sleep; `0` keeps it flat), `VERI_CI_QUEUE_WAIT` (default 3600 s),
  `VERI_CI_NO_RUN_WAIT` (default 600 s, a non-negative whole number; anything else is an
  **exit 2** naming it), `VERI_CI_ON_PR` (unset means checks are expected, unless the detection above finds no
  `pull_request` workflow).

Preflight calls it on every refusal.

Exit **0** written; **2** bad arguments, or the current body could not be read (nothing written) or the write failed. The conductor calls it for every PR-body write.

A `/bin/sh` shim over `veri/restore_production.py`, run inside a worktree: it restores every tracked path except the named test paths to `HEAD` (`git checkout HEAD`) and removes every untracked, unignored file except the named test paths (`git clean`), so the tree holds no production change beyond `HEAD` while the named test paths are left exactly as they were. Exit **0** restored, **2** no argument (usage line on stderr) or git refused. The revise loop calls it before relaunching a red leaf.
- `$S/update-veri.sh [--consent yes|no]` — fast-forward veri's own clone to its upstream default branch, and only when the clone is on that branch with a clean tree. **Exit 0** = moved, **3** = already current, **1** = not allowed (the record or `VERI_SELF_UPDATE=0` says no, or the clone is off the default branch or dirty) or not a fast-forward, **2** = no answer. It honours the consent record at `~/.veri-tools/self-update` (`VERI_SELF_UPDATE_FILE` names another path), which `--consent yes|no` writes, and `VERI_SELF_UPDATE=0` turns it off. `run-conductor.sh` calls it before pinning a fresh run, never on a resume.

Without `--record` it reads: **exit 0** prints the recorded seconds, **exit 3** that command has no record, **exit 2** an unreadable record or bad arguments.
- `$S/baseline-full-tier.sh <issue> <full-tier-command>` — settle the preflight full-tier decision. It prints `reuse <seconds>` when the run's mode is `reuse` and `full-tier-time.sh` holds a recorded time for `<full-tier-command>`, and `run` otherwise (mode `run`, or `reuse` with no record for that command); exit 0 both ways. The mode is the run's pinned value in `.tdd/issue-<issue>-baseline-full-tier` beside the full-tier-time record (the main checkout's `.tdd/`) when that file exists, else `VERI_BASELINE_FULL_TIER` (default `run`), so a resumed run keeps the launch's choice. **Exit 0** printed; **exit 2** fewer than two arguments (usage on stderr). - `$S/ready-check.sh [repo-root]` — report whether a project has what veri needs to run (`make ready-check` calls it). It reads the repo at `repo-root` (default: the main working tree, from a linked worktree too) and prints one `ok    <row>` or `fail  <row>: <fix>` line per check, in order: the fast and full test tiers (`$S/detect-test-command.sh --tier`), a workflow triggering on `pull_request` (or `VERI_CI_ON_PR` set) and one triggering on `push`, both read at the default branch's tip (`origin/HEAD`, else `main`), a tracked test file, `.tdd/` git-ignored, `gh auth status`, push access (`gh api repos/{owner}/{repo}`), the `VERI_LABEL` label (`gh label list`), bash 5+ and the Python floor. A `gh` call that fails or prints unusable output fails its row; it never crashes. It only reads: no write to the tree, index, refs or GitHub. The last line is `ready` or `not ready — <n> rows to fix`. **Exit 0** = every row holds (`ready`). **Exit 1** = at least one row fails: a clean negative, the report is the answer. **Exit 2** = no answer: more than one argument, an option, `repo-root` not a git repository, or `$S/detect-test-command.sh` exiting 2 for a tier, which shows as that tier's row failing with "no answer was obtained".
- `$S/status.sh [--json] [--scope <name>] [--watch [seconds]] | --report` — render every run under the main working tree. `--report` (alone) prints the `/vstatus` report from local files only, with no `gh` call: the sections Landed, Running, Queue and Waiting, the queue read from the cached snapshot `.tdd/report-cache.json`. When that snapshot is stale (older than `VERI_SNAPSHOT_MAX_AGE` seconds, default 60) and no refresh is running, it starts `report-cache.sh refresh` detached (its own session, no stdin, stdout or stderr), so a caller capturing the report never waits for it. **Exit 0** printed, **2** an unknown option (a usage line on stderr), **3** no runs (without `--report`).

- `$S/report.sh --report` — print the PRD report from local files only (`.tdd/report-cache.json` and `.tdd/report-owed.json` in the working tree; no `gh` call, no model): first a `snapshot age: <n> hours` line, then one block per active PRD in ascending PRD number, a PRD being the lowest-numbered issue titled `PRD <nnn>`. Each block is a `PRD <nnn> (#<issue>) — <title>` line, then `solved:` (closed children, and how many closed in the last 7 days), `left:` (solvable now, waiting on which open blockers, held by no lane), `owed:` (the stored answer, or `stale` when the PRD issue changed since it was stored) and `ETA:` (a range in days from the 7-day closing rate of the lanes holding the PRD's open children, or `no rate yet` below 3 closed issues, or `no lane`). **Exit 0** printed; **exit 2** with its usage line on stderr for no argument or an unknown one, and naming `.tdd/report-cache.json` when that snapshot is missing. - `$S/report-cache.sh refresh` — rebuild the snapshot `report.sh` and `/vstatus` read, `.tdd/report-cache.json` in the main clone's tree (the one a worktree's `.git` file points to): it lists every issue, open and closed, with `gh issue list`, and reads the comments of PRD-titled issues and of issues closed in the last 7 days. A snapshot with `cache_format` 2 and a `fetched_at` is refreshed incrementally, fetching only issues updated since it; a missing, unreadable (it says so on stderr) or older-format one is rebuilt whole. The file is replaced atomically, so a reader never sees a half-written snapshot. **Exit 0** a snapshot written; **exit 2**, naming `gh issue list`, when `gh` gave no answer; **exit 2** printing `usage: report-cache.sh refresh` for no subcommand or an unknown one.
- `$S/dispatch.sh --target <N> | --help` (`<N>` a whole number >= 0) — the operator's dispatcher: it launches the next solvable issue into a free slot once the previous launch's ledger exists, appending `launched <n> <time>` to `.tdd/dispatch.log`, and it waits for queued merges. It prints one of `done <n> <pr-url>`, `bail <n>`, `silent-exit <n>`, `merge-failed <pr-url>`, `stalled <n>` (`VERI_DISPATCH_STALL`, default 3600 s) or `queue-empty`. `--target 0` holds dispatch: it keeps watching and reporting exits (`done`, `bail`, `silent-exit`, `merge-failed`, `stalled`) and launches nothing, never printing `queue-empty` merely because it launches nothing; re-arming dispatch with a positive `--target` resumes launching. **Exit 0**, except **3** for `queue-empty`; **exit 2** for a usage error, an unreadable queue or a vanished run. For each run it launches it starts `restart-conductor.sh` beside `run-conductor.sh`, and none for a failed launch. A run whose conductor is gone while its worktree holds a `.tdd/restart-pending` marker is a planned restart, not an exit: dispatch defers it while the marker's restarter lives (an empty or unreadable marker counts as living), keeps it under watch every pass, and while the restarter lives the run holds its slot and is counted once, even beside a live run, so dispatch launches only while fewer than `<N>` runs hold a slot; a run whose `.tdd/wt/<n>/.tdd/conductor.pid` names a pid that answers `kill -0`, with the start time recorded on that file's second line matching (or none recorded), counts as a live conductor and holds a slot whatever its ledger or journal state, hand-launched runs included (the live-conductor reading `watch-runs.sh` shares); it reports `done`, `bail` or `silent-exit` (per the issue's last comment) once no conductor is live and the restarter is dead, except that `silent-exit <n>` is held until the run has been absent from the live conductors for 30 continuous seconds by dispatch's own clock (a fixed 30 s, no environment variable); a run that comes back live and is absent again gets a fresh 30 s window, and `done` and `bail` print at once; and a marker that never clears ends as `stalled <n>` after `VERI_DISPATCH_STALL`. It skips a solvable issue whose body names a path that an open run draft PR (a draft on a `tdd/` branch) changes, on any machine, and launches the next one with no such overlap; it prints one line per skip naming the issue, the path and the PR, once per issue, path and PR for the life of the process, and never reports `queue-empty` while skipped issues remain. While every solvable issue overlaps, it re-reads the open-PR list at most once per `VERI_DISPATCH_OVERLAP_POLL` seconds (default 60; a non-integer is a usage error, **exit 2**). A failed overlap read (PR list, PR diff or issue body) exits 2 naming the failure, and a rate-limited one waits for the reset. A rate-limited queue read waits for the reset. `--help` prints the usage on stdout and exits 0.
