## skills/tdd/SKILL.md

| ID | Requirement | Why |
|---|---|---|
| PF1 | Preflight runs `leaf-launchable.sh` before the baseline suite. An exit 2 from it stops the run, and its stderr diagnostic is reported verbatim. veri never unsets `CLAUDECODE` or any other launch guard itself. | A suite, worktree, spec and public `Resuming` comment are wasted if no leaf can launch (#187). |
| PF2 | A failing `gh api user` (the REST route) or a `claude auth status` that is not `"loggedIn": true` is a preflight failure: report it and stop. | An expired session makes every `claude -p` leaf fail at launch, which has no bail classification. |
| PF3 | The fast-tier baseline runs inside the issue's worktree, after `issue-worktree.sh` has cut the branch and the conductor has entered it. The caller's checkout is never what is proven. | The baseline must prove the commit the cycles build on. |
| PF4 | A red baseline stops the run as a preflight failure, whatever state the caller's checkout is in. The baseline runs in preflight, before the plan section. | A cycle must not start on a red baseline. |
| PF5 | The conductor writes `"$PPID"` to the worktree's `.tdd/conductor.pid` after entering the worktree and before the baseline starts. The lock is taken in preflight step 3, never in step 1.2. | The worktree guard has to cover the window before the baseline (#170). |
| PF6 | The run's test command comes from `detect-test-command.sh --tier fast --issue "$body"`. The issue body is read into a temp file before the baseline, so the baseline and every later leaf use one command. The baseline item runs and times that command. | Detecting after the baseline would be too late to pin the issue's own test line. |
| PF7 | The baseline is timed once, as `baseline`: elapsed wall time in whole seconds, rounded up, taken once so a suite that slows mid-run does not move the timeout. Then the full tier is timed once, as `full` (whole seconds, rounded up), run once through `detach-command.sh` like the baseline, with the same single-measurement rule; step 7 sizes the timeout from `full`, not `baseline`, because the full tier is the work a leaf actually does. A red full tier stops the run. | Leaves run the full tier, so a timeout sized from the fast tier bounds work nobody does (#300). |
| PF8 | `leaf-timeout.sh "$baseline" --full "$full"` is called only after the full-tier measurement. `--full` sizes the timeout from the full-tier number, which displaces the fast one. | See PF7. |
| PF9 | The settled timeout is recorded in `.tdd/issue-<n>-timeout`, and `supervise.sh` reads it when `VERI_TIMEOUT` is unset. The prose never claims an export in the conductor's own shell is in force for later launches. A leaf-timeout exit 2 stops the run with its diagnostic reported verbatim. | Every Bash call is a fresh shell, so an export does not survive. Prose that said otherwise was fixed in #954. |
| PF10 | `VERI_STEP_GROWTH` must be unset or a whole number ≥ 0. Set-but-empty or any other value is an exit-2 preflight stop, reporting the value verbatim. | A bad value caught here costs nothing. Caught later it surfaces mid-cycle as a refused plan insertion. |
| PF11 | Preflight runs `step-budget.sh` with no arguments, beside `refactor-budget.sh 0`. An exit 2 from it is a preflight stop, reporting its stderr diagnostic verbatim. | A budget that cannot be read is a poisoned baseline. |
| PF12 | Preflight calls `leaf-model.sh` with a developer name, a revise name and a verifier name, once each. An exit 2 stops the run with the diagnostic reported. | Each of `VERI_MODEL_DEVELOPER`, `VERI_MODEL_REVISE` and `VERI_MODEL_VERIFIER` is read only for its own name, so skipping a name lets its bad value through. |
| PF13 | An empty or whitespace-only model variable counts as unset and never stops the run. Any other value containing whitespace — internal, or a leading or trailing space (`sonnet 5`, `" sonnet"`, `"sonnet "`) — is exit 2: a preflight stop reporting the diagnostic verbatim. | A weaker rule would stop runs on blank variables (#1485); a value with whitespace cannot be a model name. |
| PF14 | A resumed run (worktree and ledger already exist) runs `rebase-onto-default.sh` before its baseline, and a new branch's run does not rebase there. | The baseline must run on the rebased tip (#1297). |
| PF15 | Exit 3 of the resume rebase goes on unchanged. Exit 1 goes on from the old base and leaves the conflict to the Draft PR step. Exit 2 bails as a system failure (`no-verdict`). | The three exits are different outcomes and must not be collapsed. |
| PF16 | `<pre-rebase-sha>` is introduced as the first stdout line of `rebase-onto-default.sh`, before it is first used. | The lease push and the reset both depend on it. |
| PF17 | A resume rebase that moved the branch is marked in the run log as its own event (`resume-rebase`, carrying `from=<pre-rebase-sha>` and `rebased=<HEAD>`). Its name is not one the Draft PR step's rebase writes. | The two rebases must be told apart in the log. |
| PF18 | Before the resume rebase, the dirty-tree discard captures `git status --porcelain` into `$stray`, then runs `git reset --hard HEAD`. `$stray` is kept for the `RESUME.md` sub-step 4 comment. | A rebase refuses a dirty tree, and the resuming comment must name what was discarded. |
| PF19 | A resume rebase that moved the branch is published only after the baseline is green, with `push-branch.sh --force-with-lease=<branch>:<pre-rebase-sha>`. The negation attaches to the bare force: a bare force is never used. | A pinned lease refuses the push when the remote has moved since the run rebased from it. |
| PF20 | A red baseline on the rebased tip resets the branch to `<pre-rebase-sha>` before the run bails. | A bailed resume must leave the branch on the commit it resumed from, not on a tip no suite proved green. |
| PF21 | If any preflight check fails, the baseline is poisoned: the run reports which check failed and stops. This is a degenerate bail — no commits, nothing to revert or push — and a red, dirty or unauthenticated baseline never gets a cycle. | Preflight exists so no leaf is spent on a run that cannot succeed. |
| PF22 | Check 1: `git rev-parse --is-inside-work-tree` succeeds and `git status --porcelain` is empty in the caller's checkout; if it is dirty, stop and ask the user to commit or stash. The check stays although the run works in a worktree. | The conductor still reads the issue and the default branch from the caller's checkout, and a dirty one means something else is mid-work in it. |
| PF23 | Check 4: the default branch is captured for the PR base with `gh api repos/{owner}/{repo} -q .default_branch`. | The PR must target the repository's real default branch, not an assumed `main`. |
| PF24 | `refactor-budget.sh 0` runs once: exit 2 (`VERI_REFACTOR_BUDGET` not a whole number ≥ 0) stops the run, reporting its stderr verbatim; exit 0 and exit 3 both mean it parses (3 only says the budget is 0, the refactor loop switched off). | Catching it here is what lets the refactor loop treat exit 2 as impossible. |
| PF25 | `refactor-budget.sh --issue 0` runs once and checks `VERI_ISSUE_REFACTOR_BUDGET`, the structural pass's budget, the same way: exit 2 is the same stop; exit 0 and 3 both mean it parses. | The structural pass's budget gets the same early check. |
| PF26 | `step-budget.sh`'s exit 2 means `VERI_STEP_BUDGET` or `VERI_RUN_BUDGET` is not a non-negative decimal number: a preflight stop before any leaf is launched. Exit 0 prints the step budget, then the run budget, one per line. | Spells out which two money budgets PF11's call checks, and what a pass prints. |
| PF27 | The `stop-requested.sh --clear` beside the lock write drops a stale stop request a killed run never got to clear, so a `.tdd/stop` left behind cannot stop the run that resumes it at its first checkpoint. | Otherwise a resume stops itself at its first checkpoint. |
| PF28 | The resumed run, its uncommitted `.tdd/` appends kept and its ledger ticks reconciled, runs `$S/rebase-onto-default.sh` before its baseline, so the baseline runs on the rebased tip. | The resume must test a tip current with the default branch. |
| PF29 | The working ledger is judged against the committed ledger by step text, counted: a working-copy `- [x]` line stays ticked only when the committed ledger holds a tick of the same step text (without its trailing markers), so n committed ticks of a text keep at most n working ticks of it; every other `- [x]` line is unticked and loses its `⟂ refactor pending` mark, and every other working-copy line is kept as written. | The committed ledger is the source of truth for done steps; a tick whose green commit is not on the branch would skip work on resume. |
| PF30 | `leaf-launchable.sh`'s exit 2 is described as the case `README.md`'s *Launching the conductor* describes (#187), naming that README section rather than a section above. | *Launching the conductor* moved from SKILL.md to README.md (#1785); the pointer must follow it. |
| CY1 | `$S/step-cost.sh '<STEP>'` follows every leaf before the green commit: develop-red, each verify-red, each revise attempt of red or green, develop-green, each verify-green. None follows a leaf after it, because the refactor leaf already has its own numeric budget (ADR-0017). | Without the check a budget is never weighed; after the green commit the step is ticked, so a check there could change nothing. |
| CY2 | The check runs only once the leaf has exited and `supervise.sh` has harvested its `usage` event. | Reading earlier gives a figure short of the real spend. |
| CY3 | `step-cost.sh` exit 3 (no leaf of the step has reported usage yet) is not a crossing: the step goes on and the next leaf is checked as usual. | Nothing has been spent, so there is nothing to weigh. |
| CY4 | The check fires at most once per step: after the crossing branch has run, later leaves are not checked and nothing re-arms it. | A step that costs 3x its budget is asked about once, not at every leaf. |
| CY5 | A crossing is not a failure, because the budget weighs cost and not whether the work is right; this is stated once, and no exit code changes meaning (1 stays process failure, 2 system failure, 3 nothing to do). | Without it a crossing could be read as a bail. |
| CY6 | On a crossing, `event.sh step-over-budget spent=<s> budget=<b>` is written once, before the `over-budget` leaf launches, on every crossing, before the split, park or carry-on branch. | A mark written only after the answer would record nothing for a crossing whose leaf never came back. |
| CY7 | The `over-budget` prompt is built with `build-develop-prompt.sh over-budget`, the leaf is launched via `detach-leaf.sh $S/supervise.sh develop-over-budget` and waited on in the foreground, and its answer is read with `exhausted-outcome.sh < .tdd/develop-over-budget.out`, never by eye. | Which outcome the leaf holds is an exit code (0 split, 1 decision for the user, 3 neither), not a per-run judgement. |
| CY8 | Exit 0 (split): run `git reset --hard HEAD` and `git clean -f -- <test-path>`, then one `add-ledger-step.sh instead-of` call with no `--criterion` (the split keeps its anchor's criterion), and commit the plan before the run goes on. | Otherwise the uncommitted work becomes the first replacement step's start, and a resumed run reads only the committed ledger. |
| CY9 | The exit-0 branch writes `step-added` and `step-split at=over-budget`; the `at=` value tells this split apart from a leaf-volunteered one (no `at=`) and from the revise-exhausted one (`at=exhausted`). | The run log shows which of the three causes grew the plan. |
| CY10 | `add-ledger-step.sh` exit 1 on the split bails with cause `step-too-big`, exit 2 with cause `step-add-refused`; the split shares `VERI_STEP_GROWTH` with the other two plan-growth causes. | Every cause of plan growth draws on one cap. |
| CY11 | Exit 1 (a decision for the user): park the step, stopping the run there carrying the leaf's answer and the two figures, leaving the plan as it is, and write `step-escalated at=over-budget`. | Parking ends the run without a bail; `at=` tells it apart from a verifier-driven park. |
| CY12 | Exit 3: carry on with the step. This is not a bail, unlike the revise-exhausted exit 3, because nothing has failed, and the branch writes no mark of its own; the earlier `step-over-budget` records the crossing. | A converging step is not bailed for being expensive. |
| CY13 | A supervisor exit 2 on the `over-budget` leaf (`wait-leaf.sh` exits 2) is a `killed-stuck` bail, and the step's budget stays crossed. | Exit 2 means no answer could be obtained from the leaf. |
| CY63 | The `over-budget` prompt is built with `<spent> <step-budget>`, so the leaf is told both figures. | The leaf decides with the numbers in front of it. |
| CY64 | After the split commit the run loops back to `next-unchecked.sh`, which now hands over the first replacement step. | The run continues on the smaller steps. |
| CY65 | On the split, `step-added` and `step-split at=over-budget` are written before `add-ledger-step.sh`, because the marks read the step's title from the ledger. | The insertion rewrites the ledger the marks read. |
| CY66 | The step's cost is also checked after the `develop-replaces-report` correction leaf. | That leaf's spend counts toward the step too. |
| CY14 | The `red` template instructs the leaf to write **exactly one** failing test pinning the criterion to observable external behavior, with **no production code**, and to run the suite holding that case, not the full suite, against the unmodified code. The only question Red asks is whether that one case fails. | Running the full suite in Red would answer a question Red does not ask, and cost the whole run's time for it. |
| CY15 | The template's definition of a valid test is behavior, not mechanism: no process, fork or call count and no timing across a suite run (those are `make profile`'s job). The one exception is a call count the criterion itself names, pinned with an in-process spy on the one wrapper called, never a `PATH` shim counting real processes. | A count or timing assertion pins how the code is built, not what it does, and breaks on a faithful refactor. |
