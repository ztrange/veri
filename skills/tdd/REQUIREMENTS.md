## skills/tdd/SKILL.md

| ID | Requirement | Why |
|---|---|---|
| CY1 | `$S/step-cost.sh '<STEP>'` follows every leaf before the green commit: develop-red, each verify-red, each revise attempt of red or green, develop-green, each verify-green. None follows a leaf after it, because the refactor leaf already has its own numeric budget (ADR-0017). | Without the check a budget is never weighed; after the green commit the step is ticked, so a check there could change nothing. |
| CY2 | The check runs only once the leaf has exited and `supervise.sh` has harvested its `usage` event. | Reading earlier gives a figure short of the real spend. |
| CY3 | `step-cost.sh` exit 3 (no leaf of the step has reported usage yet) is not a crossing: the step goes on and the next leaf is checked as usual. | Nothing has been spent, so there is nothing to weigh. |
| CY4 | The check fires at most once per step: after the crossing branch has run, later leaves are not checked and nothing re-arms it. | A step that costs 3x its budget is asked about once, not at every leaf. |
| CY5 | A crossing is not a failure, because the budget weighs cost and not whether the work is right; this is stated once, and no exit code changes meaning (1 stays process failure, 2 system failure, 3 nothing to do). | Without it a crossing could be read as a bail. |
| CY6 | On a crossing, `event.sh step-over-budget spent=<s> budget=<b>` is written once, before the `over-budget` leaf launches, on every crossing, before the split, park or carry-on branch. | A mark written only after the answer would record nothing for a crossing whose leaf never came back. |
| CY7 | The `over-budget` prompt is built with `build-develop-prompt.sh over-budget`, the leaf is launched via `detach-leaf.sh $S/supervise.sh develop-over-budget` and waited on in the foreground, and its answer is read with `exhausted-outcome.sh < .tdd/develop-over-budget.out`, never by eye. | Which outcome the leaf holds is an exit code (0 split, 1 decision for the user, 3 neither), not a per-run judgement. |
| CY8 | Exit 0 (split): run `git reset --hard HEAD` and `git clean -f -- <test-path>`, then one `add-ledger-step.sh instead-of` call with no `--criterion` (the split keeps its anchor's criterion), and commit the plan before the run goes on. | Otherwise the uncommitted work becomes the first replacement step's start, and a resumed run reads only the committed ledger. |
| CY9 | The exit-0 branch writes `step-added` and `step-split at=over-budget`; the `at=` value tells this split apart from a leaf-volunteered one (no `at=`) and from the revise-exhausted one (`at=exhausted`). | The run log shows which of the three causes grew the plan. |
| CY10 | `add-ledger-step.sh` exit 1 on the split bails with cause `step-too-big`, exit 2 with cause `step-add-refused`; the split shares `VERI_STEP_GROWTH` with the other two plan-growth causes. | Every cause of plan growth draws on one cap. |
| CY11 | Exit 1 (a decision for the user): park the step, stopping the run there carrying the leaf's answer and the two figures, leaving the plan as it is, and write `step-escalated at=over-budget`. | Parking ends the run without a bail; `at=` tells it apart from a verifier-driven park. |
| CY12 | Exit 3: carry on with the step. This is not a bail, unlike the revise-exhausted exit 3, because nothing has failed, and the branch writes no mark of its own; the earlier `step-over-budget` records the crossing. | A converging step is not bailed for being expensive. |
| CY13 | A supervisor exit 2 on the `over-budget` leaf (`wait-leaf.sh` exits 2) is a `killed-stuck` bail, and the step's budget stays crossed. | Exit 2 means no answer could be obtained from the leaf. |
| CY63 | The `over-budget` prompt is built with `<spent> <step-budget>`, so the leaf is told both figures. | The leaf decides with the numbers in front of it. |
| CY64 | After the split commit the run loops back to `next-unchecked.sh`, which now hands over the first replacement step. | The run continues on the smaller steps. |
| CY65 | On the split, `step-added` and `step-split at=over-budget` are written before `add-ledger-step.sh`, because the marks read the step's title from the ledger. | The insertion rewrites the ledger the marks read. |
| CY66 | The step's cost is also checked after the `develop-replaces-report` correction leaf. | That leaf's spend counts toward the step too. |
| CY14 | The `red` template instructs the leaf to write **exactly one** failing test pinning the criterion to observable external behavior, with **no production code**, and to run the suite holding that case, not the full suite, against the unmodified code. The only question Red asks is whether that one case fails. | Running the full suite in Red would answer a question Red does not ask, and cost the whole run's time for it. |
| CY15 | The template's definition of a valid test is behavior, not mechanism: no process, fork or call count and no timing across a suite run (those are `make profile`'s job). The one exception is a call count the criterion itself names, pinned with an in-process spy on the one wrapper called, never a `PATH` shim counting real processes. | A count or timing assertion pins how the code is built, not what it does, and breaks on a faithful refactor. |
| CY16 | Before the develop-red leaf is launched, the conductor runs `rm -f .tdd/develop-red.exit .tdd/develop-red.pid .tdd/red-prediction.md .tdd/red-run-output.txt`. | A prediction or run-output file left by an earlier attempt would be judged as the new leaf's. |
| CY17 | If the `wait-leaf.sh develop-red` wait exits 2 (killed-stuck), the leaf hung or ran away: the conductor bails cleanly (see `<base directory>/BAIL.md`), after the stop check in *Launching a leaf*, and does not retry. | A pending `now` stop must go to Stopping and not to a bail, and a hung leaf is not retried. |
| CY18 | When the leaf reports `AGAINST_UNMODIFIED: UNTESTABLE`, the conductor skips verify-red and verify-pin entirely and bails immediately with cause `untestable-criterion`, carrying the leaf's `WHY:` as the reason. This is a **process** failure: the criterion as phrased cannot be tested as behavior, not that the plumbing broke. | No test is on disk, so a verifier would only return a malformed-verdict `REJECT` for the wrong reason. |
| CY19 | On `AGAINST_UNMODIFIED: FAILS`, before any verifier, the conductor runs `$S/red-divergence.sh .tdd/red-prediction.md .tdd/red-run-output.txt < .tdd/develop-red.out > .tdd/verify-red.reason; echo $?` and branches on its exit code. | Verify-red is blind, so the prediction check is the conductor's gate: no verifier can be told the developer's reasoning. |
| CY20 | `red-divergence.sh` exit 1 means the prediction file is missing or newer than the run's output. The conductor narrates "prediction not written before the run" in the `### 🔴 Red` comment, not a divergence, and writes that line to `.tdd/verify-red.reason`. It still spends the attempt like a `REJECT`: it skips verify-red and verify-pin and enters the revise loop for red (`Read` `<base directory>/REVISE.md` when a verifier answers `REJECT`). | A prediction written after the run is not a prediction, but it must not be called a divergence either. |
| CY21 | `red-divergence.sh` exit 0 (the test failed for a reason other than the one it was written to catch) or exit 2 (the report carries no readable `PREDICTION:` line; an unreadable prediction is not a matched one) skips verify-red and verify-pin. The conductor keeps the reason the script wrote to `.tdd/verify-red.reason` (on exit 2 it writes its own one-line reason there), marks `$S/event.sh prediction-diverged`, and enters the revise loop for red exactly as a verify-red `REJECT` does (`Read` `<base directory>/REVISE.md`). The revise leaf answers `.tdd/verify-red.reason`, and the attempt spends `REVISE_BUDGET` like any other. | Beck stops on that surprise because the test is then the suspect; the divergence has to reach the run log and the revise leaf. |
| CY22 | Beside the `prediction-diverged` mark the conductor runs `$S/preserve-attempt.sh <n> "$($S/next-unchecked.sh < .tdd/issue-<n>.md)" develop-red 1 prediction-diverged`, so the tree the surprising test came from survives the next leaf that overwrites it. It is best-effort: if it fails, the conductor notes it and carries on. | The revise leaf overwrites the tree the surprising test came from, and the attempt would be lost. |
| CY23 | The `### 🔴 Red` comment carries the test, the failing output, the leaf's `PREDICTED_FAILURE:` and whether the prediction matched or diverged, with its `PREDICTION_NOTE:` when it diverged. Both halves, always. | The prediction is what the failing output is read against; a thread carrying only one of them cannot be read for divergence. |
| CY24 | Once verify-red PASSes, the conductor records the step's test files with `$S/tests-frozen.sh record --step "$($S/next-unchecked.sh < .tdd/issue-<n>.md)" <test-path>`; tests-frozen exit 2 is a bail. | Green's check compares against this record, so the test cannot be edited until it passes. |
| CY25 | With `--step "<step text>"` in place of a record file, the record file is the one `$S/tests-frozen.sh path "<step text>"` prints, `.tdd/tests-frozen-<k>.record` with `<k>` the first 16 hex digits of the step text's SHA-256: a step text is often longer than a filename may be and may hold a `/`, so the text itself is never the filename. | One definition of the record's name, shared by every record and check. |
| CY26 | A step marked `⟦suite-repair⟧` or `⟦ci-repair⟧` is never frozen: for it `record --step` writes nothing and `check --step` exits 0, because its fix is often an edit to the very test file the full run or CI left red. A `⟦ci-repair⟧` step therefore records nothing before its green, and its green may edit the test the CI job failed. | Freezing the test would forbid the very edit that repairs the step. |
| CY27 | On `AGAINST_UNMODIFIED: PASSES` the criterion is already satisfied: the test is never sent to verify-red, whose verdict on a passing test can only be `REJECT`. The conductor runs the pin check instead and continues at the pin, `Read`ing `<base directory>/PIN.md` when a Red reports `AGAINST_UNMODIFIED: PASSES`. | A passing test cannot be judged as a failing one, and a faithful test would be rejected for it. |
| CY28 | A `⟦ci-repair⟧` step is the one exception to `PASSES`: its test failed on CI and may pass here, so on `AGAINST_UNMODIFIED: PASSES` it goes on to Green with the failing CI job's log (test id and assertion diff) as its red evidence, never to verify-pin and never to the `test: pin` tick-and-commit. | A CI failure that does not reproduce locally is still real evidence; it must not be pinned away as already satisfied. |
| CY29 | On verify-red PASS (exit 0) the step continues to Green. On `REJECT` (exit 1) the conductor enters the revise loop (`Read` `<base directory>/REVISE.md`), which returns either PASS (continue to Green) or budget-exhausted (**bail**, a process failure). | The two outcomes of the red verdict go to different places, and an exhausted budget ends the run. |
| CY30 | On a `⟦replaces-case⟧` step, once the Red report is written and before verify-red launches, the conductor runs `$S/unreplaced-cases.sh "<step line>" .tdd/develop-red.out` against the current attempt's report (`.tdd/revise-red-<k>.out` after a red revise). | The check has to see the report that is current, or a corrected revise would be judged on the old one. |
| CY31 | `unreplaced-cases.sh` exit 1 prints each named case with no `REPLACES:` line, and the Red gets one chance to correct its report. The conductor launches one `develop-replaces-report` leaf (prompt built with `build-develop-prompt.sh replaces-report`, launched through `supervise.sh`), spending no `REVISE_BUDGET` attempt and writing no `revise` mark. It then runs `$S/unreplaced-cases.sh` again on both the Red report and `.tdd/develop-replaces-report.out` (`.tdd/revise-red-<k>.out` in place of `.tdd/develop-red.out` after a red revise), so a case the Red report already replaced still counts and a correction naming exactly the missing cases does not bail, before verify-red launches. | A missing line in a report is a paperwork gap, not a rejected test, so it costs no revise attempt. |
| CY32 | A second exit 1 (on the corrected report) bails with cause=unreplaced-cases, naming each case it printed, and launches no second correction leaf and no verifier. Verify-green never runs on a step whose named cases lack a replacement. | One correction is the whole allowance; a case with no replacement would be deleted unreplaced. |
| CY33 | `unreplaced-cases.sh` exit 2 (no answer could be obtained: no readable report, bad arguments) bails with cause=unreplaced-cases at once, launching no correction leaf and no verifier. | A guard that cannot answer is not a pass. |
| CY34 | If the `develop-replaces-report` wait exits 1 or 2 (a killed-stuck correction leaf included), the conductor bails with cause=replaces-report-failed and launches no verify-red. | A correction leaf that failed leaves the report still missing its cases. |
| CY67 | The template also requires a valid test to be lightweight (~100ms, costly dependencies replaced unless the behavior under test IS the dependency) and self-contained (never runs another suite, whole or sliced, and never re-runs its own). | A slow or nested test makes every later cycle pay for it. |
| CY68 | A criterion that cannot be pinned within those rules is not weakened into one that can: the leaf reports it untestable (`AGAINST_UNMODIFIED: UNTESTABLE`) instead, rather than writing a test to force a pass. | A weakened test would pass for the wrong criterion (#331: "at most N python3" was satisfiable only by a shim that re-ran whole suites under a counter). |
| CY70 | The leaf's report is `.tdd/develop-red.out`, and ends with the lines the conductor branches on: `TEST_PATH:`, `TARGET_TEST:`, `AGAINST_UNMODIFIED: FAILS \| PASSES \| UNTESTABLE`, `WHY:`, `FAIL_OUTPUT:`. The test path and target test id come from the first two, and the third decides the next sub-step. | A criterion earlier work already satisfies cannot yield a failing test, and that fact has to reach the conductor as data (#30, step 3). |
| CY71 | `red-divergence.sh` exit 3 (`PREDICTION: MATCHED`) prints nothing, and the conductor carries on with the verifier: `rm -f .tdd/verdict-red.exit .tdd/verdict-red.pid`, then `detach-leaf.sh $S/supervise.sh verdict-red $S/run-verdict.sh --step "<step>" --fast-cmd '<fast-cmd>' red .tdd/issue-<n>-spec.md <test-path> <target-test-id>`, its stdout (the reason) redirected to `.tdd/verify-red.reason`, waited on in the foreground with `$S/wait-leaf.sh verdict-red` (exit 3: call it again). | The revise step takes the reason as a path, not as text the conductor retypes. verify-red asks the question verify-green will ask, so it never passes a red that no green could make pass. |
| CY72 | The wait on a verifier returns the verdict (0 PASS, 1 REJECT, 2 malformed or killed-stuck), not the supervisor's status. The conductor notes the wait's exit code and reads the reason back out of `.tdd/verify-<phase>.reason`, a file named for the verifier that wrote it (`red`, `pin`, `green`, `refactor`) and overwritten by each verification of that phase. | The newest objection is the only one a revise leaf should answer. |
| CY74 | A step whose trailing marker is `⟦fixture-repair⟧` is frozen like any other, except for the one fixture file its text names (`repairs the fixture '<name>' in <path>,`): `check --step` exits 1 naming any other changed test file. | A fixture repair may edit its fixture, but not any other test. |

A verifier that exited cleanly with no verdict has already been relaunched by `verify.sh` itself, up to `VERI_NO_VERDICT_RETRIES` times (default 1, ADR-0020), so exit 2 arrives only once that budget is spent; the conductor never relaunches it again. | No verdict is not a verdict, and a second relaunch from here would double the budget. |

| ID | Requirement | Why |

| SC1 | The catalogue lists the scripts in `$S`, which is `<base directory>/scripts`, moved out of SKILL.md; `$S` is defined in SKILL.md. | A reader of the catalogue knows where the scripts live and where `$S` comes from. |
| SC2 | `$S/supervise.sh <name> <cmd> [args...]` is the leaf launcher: it spawns `<cmd>` under a heartbeat and hard-timeout watchdog, owns the `.tdd/<name>.log` progress log, and returns the captured output on stdout, with a one-line status on stderr. Exit 0 is success, 1 a leaf failure, 2 killed-stuck (hung past the heartbeat window or over the hard timeout, after its stuck-retry budget). Tunables: `VERI_HEARTBEAT` (silence window in seconds, default 180), `VERI_TIMEOUT` (hard cap in seconds, default 900), `VERI_STUCK_RETRIES` (extra attempts after a killed-stuck, default 1), which is the liveness axis, independent of the conductor's verdict-axis `REVISE_BUDGET` and cost-axis `VERI_REFACTOR_BUDGET`. Four more choose the model each leaf runs on, resolved through `$S/leaf-model.sh` and passed to `claude --model`: `VERI_MODEL` (every leaf), `VERI_MODEL_DEVELOPER` (developer leaves only: `develop-*`, `revise-*`), `VERI_MODEL_REVISE` (only the developer leaves that redo rejected work, `revise-*` and `develop-exhausted`, beating `VERI_MODEL_DEVELOPER` for them) and `VERI_MODEL_VERIFIER` (verifier leaves only: `verify-*`, `verify-pin` included). A role variable beats `VERI_MODEL`; with all four unset the shipped defaults are sonnet for first-try developer leaves and verifiers and opus for the redo leaves and the conductor. The value goes through verbatim, so an alias (`sonnet`, `opus[1m]`) or a full id (`claude-sonnet-5`) both work. Because leaves stream, the default heartbeat is a real silence window (a working leaf keeps it fresh, a hung one trips it), so the defaults are used and the heartbeat is not pinned to the timeout. Every leaf is launched through it, never through `run-leaf.sh` or `claude` directly. It records its own final code in `.tdd/<name>.exit` on every path, killed-stuck included, which is what makes a detached launch waitable; a killed-stuck leaf is relaunched, so one call can take more than one `VERI_TIMEOUT` of wall time, which is why the wait loops rather than naming one long timeout. | One launcher owns stuck detection, the log, the completion file and the model choice, and each knob answers one question. |

Every leaf launch goes through it and none uses `nohup`, for the reason *Launching a leaf* gives. Redirections go on the call as usual and the launched process inherits them. | A leaf outlives the call that started it and can be killed as a group, with no `nohup`. |
| SC4 | `$S/wait-leaf.sh <name> [max-seconds]` is the foreground half of a detached launch: it blocks polling for that leaf's completion file and exits with the code recorded in it as soon as it lands (0, 1 or 2, the launcher's own contract), or exit 3, nothing to report yet, once `max-seconds` pass with no completion file. The default is 540 s, inside Claude Code's 10-minute cap on one foreground Bash call. | SC6 | `$S/extract-result.sh` pulls the final result text out of a leaf's stream-json; `run-leaf.sh` uses it, and it passes plain text through unchanged. | The result is read one way, and plain output is not mangled. |
| SC7 | `$S/build-develop-prompt.sh <red\|green\|refactor\|cover\|transform\|diff\|structural\|predicate\|revise\|exhausted\|reconcile\|over-budget\|rebase\|replaces-report\|red-contradicted\|red-repair\|red-missing\|red-supersede\|expand\|migrate\|contract-a\|contract-b> …` assembles a developer leaf's prompt from a versioned template, with these shapes: `red <spec-file> <step-text> <test-cmd>`; `green <spec-file> <step-text> <test-cmd> <test-path> <target> <fast-cmd> [<owed-cases>]`, whose optional 8th argument is the named cases still owed for deletion; `refactor <spec-file> <step-text> <test-cmd> <touched-files>`; `revise <phase> <spec-file> <step-text> <test-cmd> <reason-file>`; `red-repair <case> <report-file> <superseded>…`, the Red leaf that repairs one case the step's own Red wrote, edited in place, never creating a suite; `red-missing <spec-file> <step-text> <test-cmd> <reason-file>`, the Red leaf that adds the one case pinning the `MISSING_TEST:` behaviour the reason file names and edits no other case. ## skills/tdd/SKILL-EDIT.md

| ID | Requirement | Why |
|---|---|---|
| SE1 | The conductor first reads the issue body into `.tdd/issue-<n>-body`, with `gh api repos/{owner}/{repo}/issues/<n> -q .body > .tdd/issue-<n>-body`. (Paragraph 1.) | The runner reads the approved requirements diff from a file, and the file must exist before it runs. |
| SE2 | Then it runs `$S/skill-edit-step.sh` on the issue body, `.tdd/issue-<n>-body`, the step's unit, and then every pin file the step names, in that order. (Paragraph 2.) | The runner takes the diff, the one unit the step edits, and the pin files it must keep green. |
| SE3 | On exit 0 or 3, the conductor ticks the step and commits the ticked ledger. (Paragraph 3.) | Both mean the unit is signed and committed; the ledger records the step done. |
| SE4 | On exit 1, it bails with `cause=revise-exhausted`, as an exhausted revise. (Paragraph 4.) | The author's budget ran out against the grader: a process failure, classified like any exhausted revise. |
| SE5 | On exit 2 (a bad argument, budget or heading, or no answer), it bails at once as a system failure with `cause=no-verdict`, and never relaunches the runner or spends `VERI_STUCK_RETRIES` on it. (Paragraph 5.) | No answer could be obtained; relaunching the whole runner would redo work and spend a budget that belongs to leaves. |
| SE6 | A killed or stuck author leaf is still retried under `VERI_STUCK_RETRIES` by the `supervise.sh` launch inside the runner, before that exit 2 reaches the conductor. (Paragraph 6.) | Liveness is handled where the leaf is launched, so the conductor's exit-2 bail is not a missing retry. |
| SE7 | A resumed run redoes an unfinished skill-edit step from its start, with its budget reset. (Paragraph 7.) | A step takes minutes, and a partial-step resume costs more than a redo (K9). |
| SE8 | For a skill-edit step whose ledger line carries `⟦added⟧`, the conductor runs `$S/skill-edit-step.sh` with `--added` and the step's text, before the issue body and the unit. (Paragraph 8.) | An added step brings no approved diff of its own, so the runner is told it is one. |
| SE9 | The refusal holds only for the rest: an added step bringing rows new to an already-passing unit's list is committed with its regrade and no author (exit 3, ticked); one whose text names a prose change runs with `--change`; and any other whose grade passes before any author ran, or that has nothing left to commit, gets exit 2 and is bailed, never ticked. (Paragraph 9.) | An added step that changes nothing must not be ticked as if it had done its work. |
| SE10 | The step's own text never reaches the author or the grader. (Paragraph 10.) | The grader is blind, and the author works from the requirements and the FAIL reasons only (K5). |
| SE11 | When a skill-edit step's text names a change to the prose, a sentence to delete or reword, the conductor runs `$S/skill-edit-step.sh` with `--change` and that change, so an author runs even on a unit that already grades PASS. (Paragraph 11.) | A prose change the list does not forbid would otherwise end at K4 with nothing edited. |
