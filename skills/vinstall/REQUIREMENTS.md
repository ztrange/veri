## skills/vinstall/SKILL.md

| ID | Requirement | Why |
|---|---|---|
| VI1 | Invoked as `/vinstall [repo-root]`, save the cloud form `/vinstall cloud [repo-root]`, which does not run it, it runs `install-links.sh` and reports each skill it linked, repaired or removed. | One command sets up a project, and a removed link is a change the operator should see. |
| VI2 | On exit 2 it reports the refusal the script printed and does not work around it. | A path veri did not create is the operator's. |
| VI3 | It says that re-running it is the way to repair an install. | Re-running is the repair path. |
| VI4 | When `install-links.sh` linked, repaired or removed any skill, it runs the readiness check through a subagent on the cheapest model that can do it, briefed to read `<base dir>/../vready/SKILL.md` and follow it (never `/vready`, which is not linked), told that it runs as a subagent and starts none of its own, and to return at most 10 lines, and reports the subagent's answer; when the script changed nothing, it does not. | `vready` is read on demand, not linked; a first install ends with the answer, and the table stays out of a long context (P6). A subagent cannot start a subagent, so `vready`'s red-tier summary must know it is one. |
| VI5 | During setup, after reporting the links, it runs `$S/stack-branch.sh` and routes each exit: 0 reports the named branch and asks nothing; 2 reports the refusal and writes nothing; 3 asks whether the repository stacks finished runs on a standing branch and, if so, under what branch name. On a name it writes the line `veri: stack branch: <name>` into the repository's `CLAUDE.md` and checks it again with `$S/stack-branch.sh`, taking the line out and asking once more on exit 2; on a no it writes nothing. | PRD 034 D6: stacking is off unless the repository names the branch, and setup is where the operator is asked; a line that cannot name a stack is the operator's to fix, not an answer to overwrite. |
| VI6 | A section `## Recording the test commands` says: after `install-links.sh` exits 0, when the target repo's `CLAUDE.md` lacks a `veri: fast tests:` or a `veri: all tests:` line, run `detect-test-command.sh --tier fast` and `--tier all` on it and show the operator both commands, a tier that exits 3 shown as none found. | The operator confirms a proposal instead of composing one. |
| VI7 | The same section says the operator confirms or replaces each tier command, and `record-test-commands.sh` runs only with the two tier commands the operator confirmed, each command it is given passed as one shell word: wrapped in single quotes, each `'` inside it written `'\''`; with no confirmed tier commands nothing is written. | A wrong guess committed is worse than none. |
| VI8 | The same section says that when `CLAUDE.md` already holds all four lines (`veri: fast tests:`, `veri: all tests:`, `veri: one test file:` and `veri: quiet test files:`), `/vinstall` asks nothing about test commands. | Re-running `/vinstall` is the repair path; it must not re-ask a settled question. |
| VI9 | The same section says to report the PR's URL, that runs infer the commands until that PR merges, and that `/vinstall` never merges it; on exit 2 it reports what the script printed and stops; on exit 3 it reports nothing to record. | The operator learns what is pending and whose move it is. |
| VI10 | `## Recording the test commands` says: when the target repo's `CLAUDE.md` lacks a `veri: one test file:` line, ask the operator for the command that runs one test file, taking the file as `"$1"` (it must hold `"$1"` anywhere, or `$1` as a word of its own, and the section shows the placeholder in its example), propose none, and pass the answer with `--one-file`; with no answer, record the other lines without it and say that a run's preflight stops without the line. | The operator supplies what cannot be inferred; a missing answer must not block the other lines. |
| VI11 | The same section says that when `CLAUDE.md` holds both tier lines but lacks the `veri: one test file:` or the `veri: quiet test files:` line, `/vinstall` asks only for the missing ones and passes the two recorded tier commands unchanged. | Asking nothing when both tier lines exist must not stop the other lines from being asked for. |
| VI12 | `## Recording the test commands` asks the operator for the `veri: quiet test files:` command as it asks for the tier commands: it runs `$S/detect-test-command.sh --tier "quiet test files"`, shows the proposed default beside where it came from when the runner is recognisable (pytest `-q --no-header -rf`, jest `--silent`), asks only when none can be inferred (exit 3), states the command's contract (it takes the test file paths appended as arguments, prints only the failing cases, each name plus its first failure line, and one count line, and exits 0 green, 1 a test failed, 2 the run broke) and that without the line leaves get each run's exit code and last 20 lines, and passes the confirmed command to `record-test-commands.sh` with `--quiet`. | The project owns its quiet command; veri cannot parse every runner. |
| VI13 | A `## Cloud sessions` section says `/vinstall cloud [repo-root]` runs `$S/cloud-install.sh`, which adds a `SessionStart` hook to the repository's `.claude/settings.json` running `$S/cloud-setup.sh` only when `CLAUDE_CODE_REMOTE=true`, and that the operator commits that file. It also says that the cloud form supports only veri's own repository for now: on any other repository `cloud-install.sh` exits 2 saying so and writes nothing. | A cloud session starts with no venv and an old Python; the hook is the only veri-controlled code that runs before the first prompt. |
| VI14 | The same section prints the claude.ai environment settings the operator must make by hand, `GH_TOKEN` and a network level reaching github.com and pypi.org, says no CLI sets them, then runs `/vready`. | Without the token or PyPI, setup and every gh call fail, and the operator could not know the settings live in the web UI. |
